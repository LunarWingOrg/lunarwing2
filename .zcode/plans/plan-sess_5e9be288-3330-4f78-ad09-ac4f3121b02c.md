# B-2 + B-3 — Skills demotion/pruning + cross-agent sharing

**Branch:** `feat/skills-b2-b3-01` (current). **Plan doc:** `docs/plans/SELF_IMPROVING_SKILLS_B2_B3.md`.
**Decisions locked by user:** (1) Demotion hook = Rust filter in `handle_list_skills`; (2) Sweep = `OnSystemEvent` on skill usage (no cron mission — cron missions don't fire in production today); (3) Prune = **archive** (soft delete via `archived_at`); (4) Scope = **both B-2 and B-3** in this branch.

**Verified facts driving the design:**
- The real V2 selection path is `handle_list_skills` (orchestrator.rs:1733, returns ALL skill docs) → Python `select_skills`/`score_skill` (default.py). `apply_confidence_factor` (selector.rs) has **zero** production callers.
- `LeakDetector` lives in `lunarwing_safety` (sibling crate); **not** a dep of `lunarwing_skills`/`engine` today. API: `LeakDetector::new().scan(content) -> LeakScanResult`, `.is_clean()`.
- Install path writes v1 `LoadedSkill` to disk; v2 `MemoryDoc` is created later by `migrate_v1_skill_list` (skill_migration.rs:42) at engine init, idempotent on `content_hash`.
- ClawHub publish is real: `POST /api/v1/skills`, multipart `payload`+`files`, Bearer auth. Resolve: `GET /api/v1/resolve?slug=&hash=`.
- B-1 surface to extend: `SkillPatchProposal` DTO (router.rs:3508), `list_pending_skill_patches`/`approve_skill_patch`/`reject_skill_patch` (router.rs:3534–3644), web handlers (skills.rs:286–333), GUI panel (app.js:4762–4860, index.html:391–396).

## Part B — B-2: confidence-based demotion & pruning

### B1. Data model — `ic/crates/lunarwing_skills/src/v2.rs`
Add to `V2SkillMetadata` (all `#[serde(default)]`, back-compat):
- `deprecated_at: Option<DateTime<Utc>>` + `deprecation_reason: String` — demotion flag (reversible).
- `archived_at: Option<DateTime<Utc>>` + `archived_reason: String` — prune = archive (soft delete).
- `pending_prune: Option<PendingSkillPrune>` — staged prune awaiting approval.

New struct `PendingSkillPrune { reason, staged_at, confidence_at_staging, usage_count_at_staging, source_thread_id: Option<String> }`.

New consts: `DEFAULT_DEMOTE_CONFIDENCE: f64 = 0.3`, `DEFAULT_DEMOTE_MIN_USAGE: u64 = 5`, `DEFAULT_PRUNE_CONFIDENCE: f64 = 0.0`, `DEFAULT_PRUNE_MIN_USAGE: u64 = 10`.

New methods on `V2SkillMetadata`:
- `is_demote_candidate(threshold, min_usage) -> bool`: `source == Extracted && trust != Installed && metrics.usage_count >= min_usage && metrics.confidence() < threshold`.
- `is_prune_candidate(threshold, min_usage) -> bool`: stricter — `source == Extracted && trust != Installed && metrics.usage_count >= min_usage && metrics.confidence() <= threshold`.

Tests: serde round-trip with new fields (old skills default to `None`/empty); candidate predicates (authored/Installed exempt; below/above thresholds; min-usage gate).

### B2. Runtime demotion hook — `ic/crates/lunarwing_engine/src/executor/orchestrator.rs` (`handle_list_skills`, ~line 1742)
After the `DocType::Skill` filter, parse `V2SkillMetadata` and **exclude** docs where `archived_at.is_some() || deprecated_at.is_some()`. This is the single choke point (user's choice). Document the tradeoff: a deprecated skill is removed from *all* activation (explicit `/skill` mention included); `undeprecate_skill` is the recovery path. Keep the existing `serde_json::json!` shape for non-excluded skills unchanged.

Test: `handle_list_skills` (or a unit test on the filter predicate) excludes archived/deprecated, includes healthy + below-floor-not-yet-deprecated.

### B3. Storage methods — `ic/crates/lunarwing_engine/src/memory/skill_tracker.rs`
Add (mirror the B-1 `propose_patch`/`apply_pending_patch`/`discard_pending_patch` shape):
- `demote_skill(doc_id, reason)`: set `deprecated_at` + reason. Refuse if `source == Authored || trust == Installed`.
- `undeprecate_skill(doc_id)`: clear `deprecated_at` + reason (recovery after a B-1 patch epoch-reset earns confidence back).
- `propose_prune(doc_id, reason, source_thread_id?)`: set `pending_prune`. Refuse authored/Installed; refuse if already archived.
- `apply_prune(doc_id, reason)`: set `archived_at` + reason, clear `pending_prune`. (Archive, not delete.)
- `discard_prune(doc_id)`: clear `pending_prune`.

Inline demotion on usage: extend `record_usage` — after updating metrics, if `meta.is_demote_candidate(DEFAULT_DEMOTE_CONFIDENCE, DEFAULT_DEMOTE_MIN_USAGE)` and `deprecated_at.is_none()`, set `deprecated_at` + a reason string ("confidence {c} below demotion floor {t} over {n} uses"). This is the automatic, reversible demotion (no proposal); prune stays propose→approve.

Tests (mirror B-1's 11 tests): demote sets/clears `deprecated_at`; authored/Installed refused; `propose_prune` stages without archiving; `apply_prune` sets `archived_at`; `discard_prune` clears; inline demotion in `record_usage` trips at floor and not above; `undeprecate_skill` clears.

### B4. Sweep mission — `mission.rs` + new prompt
- Add `const SKILL_MAINTENANCE_GOAL: &str = include_str!("../../prompts/mission_skill_maintenance.md");`
- In `ensure_learning_missions`, append a 5th `ensure_mission_by_metadata("skill_maintenance", "skill-maintenance", SKILL_MAINTENANCE_GOAL, MissionCadence::OnSystemEvent { source: "engine", event_type: "thread_completed_with_issues" }, "Scan skills for dead/rotten ones and stage prune proposals", 1)` (max 1/day — sweep is cheap, catches stale skills the inline check misses).
- New `prompts/mission_skill_maintenance.md`: conservative, propose-only. Input: `trigger_payload.candidates` = skills that are `is_prune_candidate` (confidence 0.0 over ≥ prune_min_usage), with name/doc_id/confidence/usage. Process: for each candidate, emit one `__propose_skill_prune__(doc_id, reason)` call (new host fn, B5). Rules: never propose pruning authored/Installed skills; one action per skill; propose-only (user approves via proposals surface).
- Enrichment helper `collect_prune_candidate_skills(store, user)` (mirror `collect_patch_candidate_skills`): enumerate ALL user skills via `list_memory_docs_with_shared`, filter `is_prune_candidate`, build the `candidates` payload. Wire into the `thread_completed_with_issues` branch alongside the existing `active_skills` enrichment (mission.rs:517).

### B5. Orchestrator host fn — `__propose_skill_prune__`
Add to the host-fn dispatch table (orchestrator.rs:453) and implement `handle_propose_skill_prune(args, thread, store)` mirroring `handle_propose_skill_patch`: validates `doc_id` + `reason`, builds `SkillTracker`, calls `propose_prune`. Refuses authored/Installed (the tracker enforces it; the host fn just forwards the error).

### B6. Bridge + API + GUI
- Bridge: covered by Part A generalized surface (`list_pending_skill_proposals` includes `pending_prune`; `approve_skill_proposal(kind=Prune)` → `SkillTracker::apply_prune`; reject → `discard_prune`).
- GUI: Prune card variant (Part A4).

### C2. Provenance data model — `ic/crates/lunarwing_skills/src/v2.rs`
Add to `V2SkillMetadata` (serde-default): `registry_url: Option<String>`, `registry_publisher: Option<String>`, `registry_version: Option<String>`, `pulled_at: Option<DateTime<Utc>>`, `registry_content_hash: Option<String>`, `pending_update: Option<PendingSkillUpdate>`.

New struct `PendingSkillUpdate { registry_version_available, registry_url, new_content_hash, staged_at }`.

New consts: `DEFAULT_PUBLISH_CONFIDENCE: f64 = 0.7`, `DEFAULT_PUBLISH_MIN_USAGE: u64 = 10`.

New method `is_publish_eligible() -> bool`: `trust == Trusted && source == Extracted && metrics.usage_count >= DEFAULT_PUBLISH_MIN_USAGE && metrics.confidence() >= DEFAULT_PUBLISH_CONFIDENCE && pending_patch.is_none()`. (Only proven, Trusted, non-extracted... actually also allow Authored Trusted skills to be published — user-authored skills are the most shareable. Revise: `trust == Trusted && metrics.usage_count >= min && confidence >= threshold`. Authored skills start with confidence 1.0 but usage_count 0, so the usage floor naturally gates them until they've been used enough. Keep `source != Migrated`? Migrated is fine to publish. Let me gate on `trust == Trusted` + usage/confidence floors, no source restriction.)

Test: serde round-trip; publish eligibility (below-usage excluded; low-confidence excluded; Installed excluded).

### C3. Provenance on install — sidecar approach
- `ic/src/skills/registry.rs` / install path: when installing from the catalog (`skills_install_handler` with a slug source), write a sidecar `{skill_dir}/.registry.json` containing `{ registry_url, publisher, version, pulled_at, content_hash }`. The `content_hash` is computed from the downloaded SKILL.md body (reuse `compute_hash`).
- `ic/src/bridge/skill_migration.rs` `v1_skill_to_memory_doc`: after building `V2SkillMetadata`, check for a `.registry.json` sidecar next to the skill's source path; if present, populate the provenance fields. (Read best-effort; missing sidecar = locally-authored, provenance stays `None`.)
- Leak scan on pull: in `skills_install_handler` (skills.rs:123), after `fetch_skill_content` and before `commit_install`, run `LeakDetector::new().scan(&content)`; if `!is_clean()`, refuse with 400 + the match summary. (Reuse — `lunarwing_safety` is already a top-level `ic` dep.)

Tests: sidecar write/read round-trip; migration populates provenance when sidecar present, leaves `None` when absent; leak scan refuses a skill body containing an API-key pattern.

### C4. Publish path — `ic/crates/lunarwing_skills/src/catalog.rs`
- Fix `SkillDetailResponse`/`SkillDetail` to capture `latestVersion` (currently dropped → `version: None` hardcode at catalog.rs:356). Add `latest_version: Option<SkillLatestVersion>` with `{ version, created_at, changelog }`. Populate `SkillDetail.version` from it.
- Add `SkillCatalog::publish(&self, req: &PublishRequest, token: &str) -> Result<PublishResponse, CatalogError>`:
  - `PublishRequest { slug, display_name, version (semver string), changelog, tags, skill_md_content, code_snippets: Vec<(name, body)> }`.
  - Build multipart `form-data`: `payload` field = JSON of `CliPublishRequest` (slug, displayName, version, changelog, tags, files=[{path:"SKILL.md",...}, ...code snippet paths...]) with `files` blobs attached as FormData entries named `files` (the SKILL.md blob + one blob per code snippet). Note: in multipart mode the server computes size/sha256/storageId, so the payload's `files` array can omit those (the server's `parseMultipartPublish` reconstructs them).
  - `POST {registry_url}/api/v1/skills`, header `Authorization: Bearer {token}`.
  - Parse `ApiV1PublishResponseSchema` `{ ok, skillId, versionId }`.
- Add `SkillCatalog::check_for_update(&self, slug, current_version) -> Result<Option<UpdateInfo>, CatalogError>`:
  - `GET {registry_url}/api/v1/resolve?slug={slug}` → `{ match: {version}|null, latestVersion: {version}|null }`. If `latestVersion.version` exists and differs from `current_version`, return `UpdateInfo { version, registry_url }`.

Tests: publish eligibility helper (covered in C2); publish multipart body shape (unit test on the form builder, no network); check_for_update flags a newer version, no-op on same version. (Live HTTP gated behind `#[ignore]` integration tests.)

### C5. Update proposal staging — `skill_tracker.rs` + mission
- Add `SkillTracker::propose_update(doc_id, registry_version, registry_url, new_hash)`: set `pending_update`. `apply_update(doc_id, new_content)`: re-install (pull new version) + update provenance + clear `pending_update` + bump version. `discard_update(doc_id)`: clear.
- The B-2 maintenance mission (B4) gets a second responsibility: for skills with provenance (`registry_version.is_some()`), call `check_for_update` and, if newer, `propose_update`. Add to `collect_prune_candidate_skills` payload (or a parallel `collect_update_candidates`) the registry-sourced skills for the mission prompt to act on via a new `__propose_skill_update__(doc_id, version, url, hash)` host fn. (Or do update-checking directly in Rust in the enrichment helper without LLM involvement — simpler and more reliable. **Decision:** do update-checking in Rust (`collect_update_candidates` calls `check_for_update` for each provenance-bearing skill and stages `pending_update` directly via SkillTracker, no LLM/mission needed). The mission only handles prune proposals; updates are staged deterministically.)

### C6. Bridge + API + GUI
- Bridge: `publish_skill(doc_id, user_id, token) -> Result<PublishResponse>` — load skill, check `is_publish_eligible`, leak-scan body + snippets, build `PublishRequest`, call `catalog.publish`, return result. Token from `CLAWHUB_TOKEN` env (read inside the fn, never logged).
- API: `POST /api/skills/{doc_id}/publish` (auth-gated, user-scoped). The update approve/reject reuses Part A's `approve_skill_proposal(kind=Update)` → `SkillTracker::apply_update`.
- GUI: "Publish" button on eligible skill cards (disabled with tooltip if not eligible); "Update available" badge + the Update proposal card (Part A4).

### Risk callouts
- **Security**: publish path sends skill content to an external registry (clawhub.ai). Leak scan is defense-in-depth; the user must explicitly trigger publish (never automatic). `CLAWHUB_TOKEN` treated as a secret (secrecy crate conventions, never logged).
- **SkillTrust untouched** — demotion is a metadata flag, not a trust tier (SAETY comment at types.rs:30 honored).
- **GUI requires release rebuild** to take effect (`include_bytes!`-compiled static assets) — note in summary, don't block.
- **Cron-mission gap avoided** — using `OnSystemEvent` per user decision; no changes to the mission cron-fire path.
- **Migration sidecar** is a new on-disk artifact in skill install dirs; `.registry.json` — document it, handle missing-file gracefully.
- Update-checking does outbound HTTP to the registry on thread completion (for provenance-bearing skills only, rate-limited by the 1/day mission cap + in-memory cache reuse). Mirror the catalog's existing best-effort/never-block posture.

### Out of scope (explicitly deferred)
- Live HTTP integration tests against ClawHub (publish/resolve) — `#[ignore]`-gated, need a real `CLAWHUB_TOKEN`.
- A self-hosted/private registry for fleet-internal sharing (ClawHub-compatible endpoint is configurable via `CLAWHUB_REGISTRY`, so this works for free if an operator points at SkillHub; no extra code).
- Notification (Gotify) on demotion/prune — the `MissionNotification` broadcast + `notify_channels` surface exists; wiring a channel name into the maintenance mission is a one-line follow-up if desired, not blocking.
