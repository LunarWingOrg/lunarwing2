# Semantic Memory Search

LunarWing provides persistent memory for agents with hybrid search combining full-text search (BM25-style keyword matching) and vector search (cosine similarity on embeddings). Results are fused using Reciprocal Rank Fusion (RRF) to produce a single ranked list.

## Architecture Overview

```
Agent calls memory_search("dark mode preference", limit=5)
  |
  v
Workspace::search()
  |
  +-- embed query via EmbeddingProvider (if enabled)
  |     |
  |     +-- check LRU cache (10,000 entries default)
  |     +-- on miss: call provider API (OpenAI / OpenAI-compatible / Ollama / LunarWing Cloud)
  |
  +-- parallel search
  |     |
  |     +-- FTS: PostgreSQL ts_rank_cd / libSQL FTS5
  |     +-- Vector: pgvector cosine distance / libsql_vector_idx
  |
  +-- fuse results (RRF or WeightedScore)
  |
  +-- filter by min_score, sort descending, limit
  |
  v
SearchResult[] { document_id, document_path, chunk_id, content, score,
                 fts_rank, vector_rank }
```

`SearchResult::is_hybrid()` derives hybrid-match state from the two rank fields.
The `memory_search` tool exposes that derived value as `is_hybrid_match` and
renames `document_path` to `path` in its JSON response.

## Full Pipeline

### Step 1: Content Ingestion

When an agent writes to the workspace, the document is stored and indexed:

```
workspace.write(path, content)
  |
  +-- normalize path and scan system-prompt files for prompt injection
  +-- prepare chunks and optional embeddings before opening a transaction
  |     - skip indexing for internal engine/.runtime/** state
  +-- atomically update memory_documents and replace memory_chunks
        - 800-word chunks, 15% overlap
        - tsvector generated by PostgreSQL / FTS5 triggers in libSQL
        - embedding vector present only when a provider is enabled
```

`update_document_and_replace_chunks()` performs the content update and complete
chunk replacement in one transaction, so search does not observe a new document
body with stale chunks. Appends use an atomic database append and then reindex.

The append path commits content first and re-chunks in a separate transaction
(`Workspace::append` -> `append_document` -> `reindex_document`). A crash
between the two strands the document zero-chunked forever, so chunk-driven
search under-reports content that `ws.read` still serves in full (the Sep-2026
Kageho "0 vs 6671" symptom). Migration V27 adds the `indexed_at` outbox marker:
`NULL` = content changed but chunks not yet rebuilt; non-`NULL` = projection
current. It is set to `NULL` in the same statement that commits content
(append/content-only update) and stamped `NOW()` inside the transaction that
replaces chunks. A repair sweep (`Workspace::repair_stale_index`, limit-bounded)
re-chunks stranded documents; the daemon runs it at startup -- before the
embedding backfill -- and the heartbeat hygiene pass repeats it. V27 backfills
existing documents as indexed (`indexed_at = updated_at`), so an upgrade does
not trigger a mass re-chunk/re-embed.

Engine recovery files under `engine/.runtime/**` remain in `memory_documents` so
threads, checkpoints, events, and leases survive restarts. They receive an empty
chunk set and therefore cannot enter FTS or vector search. Migration V23 removes
chunks created for these paths by older versions without deleting source documents.
The same exclusion covers the mission-directory subtree
`engine/projects/{project}/missions/**` (any depth or suffix, not just
`mission.json`) and the project-level `engine/projects/{project}/missions.json`
manifest (WI#135/WI#136): everything under a mission directory stays readable via
`read()`/`list()` -- mission hydration reads documents, not chunks -- but never
enters search. Legacy chunks from pre-fix builds are removed by the idempotent
`purge_mission_index_chunks()` sweep (boot, before the embedding backfill, and
heartbeat hygiene); its SQL `LIKE` patterns mirror `is_mission_path`.

### System-Prompt Write Guard

Default-scope `Workspace::write()`, `append()` and `append_memory()` scan files
injected into the system prompt (`SOUL.md`, `AGENTS.md`, `USER.md`,
`IDENTITY.md`, `MEMORY.md`, `TOOLS.md`, `HEARTBEAT.md`, `BOOTSTRAP.md`,
assistant directives, profile data, `lorebooks/` and `daily/*.md`) with the
shared safety `Sanitizer`. High-severity prompt injection patterns return
`WorkspaceError::InjectionRejected`, which `memory_write` surfaces as
`ToolError::ContentRejected` with rephrase guidance (WI#290). An append refused
only because content already stored in the file trips the gate returns
`WorkspaceError::ExistingContentRejected` (escalate-first repair guidance: the
entry was clean, so rephrasing it cannot help); a default-scope daily log in
that state is quarantined instead (`WorkspaceError::DailyLogQuarantined`, retry
the same entry unchanged, WI#288). The workspace README's "Prompt-Injection
Write Scanning" section covers the daily-log quoting route and the HTTP
statuses (422 for injection rejections, 409 for existing-content rejections
and quarantines).

Layer-aware `write_to_layer()` and `append_to_layer()` apply layer
permissions and privacy classification, and run the same system-prompt
injection guard as the default-scope path (appends to prompt-visible files
re-validate the concatenated content). A layer append refused only because of
stored content returns `ExistingContentRejected` as well; layer daily logs are
not quarantined.

### Step 2: Document Chunking

Documents are split into overlapping chunks for better search recall. Overlap ensures context is preserved across chunk boundaries.

```rust
ChunkConfig {
    chunk_size: 800,          // words per chunk (~800 tokens for English)
    overlap_percent: 0.15,    // 15% overlap between adjacent chunks
    min_chunk_size: 50,       // tiny trailing chunks merge with previous
}
```

Example: a 2,000-word document produces 3 chunks of ~800 words each, with ~120 words of overlap between adjacent chunks.

Source: `ic/src/workspace/chunker.rs`

### Step 3: Embedding Generation

Embeddings convert text into dense vectors that capture semantic meaning. Similar concepts have similar vectors, enabling semantic search beyond keyword matching.

```rust
trait EmbeddingProvider: Send + Sync {
    fn dimension(&self) -> usize;
    fn model_name(&self) -> &str;
    fn max_input_length(&self) -> usize;
    async fn embed(&self, text: &str) -> Result<Vec<f32>, EmbeddingError>;
    async fn embed_batch(&self, texts: &[String]) -> Result<Vec<Vec<f32>>, EmbeddingError>;
}
```

#### Supported Providers

| Provider | Models | Default Dimension | Config |
|----------|--------|-------------------|--------|
| **OpenAI** | `text-embedding-3-small`, `text-embedding-3-large`, `text-embedding-ada-002` | 1536 / 3072 / 1536 | `OPENAI_API_KEY` |
| **Ollama** | `nomic-embed-text`, `mxbai-embed-large`, `all-minilm` | 768 / 1024 / 384 | `OLLAMA_BASE_URL` (default `http://localhost:11434`) |
| **LunarWing Cloud** | Configurable | Configurable | LunarWing Cloud session auth |
| **OpenAI-compatible** | Any compatible model | Configurable | `EMBEDDING_PROVIDER=openai_compatible`, `OPENAI_API_KEY`; `EMBEDDING_BASE_URL` optional (defaults to `https://api.openai.com`, required for non-default endpoints) |
| **Mock** | Deterministic | Configurable | Test harness only |

Source: `ic/src/workspace/embeddings.rs`

#### Embedding Cache

An LRU cache wraps the embedding provider to avoid duplicate API calls:

- Default capacity: 10,000 entries
- Approximate memory: `cache_size x dimension x 4 bytes` (payload only)
  - 10,000 x 1,536 floats = ~58 MB for OpenAI small
  - 10,000 x 768 floats = ~29 MB for Ollama nomic
- Configurable via `EMBEDDING_CACHE_SIZE`

Source: `ic/src/workspace/embedding_cache.rs`

### Step 4: Hybrid Search

Search combines two retrieval methods and fuses them into a single ranked list.

#### Full-Text Search (FTS)

**PostgreSQL**: Uses `tsvector` columns with GIN indexes and `ts_rank_cd` for relevance scoring.

```sql
SELECT c.id, c.document_id, d.path, c.content,
       ts_rank_cd(c.content_tsv, plainto_tsquery('english', $query)) as rank
FROM memory_chunks c
JOIN memory_documents d ON d.id = c.document_id
WHERE d.user_id = $user_id
  AND d.agent_id IS NOT DISTINCT FROM $agent_id
  AND c.content_tsv @@ plainto_tsquery('english', $query)
ORDER BY rank DESC
LIMIT $pre_fusion_limit
```

**libSQL**: Uses FTS5 virtual tables with sync triggers that keep the FTS index updated.

#### Vector Search

**PostgreSQL**: Uses pgvector cosine distance (`<=>` operator).

```sql
SELECT c.id, c.document_id, d.path, c.content,
       1 - (c.embedding <=> $embedding) as similarity
FROM memory_chunks c
JOIN memory_documents d ON d.id = c.document_id
WHERE d.user_id = $user_id
  AND d.agent_id IS NOT DISTINCT FROM $agent_id
  AND c.embedding IS NOT NULL
ORDER BY c.embedding <=> $embedding
LIMIT $pre_fusion_limit
```

**libSQL**: Uses `libsql_vector_idx` with `F32_BLOB(N)` storage, dimension set dynamically by `ensure_vector_index()` during startup.

After migration V9, PostgreSQL uses brute-force cosine distance (the HNSW index was dropped to support flexible embedding dimensions). This is O(N x D) where D is the embedding dimension.

#### Fusion Strategies

Two strategies for combining FTS and vector results into a unified ranking:

**RRF (Reciprocal Rank Fusion)** -- default:

```
score(d) = SUM( 1 / (k + rank(d)) ) for each method where d appears
```

- k=60 (configurable via `rrf_k`)
- Normalized to [0, 1]
- Documents appearing in both FTS and vector results get boosted scores (the `is_hybrid_match` flag marks these)

**WeightedScore** -- alternative:

```
score(d) = (fts_weight * fts_score) + (vector_weight * vector_score)
```

- Converts ranks to scores via `1/rank`
- Combines with configurable weights (default 0.5/0.5)
- Normalizes by max score

Source: `ic/src/workspace/search.rs`

### Step 5: Agent Access via Memory Tools

Four tools in `ic/src/tools/builtin/memory.rs`:

| Tool | Purpose |
|------|---------|
| `memory_search` | Hybrid FTS + vector search, returns bounded scored results (limit 1-20) |
| `memory_write` | Write to user memory paths; internal Engine runtime paths are rejected |
| `memory_read` | Read a bounded page by path and continue with `next_offset` |
| `memory_tree` | View a bounded directory tree with truncation metadata |

Search results include:
```json
{
  "content": "User prefers dark mode...",
  "score": 0.95,
  "path": "context/preferences.md",
  "document_id": "uuid",
  "is_hybrid_match": true
}
```

Each `content` string is bounded to 2,000 JSON-encoded bytes. Query and path
echoes are also bounded, and the complete pretty-serialized result is at most
8,000 bytes. Truncation occurs before tool-result persistence and always retains
valid UTF-8 and valid JSON. Queries over 1,024 UTF-8 bytes are rejected before
embedding or database search. Results remain a ranked prefix, and `result_count`
reports results actually emitted.

All three path-based tools normalize paths before enforcing the internal runtime
boundary. `memory_read` and `memory_write` reject exact or descendant
`engine/.runtime/**` paths, while `memory_tree` also filters that subtree from
recursive listings. This policy exists only at the agent-facing tool boundary;
the Engine continues to use direct `Workspace` APIs for persistence and recovery.

`memory_read` pages by UTF-8 byte offset. Each page consumes at most 6,000 source
bytes while also respecting JSON escape expansion, and the complete response is
bounded to 8,000 serialized bytes. `next_offset` is always a valid UTF-8 boundary
and is `null` at EOF. Page two and later require the prior response's content-hash
`revision`; a changed document is rejected instead of producing mixed content.

`memory_tree` returns an object containing `path`, `depth`, `tree`, `entry_count`,
`truncated`, `offset`, `next_offset`, and `revision`. Traversal stops at 256
entries, then removes the deterministic tail if needed to keep the complete
serialized response within 8,000 bytes. `next_offset` continues omitted entries
at the selected root; page two and later require the prior root-list `revision`
so inserts or deletes cannot shift pagination silently. Query a returned
subdirectory directly for a truncated nested subtree.

Memory tools register whenever the database-backed workspace exists; no
`TOOL_*` environment variable gates them. Their seeded baseline permission is
`AlwaysAllow`. A separate security boundary can still remove tools before the
LLM sees them: if an active registry-installed skill has `Installed` trust,
`skills/attenuation.rs` limits the advertised set to its conservative read-only
allowlist. `memory_search`, `memory_read`, and `memory_tree` remain visible, but
`memory_write` is intentionally absent until only trusted skills are active.

### Step 6: Study-Notes Knowledge Layer

Study notes are ordinary indexed workspace documents at
`study-notes/<agent>/<topic>.md`. Their document metadata carries canonical topic
and agent slugs, title, lifecycle status, confidence, `studied_at`, source commit,
tags, staleness policy, replacement/status reason, and caller/session
attribution. Migration V26 adds a partial PostgreSQL index for the provenance and
topic filters; it does not create a separate note table. Because the body remains
a normal `memory_document`, normal chunking and backend FTS apply without a
second search store.

Seven native tools in `ic/src/tools/builtin/knowledge.rs` mirror the canonical
lw2studymcp surface:

| Tool | Purpose |
|------|---------|
| `knowledge_search` | FTS with topic, agent, lifecycle, tag, and confidence filters |
| `knowledge_get_topic` | Return every per-agent version of one canonical topic |
| `knowledge_list_topics` | Summarize topic coverage, versions, scopes, agents, statuses, and tags |
| `knowledge_submit_note` | Validate and write a new note or replace the caller's own version |
| `knowledge_update_status` | Patch lifecycle/provenance metadata without changing note content |
| `knowledge_list_stale` | Find status-, age-, or source-commit-stale notes |
| `knowledge_stats` | Count documents, topics, statuses, and scopes |

Reads default to the caller's private scope plus the `shared` herd scope and can
be narrowed to `private` or `shared`; writes default private and may explicitly
target shared. A cadence-guarded background sweep marks aging active notes stale
and also reaps stranded coordination-wire notes after their grace period.

New tenants provisioned with `add-tenant --with-study-mcp` have a separate,
one-shot bootstrap. mt-admin syncs the external checkout, configures
`LW2STUDYMCP_HOME`, and appends `KNOWLEDGE_SEED_FROM_STUDY_MCP=1` only on that
new-tenant path. At first startup a background task imports
`agent-notes-by-agent/<agent>/<topic>.md` into the private scope, preserves
canonical metadata, skips the reserved `coord-*` wire namespace, and never
overwrites an existing path. `knowledge_seed_state.json` records a completed
pass (including per-note failures), so later restarts do not repopulate the
store. `configure-study-mcp` and `upgrade-tenant` do not arm this seed.

The additive refresh path (item 6, WI#121) replaces the static-snapshot
limitation of the seed. A host-side scheduler (`ensure_knowledge_source_scheduler`,
mt-admin module `14-knowledge-sync.sh`) fast-forwards the published Study Notes
checkout and writes a generation manifest
(`.git/lunarwing-study-notes-generation.json`) only after a clean,
validated checkout. Tenant daemons poll that manifest on their own cadence
(`KNOWLEDGE_SYNC_ENABLED`, default false; `KNOWLEDGE_SYNC_CADENCE_HOURS`,
default 6; `KNOWLEDGE_SYNC_MAX_RECORDS_PER_RUN`, default 500;
`KNOWLEDGE_SYNC_MAX_BYTES_PER_RUN`, default 10 MiB) and import missing paths
through the same parser as the one-shot seed. Existing paths are never changed,
so locally authored or edited notes remain authoritative; genuine import
failures back off while healthy skips do not. `configure-study-mcp
--enable-knowledge-sync` / `--disable-knowledge-sync` toggle the tenant
cadence, and `refresh-knowledge <tenant> [--sync-source]` triggers a pass
manually. This fallback reports Git-bounded additive freshness; it is not an
exact mirror of the hosted Study Notes database.

## Database Schema

### PostgreSQL

**`memory_documents`** table:
- `id` (UUID), `user_id` (TEXT), `agent_id` (UUID, nullable)
- `path` (TEXT), `content` (TEXT)
- `created_at`, `updated_at` (TIMESTAMPTZ), `metadata` (JSONB),
  `indexed_at` (TIMESTAMPTZ, nullable — index outbox marker; see Step 1)
- Unique constraint: `UNIQUE NULLS NOT DISTINCT (user_id, agent_id, path)`;
  migration V21 fixed duplicate primary-scope paths when `agent_id` is `NULL`

**`memory_chunks`** table:
- `id` (UUID), `document_id` (UUID FK)
- `chunk_index` (INT), `content` (TEXT)
- `content_tsv` (TSVECTOR, GENERATED, GIN-indexed)
- `embedding` (VECTOR, flexible dimension after V9)

**`memory_document_versions`** table:
- `id`, `document_id`, `version`, `content`, `content_hash`, `created_at`,
  `changed_by`
- Unique constraint: `(document_id, version)`
- The PostgreSQL and libSQL storage APIs support save/get/list/prune operations;
  normal `Workspace::write()` does not automatically create a version row

Key migrations:
- `V1__initial.sql`: base schema with documents, chunks, tsvector, pgvector
- `V9__flexible_embedding_dimension.sql`: dropped HNSW index, changed to unbounded `vector` type
- `V16__document_versions.sql`: document version history
- `V21__fix_null_agent_id_unique_constraint.sql`: treats `NULL` agent IDs as
  equal for path uniqueness
- `V23__exclude_engine_runtime_from_search.sql`: removes legacy search chunks
  for persisted Engine runtime state
- `V26__study_notes_knowledge.sql`: partial PostgreSQL index for study-note
  provenance/topic metadata filters
- `V27__memory_index_outbox.sql`: adds `memory_documents.indexed_at` (outbox
  marker plus partial stale-index index) for the append->reindex two-phase
  repair sweep
- Legacy purge sweeps are code, not migrations: `purge_mission_index_chunks()`
  (mission subtree/manifest chunks) and `repair_stale_index()` (stranded
  content) with `engine/.runtime/**` exclusion pinned by V23

### libSQL

Schema mirrors PostgreSQL with SQL dialect translation:
- `UUID` -> `TEXT`
- `TIMESTAMPTZ` -> `TEXT` (ISO-8601), including `indexed_at` (V27 mirror)
- `JSONB` -> `TEXT` (JSON string)
- `VECTOR` -> `BLOB` in the base schema; when `EMBEDDING_ENABLED=true` is present
  in the process environment, startup `ensure_vector_index()` rebuilds the
  column as `F32_BLOB(N)` and creates `libsql_vector_idx`
- `tsvector` + `ts_rank_cd` -> FTS5 virtual table + sync triggers

Source: `ic/src/db/libsql_migrations.rs`

## Multi-Scope Reads

When a workspace has additional read scopes (via `with_additional_read_scopes()`), read operations can span multiple user scopes. A user with scopes `["alice", "shared"]` can read documents from both.

**Identity files are exempt.** System prompt reads identity and configuration files from the primary scope only (`read_primary()`), never from secondary scopes:

| File | Read method | Rationale |
|------|-------------|-----------|
| AGENTS.md, SOUL.md, USER.md, IDENTITY.md, TOOLS.md, BOOTSTRAP.md | `read_primary()` | Per-user identity, prevents silent inheritance |
| MEMORY.md, daily/*.md | `read()` | Shared memory is a feature |

PostgreSQL optimization: single query with `WHERE user_id = ANY($1::text[])`.

## Memory Layers And Privacy

Workspaces can define named `MemoryLayer` entries. Each layer maps to a
workspace `user_id` scope and declares whether it is writable and whether its
sensitivity is `private` or `shared`. `memory_write` accepts a `layer` and uses
`write_to_layer()` / `append_to_layer()`; all layer scopes participate in reads.

Sensitive content can auto-redirect from a shared layer to the first private
layer via an optional `PrivacyClassifier` trait:

```rust
workspace.with_privacy_classifier(Arc::new(PatternPrivacyClassifier::new()))
```

`PatternPrivacyClassifier` matches only hard PII and credential terms (SSNs,
credit cards, passwords, API keys, auth tokens, and secret keys). It
intentionally excludes broad health/contact vocabulary to avoid silent false
positive redirects. `ConfigurablePrivacyClassifier` accepts operator-provided
regex patterns. No classifier is installed by default; without one, writes go
to the requested layer.

Layer scopes are currently used directly as database `user_id` values. On a
multi-tenant deployment, operators must ensure configured scopes cannot collide
with another tenant's user ID; automatic scope namespacing is not implemented.

## Search Configuration

```rust

    limit: 10,                          // max results returned
    rrf_k: 60,                          // RRF constant (higher = flatter rank differences)

    use_vector: true,                   // enable vector search

    vector_weight: 0.5,                 // WeightedScore only
}
```

## Graceful Degradation

The system is designed to work at multiple capability levels:

1. **Full hybrid search** (embeddings enabled): FTS + vector search + RRF fusion
2. **FTS only** (embeddings disabled): `use_vector` remains configured, but no
   query embedding is generated, so the vector arm returns no results and FTS
   continues normally
3. **No database**: no `Workspace`, memory tools, or native knowledge tools are
   registered; this database-backed subsystem has no local-filesystem
   persistence fallback

When `EMBEDDING_ENABLED=false` (the default), documents are still chunked and
FTS-indexed. Only vector embeddings are skipped. After enabling a provider,
`Workspace::backfill_embeddings()` embeds up to 100 missing-vector chunks per
call; callers can repeat it until no chunks remain.

The knowledge seed is independently fail-soft. It does nothing unless both its
flag and checkout path are present, retries a missing checkout on a later boot,
records individual malformed-note failures without aborting startup, and writes
the completion marker after walking the available notes.

## V2 Engine Integration

The v2 engine (`ic/crates/lunarwing_engine/`) has its own retrieval layer
(`memory/retrieval.rs`) for project-scoped `MemoryDoc` objects. `HybridStore`
persists those objects through the workspace, but Engine context selection does
not call the workspace hybrid-search pipeline:

| System | Scope | Search method | Used by |
|--------|-------|---------------|---------|
| Workspace (`src/workspace/`) | User scope plus configured read scopes | Hybrid FTS + vector with RRF fusion | v1 agent, memory/knowledge tools, system prompt |
| Engine memory (`crates/lunarwing_engine/src/memory/`) | Project + user scope | Keyword retrieval from MemoryDocs | v2 engine execution context |

The Engine `RetrievalEngine` selects summaries, lessons, skills, and other
MemoryDocs for execution context. Agent-facing semantic search remains the
workspace tool path; Study Notes use a specialized backend FTS query over the
same document/chunk store.

## Performance Characteristics

Wall-clock timings depend on database size, provider, network, and hardware; the
code guarantees these structural properties rather than fixed latency targets:

- **Embedding cache hit:** in-memory LRU lookup; no provider call
- **Embedding cache miss:** one provider request (or batch request during writes/backfill)
- **Chunking:** linear in document size
- **FTS search:** indexed GIN scan in PostgreSQL or FTS5 in libSQL
- **Vector search (PostgreSQL):** O(N x D) brute-force cosine after V9
- **Vector search (libSQL):** `libsql_vector_idx` / `vector_top_k` when startup
  created the dimension-specific index
- **RRF fusion:** O(N log N) sort after combining the bounded ranked lists
- **Cache payload:** about 58 MB for 10,000 x 1,536-dimensional `f32` vectors,
  excluding map/vector overhead
