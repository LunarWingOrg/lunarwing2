## WI#109 — sanitize-memory mission registered Active but not firing on thread_start

Tracker body (unchanged since 2026-09-03) claims a decision-locked spec at
`projects/sanitize-memory/spec.md` (2026-08-25) whose purpose is: purge stale
cached tool output (Tier 1: time/date; Tier 2: web_search/http/shell by age)
from `state` before mission threads execute.

Re-verified on the current tree and this VM:

1. **The spec does not exist in this repository.** `projects/sanitize-memory/`
   is absent from git (all branches), from the dev-VM tenant workspaces
   (`/home/rarity/lunarwing`, `/home/rarity/lunarwing_v2`,
   `/home/antelope/lunarwing`), and from the engine's self-modifiable
   orchestrator docs. The only `projects/` trees are `ocr-sidecar` and
   `voice-sidecar`. The "registered Active" evidence in the WI was
   `engine/README.md` on a tenant, which is generated from mission
   name/status/goal only and cannot prove trigger wiring — the exact trap the
   v2.1.1.0 record called out.
2. **The stale-cache mechanism is real.** The Python orchestrator writes tool
   outputs into `state[action_name]`, `state["last_return"]`, and
   `state["step_N_return"]` (`orchestrator/default.py:1324-1327`), and the
   same `state` dict is injected as a global into every repl-code step
   (`ic/crates/lunarwing_engine/src/executor/scripting.rs:213-217`). So stale
   `state['time']` / `state['web_search']` values are genuinely readable by
   the model on resumed threads.
3. **A mission trigger cannot fix this** — the event bus is lossy and
   asynchronous; the source thread can start model work before a triggered
   mission runs (v2.1.1.0 record, "Why WI#109 is not the two-line event
   fix"). The correct shape is the scope-B contract: a deterministic
   synchronous sanitizer at the execution boundary.

### What was implemented (scope B)

`ic/crates/lunarwing_engine/src/executor/loop_engine.rs`:

- `sanitize_checkpoint_state()` purges cached tool output from the loaded
  checkpoint state:
  - **Tier 1** (`time`, `date`, `datetime`): always removed.
  - **Tier 2** (`web_search`, `http`, `shell`): removed only when the value's
    `_cached_at` RFC 3339 timestamp is older than 30 minutes. Values without a
    valid timestamp are never purged (fail-safe: no timestamp means no
    evidence of staleness).
- `ExecutionLoop::run` invokes it after checkpoint loading and **before** the
  `Running` transition and the first model call, so the first inference of
  every thread — including Mission threads — sees sanitized state. This is
  not a mission; it is an execution invariant, exactly per the scope-B
  contract.
- When anything is purged, the sanitized state is written back to
  `runtime_checkpoint.persisted_state` and a bounded `sanitized_at` RFC 3339
  marker is stamped on the thread metadata (observability counter: `debug!`
  log with `purged` count). When nothing is purged, no metadata is touched.

- `sanitizer_ignores_non_object_state` — no panic on malformed state.
- `run_sanitizes_checkpoint_before_first_model_call` — end-to-end run writes
  the `sanitized_at` marker and terminal cleanup still clears the checkpoint.
- `run_sanitizes_checkpoint_before_first_repl_step` — **the first repl-code
  step asserts the sanitized state is visible**, proving sanitization
  precedes the first inference (the scope-B completion condition).
- `run_leaves_clean_checkpoint_untouched` — no marker, no rewrite when the
  checkpoint is clean.

### Design notes / residuals

- **Fresh values are retained** by design: Tier 2 caches younger than 30
  minutes survive, because web/http/shell results are expensive to recompute
  and the WI only asked to purge them "by age". Tier 1 is unconditional
  because time/date are cheap and always wrong when cached.
- **`_cached_at` is now stamped by the Python orchestrator** (item 11
  follow-up): `stamp_cached_at` in `default.py` writes an RFC 3339 UTC
  `_cached_at` onto Tier 2 dict outputs at the persisted-state write site
  (`state[action_name] = stamp_cached_at(...)`), mirroring
  `TIER2_STALE_STATE_KEYS` in `loop_engine.rs`. Tier 2 aging is therefore
  fully effective. Only dict outputs are stamped — scalar outputs (e.g.
  plain-text tool results) stay un-stamped and un-purged (fail-open, per the
  sanitizer contract), because wrapping them would change what repl code
  reads back. Rust tests in `executor/orchestrator.rs` evaluate the helper
  through the Monty VM and verify the timestamp parses as RFC 3339 on the
  Rust side.
- **Sanitization is a fresh-start hook.** The only threads that load a
  checkpoint are new threads seeded with `initial_state` (missions) and
  Suspended-thread resumes; Waiting-thread gate resumes discard the live
  checkpoint by design (`clear_waiting_checkpoint_preserving_recovery`). The
  sanitizer therefore runs exactly where stale state can enter execution.
- **The sanitize-memory mission itself should not be re-created.** A
  model-powered mission is an unnecessarily expensive mechanism for
  deterministic state cleanup, and a mission trigger cannot meet the
  before-execution ordering requirement. If the tracker wants the mission
  form anyway, the spec must first be re-created in-repo (it is absent).
