# WI#205 — Credential exposure to the sandbox and worker lanes

**Status:** Fixed (workdir containment + scoped worker credential)
**Branch:** `kagehoenvara212envfix`
**Work item:** <https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/205>
**Date:** 2026-09-20

## Summary

WI#205 reports that the sandbox shell can read the tenant env file and obtain
the plaintext `GATEWAY_AUTH_TOKEN`, granting the full tenant-scoped gateway API
surface from inside the agent lane. The report is correct about the exposure.

The report's framing of the cause and the fix candidates was **not** correct,
and this matters because the suggested "easy" fix does not exist:

> "removing the env file from sandbox mounts sounds easy"

There is no env-file mount. The sandbox mounts exactly one host directory, and
it is chosen by the agent. Two separate exposures were found and fixed:

1. **Sandbox lane** — an unvalidated, agent-supplied working directory becomes
   the single bind mount, so pointing it at the tenant config directory exposes
   `lunarwing.env`.
2. **External-worker lane** — workers were launched with the tenant's *full*
   gateway bearer as their WebSocket handshake secret, and that value is
   readable via `podman inspect` and in tenant-readable unit files.

## Finding 1 — the sandbox mount is agent-chosen, not a fixed env mount

### What the code actually does

The generic sandbox builds one bind mount
(`ic/src/sandbox/cli_runner.rs`, `build_run_args`):

```rust
// Workspace mount: policy decides ro/rw; `z` lets SELinux hosts relabel
// the bind mount (harmless on non-SELinux hosts).
let mode = if spec.policy.allows_writes() { "rw" } else { "ro" };
args.push("-v".into());
args.push(format!(
    "{}:/workspace:{mode},z",
    spec.working_dir.display()
));
```

`spec.working_dir` originates from the shell tool's `workdir` argument
(`ic/src/tools/builtin/shell.rs`):

```rust
let cwd = workdir
    .map(PathBuf::from)
    .or_else(|| self.working_dir.clone())
    .unwrap_or_else(|| std::env::current_dir().unwrap_or_else(|_| PathBuf::from(".")));
```

Nothing validated that path. An agent passing `workdir: "/home/<tenant>/lunarwing"`
or `".../env"` produces `-v /home/<tenant>/lunarwing/env:/workspace:ro,z`, and
the 0600 tenant-owned `lunarwing.env` is then readable inside the container
(the container runs with the tenant's UID via podman `keep-id`).

Sandbox containers otherwise receive **no** tenant secrets: the shell tool
deliberately passes an empty env map to the runner, and the only `-e` entries
injected by the runner are proxy URLs.

### Why the re-probe returned `NO_ENV_FILE`

The item records that a second probe from the same lane returned
`NO_ENV_FILE`. That is **path-dependence, not mitigation**: the directory and
file are still present and still 0600 (verified on tenant `brightdawn`:
`/home/brightdawn/lunarwing/env/lunarwing.env`, mode 0600). The second probe
simply ran with a working directory that did not reach `env/`.

### Fix

New module `ic/src/sandbox/mount_guard.rs` validates the mount directory and is
enforced at both the manager and runner boundaries (defense in depth, so a
future direct caller of `CliRunner` cannot bypass it):

- **Canonicalize first.** Symlinks, `..` and lexical tricks resolve to their
  real path before any check, then the *resolved* path is mounted. This closes
  `/home/u/env/../workspace` style traversal and symlink swaps.
- **Protected directories.** Three directories under the tenant root may not be
  mounted, nor may a mount live inside them:
  - `<root>/env` — `GATEWAY_AUTH_TOKEN`, `WORKER_AUTH_TOKEN`, `LLM_API_KEY`, the
    PostgreSQL password
  - `<root>/state` — `config.toml` (three worker `auth_token` values),
    `pending-gates.json`, `coordination-violations.json`, `workspace-template/`
  - `<root>/run` — `lunarwing.sock` and a world-writable
    (`srw-rw-rw-`) `ssh-agent.sock`, i.e. the tenant's SSH identity

  The tenant root itself is deliberately **not** protected: the daemon's
  `WorkingDirectory` is `<root>/ic`, and because the shell tool defaults to the
  daemon's cwd, protecting the parent would refuse every default sandboxed
  command. The remaining children hold source, not credentials.
- **Protected filenames.** Credential-bearing names (`*.env`, `pg.secret`,
  `.env`, case-insensitive) are refused even inside an otherwise legitimate
  workspace, so a copy of the env file in the workspace is not exposed either.
- **Masking.** A protected directory *inside* an otherwise legitimate mount is
  shadowed by an empty read-only directory bind, so an agent working at the
  tenant root (or the tenant home) keeps working while the credential
  directories appear empty. Denying those mounts instead would break ordinary
  work. Note `--tmpfs` does **not** work for this — it was tested and the file
  remained readable; only the empty-directory bind actually shadows.
- **Fail closed.** A refusal is a hard error (`SandboxError::MountPathDenied`,
  kind `mount_path_denied`), surfaced to the agent as
  `[sandbox:mount_path_denied]`. It never falls back to unsandboxed execution.

A new `mount_path_denied` kind was added to the pinned `SandboxError::kind()`
taxonomy (the taxonomy test was extended accordingly). It is distinct from
`execution_failed` because the command never ran — the request was refused
before the runtime started.

### Residual risk (documented, not fixed)

Path blocking prevents mounting the config directory through the sandbox lane.
It is **not** a claim that the sandbox is safe against the agent reading the
daemon's own environment by other means: podman `keep-id` maps the container
UID onto the tenant user, who legitimately owns those files. The durable fix is
that the credential should not be reachable in plaintext at all — see the
follow-up design in `v2.1.2.0_WI205_SANDBOX_SCOPED_CREDENTIAL_DESIGN.md`.

## Finding 2 — external workers received the full gateway bearer

### What the code actually does

mt-admin passed the tenant's `GATEWAY_AUTH_TOKEN` to every external-worker
container as `AGENT_AUTH_TOKEN` and mirrored it into the daemon's
`config.toml` as `auth_token`:

```sh
gateway_token="$(_read_env_value "$tenant_env_path" GATEWAY_AUTH_TOKEN)"
[[ -n "$gateway_token" ]] && env_flags+=(-e "AGENT_AUTH_TOKEN=$gateway_token")
```

The token's **direction** is inverted from the intuitive reading. The worker is
the WebSocket **server** (`WS_ROLE=server`, bound to `127.0.0.1:<wss_port>` at
`/ws/agent`); the daemon is the client and presents the bearer on the upgrade
(`ic/src/orchestrator/external_worker.rs`, `connect_and_handshake`). No worker
ever calls the gateway API — memory, missions, logs and chat routes are all
unused by workers; LLM access goes through the separate `TENSORZERO_API_KEY`.

So the only capability this secret needs is *"authenticate one worker's inbound
task-dispatch handshake for one tenant"*. Granting the full gateway bearer
instead meant that anyone reading the value from `podman inspect` or the
tenant-readable Quadlet unit obtained the entire tenant dashboard surface:
memory read/write, log level changes, mission webhooks, voice, and file access.

### Fix

A new per-tenant `WORKER_AUTH_TOKEN` is generated in
`ic/scripts/mt-admin-lib/06-env-generation.sh`, deliberately distinct from
`GATEWAY_AUTH_TOKEN`. All worker consumers resolve it through one helper,
`resolve_worker_auth_token()`, so the container env and the daemon config can
never drift:

| Consumer | File |
| --- | --- |
| Daemon `config.toml` `auth_token` | `09-worker-config.sh` (`ensure_external_worker_config`) |
| opencode container env | `09-worker-config.sh` |
| opencode2 container env | `09-worker-config.sh` |
| pebble container env | `09-worker-config.sh` |
| kimi runtime env file | `09-worker-config.sh` (`write_kimi_runtime_env`) |
| systemd Quadlet `Environment=` | `07-units-systemd.sh` (`render_worker_quadlet`) |

Because the value is never accepted by the gateway, a leaked worker secret no
longer grants API access; it only permits impersonating the daemon toward that
one worker's local socket.

### Migration

Tenants provisioned before this change have the legacy shape baked into four
places at once (`config.toml`, three container envs, the Quadlet). Writing the
new token into only some of them would break the handshake silently — the
symptom is a refused worker connection, not a config error.

`upgrade_external_worker_auth_token()` therefore rewrites an existing
`config.toml` entry when it does not match the scoped token. It runs on the
*skip* path of `ensure_external_worker_config` too, so an existing tenant
converges on the next lifecycle pass without re-provisioning. The rewrite is a
two-pass awk (record, then emit) because a single pass can insert the new key
ahead of the existing one, producing a duplicate `auth_token` that TOML
rejects.

For tenants with no `WORKER_AUTH_TOKEN` yet, `resolve_worker_auth_token()` falls
back to `GATEWAY_AUTH_TOKEN`, so the value stays consistent with what those
containers were launched with. Such a tenant converges when its env file is
regenerated, and from that point the container env, the Quadlet and
`config.toml` all move to the scoped token together.

## Follow-up

A sandbox-scoped *gateway* credential (so the lane holds a single-purpose badge
rather than no path to the API) remains open: the gateway currently has no
token scoping at all — `UserIdentity` carries only `user_id` and
`workspace_read_scopes`, with no route scope, capability list or expiry.
Design: `v2.1.2.0_WI205_SANDBOX_SCOPED_CREDENTIAL_DESIGN.md`.
