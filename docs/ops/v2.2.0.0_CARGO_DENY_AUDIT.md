# Crate Security Audit — v2.2.0.0

**Date:** 2026-11-09 (item 2, branch `aj/kimi-2-20261109-0901`).

**Scope:** pre-release checklist item #2 — "audit all crates for security and
write report to docs/ops". Item 1's crate sweep landed as merge commit
`3e9bf3246`, so this audit runs on the post-sweep tree with LunarWing-owned
packages at 2.2.0. It covers every **27 tracked non-vendor `Cargo.lock` roots**,
including the manifest-less Pebble worker-image override, plus an
all-transitive maintenance-notice pass and a re-verification of every accepted
advisory. The six standalone lockless development/test/stray manifests are
disclosed separately below; they have no committed dependency resolution and
are not shipped.

**References:** previous release audits
[`v2.1.9.0_CARGO_DENY_AUDIT.md`](v2.1.9.0_CARGO_DENY_AUDIT.md),
[`v2.1.8.0_CARGO_DENY_AUDIT.md`](v2.1.8.0_CARGO_DENY_AUDIT.md), and the WI#418
[libSQL legacy-chain decision](v2.1.6.0_WI418_LIBSQL_LEGACY_CHAIN.md).

## Outcome

- **No unaccepted, reachable vulnerability or unsound finding and no yanked
  registry pin was found.** The only unaccepted raw-lock vulnerability IDs are
  the two `pyo3` advisories whose package never resolves into either guarded
  build graph.
- All four advisory gates pass against the current RustSec database. An
  independent `cargo-audit` pass completed over all 27 lockfiles, and a direct
  sparse-index pass checked every registry pin and checksum.
- The **13 existing advisory acceptances remain necessary and unchanged**. No
  ignore was added, removed, or widened. Only the RSA rationale was refreshed:
  RustSec now marks RSA 0.10.0 patched, but both locked and latest `russh`
  still require the affected 0.10.0-rc.18 prerelease exactly.
- **No new informational maintenance notice appeared this cycle.** The ten
  unaccepted notices in the all-transitive pass are carried from v2.1.9.0.
  `astral-tl 0.8.1` (RUSTSEC-2026-0444) remains blocked by parent releases
  that require Rust 1.99, above LunarWing's 1.96.1 MSRV.
- **No dependency, manifest, lockfile, vendor source, or CI gate changed.** The
  audit changes are this report, the checklist trail, and the rationale-only
  `ic/deny.toml` update.

## Tooling, database, and coverage

- CI-pinned `cargo-deny 0.20.2`, driven through the same wrappers as CI. The
  main and satellite gates run from the repository root, outside `ic/`'s
  vendored source replacement, so the real crates.io index is consulted and
  any `index-failure` fails the main gate.
- `cargo-audit 0.22.2` for an independent lockfile-text pass. This pass does
  not honor `ic/deny.toml` acceptances and includes pins that feature
  resolution leaves uncompiled; its raw counts are therefore not gate failures.
- RustSec advisory-db **`7a40350e1b8ba5b656d909f88222a8059a83d88d`
  (2026-11-08)**, confirmed equal to upstream `origin/main` at audit time
  (`HEAD..origin/main` = 0, `origin/main..HEAD` = 0). The checkout contains
  1,402 crate advisory files and 20 Rust CVE advisory files.
- The 27 locks contain **4,204 package records and 4,130 registry pins**.
  Those pins represent 1,140 unique crate/version pairs across 851 crates.
  Forty tracked manifests belong to these lock roots, their workspaces, or
  their resolved path dependencies.
- The final four-gate run followed the RSA rationale-only commit. Parsed TOML
  comparison confirmed identical advisory IDs and enforcement settings; only
  the RUSTSEC-2023-0071 reason string and its adjacent rationale changed.

## Accepted advisories — all 13 re-verified

Each acceptance was checked against the current advisory-db, locked package
versions, graph guards, and live crates.io metadata on 2026-11-09. Every one
still applies. None can be cleared by a compatible parent update on the current
locked lines.

| IDs | Current path and re-verification |
|---|---|
| RUSTSEC-2026-0049 / 0098 / 0099 / 0104 / 0382 | `libsql 0.6.0 → hyper-rustls 0.25.0 → rustls 0.22.4 → rustls-webpki 0.102.8`. Latest libsql is still **0.10.0** and still requests `hyper-rustls ^0.25`, `hyper ^0.14`, and `tonic ^0.11`. Patched webpki ranges begin at 0.103.x; the modern copy is fixed at **0.103.16**. Exposure remains opt-in `libsql-remote-replica` builds only under WI#418. |
| RUSTSEC-2026-0258 | Same legacy chain's `h2 0.3.27` via tonic 0.11 / hyper 0.14. There is no patched 0.3 release; the modern **0.4.20** copy is patched. The default-graph guard excludes the legacy copy. |
| RUSTSEC-2026-0346 / 0349 | Same legacy chain's `rustls 0.22.4`; no patched 0.22 release exists. The modern copy remains fixed at **0.23.46**, and no custom `ClientSessionStore` exists in LunarWing sources. |
| RUSTSEC-2023-0071 | `russh 0.62.7 → rsa 0.10.0-rc.18`. **RustSec now declares `patched = [">= 0.10.0"]`; stable RSA 0.10.0 is published and not yanked.** The locked rc.18 prerelease remains affected, and newest russh **0.65.1** still pins `rsa =0.10.0-rc.18`, so even the out-of-scope russh major bump clears nothing. Clearing now requires an upstream russh release adopting patched RSA, a reviewed vendored backport, or the WI#368 policy change. Tenant SSH-agent exposure is unchanged. |
| RUSTSEC-2019-0036 / 2020-0036 | Vendored `libsignal-protocol → failure 0.1.8`; crates.io confirms 0.1.8 remains the final release. Clearing remains the WI#367 wrapper port. |
| RUSTSEC-2021-0134 | `rental 0.5.6` unmaintained notice in the same vendored wrapper; 0.5.6 remains newest. Informational, not a vulnerability. |
| RUSTSEC-2021-0145 | `atty 0.2.14` unsound, Windows-only unaligned read; 0.2.14 remains newest and no patched release exists. It is confined to the vendored libsignal dev graph by the lockfile-only guard and `[bans]` parent restrictions. |

The rationale-only follow-up updates RUSTSEC-2023-0071 from last cycle's
`patched = []` / RSA rc.22 observation to the verified stable RSA 0.10.0 patch.
It does not alter the acceptance's ID, exposure, clearing owner, or enforcement.
The new upstream patch is a clearing opportunity for a future russh release,
not a presently applicable version bump.

Two additional raw-lock IDs are **not acceptances**: RUSTSEC-2026-0176/0177 on
`pyo3 0.28.3`, reached only as a lock pin through jiter 0.13.0's optional
`python` feature. Monty 0.0.17 does not enable it, and the guard fails loudly
if `pyo3` ever enters either graph. Latest jiter is still **0.19.0** and
requests `pyo3 ^0.30.1`; clearing the text pin requires the separate
monty/jiter major upgrade, not an audit-time patch bump.

## Yanked versions, checksums, and build exposure

`yanked = "deny"` was enforced by both cargo-deny gates with no index failures.
The independent pass also fetched each of the 851 relevant sparse-index files
and matched every locked registry version and checksum: **4,130 pins, zero
yanked, zero missing, zero checksum mismatches**. Git dependencies are not
registry pins; the main gate's `sources ok` verdict confirms they remain limited
to the reviewed monty and ruff sources.

The WI#418 per-release manual review also checked effective shipped build
commands, including mt-admin's `_vendor_guarded_cargo_build` call sites and
`scripts/build-lunarwing.sh`'s command array. `ic/Dockerfile`,
`ic/Dockerfile.worker`, mt-admin tenant builds, and the release build script
all use default features; none passes `libsql-remote-replica` or
`--all-features`. The textual guard and both default production graphs agree.

## Scope limits and remaining work

- "All crates" here means the Rust dependency graphs and every committed
  lockfile. Python requirements, npm lockfiles, and container-image/package
  scanning are separate CI surfaces and are not re-audited by this item.
- Six tracked manifests intentionally have no committed lock: the two identical
  `git-lunarwing-unix-socket-repl-server-repo` copies (the second under
  `replv2git/`), `ic/fuzz`, `ic/crates/lunarwing_safety/fuzz`, `ic/job_prompt`,
  and the stray `ic/unix-socket-client/src/Cargo.toml`. They are standalone
  development, fuzzing, WASM-staging, or stray manifests, not shipped binaries;
  their dependencies resolve at build time, so no committed exact graph exists
  for this lockfile audit. The other 40 tracked manifests are covered above.
- Routine major upgrades, the libSQL TLS migration, the vendored Signal wrapper
  port, the monty/jiter major jump, zbus 6 migration, and an MSRV-compatible
  `astral-tl` replacement remain dependency work, not new acceptances. RSA's
  new patched stable release additionally leaves WI#368 waiting on russh to
  adopt it or a deliberate local remediation decision.
- The MR pipeline on the exact final head is CI-only and cannot be run from
  this checkout; no push or MR was requested. All local advisory, registry,
  graph, and focused regression gates are green.
