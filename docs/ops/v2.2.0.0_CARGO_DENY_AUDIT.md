# Crate Security Audit — v2.2.0.0

**Date:** 2026-11-09 (item 2, branch `aj/kimi-2-20261109-0901`).

**Scope:** pre-release checklist item #2 — "audit all crates for security and
write report to docs/ops". Item 1's crate sweep landed as merge commit
`3e9bf3246`, so this audit runs on the post-sweep tree with LunarWing-owned
packages at 2.2.0. It covers every **27 tracked non-vendor `Cargo.lock` roots**,
including the manifest-less Pebble worker-image override, plus an
all-transitive maintenance-notice pass and a re-verification of every accepted
advisory. The six standalone lockless development/test/stray manifests are
disclosed separately below; they have no committed dependency resolution and
are not shipped.

**References:** previous release audits
[`v2.1.9.0_CARGO_DENY_AUDIT.md`](v2.1.9.0_CARGO_DENY_AUDIT.md),
[`v2.1.8.0_CARGO_DENY_AUDIT.md`](v2.1.8.0_CARGO_DENY_AUDIT.md), and the WI#418
[libSQL legacy-chain decision](v2.1.6.0_WI418_LIBSQL_LEGACY_CHAIN.md).

## Outcome

- **No unaccepted, reachable vulnerability or unsound finding and no yanked
  registry pin was found.** The only unaccepted raw-lock vulnerability IDs are
  the two `pyo3` advisories whose package never resolves into either guarded
  build graph.
- All four advisory gates pass against the current RustSec database. An
  independent `cargo-audit` pass completed over all 27 lockfiles, and a direct
  sparse-index pass checked every registry pin and checksum.
- The **13 existing advisory acceptances remained necessary and unchanged at
  this audit's cutoff**. No ignore was added, removed, or widened. Only the RSA
  rationale was refreshed: RustSec now marks RSA 0.10.0 patched, but both
  locked and latest `russh` still require the affected 0.10.0-rc.18
  prerelease exactly. The set is **14 today**: the 2026-11-11 WI#368 follow-up
  cleared RUSTSEC-2023-0071 (13 → 12), and the 2026-11-17 WI#749 follow-up
  below added RUSTSEC-2026-0543 and RUSTSEC-2026-0555 (12 → 14).
- **No new informational maintenance notice appeared in this cycle's
  advisory-db.** The ten unaccepted notices in the all-transitive pass are
  carried from v2.1.9.0. A later database backfill added the two chrono
  notices — see the 2026-11-17 WI#749 follow-up below.
  `astral-tl 0.8.1` (RUSTSEC-2026-0444) remains blocked by parent releases
  that require Rust 1.99, above LunarWing's 1.96.1 MSRV.
- **No dependency, manifest, lockfile, vendor source, or CI gate changed.** The
  audit changes are this report, the checklist trail, and the rationale-only
  `ic/deny.toml` update.

## 2026-11-11 WI#368 RSA clearing follow-up

- LunarWing no longer enables russh's optional `rsa` feature. The daemon and
  XMPP bridge locks each drop `rsa`, `pkcs1`, and `crypto-primes` (973 → 970 and
  895 → 892 package records respectively). The mandated vendor refresh pruned
  exactly those three crate names, taking the vendor set from 1,150 to 1,147
  crate directories. `ic/deny.toml` now has 12 acceptances; RUSTSEC-2023-0071
  and its exposure note are removed rather than widened or re-justified.
- Feature removal alone did not reject parsed RSA OpenSSH keys, so the shared
  decoder now refuses `Algorithm::Rsa` explicitly. The client decodes before
  connecting, closing the old declared-label bypass for built-in and WASM `ssh`;
  the same decoder prevents RSA identities entering the agent used by workers
  and `ssh_git`. Tests use russh's public valid RSA fixture to prove agent
  rejection without insertion and mislabeled-client rejection before connection.
- `taskset -c 0-17 cargo test -j18 --locked --lib bridge::ssh --
  --test-threads=18` passed 38/38; the equivalent `tools::builtin::ssh` lane
  passed 19/19. The broader RSA/traversal/conversation filter passed 80/80.
  Locked default `--all-targets` and `--all-features` checks, default
  `cargo clippy --lib --tests -- -D warnings`, `cargo fmt --all -- --check`, the
  vendor artifact guard, and `git diff --check` all pass. The deny-policy,
  cargo-deny, and lockfile-only guard suites pass 23/23, 15/15, and 5/5.
  CI-pinned Gitleaks v8.30.1 reports no leaks in either the non-vendor or vendor
  scan.
- Main `cargo-deny-check.sh`, `check-default-graph-advisories.sh`, and
  `check-lockfile-only-advisories.sh` are green with zero RSA warnings on
  advisory-db `31cf5a8673e10d3a4d7d829ad5095f47ed419049` (2026-11-11).
  `check-satellite-advisories.sh` has 25 roots green but fails at `pebble` on
  the unrelated, newly published RUSTSEC-2026-0486 (`rustix 1.1.5`; patched
  1.1.6). The manifest-less pinned override also carries `rustix 1.1.4`.
  These are frozen Pebble-ref contracts, so this RSA item neither rewrites them
  nor adds an ignore. The all-roots-green acceptance therefore remains blocked
  until the Pebble ref/advisory is handled separately.

## 2026-11-17 WI#749 chrono / chrono-tz acceptance follow-up

- RustSec published RUSTSEC-2026-0543 (`chrono 0.4.45`) and
  RUSTSEC-2026-0555 (`chrono-tz 0.10.4`) as unmaintained notices. Neither names
  a vulnerability, both declare `patched = []` ("all versions are affected"),
  and both point at the same announcement, chronotope/chrono issue 1768.
- **The arrival was a database backfill, not a fresh publication.** Read at the
  revision that produced the red, `advisory-db 233155b4` (2026-11-17),
  both advisories carry `date = 2026-09-14` and were added by that single bulk
  ID-assignment commit, so a tree green on 2026-11-17 morning went red at
  11:34Z with no dependency change. This is what falsified the earlier
  "no new maintenance notice" and "none justifies an ignore" statements in
  this report; both now carry a dated correction.
- `ic/deny.toml` gains one entry per ID, each with the WI#363-required reason
  shape (a work item plus a clearing owner). No other policy changed: every
  version floor and all twelve pre-existing acceptances are untouched.
- **These are the first acceptances here that a `[bans]` version floor cannot
  narrow.** The floors above exist because an ID-keyed ignore would otherwise
  cover every copy of a crate; with `patched = []` there is no safe range to
  permit, so the ignore is unbounded by construction, and it also covers any
  future direct `chrono`/`chrono-tz` dependency in another lock root.
- Scope: chrono and chrono-tz are direct dependencies of `ic` and
  `lunarwing_engine`, and chrono of `lunarwing_skills`. Only the `ic` root of
  the 26 enumerated by the satellite sweep resolves them that way, which is
  why the sweep failed for that root alone and why the ignores are inert
  everywhere else.
- Clearing is the chrono → `jiff`/`time` migration. At acceptance time 137
  Rust files under `ic/src`, `ic/crates`, and `ic/tests` name chrono in 675
  lines. That migration is dependency work tracked separately from WI#749;
  replacing chrono is explicitly not part of this item.
- Measured on this tree with the CI-pinned `cargo-deny 0.20.2`:
  `bash .gitlab/scripts/cargo-deny-check.sh` → `advisories ok, bans ok,
  licenses ok, sources ok`, exit 0, zero `index-failure` diagnostics, on
  advisory-db `233155b4` (2026-11-17). `bash
  .gitlab/scripts/check-satellite-advisories.sh` → **26 roots ok**, one
  manifest-less skip. `validate_config.py` accepts both reasons (8 YAML
  files), and `.gitlab/tests/test_deny_toml_guards.py` passes 23/23.
- The Pebble RUSTSEC-2026-0486 blocker recorded in the WI#368 follow-up above
  was cleared on 2026-11-11 (`rustix` moved to 1.1.6, WI#610 part 1), so the
  satellite sweep is all-roots green on this tree rather than 25-of-26; the
  earlier paragraph is retained as the state at that date.
