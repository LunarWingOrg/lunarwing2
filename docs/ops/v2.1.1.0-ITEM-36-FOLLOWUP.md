## The item-36 (!925) follow-up fix explained

**What just merged:** WI#133/#134 — the OpenRC quiesce-bypass defect. During tenant stop/start cycles, the init system could respawn writer containers (Pebble/OpenCode/Kimi/Vision) during the Postgres-only populate window. The fix added two things: the kawarimi loader now runs `mt-admin stop-writers` before populate (fails closed), and `stop_tenant` now verifies writers are quiesced after shutdown.

**The problem the follow-up needs to fix:**

The new verification in `stop_tenant` (`ic/scripts/mt-admin-lib/04-tenant-lifecycle.sh:962-975`) calls `tenant_writers_active` to confirm nothing is running. One of its branches inspects **containers** via `_ctr ps -a` (`04-tenant-lifecycle.sh:355-365`). `_ctr` calls `ensure_container_runtime` → `detect_container_runtime`, which **hard-dies if podman/docker is missing or broken**.

That means: on a host where the container runtime is absent (uninstalled, broken install, daemon-only tenant), **every** `stop_tenant` now fails with "could not verify writer quiescence" — including `stop_tenant` invoked from `restart_tenant` (`:1125`), upgrades (`:1227`), and `remove_tenant`. Even though all writer *services* were stopped fine.

**Why it's wrong logic, not just noise:** the defect being defended against is a container *respawning* — which requires a working container runtime. If the runtime is absent, zero writer containers can exist or respawn, so the correct answer is "quiesced," not "error." The verification conflates "can't check" with "not quiesced" in the one case where checking is unnecessary.

**The fix (small shell guard):** inside `tenant_writers_active`'s container branch, detect runtime presence first and treat absence as quiesced:

```bash
# inside the container-check branch
local rt
rt="$(detect_container_runtime 2>/dev/null || true)"
if [[ -z "$rt" ]]; then
  return 1   # no runtime → no writer containers can exist or respawn → quiesced
fi
```

(adjusting to the function's not-active/quiesced return convention), keeping the hard check for when the runtime exists but introspection fails — that case *should* still fail closed, since a live runtime could respawn writers.

**Why it matters before release:** without it, upgrading or removing a tenant on a host with a degraded/removed runtime bricks those lifecycle operations until the runtime is reinstalled — an operator-visible regression introduced by the fix itself. It also matters because `restart_tenant` is on that path, so routine restarts hit it.
