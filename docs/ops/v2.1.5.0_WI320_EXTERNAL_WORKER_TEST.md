## Scope

Test every external worker (pebble, opencode, opencode2, kimi) on a fresh
multi-tenant tenant, with worker images built **with toolchains**
(Rust/Go/C++/Python/Node in-image). Drive long-running, complex jobs through
the tenant daemon's `job_create` builtin tool that exercise the workers' own
tools: Python, Rust, and C compiles/runs inside the worker containers.

Host: Gentoo dev VM (Vultr VPS), systemd (user-manager tenant units), podman
rootless per-tenant stores, 12 cores / 23 GiB RAM. Tenant daemon ENGINE_V2=true
(rendered default).

## Test design

Per worker, driven through the tenant's web gateway chat
(`POST /api/chat/send` on a fresh thread) instructing the tenant agent to call
`job_create` with `mode: <worker>`, `wait: false`:

1. **gauntlet** (primary): write+compile+run a C program (gcc -O2, 300x300
   matrix multiply with checksum + timing), create+build+run a Rust cargo
   project (naive recursive fib(35)), write+run a Python 3 script that parses
   both outputs into report.json, optional Go run, then write SUMMARY.md and
   list the workspace.
2. **smoke** (fallback/diagnostic): write smoke.txt and cat it back.

Jobs polled via `GET /api/jobs` / `/api/jobs/{id}`; evidence collected via
`/api/jobs/{id}/events` (the `files/*` endpoints cover sandbox jobs only, not
external-worker jobs). Tool approvals answered with `always` via
`POST /api/chat/approval`.

## Findings and failure analysis

### F1 — Engine V2 gate path (not v1 approvals) governs `job_create` from gateway chat

Gateway threads route through the Engine V2 Monty CodeAct orchestrator
("routing user input through engine v2" at daemon debug level). `create_job`
is a Privileged action: the call parks in the engine gate store and the thread
goes `Waiting`. The v1 `pending_approval` field in `/api/chat/history` stays
empty; the gate surfaces at `GET /api/chat/pending-gates`. Approval via
`POST /api/chat/approval {request_id, action: "always", thread_id}` resumes
the thread. Any harness driving job creation on an Engine-V2 tenant must poll
the gates endpoint, not history.

### F2 — Gate-resume flakiness (observation; engine follow-up candidate)

First-round dispatch parked 4 gates. kimi's approval resumed into a real
`create_job` (job created 4s later). The pebble/opencode threads' identical
approvals resumed the threads, but the model answered with plain text
("2 text response(s) without code blocks — model may not be following
CodeAct prompt") and went terminal WITHOUT re-issuing the gated call; the two
gates remained listed in `pending-gates` after their threads were terminal,
and re-delivered approvals were correctly dropped as stale
("Ignoring stale approval: thread not in AwaitingApproval state state=Idle").
Workaround: re-dispatch in a fresh thread. The gate-store entries for
terminal threads also linger (visible in pending-gates until restart
reconciliation). Deterministic resume + gate cleanup on thread termination
looks worth an engine work item.

### F3 — kimi baked config uses a NetBird MagicDNS name that containers cannot resolve (fixed for the tenant)

`kimicode4lunarwing/config/config.toml` bakes
`base_url = "http://cotterhomelab3.netbird.selfhosted:3000/openai/v1"`.
Rootless podman containers resolve via 169.254.1.1/9.9.9.9 — MagicDNS names
only resolve on the host. In-container: `getent hosts` → fail, curl →
`http_code=000`. The kimi CLI retried 9 times over 140s and the job failed
with `provider.connection_error: Connection error.`

Fix (tenant-level, via supported knobs):
`mt-admin configure-kimi extworktest --base-url http://100.88.232.146:3000/openai/v1 --model tensorzero::function_name::lunarwing`
(numeric NetBird IP of the TensorZero host; verified reachable (HTTP 400 to an
empty POST) from BOTH host and container). After `restart-worker extworktest kimi`
the gauntlet completed first-try with zero errors.

Note: the kimi baked default model is `tensorzero/FrontierCODEK`; the override
also pinned the known-good `lunarwing` function. Whether FrontierCODEK exists
on the gateway was not tested (connectivity was fixed and model pinned in one
step).

**Repo-level candidate:** bake the numeric-reachable default or document the
MagicDNS limitation in `docs/ops/WORKER-CONTAINERS.md` — other MT hosts with
NetBird-only TensorZero will hit the same wall for the kimi lane.

### F4 — opencode v1 (pinned v1.18.25) crashes deterministically at session start (upstream; unfixable from config)

Every task on the opencode v1 worker failed in ~28s with the bridge reporting
"Unexpected server error. Check server logs for details." The in-container
opencode log shows the session dying at `loop step=0`:

```
SystemPrompt.environment — TypeError: undefined is not an object (evaluating 'a.name')
```

Upstream v1.18.25 `SystemPrompt.environment` sorts project references with
`a.name.localeCompare(b.name)`; an undefined entry in the Reference list
crashes the prompt build before any model call. Deterministic across five
attempts and all remediation shapes tried:

- base-URL override (materialized workspace config) — crash unchanged
- MCP block stripped (context7/exa removed) — crash unchanged
- plugin list stripped (opencode-mem, opencode-caveman, opencode-agent-skills,
  envsitter-guard, opentmux removed) — crash unchanged
- workspace converted to a git repo (`ctx.project.vcs` path) — crash unchanged

No alternative invocation mechanism can dodge this: every job path funnels
into `opencode serve` session prompt assembly. This matches the WI author's
expectation ("opencode v1 maybe has issues but opencodev2 should be ok").
**Recommendation:** treat the opencode v1 lane as broken at v1.18.25 for this
deployment shape; opencode2 (v2.0.21) passed the same gauntlet twice and is
the working lane. (Antelope's v1 worker shows one started task with no
completion — consistent, though inconclusive.)

### F5 — opencode/opencode2 baked baseURL is an RFC1918 address (worked briefly, then dead)

`opencode4lunarwing/config/opencode.json` and `opencode2.4lunarwing/config/opencode2.json`
bake `http://192.168.1.157:3000/openai/v1/`. This host has no 192.168.x
interface; the address routes to the public gateway. opencode2's first
gauntlet succeeded against it at 15:23Z (real tool calls in the worker log:
gcc, cargo, python3, go), but by ~15:31Z the address was unreachable from both
host and container (connect timeouts, 3/3 host attempts). The address's
reachability is therefore ephemeral on this host — presumably a datacenter
path that flapped. Both workers were given the numeric NetBird IP override
(100.88.232.146) and the rerun passed. **Repo-level candidate:** same as F3 —
the baked RFC1918 default is only valid on the original author's LAN.

### F6 — pebble image PATH warts (worker recovered)

In the pebble worker's task shell, `cargo` and `go` are not on the default
PATH (the image installs them; verified via direct `podman run`). The agent
hit `cargo: command not found`, located the rustup toolchain at
`/usr/local/rustup/toolchains/1.96.1-x86_64-unknown-linux-gnu/bin/` itself,
prefixed PATH, and completed the Rust step; it recorded `go` as missing in
SUMMARY.md. Cosmetic image fix: export the toolchain PATH for the task shell
environment in `pebble4lunarwing/entrypoint.sh`.

### F7 — opencode2 executor SDK drift (non-fatal)

`[opencode_task_executor] failed to list session messages: TypeError:
sdk.session.message.list is not a function` (opencode_task_executor.ts:475).
The assistant-text fetch path is broken against opencode v2.0.21's SDK, but
the task still completed and reported success through the event stream.
Worth a bridge fix so final text extraction works on the pinned v2 SDK.

## Mechanisms exercised (per WI: "different ways and mechanisms")

1. Chat-driven `job_create` via web gateway with engine-v2 gate approval
   (`always`) — primary path, all four workers.
2. Gate denial + model re-dispatch with corrected mode (opencode2 first round).
3. Fresh-thread redispatch after gate-resume FINAL-out (pebble/opencode first
   round).
4. Per-worker env override knobs (`configure-kimi`, `configure-opencode`,
   `configure-opencode2`) + `restart-worker` — the supported remediation path.
5. Direct workspace config surgery for opencode v1 (MCP strip, plugin strip,
   git init) with hot-reload — all insufficient against the upstream crash.
6. Smoke vs gauntlet task shapes (minimal vs multi-toolchain).
