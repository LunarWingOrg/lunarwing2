## Verdict

**WI#126 is an investigation and scoping item, not an implementation request.**
The current engine has neither a lifecycle producer nor a mission consumer for
`thread_start`, and it does not install a default thread-start mission. A
mission shown as `Active` can therefore still be incapable of firing on a
thread start.

There are also two different meanings hidden behind the word "event":

- the public cadence `event:<pattern>` matches inbound channel-message text;
- the internal `OnSystemEvent { source, event_type }` cadence matches structured
  events explicitly dispatched by the engine.

`event:thread_start` is the first form. It does not subscribe to thread
lifecycle changes. The public `mission_create` and `mission_update` surfaces
cannot currently create the second form.

A simple asynchronous mission trigger is **not** a valid fix for WI#109's stated
requirement to sanitize state before a thread executes. The engine's event bus
is lossy, the listener runs concurrently, and the source thread can begin model
work before a triggered mission finishes. WI#109 therefore remains open and
needs a synchronous pre-execution sanitation contract. No production code was
changed for WI#126.

## Current behavior, source-verified

### Default missions

`MissionManager::ensure_learning_missions` is the only startup seeding path for
the managed mission fleet (`ic/src/bridge/router.rs:1765`). With skill
self-improvement enabled, it manages five missions
(`ic/crates/lunarwing_engine/src/runtime/mission.rs:1509-1613`):

| Mission | Structured source | Structured event |
|---|---|---|
| `self-improvement` | `engine` | `thread_completed_with_issues` |
| `skill-extraction` | `engine` | `thread_completed_with_learnings` |
| `conversation-insights` | `engine` | `conversation_insights_due` |
| `expected-behavior` | `user_feedback` | `expected_behavior` |
| `skill-maintenance` | `engine` | `skill_maintenance_due` |

There is no managed `thread_start` mission and no sanitize-memory definition in
this repository (a repo-wide `rg -i sanitize` over the Rust tree finds only the
input/prompt-injection sanitizer in `lunarwing_safety` and Monty's
`sanitize_action_results`, unrelated to missions). When skill self-improvement
is disabled, the three skill-learning missions are absent or paused
(`ic/crates/lunarwing_engine/src/runtime/mission.rs:594-602,748`); that does not
change the thread-start conclusion.

The generated `engine/README.md` is not evidence of trigger wiring: its mission
summary prints only name, status, and truncated goal, not cadence or listener
state (`ic/src/bridge/store_adapter.rs:399-407`). This explains how WI#109 could
observe a mission labelled `Active` without proving that it had an executable
thread-start subscription.

### Lifecycle event producer gap

Every fresh engine thread is persisted while still `Created`
(`ic/crates/lunarwing_engine/src/runtime/manager.rs:399-423`), then handed to
`ExecutionLoop::run`. `ExecutionLoop::run` records the transition from `Created`
to `Running` (`ic/crates/lunarwing_engine/src/executor/loop_engine.rs:250-258`),
and the existing test `events_are_recorded` confirms that event is first in the
thread history.

That transition uses `Thread::transition_to`, which records the event only. It
does not use the adjacent `transition_to_broadcast` helper
(`ic/crates/lunarwing_engine/src/executor/loop_engine.rs:148-173`). Therefore
subscribers never receive the fresh-thread transition. Terminal `Done` and
`Failed` transitions are broadcast only after final persistence succeeds
(`ic/crates/lunarwing_engine/src/runtime/manager.rs:721-793`).

No dedicated `ThreadStarted` variant exists in `EventKind`; lifecycle is already
represented by `StateChanged { from, to, reason }`
(`ic/crates/lunarwing_engine/src/types/event.rs:129-137`). A future producer does
not need a new serialized event variant: the exact
`Created -> Running` transition is sufficient and distinguishes a fresh start
from `Waiting/Suspended -> Running` resume.

### Mission consumer gap

`MissionManager::start_event_listener` subscribes to the thread broadcast bus,
but immediately discards everything except transitions to `Done` or `Failed`
(`ic/crates/lunarwing_engine/src/runtime/mission.rs:1151-1210`). Its four
subsequent dispatches cover issue diagnosis, skill maintenance, skill
extraction, and conversation insights (`mission.rs:1277,1309,1377,1435`); none
dispatches `thread_start`.

Even if the `Created -> Running` transition were broadcast, the current listener
would ignore it. Conversely, adding only a listener arm would do nothing because
the transition is not broadcast. Both halves are missing.

The existing structured-event fire path is otherwise usable. It filters active
missions by exact source/event type and by owner (or shared ownership), then
uses the normal fire path (`ic/crates/lunarwing_engine/src/runtime/mission.rs:982-1032`).
A payload containing `source_thread_id` receives durable replay deduplication
(`ic/crates/lunarwing_engine/src/types/mission.rs:173-193`).

### Public cadence mismatch

The bridge advertises `event:<pattern>` as a `mission_create` cadence
(`ic/src/bridge/router.rs:1544`). The parser maps it to `MissionCadence::OnEvent`
(`ic/src/bridge/effect_adapter.rs:1091-1098`); `OnSystemEvent` has no public
syntax. `OnEvent` missions are checked against ordinary inbound message content
after safety validation (`ic/src/bridge/router.rs:3402,4894-4923`).

Consequently:

- `event:thread_start` fires only when a user's message text contains
  `thread_start`;
- an internal `OnSystemEvent { source: "engine", event_type: "thread_start" }`
  mission would never fire because there is no producer or consumer dispatch;
- an `Active` status means the mission is eligible to be considered, not that a
  matching event source exists.

## Why WI#109 is not the two-line event fix

A broadcast-based mission trigger has intentionally weak delivery and ordering
semantics:

1. The channel has capacity 256 (`ic/crates/lunarwing_engine/src/runtime/manager.rs:106`).
2. A lagged mission receiver logs and drops skipped events
   (`ic/crates/lunarwing_engine/src/runtime/mission.rs:1447-1450`).
3. The listener starts after persisted mission/thread recovery
   (`ic/src/bridge/router.rs:1753-1786`), so it cannot be a recovery barrier.
4. A triggered mission is a separate asynchronous `ThreadType::Mission` thread
   (`ic/crates/lunarwing_engine/src/runtime/mission.rs:821-864`). Nothing waits
   for it before the source thread proceeds.
5. Triggering on Mission thread starts would recurse: firing the mission creates
   another Mission thread. The terminal listener already avoids the analogous
   loop by skipping Mission threads
   (`ic/crates/lunarwing_engine/src/runtime/mission.rs:1202-1205`).

Those properties are acceptable for best-effort learning work after a thread,
but not for a required purge before inference. They also make a model-powered
mission an unnecessarily expensive mechanism for deterministic state cleanup.

## Executable follow-up scopes

### A. Optional generic background `thread_start` event

This is useful only for best-effort observational routines. Implement it as a
separate follow-up with this contract:

1. The canonical key is `source = "engine"`,
   `event_type = "thread_start"`.
2. "Start" means exactly the first `Created -> Running` transition. Resumes and
   recovery transitions do not count.
3. Broadcast only after the source thread has a durable `Created` record.
4. The mission listener dispatches a payload containing at least
   `source_thread_id`, `project_id`, and `thread_type`; the source ID is the
   deduplication identity.
5. Never dispatch from `ThreadType::Mission`. Initially restrict dispatch to
   top-level `Foreground` threads; including `Research` children creates hidden
   fan-out and can indirectly recurse when mission threads spawn research
   children.
6. Keep the cadence engine-internal initially. If user-created structured
   subscriptions are later required, add an explicit, allowlisted syntax such
   as `system:engine:thread_start`; do not reinterpret existing
   `event:<pattern>` values.
7. Do not seed a sixth default mission as part of the plumbing change. A default
   needs a separately approved goal, budget, feature gate, and rollback policy.

Required tests:

- one fresh foreground thread emits and dispatches exactly once;
- a resumed waiting/suspended thread does not dispatch;
- Mission and Research threads do not dispatch;
- duplicate delivery with the same `source_thread_id` does not spawn twice;
- another user's mission does not fire;
- the new broadcast remains visible and correctly ordered on the gateway SSE
  path, which converts `StateChanged` into `ThreadStateChanged`
  (`ic/src/bridge/router.rs` SSE conversion).

### B. WI#109 synchronous state sanitation

Treat sanitation as an execution invariant, not as a mission cadence:

1. Put the decision-locked sanitize-memory specification in this repository (or
   link a durable, versioned source) before implementation; it is not present in
   the inspected tree.
2. Define precisely which state is sanitized: runtime checkpoint state,
   previous tool-result messages, workspace memory, or some combination. These
   are different persistence layers.
3. Add a deterministic pre-execution sanitizer at the owning runtime boundary,
   after state/checkpoint loading but before the first prompt/model call.
4. Apply it to the explicitly approved thread types, including Mission threads
   if WI#109 retains that requirement. Do not spawn another Mission thread.
5. Persist the sanitized representation before execution when restart behavior
   depends on it, and record bounded, non-secret observability counters.
6. Test with stale Tier 1 and Tier 2 values that the first model request sees the
   sanitized state; test fresh-value retention, resume/recovery behavior,
   tenant isolation, and failure policy.

This scope gives WI#109 a verifiable completion condition: sanitation must be
visible in the **first** model context of every in-scope thread. Merely observing
a later mission run or an `Active` listing is not sufficient.

## Default-policy decision

The recommended 2.1.1.0 policy is:

- retain the existing five managed missions;
- add no default thread-start mission under WI#126;
- reserve `thread_start` for a future best-effort structured event if a concrete
  consumer is approved; and
- implement mandatory pre-thread cleanup synchronously under WI#109.

This preserves current defaults, avoids per-turn model cost and event fan-out,
and separates an optional notification mechanism from a correctness boundary.
WI#126 can close with this scope; checklist item 9 / WI#109 must remain open
until its separate implementation and live reproduction are complete.
