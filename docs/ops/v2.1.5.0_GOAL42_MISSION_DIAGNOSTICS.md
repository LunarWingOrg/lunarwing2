## Findings

1. **The reported deployed build predates the fix.** The notes cite pipeline
   5141, revision `5e2b3aae8` (01:56 UTC). The first WI#311 fix is `01ef437e6`
   (03:06 UTC); its follow-up is `ae9a2ab74` (04:54 UTC). Neither is an ancestor
   of the cited build. The operator confirmed the cited build is correct.
   Continued Completed-parking on that build does not demonstrate a regression
   in the later fix. No deployed state was changed during this investigation.
2. **The cron expression does not match the stated intended time.**
   `0 10 15 * * *` fires daily at **15:10 UTC**, not 10:15. At the reported
   10:31 check it is not due. Daily 10:15 is `0 15 10 * * *` (six fields) or
   `15 10 * * *` (five). A fixed-date regression runs the actual engine parser
   against all three forms; schedule semantics are unchanged.
3. **Confirmed reporting defect, corrected here:** `last_fired_at` is an
   optional, serde-defaulted field. Legacy mission records can have thread
   history while lacking it. Both bridge and host query paths previously
   derived `never_fired` only from that timestamp. They now use
   `Mission::has_fired()`, which checks both recorded sources. Missing historical
   timestamps stay null; no timestamps or runs are invented.
4. **Creation is Active by default, and the "born terminal" mystery is settled
   by the code, not unresolvable.** `Mission::new` initializes Active;
   `create_mission` persists it before registering it in the active index.
   Review correction (!1431 note 6231, P-2): the explicit completion APIs
   `complete_mission`/`complete_mission_with_owner` have **no production
   caller** at either the reported build or this head — their only host caller
   was `mission_delete`, removed in `b10b51201` (2026-07-26). The canaries and
   standup missions showing `threads >= 1` with `last_fired_at = None` were
   therefore not born terminal and were not completed by a live API: history
   and `last_fired_at` are always written together by `record_thread`, so
   history without a timestamp can only come from a record written by a
   binary older than WI#143 (`b9fd0a5d7`, reached master 2026-09-16), a
   downgrade re-save, or a mission file written outside the engine (see the
   P-8 follow-up). The old phrase rule then completed them. Note that
   `threads_today = 1` on a Completed mission is a **frozen** counter, not
   "fired today": `rollover_daily_budget` runs only for Active missions.
   **Deciding check for the operator:** per affected mission, read
   `created_at`, `updated_at` and `threads_today_date` in `mission.json`,
   plus the `created_at` of each thread id in `thread_history`. Only the
   thread dates settle the pre-WI#143 explanation: a history thread created
   before 2026-09-16 confirms it, because `created_at`/`updated_at` on the
   mission row do not discriminate (any older mission phrase-completed in
   September shows old dates, and the restart recorder can re-stamp
   `updated_at`).
5. **Persistence and listing have different scopes.** Startup reloads workspace
   mission documents into HybridStore, then globally bootstraps active missions
   into the manager. Ticks use this index; conversation respawn does not rebuild
   it. `mission_list` only returns the caller's own/shared missions in the current
   project.
   Review correction (!1431 note 6231, P-5): the project-switch hypothesis does
   not explain the vanished `pr-digest-rebuild-1005` — the same listing context
   still showed the canaries at 11:30, and for one user the project is stable
   across conversations. The three silent mechanisms that can actually remove a
   mission from the listing are:
   1. **deletion** — logged only at `debug!` in the tester's build
      (`5e2b3aae8`), raised to `info!` by `ae9a2ab74`;
   2. **a boot load/parse failure of a `mission.json`** — the record is dropped
      from the map at debug level only, so the mission is neither listed nor
      scheduled (a `warn!` for this is tracked as a follow-up);
   3. **duplicate default projects** — an unlocked check-then-create or a
      `project.json` that failed to load at boot can leave two "default"
      projects, splitting visibility.

## Changes and coverage

- Create/list/history tool results expose project ID, cadence, effective
  timezone, cron field order and **persisted** next-fire timestamp. Creation
  additionally exposes actual lifecycle status, including deduped records.
- Review fold-ins (!1431 note 6231): create/list/history now also expose
  `created_at`, `updated_at` and `threads_today_date` (P-3 — `threads_today`
  is frozen on non-Active missions, so it must travel with its date), and
  `mission_create` answers `deduplicated: true` with the requested cadence
  alongside the persisted `schedule.cadence` plus a `mission_update` pointer
  when a same-named non-terminal mission is returned unchanged (P-4 — the
  exact `pr-digest-rebuild-1005` re-create trap). `codeact_preamble.md`
  documents the cron field order and the dedup marker.
- Tool schemas spell out cron field order and the 10:15 example. List guidance
  explicitly describes visibility scope and recovery for Completed missions.
- Legacy-record regressions omit `last_fired_at` while retaining thread
  history; tool and host query results must not claim the mission never fired.
- The persistence regression creates a cron mission through the tool against
  a real libSQL-backed Workspace, verifies Active/no fire before its due time,
  simulates a missed tick, discards store/manager state, loads a fresh store,
  globally bootstraps from another project, and verifies exactly one spawned
  thread, correct owner, successful completion, Active status and a future
  next-fire time. It also checks that another project's list is empty while
  the original project still sees the persisted mission.
- A webhook regression ensures schedule diagnostics do not expose its secret.
- Existing recurring-run, terminal-state, explicit-resume, event/webhook and
  scheduler tests remain authoritative for WI#311 lifecycle behavior.
