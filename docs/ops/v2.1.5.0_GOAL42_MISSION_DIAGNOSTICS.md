## Findings

1. **The reported deployed build predates the fix.** The notes cite pipeline
   5141, revision `5e2b3aae8` (01:56 UTC). The first WI#311 fix is `01ef437e6`
   (03:06 UTC); its follow-up is `ae9a2ab74` (04:54 UTC). Neither is an ancestor
   of the cited build. The operator confirmed the cited build is correct.
   Continued Completed-parking on that build does not demonstrate a regression
   in the later fix. No deployed state was changed during this investigation.
2. **The cron expression does not match the stated intended time.**
   `0 10 15 * * *` fires daily at **15:10 UTC**, not 10:15. At the reported
   10:31 check it is not due. Daily 10:15 is `0 15 10 * * *` (six fields) or
   `15 10 * * *` (five). A fixed-date regression runs the actual engine parser
   against all three forms; schedule semantics are unchanged.
3. **Confirmed reporting defect, corrected here:** `last_fired_at` is an
   optional, serde-defaulted field. Legacy mission records can have thread
   history while lacking it. Both bridge and host query paths previously
   derived `never_fired` only from that timestamp. They now use
   `Mission::has_fired()`, which checks both recorded sources. Missing historical
   timestamps stay null; no timestamps or runs are invented.
4. **Creation is Active by default.** `Mission::new` initializes Active;
   `create_mission` persists it before registering it in the active index.
   Existing explicit completion APIs and old phrase-based completion can mark
   missions terminal, but current source has no session-boundary transition
   that creates ordinary cron missions as Completed. A status snapshot cannot
   establish when the transition occurred. The reported canaries need their
   actual persisted history to determine what happened.
5. **Persistence and listing have different scopes.** Startup reloads workspace
   mission documents into HybridStore, then globally bootstraps active missions
   into the manager. Ticks use this index; conversation respawn does not rebuild
   it. `mission_list` only returns the caller's own/shared missions in the current
   project. A missing row in one conversation is not proof of lost persistence.
   This is a possible explanation for the replacement digest's disappearance,
   not a verified diagnosis of that tenant's records.

## Changes and coverage

- Create/list/history tool results expose project ID, cadence, effective
  timezone, cron field order and **persisted** next-fire timestamp. Creation
  additionally exposes actual lifecycle status, including deduped records.
- Tool schemas spell out cron field order and the 10:15 example. List guidance
  explicitly describes visibility scope and recovery for Completed missions.
- Legacy-record regressions omit `last_fired_at` while retaining thread
  history; tool and host query results must not claim the mission never fired.
- The persistence regression creates a cron mission through the tool against
  a real libSQL-backed Workspace, verifies Active/no fire before its due time,
  simulates a missed tick, discards store/manager state, loads a fresh store,
  globally bootstraps from another project, and verifies exactly one spawned
  thread, correct owner, successful completion, Active status and a future
  next-fire time. It also checks that another project's list is empty while
  the original project still sees the persisted mission.
- A webhook regression ensures schedule diagnostics do not expose its secret.
- Existing recurring-run, terminal-state, explicit-resume, event/webhook and
  scheduler tests remain authoritative for WI#311 lifecycle behavior.
