## Scope

Live end-to-end verification of the MCP Part-2 trust and runtime surfaces on a
real multi-tenant deployment (systemd user units, per-tenant Postgres):

1. Publisher signatures (ed25519 `verify_strict` over canonical manifests)
2. Dependency locks (signed lockfiles pinning exact version + SHA-256)
3. Marketplace revocation distribution (signed lists, monotonic sequence,
   startup HTTPS/localhost refresh, activation re-check, rollback/refusal)
4. Mandatory sandbox profiles (`require_sandbox_profiles`)
5. Persistent external-worker placement (`placement = external_worker`)
6. Bundled gateway control-plane service (`/admin/routes` + `/mcp` data plane)
7. Generic external runtime descriptors (`external_runtimes` + `--transport external`)

Code under test: integration commits `bed3c9d9`, `082ded85`, `cf9aff8f`
(marketplace trust gates, gateway control plane, external runtime descriptors),
already merged on this branch.

## Method

- Tenant provisioned with
  `sudo ic/scripts/lunarwing-mt-admin.sh add-tenant mcp8 --no-health --no-ssh --no-weechat-bootstrap`
  (port block 10010-10019, extended 20010-20019; no workers, no DarkIRC).
- Release build via `mt-admin build-tenant mcp8` (tmux session `mcp8build`,
  log `/tmp/mcp8-build.log`).
- Fixtures (test scaffolding, kept out of the repo under `/tmp/mcp8-fixtures`):
  - `fake_mcp_server.rs` — dependency-free MCP 2024-11-05 stdio server
    (initialize / tools.list / tools.call), built with plain `rustc -O` so it
    is a native Linux executable (pinning requires native bytes).
  - `gen_fixtures.py` — ed25519 fixture generator (Python `cryptography`)
    replicating the exact signing contract of `ic/src/tools/mcp/marketplace.rs`:
    canonical payload = compact serde_json of the struct in declaration order,
    signature = ed25519 over those bytes, lowercase hex. The daemon accepting
    these lists is itself the cross-implementation interop proof.
  - `revocation_server.py` — loopback HTTP distribution point (localhost HTTP
    is explicitly allowed for test harnesses by `MarketplaceConfig`).
  - `echo_upstream.py` — loopback HTTP upstream that echoes received headers
    (verifies gateway routing-header stripping / auth handling) and answers
    MCP `initialize`.
- Tenant-side ports (from the mcp8 extended block, unused by real services):
  20013 revocation HTTP, 20014 gateway control plane, 20015 echo upstream.
- The complete `mcp-servers.json` (including the file-level `marketplace`,
  `external_runtimes`, and `require_sandbox_profiles` sections, which have no
  CLI surface) is seeded on disk before first daemon start so the one-shot
  disk-to-DB migration imports it for owner `mcp8`.

  `Applied newer marketplace revocation list sequence=1`,
  `Injecting startup MCP clients into extension manager count=2`
  (fake + fake-external; fake-worker correctly not host-activated), and
  `MCP gateway control plane listening bind=127.0.0.1:20014`.
- Revocation cache persisted atomically at the configured path (0600, tenant-owned).
- `mcp list` (DB-backed, owner mcp8) shows all three seeded servers with correct
  placements; `mcp list --verbose` shows provenance/sandbox/options detail.
- Live sandbox verification on the two spawned children (pid status):

### Marketplace trust (signatures, locks, revocation)

- Publisher signatures: the daemon verified Python-generated ed25519
  signatures over canonical serde_json bytes (cross-implementation interop of
  the exact `marketplace.rs` signing contract) on every startup fetch.
  Signed manifest (`signed-manifest.json`) and signed dependency lockfile
  (`signed-lockfile.json`) artifacts were generated in the exact enforced
  formats; their verify paths are library-level (no catalog install CLI yet —
  deferred) and covered by the MCP unit suite.
- R1 distribute+startup: staging list seq 2 (revokes `@test/pinned-server`
  1.0.0) and restarting applied it (`Applied ... sequence=2`) and skipped the
  revoked server: `Skipping startup activation: package is revoked by the
  marketplace list server=fake` (injection count dropped 2 → 1).
- R2 activation re-check: `mcp toggle fake --enable` fails —
  `marketplace: server 'fake': ... package '@test/pinned-server' is revoked by
  the marketplace list`.
- R4 recovery: operator DB surgery (`enabled=false` on the revoked row),
  restart → seq 3 (un-revoke, empty entries) applied, `fake-external`
  re-activated, `mcp toggle fake --enable` then succeeded through the live
  gateway and both children respawned.
- R6 bad signature: a seq-3 list signed by an attacker key but claiming the
  trusted publisher is rejected (`signature verification failed for publisher
  'test-marketplace'`); cached list retained.
- R7 rollback refusal: re-serving seq 1 while the cache holds seq 3 is
  silently not applied (no `Applied` log, cache unchanged).
- R8 fail-closed reads: corrupting the revocation cache makes every config
  load fail (`revocation store: ... revocation list JSON: expected value`);
  corrupting the trust store likewise (`trust store ... invalid JSON`).
  Restoring both files restores normal operation.

### FINDING (documented, not fixed here) — revocation recovery trap

Once the cached list revokes an *enabled* server, every MCP config load fails
closed (`McpServersFile::validate` → `MarketplaceConfig::validate` rejects
revoked enabled servers). Consequences observed live:

1. The startup load runs *before* the revocation refresh, against the stale
   cache; when it fails, the daemon logs `MCP server configuration is invalid
   ... Fix or remove the corrupted config`, starts with zero MCP servers, and
   **never fetches a newer (remedying) list** — the marketplace cannot heal
   the tenant by publishing an un-revoke list.
2. All CLI remediation paths (`mcp toggle --disable`, `mcp remove`,
   `mcp revoke`, `mcp unpin`) fail closed too, because they load+validate the
   same poisoned config. Only direct DB surgery (or handing the tenant a newer
   cache file out-of-band) recovers.
3. Collateral: in the restart where seq 2 was fetched, the healthy
   `fake-external` server was activated successfully but then **rejected and
   torn down** at injection (`Rejected MCP startup injection without current
   host placement`) because `inject_mcp_client`'s re-read of the config failed
   on the revoked sibling. The warn message is misleading (placement was
   correct).

Recommendation (follow-up work item): load-time revocation checks should not
invalidate the whole config — e.g. validate only at activation/persist time,
or demote revoked enabled servers to skipped-with-warning at load so refresh
and CLI remediation (`toggle --disable`) keep working.

### FINDING 2 (fixed on this branch) — DB persist path bypassed file-level validation

`mcp add nosandbox --transport stdio ...` (no `--sandbox`) under
`require_sandbox_profiles = true` **succeeded and persisted** on the tenant:
`mutate_mcp_servers_db` CAS-wrote the mutated `McpServersFile` without
re-validating it (the disk path `save_mcp_servers` does validate). Every
subsequent MCP CLI command then failed closed on load
(`Server 'nosandbox': require_sandbox_profiles is set ...`), requiring DB
surgery to remove the row. Activation itself stayed fail-closed (startup load
rejects the poisoned config), so this was a consistency/DoS bug, not a sandbox
escape. Fixed on this branch: `mutate_mcp_servers_db` now runs
`servers.validate()` before the CAS write
(`ic/src/tools/mcp/config.rs`), plus a libsql-backed regression test
`db_persist_rejects_whole_file_validation_failures`. Live behavior above was
recorded against the pre-fix tenant binary; the fix is verified by the
regression test (tenant rebuild not repeated for a one-line write-path gate).

### Mandatory sandbox profiles

- S1: with `require_sandbox_profiles = true`, `mcp add` of an enabled stdio
  server without `--sandbox` — see Finding 2 (pre-fix binary persisted it;
  post-fix behavior is the load-time rejection shown by
  `mcp list`: `require_sandbox_profiles is set: host stdio servers must carry
  a sandbox policy`).
- S2: `mcp add withsandbox ... --sandbox` succeeded and persisted the
  baseline (`no-core-dumps, process-group, no-new-privileges, ptrace-denied`);
  `mcp test withsandbox` activated it through the sandboxed spawn path and
  listed the `fake_echo` tool.
- S3 (live enforcement): both startup-activated children run with
  `NoNewPrivs=1` and an active seccomp filter as the tenant uid.
- S4: flipping `require_sandbox_profiles` to `false` (DB edit) let an
  unsandboxed `mcp add legacy ...` succeed — legacy opt-in default preserved;
  flag restored to `true` afterwards.
- `lunarwing doctor` renders the policy per server
  (`sandbox: memory<=512MiB, fds<=256, processes<=64, no-core-dumps,
  process-group, no-new-privileges, ptrace-denied`).

### Persistent external-worker placement

- Seeded `fake-worker` (`placement: external_worker`, `external_worker:
  opencode`) loads and lists correctly; startup activated 2 of 3 servers —
  the external-worker server is never spawned in the daemon
  (`pgrep fake-mcp-server` shows only the two host servers).
- Validation matrix (scratch `--no-db` configs): placement without a worker
  name, worker name with host placement, and worker placement with a host
  sandbox policy are each rejected with precise errors.
- `lunarwing doctor` cross-check: `fake-worker — external worker 'opencode'
  is not configured`. Observation (minor): doctor resolves configured workers
  from DB settings (`sandbox.external_workers`, empty here) while the daemon
  logs `External workers configured: pebble, opencode` from env-derived
  config, so doctor can false-positive on env-only worker definitions.
- Worker-protocol MCP delivery remains deferred by design (documented in
  MCP_ADDITIONS.md): the placement is config-validated and excluded from host
  activation and job snapshots, but nothing pushes it to a worker yet.

- Enabled purely by tenant env (`LUNARWING_MCP_GATEWAY_CONTROL_BIND=127.0.0.1:20014`,

  startup log: `MCP gateway control plane listening bind=127.0.0.1:20014`.

- G2: `PUT /admin/routes/echo` with a loopback-HTTP upstream and route bearer
  token succeeded; `GET /admin/routes` shows the route with
  `has_bearer_token: true` and never returns the token.
- G3: non-HTTPS non-loopback upstream rejected 400
  (`upstreams must use HTTPS (loopback HTTP allowed)`).
- G4 data plane: missing `X-LunarWing-MCP-Route` → 400; unknown route → 404;
  a proxied POST reached the echo upstream with **both routing headers
  stripped**, the spoofed client `Authorization: Bearer attacker-token`
  dropped and replaced by the route's bearer token, and a custom client
  header removed (3-header allowlist); body forwarded intact.
- G5: a full MCP `initialize` POST through `/mcp` returned the upstream's
  real MCP result (`serverInfo: echo-upstream`).
- G6: `DELETE /admin/routes/echo` → 200; the on-disk route table
  (`gateway-routes.json`) updated atomically.
