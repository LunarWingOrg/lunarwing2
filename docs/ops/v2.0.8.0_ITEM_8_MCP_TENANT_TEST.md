## Method

- Tenant provisioned with
  `sudo ic/scripts/lunarwing-mt-admin.sh add-tenant mcp8 --no-health --no-ssh --no-weechat-bootstrap`
  (port block 10030-10039, extended 20030-20039; no workers, no DarkIRC) —
  the **refactored** mt-admin (composition root + sourced modules).
- Release build via `mt-admin build-tenant mcp8` (tmux session `mcp8build`,
  log `/tmp/mcp8-build.log`); tenant clone tracks this branch at `9bbd96eb`.
- Fixtures (test scaffolding, kept out of the repo under `/tmp/mcp8-fixtures`):
  - `fake_mcp_server.rs` — dependency-free MCP 2024-11-05 stdio server
    (initialize / ping / tools.list / tools.call), built with plain
    `rustc -O` so it is a native Linux executable (pinning requires native
    bytes). Logs each spawn (argv + `LUNARWING_MCP_EXTERNAL_OPTIONS`) to
    `FAKE_MCP_LOG`.
  - `gen_fixtures.py` — ed25519 fixture generator (Python `cryptography`)
    replicating the exact signing contract of `ic/src/tools/mcp/marketplace.rs`:
    canonical payload = compact serde_json of the struct in declaration order,
    signature = ed25519 over those bytes, lowercase hex. The daemon accepting
    these lists is itself the cross-implementation interop proof.
  - `revocation_server.py` — loopback HTTP distribution point on 20033
    (localhost HTTP is explicitly allowed for test harnesses by
    `MarketplaceConfig`).
  - `echo_upstream.py` — loopback HTTP upstream on 20035 that echoes received
    headers (verifies gateway routing-header stripping / auth handling) and
    answers MCP `initialize` (serverInfo `echo-upstream`).
- Tenant-side ports (from the mcp8 extended block 20030-20039, slots unused by
  real services): 20033 revocation HTTP, 20034 gateway control plane, 20035
  echo upstream.
- The complete `mcp-servers.json` (including the file-level `marketplace`,
  `external_runtimes`, and `require_sandbox_profiles` sections, which have no
  CLI surface) is seeded at `/home/mcp8/lunarwing/mcp-servers.json` before
  first daemon start so the one-shot disk-to-DB migration imports it for
  owner `mcp8`. Gateway env (`LUNARWING_MCP_GATEWAY_CONTROL_BIND=127.0.0.1:20034`,
  admin token, routes path) appended to the tenant `lunarwing.env`.

  expected value`); corrupting the trust store likewise (`trust store ...
  invalid JSON`). Restoring both files restores normal operation.

### FINDING 1 (reproduced, still open — documented follow-up) — revocation recovery trap

Reproduced identically on this branch:

1. Once the cached list revokes an *enabled* server, the next restart's
   startup load runs against that cache and fails closed:
   `MCP server configuration is invalid: marketplace: server 'fake': ...
   is revoked ... Fix or remove the corrupted config` — the daemon starts
   with zero MCP servers and **never fetches a newer (remedying) list**:
   the marketplace cannot heal the tenant by publishing an un-revoke list.
2. All CLI remediation paths (`mcp toggle --disable`, `mcp remove`) fail
   closed too — both verified live on the tenant. Only direct DB surgery
   (or handing the tenant a newer cache file out-of-band) recovers.
3. Collateral: in the restart where seq 2 was fetched, the healthy
   `fake-external` server was activated successfully but then **rejected and
   torn down** at injection (`Rejected MCP startup injection without current
   host placement server=fake-external`) because `inject_mcp_client`'s
   re-read of the config fails closed on the revoked sibling. The warn
   message is misleading (placement was correct).

Recommendation (unchanged from the prior run's follow-up): load-time
revocation checks should not invalidate the whole config — e.g. validate only
at activation/persist time, or demote revoked enabled servers to
skipped-with-warning at load so refresh and CLI remediation keep working.

### FINDING 2 (fixed on the prior branch, re-applied here, now verified live)

Prior run: `mcp add nosandbox --transport stdio ...` (no `--sandbox`) under
`require_sandbox_profiles = true` succeeded and persisted because
`mutate_mcp_servers_db` skipped whole-file validation, poisoning every
subsequent load. Fix: `servers.validate()` before the CAS write +
libsql-backed regression test (re-applied on this branch as `9bbd96eb`).
This run verifies the fixed behavior live: the unsandboxed add is rejected
up front (`Server 'nosandbox': require_sandbox_profiles is set ...`), the
stored config is not poisoned, and subsequent CLI commands work normally.
