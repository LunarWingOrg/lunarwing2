### F1 (HIGH) — Retry re-fire leaks an internal `retry_attempt` key into model prompts and persisted trigger payloads

`refire_mission_thread` (`ic/crates/lunarwing_engine/src/runtime/mission.rs:2275-2291`)
injects `retry_attempt` **into the trigger payload map** before calling
`fire_mission_inner`:

```rust
let mut payload = payload.map(|mut p| {
    if let serde_json::Value::Object(map) = &mut p {
        map.insert(RETRY_ATTEMPT_METADATA_KEY.to_string(), serde_json::json!(attempt));
    }
    p
});
```

This directly contradicts the constant's own doc comment at
`mission.rs:41-44` — "`retry_attempt` … Rides the thread's top-level
metadata (**not inside the trigger payload**) so prompts never see it and
channel producers' `content_hash`/`source_thread_id` keep their meaning."
Three concrete consequences:

1. **Prompt pollution.** `build_meta_prompt` (`mission.rs:~2678`) renders
   the whole payload into a `## Trigger Payload` JSON block in the mission
   meta-prompt, and `fire_mission_inner` seeds the same payload into the
   thread's initial orchestrator state as `state["trigger_payload"]`
   (`mission.rs:193-196` region). Every retried thread's model prompt now
   contains a foreign `retry_attempt` integer that no producer ever sent.
2. **Payload/dedup contamination risk.** `trigger_dedup_key` today only
   reads `source_thread_id`/`content_hash`, so the dedup key itself is
   unchanged. But the *persisted* `mission.last_trigger_payload` now carries
   the injected key, so any consumer that hashes or compares whole payloads
   (redelivery checks, debugging, future dedup extensions) sees a mutated
   payload. The doc comment explicitly promises the key set
   (`content_hash`/`source_thread_id`) keeps its meaning — the injection
   violates that stated invariant.
3. **Self-defeating redundancy.** After spawning, the code *also* persists
   the attempt marker onto the thread's top-level metadata via
   `persist_retry_attempt_marker` (`mission.rs:2240-2262`), which is the
   correct mechanism `current_attempt` reads. The payload injection is
   duplicate, un-read plumbing — nothing reads `retry_attempt` out of the
   payload (grep confirms the only readers are the metadata path). Safe to
   delete outright.

**Fix:** drop the payload mutation; rely solely on
`persist_retry_attempt_marker` (already called after spawn in the same
function).

### F2 (HIGH) — Non-Completed outcomes blanket-release the trigger dedup key, including `GatePaused`

`process_mission_outcome_and_notify` (`mission.rs:2930-2950`) releases the
dedup key for **every** non-`Completed` outcome:

```rust
if !matches!(outcome, ThreadOutcome::Completed { .. })
    && let Some(key) = mission.last_trigger_payload.as_ref().and_then(trigger_dedup_key)
    ...
```

`ThreadOutcome` has five variants; the match above arms `Stopped` and
`Failed`, `MaxIterations` is deliberately excluded from retry, and
`GatePaused` is a *normal, recoverable* pause (approval pending). A
`GatePaused` fire that ends the thread's first run therefore has its dedup
key released while the thread waits for human approval. An external
redelivery of the same event/webhook during the approval window then spawns
a **second** thread for the same logical event — duplicate side effects, the
exact thing the dedup set exists to prevent (work item #69). The retry
scheduling for `GatePaused` is not the issue (it schedules none); the
*dedup release* is. This appears to be an unmodelled interaction: the
tri-state work modeled `Stopped`/`Failed`/join-lost but the release
condition was written against `!Completed` rather than the retried-outcome
set.

**Fix:** release the key only for outcomes that actually schedule a retry
(`pending_retry.is_some()`), or at minimum exclude `GatePaused` (and
arguably `MaxIterations`, which is a deliberate terminal state).

Related, smaller: the release is derived from `mission.last_trigger_payload`
— if a *different* mission fire happened between the failing fire and the
outcome write, the released key belongs to the newer payload, not the failed
fire. The lock ordering (outcome taken under the mission fire-lock) mostly
protects this, but the key is inferred, not carried by the outcome.

### F3 (MEDIUM) — Restart retry sweep only finds missions in the in-memory `active` set; ordering couples it to bootstrap

`recover_pending_mission_retries` (`mission.rs:2330-2379`) iterates
`self.active` — populated by `bootstrap_project` / `bootstrap_all_projects`
/ `ensure_learning_missions`. In `router.rs:1752-1766` those calls all run
**before** the sweep, so today the wiring is correct, but:

- a mission that failed to load during bootstrap (store error path
  `continue`s with only a `warn!`) is silently skipped — its pending retry
  marker stays on the thread forever, and the fire is lost with only a
  warn-level log;
- the correctness depends on call order in one init function; nothing in
  the type system or the function docs at the call site pins the ordering
  contract ("bootstrap first, sweep second").

Minor related gap: the sweep `break`s after the first marker per mission
("newest fire wins"), but it iterates `thread_history.iter().rev()` and
clears markers as it goes — an older thread's marker that precedes a
non-marker thread in history is simply never visited (fine), while an older
marker *after* a newer non-terminal thread in the reversed walk is cleared
before the break (also fine). Behavior is correct but subtle; a comment
exists, complexity is at the limit.

**Fix:** iterate `list_all_active_missions_global()` (already exists,
`mission.rs:434`) instead of the in-memory set, removing the ordering
coupling and the bootstrap-failure hole.

### F5 (MEDIUM) — Tautological assertions in the WI#215 regression test

`masks_protected_dir_created_after_planning` (`ic/src/sandbox/mount_guard.rs:554-600`)
ends with:

```rust
assert!(sibling.starts_with(&run_dir) && covered.starts_with(&destination), ...);
```

`sibling` is constructed as `run_dir.join(created)` and `covered` as
`Path::new(&destination).join(created)` two lines earlier — both
`starts_with` checks are true **by construction**, regardless of any
production code. The test's meaningful assertions (validate accepts tenant
root, absent `run/` planned for masking, mask destination is
`/workspace/run`) all pass before this block; the final loop adds coverage
theater, not a regression net. If the mask destination logic ever regressed,
the earlier `assert_eq!(destination, "/workspace/run")` catches it; the
tautology only muddies what is actually pinned. The test also uses
`.expect()` in test code (fine) but writes into the repo workspace tree via
`Fixture::new()` — consistent with the file's other tests, so not a
separate finding.

**Fix:** replace the loop with an assertion that exercises the real
masking path (e.g. that `masked_dirs_for_mount` output maps `run_dir` →
`/workspace/run` via the actual `mask_destination` for a second created
file), or delete the loop.

### F10 (LOW) — Retry-policy tool params absent from the `mission_update` router schema

`initial_delay_secs`, `backoff_multiplier`, `max_delay_secs` from

overstates the surface.

### F11 (INFO) — `RetryState::to_value` silently degrades to empty object on serialize failure

`ic/crates/lunarwing_engine/src/types/mission.rs:315-318`: on a serialization
error the marker becomes `{}` — an empty marker that the restart sweep's
`RetryState::from_metadata` will then fail to parse and skip. Given the
struct is plain JSON data, serialization can't realistically fail, and the
fallback is unwrapped-safe, so this is acceptable; noted only because
"silent empty marker" is a confusing failure mode if fields ever gain
non-serializable types. `unwrap_or` matches repo error-handling rules.

### F12 (INFO) — Budget interaction is intentional but sharp: retries draw from the daily thread budget

Default policy (`max_retries: 3`) plus default budget
(`DEFAULT_MAX_THREADS_PER_DAY: 30`) means a flapping hourly mission can
consume up to 4 slots per fire window before the day is spent. The type docs
(`types/mission.rs` `MissionRetryPolicy`) call this out deliberately, so it
is a documented design choice, not a bug. Flagging for release-notes
visibility: operators upgrading missions get retry-on-by-default with no
migration notice in the range (ENGINE-V2.md documents it, the goals file
records it, but there is no ops-facing "behavior change" callout in
`docs/ops/` for existing tenants).
