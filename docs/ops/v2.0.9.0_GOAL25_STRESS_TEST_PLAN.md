# v2.0.9.0 — Goal 25: Comprehensive Stress Test Plan (Gentoo/OpenRC)

Status: plan written 2026-08-26, execution results recorded in
`v2.0.9.0_GOAL25_STRESS_TEST_FINDINGS.md`.

Companion to item #25 of `AGENT_GOALS_2.0.9.0.md`. Item #26 is the same
exercise on the Arch host; this document is the Gentoo (OpenRC) run.

## Objective

Prove that a freshly provisioned multi-tenant LunarWing instance survives
realistic and abusive load across every user-visible surface — web gateway
chat, tool loop, memory subsystem, and the WeeChat relay channel — without
message loss, data corruption, hangs, or resource exhaustion. All findings
are recorded in the findings doc; the tenant is destroyed at the end.

## Environment

- Host: this Gentoo/OpenRC dev machine (18 threads usable, cgroup v2
  pre-delegated subtrees, podman for tenant containers).
- Tenant: `stress25`, created via `ic/scripts/lunarwing-mt-admin.sh
  add-tenant` from this working branch
  (`rarity/kimi-25-20260826-1801`), release build with all WASM extensions
  (`build-tenant stress25 --with-wasm`).
- LLM: same LAN TensorZero upstream as tenant `camel`
  (`LLM_BASE_URL=http://192.168.1.157:3000/openai/v1`,
  `LLM_MODEL=tensorzero::function_name::FrontierTEED`). If the upstream is
  unreachable at execution time, LLM-dependent phases degrade to
  transport-only assertions and the degradation is recorded as a finding.
- Init: OpenRC units rendered by mt-admin (`lunarwing-stress25`,
  weechat relay + ws-adapter units, postgresql container).
- Existing tenants (antelope, barracuda, camel) keep running — the test
  must not disturb them, and their presence makes the port/registry and
  cgroup isolation realistic.

## Seed data ("real data" requirement)

Seeded through the authenticated web gateway memory API
(`/api/memory/write`, bearer token from `mt-admin tokens stress25`):

- `SOUL.md` — non-trivial persona definition (~2 KB prose).
- `AGENTS.md` — house rules doc the agent must follow.
- `context/profile.json` — valid `PsychographicProfile`-shaped JSON written
  with `append: false` (per the item-14 guidance).
- `memory/people/*.md`, `memory/projects/*.md` — ~20 topical notes.
- `daily/2026-08-26.md` — a daily log with several entries.
- `memory/stress/ledger.md` — the integrity ledger used by the write/read
  verification phases (known content, appended to under concurrency).

## Phases

Each phase records: request count, success/failure counts, latency
(min/avg/max), observed errors, and pass/fail against the criteria.

### P0 — Provision, seed, baseline

1. `add-tenant stress25` (+ LLM overrides), `build-tenant --with-wasm`,
   `start-tenant stress25`.
2. Wait for `/api/health` 200 and `mt-admin status stress25` all-green
   (OpenRC `started` shape).
3. Seed all data above; read back every document and byte-compare.
4. PASS: tenant healthy, all seeds verified.

### P1 — Memory API stress (no LLM)

Direct gateway API, bearer auth, concurrency via parallel `curl` workers:

- W1: 200 sequential `memory_write` to distinct paths → 200 reads,
  byte-compare each. PASS: 0 mismatches.
- W2: 50 concurrent writers (`xargs -P10`) to distinct paths, then read-all
  compare. PASS: 0 mismatches, no 5xx.
- W3: 40 concurrent appends to the single shared ledger path
  (`append: true`). PASS: final doc contains all 40 unique markers
  (order-free), no interleaved corruption (each marker line intact).
- W4: 200 `memory_search` queries mixed with 100 writes concurrently.
  PASS: no 5xx, search latency p95 sane, writes intact afterwards.
- W5: large-document write (500 KB markdown) → read-back compare; then
  1.5 MB write → expect a clean, documented rejection (413/4xx), not a
  500 or silent truncation.
- W6: `memory_tree` + `memory_list` under concurrent write load.
  PASS: consistent shape, no 5xx.

### P2 — Chat + tool-loop stress (LLM)

Via `POST /api/chat/send` (fresh thread per worker):

- C1: 10 sequential turns of prompts that force multiple tool calls in one
  turn ("write X to memory/stress/c1.md, read SOUL.md, search memory for
  Y, then summarize"). PASS: every turn completes, expected tool calls
  appear in the response events/history.
- C2: 8 concurrent chat sessions × 3 turns each, same multi-tool prompt
  shape. PASS: all 24 turns complete, no cross-session bleed (each answer
  references its own session token embedded in the prompt).
- C3: rapid-fire same-thread: 10 sends back-to-back on one thread without
  waiting. PASS: documented behavior (queue or clean 409/busy), no daemon
  wedge, thread history coherent afterwards.
- C4: memory consistency after chat: read the paths the agent wrote in
  C1/C2 and byte-compare against instructed content. PASS: 0 corruption.
- If LLM upstream is down: record as BLOCKED-EXTERNAL and substitute
  transport-only checks (auth, 4xx/5xx shape, event stream liveness).

### P3 — WeeChat channel stress

The tenant's WeeChat relay + ws-adapter (auto-bootstrapped by add-tenant)
is the channel under test. Drive it through the adapter's HTTP input API
on its registry port (`WS_ADPT` column, `/api/input`), which injects lines
into the relay buffer exactly as a WeeChat user would:

- H1: relay/adapter healthy: adapter `/api/health` 200, relay port
  listening, buffer visible.
- H2: 20 sequential channel messages with unique markers. PASS: agent
  reply for each lands back in the relay buffer (polled via adapter),
  markers all present, ordering preserved.
- H3: burst 50 messages as fast as the adapter accepts them.
  PASS: no 5xx from adapter, no lost accepted messages (adapter outbox +
  relay buffer account for all 50), agent remains responsive afterwards.
- H4: adapter restart mid-burst (`restart-weechat-adapter stress25` while
  H3-style traffic flows). PASS: accepted-before-restart messages are not
  silently dropped (outbox/reconnect behavior per item #1: 202-queued or
  delivered), adapter recovers, subsequent messages flow.
- H5: channel ↔ memory: ask the agent over WeeChat to write a marker to
  memory, verify via gateway API. PASS: marker present and correct.

### P4 — Mixed soak

15 minutes: loop of (memory write + read + search) + (1 chat turn every
30 s) + (1 weechat message every 20 s), from parallel workers.
PASS: no crash, no unit restart flapping (`mt-admin status` stable), no
runaway error rate (< 1% failures, all explained), memory docs intact at
the end.

### P5 — Restart resilience

`restart-tenant stress25` immediately after the soak, then:
PASS: all seeded + stress-written documents byte-identical, chat history
intact, weechat channel reconnects, `/api/health` 200 within 2 minutes.

### P6 — Resource observation

Sampled during P4/P5 from the tenant's OpenRC cgroup subtree and
`ps`/`/proc`: daemon RSS, task/thread count, open FD count, postgres
container RSS. PASS: RSS within the unit's MemoryMax with headroom, no
monotonic FD leak across the soak (end ≈ start + small delta).

## Isolation & safety

- Tenant gets its own auto-allocated port block; no hand-picked ports.
- All traffic targets the tenant's own ports only; other tenants are
  untouched and serve as isolation witnesses (their health is checked
  before and after).
- No changes to daemon code; this is black-box plus API-level testing.

## Cleanup (mandatory)

1. `stop-tenant stress25` → `remove-tenant stress25 --purge`
   (stops services, deallocates ports, deletes OS user + home + PG
   container/volume).
2. Verify: tenant absent from `list-tenants`, no `stress25` user, no
   leftover ports in `/etc/lunarwing/ports.json`, other tenants still
   healthy.
3. Findings doc committed; item #25 checked off in the goals file.
