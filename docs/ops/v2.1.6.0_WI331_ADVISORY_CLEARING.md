## 1. libsql legacy chain → mitigation: `libsql-remote-replica` feature gate

### Clearing options considered

- **Upstream libsql bump — rejected (clears nothing today).** Re-verified
  2026-10-10 via the crates.io API: libsql 0.9.30 (latest stable) and
  0.10.0-pre.4 (latest prerelease) both still request `hyper-rustls ^0.25`
  (optional, behind their `tls` feature) and `hyper ^0.14`. Even a major
  bump would keep the rustls 0.22 / webpki 0.102 chain. Clearing via bump
  requires an upstream libsql release adopting rustls 0.23 /
  hyper-rustls 0.27+.
- **Driver migration — rejected (disproportionate).** PostgreSQL is the
  primary backend; replacing the libSQL driver is a dedicated project, not
  an advisory-hygiene edit.
- **Mitigation: feature-gate remote replicas — ADOPTED.** libsql 0.6.0
  already isolates the vulnerable chain behind its `remote`, `replication`,
  and `tls` features (`tls = dep:hyper-rustls`; `replication → tonic 0.11 →
  h2 0.3.27`). LunarWing's local/embedded libSQL usage only needs `core`.

### What changed

- `ic/Cargo.toml`: the `libsql` dependency now enables only
  `features = ["core"]`. A new non-default cargo feature
  **`libsql-remote-replica`** = `libsql/remote + libsql/replication +
  libsql/tls` restores Turso cloud sync for builds that explicitly want it.
- `ic/src/db/libsql/mod.rs`: `LibSqlBackend::new_remote_replica` is
  `#[cfg(feature = "libsql-remote-replica")]`. New `from_config_parts`
  helper centralizes the local/remote branch; without the feature,
  `LIBSQL_URL` set → clear startup error instead of silently local-only.
  Fail-closed unit tests pin all three config combinations (MR !1513
  review CZ-3).
- `ic/src/db/mod.rs`: all three connect paths
  (`connect_with_handles`, `create_secrets_store`,
  `connect_without_migrations`) route through `from_config_parts`.
- `ic/src/setup/wizard.rs`: the Turso prompt and menu mention only appear
  with the feature; a configured Turso URL in a feature-less build fails
  the connection test with a clear message that also warns against the
  divergent-local-file fallback (CZ-4), and is pinned by fail-closed
  wizard tests (CZ-3). The !1529 follow-up closes the remaining CZ-8 gap:
  its connection test now delegates to `from_config_parts`, so URL alone
  fails for the missing token instead of silently opening a local database.
  URL-without-token and local-only tests are enabled with and without the
  remote-replica feature; the feature-off refusal also checks that no local
  replica file was created.
- `ic/src/cli/status.rs` / `ic/src/cli/doctor.rs`: both are feature-aware
  — `LIBSQL_URL` set without the feature reports "configured but not
  compiled in" (status) / a failed check (doctor) instead of healthy
  output (CZ-5).
- `ic/src/setup/README.md`, `ic/src/db/CLAUDE.md`: feature gate and
  `from_config_parts` routing documented (CZ-9).
- `.gitlab/scripts/check-default-graph-advisories.sh` + CI job
  `default-graph-advisory-guard` + `.gitlab/tests/test_default_graph_guard.py`:
  the default-feature production graph is pinned free of
  rustls-webpki 0.102.8 / h2 0.3.27 at both build roots, closing the
  "every gate stays green while the mitigation regresses" hole (CZ-1).
  The !1529 follow-up runs each query from its own root with `--locked`,
  honoring `ic/.cargo/config.toml` and its vendor directory for crates.io.
  Git sources (monty/ruff) are not vendor-replaced: `--offline` was removed
  after review #7583 / CI job 103876 so cold caches can fetch pinned revisions.
  Only a successful forward dependency graph proves absence: resolution
  errors fail with their diagnostics, even if they contain an old
  "nothing to print" absence marker. Both roots and exact versions are
  covered by the script regressions.
- `ic/bridges/xmpp-bridge/Cargo.lock`: re-resolved offline against the
  merged manifests (not hand-merged, CZ-7) — 931 → 895 packages; the
  legacy chain (rustls-webpki 0.102.8, h2 0.3.27, rustls 0.22.4,
  hyper-rustls 0.25, tonic 0.11) is gone because the bridge builds
  lunarwing with default features. `ic/Cargo.lock` keeps the chain
  because a workspace lock resolves over all member features.

### Upgrade note (breaking change, for the item-40 release-notes draft)

Installs configured for Turso sync (`LIBSQL_URL` + `LIBSQL_AUTH_TOKEN`
set) **will not start** on default v2.1.6.0 builds: the daemon now fails
closed at startup with an error naming the `libsql-remote-replica` cargo
feature, and `lunarwing doctor` reports the same. To keep Turso sync,
rebuild with `--features libsql-remote-replica` (and accept the pinned
rustls-webpki 0.102 / h2 0.3 exposure documented above). Do **not** simply
unset `LIBSQL_URL`: the existing replica file then becomes a diverging
standalone database whose writes never reach the Turso primary — the
wizard now warns about this explicitly. Impact today is small: no shipped
tooling writes `LIBSQL_URL`, the wizard never persisted the token, and
every shipped build path (mt-admin `05-tenant-build.sh`,
`scripts/build-lunarwing.sh`, `ic/Dockerfile`, `Dockerfile.worker`) uses
default features, so shipped binaries fail loudly rather than silently
diverging. mt-admin currently exposes no opt-in feature knob; one can be
added to `05-tenant-build.sh` when a tenant actually needs Turso sync.


### Resulting exposure

- **Default builds** (`postgres + libsql + html-to-markdown`) and
  postgres-only builds **no longer compile** rustls-webpki 0.102.8 or
  h2 0.3.27 at all. Verified 2026-10-10:
  `cargo tree -i rustls-webpki@0.102.8` / `cargo tree -i h2@0.3.27`
  (default features) → "did not match any packages".
- **Opt-in builds** (`--features libsql-remote-replica`) still compile the
  chain, so the exposure narrows to: builds that explicitly enable Turso
  sync AND configure `LIBSQL_URL`. The X.509-validation bypasses
  (RUSTSEC-2026-0098/0099) then apply to TLS between LunarWing and the
  third-party database host, as before.
- `--workspace --all-features` (CI's compiled and cargo-deny graph)
  includes the opt-in feature, so the chain remains visible there and the
  `ic/deny.toml` ignores stay required.

## 2. rsa (RUSTSEC-2023-0071) → keep accepted, track upstream (WI#368)

Re-verified 2026-10-10 against the RustSec advisory DB and crates.io:

- The advisory still lists `patched = []` ("Still affected as of
  2026-09-12: rsa 0.9.10 and rsa 0.10.0-rc.18"). Mitigation work remains
  in-flight upstream (implicit rejection RustCrypto/RSA#680, default-path
  blinding RustCrypto/RSA#702).
- rsa **0.10.0-rc.19** is now the newest published release (max stable
  0.9.10) but is **not** marked patched by the advisory.
- russh **0.64.1** (latest; we pin 0.62.7) still requests `rsa
  =0.10.0-rc.18` exactly as an optional dep — bumping russh would not
  clear the advisory, so no bump was done as part of this item.

Clearing remains conditional on an upstream constant-time rsa release or a
LunarWing policy change (reject RSA keys at ssh-tool ingestion / drop the
russh `rsa` feature). That ongoing tracking — including the corrected
tenant-SSH-agent exposure recorded in `ic/deny.toml` (auto-confirming
`0o666` agent socket mounted into untrusted worker containers, unblinded
signing) — is owned by **WI#368**, filed with this item so the acceptance
keeps an open owner after WI#331 closes.

## 3. failure / rental (vendored libsignal-protocol) → keep accepted; port owned by WI#367

- `failure 0.1.8` is the final release (EOL). The vendored
  `libsignal-protocol` wrapper uses failure/failure_derive throughout the
  crate (≈40 call sites across ≈20 `.rs` files) — porting it off is a
  dedicated refactor, not an advisory-hygiene edit. Filed as **WI#367**
  with this item (covers `rental` too), so the acceptance keeps an open
  owner after WI#331 closes.
- Exposure unchanged: compiled into every feature set via the XMPP OMEMO
  implementation (`ic/src/channels/xmpp/omemo/`). `rental` remains
  informational-only and visible only in the `--workspace --all-features`
  graph.

## Release re-verification protocol (standing, from WI#331 ask 3)

At every release, for each `ic/deny.toml` `ignore` entry:

1. Re-check the upstream state (crates.io max versions; the advisory's
   `patched` field in the RustSec DB).
2. Refresh the `(re-verified YYYY-MM-DD)` marker and any version numbers in
   the entry's comment block and `reason` string.
3. Keep the WI#331 reference until the entry is removed; remove an entry
   only when its clearing upgrade has landed in Cargo.lock AND the
   lockfile root has been re-checked with `--config` overrides so the
   advisory resurfaces as a hard error if it regresses.
