## 1. libsql legacy chain → mitigation: `libsql-remote-replica` feature gate

### Clearing options considered

- **Upstream libsql bump — rejected (clears nothing today).** Re-verified
  2026-10-10 via the crates.io API: libsql 0.9.30 (latest stable) and
  0.10.0-pre.4 (latest prerelease) both still request `hyper-rustls ^0.25`
  (optional, behind their `tls` feature) and `hyper ^0.14`. Even a major
  bump would keep the rustls 0.22 / webpki 0.102 chain. Clearing via bump
  requires an upstream libsql release adopting rustls 0.23 /
  hyper-rustls 0.27+.
- **Driver migration — rejected (disproportionate).** PostgreSQL is the
  primary backend; replacing the libSQL driver is a dedicated project, not
  an advisory-hygiene edit.
- **Mitigation: feature-gate remote replicas — ADOPTED.** libsql 0.6.0
  already isolates the vulnerable chain behind its `remote`, `replication`,
  and `tls` features (`tls = dep:hyper-rustls`; `replication → tonic 0.11 →
  h2 0.3.27`). LunarWing's local/embedded libSQL usage only needs `core`.

### What changed

- `ic/Cargo.toml`: the `libsql` dependency now enables only
  `features = ["core"]`. A new non-default cargo feature
  **`libsql-remote-replica`** = `libsql/remote + libsql/replication +
  libsql/tls` restores Turso cloud sync for builds that explicitly want it.
- `ic/src/db/libsql/mod.rs`: `LibSqlBackend::new_remote_replica` is
  `#[cfg(feature = "libsql-remote-replica")]`. New `from_config_parts`
  helper centralizes the local/remote branch; without the feature,
  `LIBSQL_URL` set → clear startup error instead of silently local-only.
- `ic/src/db/mod.rs`: all three connect paths
  (`connect_with_handles`, `create_secrets_store`,
  `connect_without_migrations`) route through `from_config_parts`.
- `ic/src/setup/wizard.rs`: the Turso prompt and menu mention only appear
  with the feature; a configured Turso URL in a feature-less build fails
  the connection test with a clear message.
- `ic/src/setup/README.md`: `LIBSQL_URL` documented as feature-gated.

### Resulting exposure

- **Default builds** (`postgres + libsql + html-to-markdown`) and
  postgres-only builds **no longer compile** rustls-webpki 0.102.8 or
  h2 0.3.27 at all. Verified 2026-10-10:
  `cargo tree -i rustls-webpki@0.102.8` / `cargo tree -i h2@0.3.27`
  (default features) → "did not match any packages".
- **Opt-in builds** (`--features libsql-remote-replica`) still compile the
  chain, so the exposure narrows to: builds that explicitly enable Turso
  sync AND configure `LIBSQL_URL`. The X.509-validation bypasses
  (RUSTSEC-2026-0098/0099) then apply to TLS between LunarWing and the
  third-party database host, as before.
- `--workspace --all-features` (CI's compiled and cargo-deny graph)
  includes the opt-in feature, so the chain remains visible there and the
  `ic/deny.toml` ignores stay required.

## 2. rsa (RUSTSEC-2023-0071) → keep accepted, track upstream

Re-verified 2026-10-10 against the RustSec advisory DB and crates.io:

- The advisory still lists `patched = []` ("Still affected as of
  2026-09-12: rsa 0.9.10 and rsa 0.10.0-rc.18"). Mitigation work remains
  in-flight upstream (implicit rejection RustCrypto/RSA#680, default-path
  blinding RustCrypto/RSA#702).
- rsa **0.10.0-rc.19** is now the newest published release (max stable
  0.9.10) but is **not** marked patched by the advisory.
- russh **0.64.1** (latest; we pin 0.62.7) still requests `rsa
  =0.10.0-rc.18` exactly as an optional dep — bumping russh would not
  clear the advisory, so no bump was done as part of this item.

Clearing remains conditional on an upstream constant-time rsa release or a
LunarWing policy change (reject RSA keys at ssh-tool ingestion / drop the
russh `rsa` feature). Exposure unchanged: every feature set, exercised only
when the ssh tool authenticates with RSA keys; Ed25519/ECDSA never reach
the vulnerable path.

## 3. failure / rental (vendored libsignal-protocol) → keep accepted; port is follow-up work

- `failure 0.1.8` is the final release (EOL). The vendored
  `libsignal-protocol` wrapper uses failure/failure_derive in 52 places
  across 23 files — porting it off is a dedicated refactor, not an
  advisory-hygiene edit. Recommended: file a dedicated work item for the
  port (covers `rental` too) at release planning.
- Exposure unchanged: compiled into every feature set via the XMPP OMEMO
  implementation (`ic/src/channels/xmpp/omemo/`). `rental` remains
  informational-only and visible only in the `--workspace --all-features`
  graph.

## Release re-verification protocol (standing, from WI#331 ask 3)

At every release, for each `ic/deny.toml` `ignore` entry:

1. Re-check the upstream state (crates.io max versions; the advisory's
   `patched` field in the RustSec DB).
2. Refresh the `(re-verified YYYY-MM-DD)` marker and any version numbers in
   the entry's comment block and `reason` string.
3. Keep the WI#331 reference until the entry is removed; remove an entry
   only when its clearing upgrade has landed in Cargo.lock AND the
   lockfile root has been re-checked with `--config` overrides so the
   advisory resurfaces as a hard error if it regresses.
