# Goal 13 — GitLab WASM “Always allow” audit

## Root cause

The GitLab extension is registered as `gitlab-tool`, while model-facing calls
may use `gitlab_tool`. Both spellings resolve to the same tool in
`ToolRegistry::resolve_name`, but permission storage previously used the
spelling at each call site:

- Legacy chat read/wrote `tool_permissions.<tool-call-name>` in
  `agent/thread_ops.rs`.
- Engine V2 checked `tool_permissions.<resolved-name>` in
  `bridge/effect_adapter.rs`, and only tried the hyphenated alternate when
  starting with the underscore spelling.
- Engine V2's approval resolution wrote `tool_permissions.<action-name>` in
  `bridge/router.rs`.

Thus an explicit grant for `gitlab_tool` could be invisible to a later
`gitlab-tool` call, especially when crossing execution paths. The older
hyphenated grant could likewise be invisible to legacy chat's underscore
spelling. This is independent of the earlier fixes for the sidecar policy
(`unless_auto_approved`, v2.0.4), GitLab API errors during approval resolution
(v2.0.8), and repeated pagination requests (v2.0.7).

## Fix and scope

Both engines now prefer `tool_permissions.gitlab_tool` for either spelling.
If the canonical row is absent, they read the previous hyphenated row for
compatibility. An explicit canonical `ask_each_time` or `disabled` row wins
over a stale legacy grant. New explicit grants are written under the
canonical key. Legacy chat's in-memory session cache uses the same name when
no settings store is configured. Other extensions are not normalized by the chat path: two
distinct installed tools can differ only by hyphen/underscore, so broad grant
sharing would be unsafe. In particular, old `gitlab` grants are not promoted
to `gitlab_tool`. If **both** `gitlab_tool` and `gitlab-tool` are independently
registered, neither receives an automatic grant: exact name resolution treats
them as separate tools, so sharing a stored grant would cross an authority
boundary.

For a user with a historical `tool_permissions.gitlab-tool` row, deleting a
canonical row alone is not sufficient to revoke the *historical* grant: clear
both spellings, or set `tool_permissions.gitlab_tool` to `ask_each_time` or
`disabled` (which takes precedence). Existing consumers of these settings
should use the canonical name when changing a GitLab tool permission.
Rolling back to a build that only reads the hyphenated key may require the
user to approve again; the new underscore grant is not recognized there.

This does not override approval policy: `ssh`-capable WASM tools still require
explicit approval, shared conversations continue to block approval-required
actions, and supervised threads gate each action even with a saved grant.
Authentication, credential availability, and runtime errors remain separate
from tool approval. Those cases can look like a repeated prompt, but are not
an “Always allow” permission decision.

## Verification

Regression tests cover legacy chat writing and reading both spellings (plus
session-only operation), Engine V2 reading either spelling of a persisted
legacy grant, canonical revocation taking precedence, and independent
registrations refusing grant sharing. The focused `gitlab_` run passes 7/7;
two existing approval regression tests pass; clippy `--lib --tests -- -D
warnings`, format, and diff-whitespace checks are clean.

Live-tenant acceptance for the installed GitLab WASM tool:

1. From a private conversation, invoke a read action (for example, current
   user) as `gitlab_tool`; choose **Always allow** at the approval gate.
2. Repeat a different GitLab action and confirm there is no approval gate.
   Exercise both the legacy chat and Engine V2 paths if both are enabled on
   that tenant; use `gitlab-tool` as a call spelling where supported.
3. Induce a GitLab API error (such as a nonexistent project) and confirm that
   the previously saved grant remains effective for subsequent calls. An
   authentication prompt is a *different* gate and is not a failure here.
4. Set the canonical permission to `ask_each_time` and confirm subsequent
   calls prompt again; confirm shared-room and supervised-thread policy still
   prevents silent execution.
