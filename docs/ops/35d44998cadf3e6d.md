# Ironclaw 1.0 / 1.1 Analysis — Ideas & Takeaways for LunarWing

**Researched:** 2026-08-07
**Source:** [nearai/ironclaw](https://github.com/nearai/ironclaw) CHANGELOG.md, releases page
**Context:** Christopher asked Baud to review Ironclaw's 1.0 and 1.1 releases for good ideas worth considering for LunarWing's roadmap.

---

## Overview

Ironclaw 1.0 ("Reborn") shipped 2026-07-27 as a **ground-up rewrite** — new agent runtime, storage, extension host, and WebUI. No migration path from 0.29.x; clean break. Ironclaw 1.1 shipped 2026-08-03 focused on extension reach and failure legibility.

These are fully independent codebases from LunarWing now. The only shared compatibility layer is WASM tool interfaces.

---

## Ideas Worth Stealing

### 1. Model Failure Recovery with Next-Steps (HIGH PRIORITY)

**What they did:** Every termination path — no progress, iteration limit, disabled capability, denied call, provider error — tells the model *what would unlock the call* instead of stopping opaquely. One-shot warning preserved across checkpoints, with one recovery turn allowed before the typed failure path kicks in.

**Why it matters for LunarWing:** Agents currently die on failures with opaque stops. Telling the model "you hit the iteration limit — try consolidating your tool calls" or "that capability is disabled — here's what you need enabled" turns dead ends into self-correction opportunities. Small change to the termination path, compounding improvement across every agent interaction.

**Fits with:** Self-heal philosophy, agent-loop resilience work
**Suggested target:** 2.0.7.0+

### 2. Memory as Extension with Declared Capabilities

**What they did:** Memory provider modeled as a userland extension with a host-managed lifecycle. Provider advertises what it can actually do (search, get, submit, list-stale, stats) via declared capabilities instead of being assumed uniform.

**Why it matters for LunarWing:** The study-notes knowledge layer (2.0.6.0) already moved toward this pattern with `knowledge_search`, `knowledge_get`, etc. as native MCP tools. Formalizing memory/knowledge as a capability-declaring extension would make it easier to swap providers, add new knowledge backends, and let agents reason about what memory operations are available.

**Fits with:** Knowledge Layer Phase 1 & 2 (2.0.6.0), MCP Phase 2
**Suggested target:** 2.0.8.0+ (after MCP Phase 2 stabilizes)

### 3. Durable Cross-Channel Attachments

**What they did:** A file sent on one channel stays retrievable from all other channels and the WebUI. Attachments are durable across the full channel surface.

**Why it matters for LunarWing:** Multi-channel agents (IRC, Telegram, Slack, XMPP) currently lose file context when conversations cross channels. A shared attachment store indexed by conversation/thread ID would let agents reference files regardless of which channel the user is on.

**Fits with:** Multi-tenant architecture, channel abstraction layer
**Suggested target:** 2.0.7.0+

### 4. BENCHMARKING_MODE

**What they did:** Opt-in system-prompt addendum for unattended evaluation runs. Adjusts agent behavior for automated benchmarking without manual prompt engineering.

**Why it matters for LunarWing:** With the family growing (Ruffles orchestrating, Rarity doing code review, AJ on builds), automated evaluation of agent quality across versions would be valuable. A benchmarking mode ensures consistent, comparable results without human-in-the-loop bias.

**Fits with:** QA pipeline, CI/CD testing
**Suggested target:** Whenever automated eval infrastructure becomes a priority

### 5. Sandbox Lane Scaffolding

**What they did:** `RuntimeKind::Sandbox` runtime lane with credential reuse, leaf-scoped mount containment, per-user sandbox identity primitives, and a credential placeholder registry. Ships unwired in 1.1 — Docker-connect retry, egress allowlist, and shell limits are all present but not connected.

**Why it matters for LunarWing:** MCP Phase 2 sandboxing (2.0.6.0 checklist item #9) is a more focused version of this. Ironclaw's per-user sandbox identity and credential placeholder registry patterns are worth reviewing for the MCP-over-WASM and worker-local placement work.

**Fits with:** MCP Phase 2 (sandboxing, runtime adapters, worker-local placement)
**Suggested target:** 2.0.6.0 (already in scope) — reference their patterns during implementation

## CAS-Protected Extension Lifecycle Patterns

**What they did:**
- Typed installation records with embedded, hash-pinned manifest definitions
- User-membership and credential-binding as separate child records
- Bounded CAS (compare-and-swap) updates for mutations
- CAS-protected mutation lease for membership and removal transitions
- `removed_at` soft-removal tombstones
- Legacy aggregate compatibility views (rows from previous releases keep deserializing)
- Restart repair

**Why it matters:** These are solid persistence patterns for any extension/tool lifecycle system. LunarWing's MCP provenance work touches similar territory. Worth referencing for robustness.

## Red Flags & Warnings

### CLI Regression
- `channels list`, `hooks list`, `logs` all return "not implemented yet"
- MCP, memory, pairing, import, and login CLI subcommands removed — only reachable through WebUI
- This is a clear philosophical shift away from CLI-first design
- **LunarWing contrast:** Christopher built a REPL server/client from scratch specifically because the Ironclaw CLI was awful. LunarWing should double down on CLI/REPL quality as a differentiator.

### No Migration Path
- Zero migration from 0.29.x. Completely fresh install required.
- Existing users lose all config, databases, settings, secrets.
- Aggressive for a 1.0 release. May alienate existing users.

### Performance Bugs in 1.0
- **libSQL prefix scan:** Descendant queries used `LIKE` instead of path-indexed range scans, causing full-table scans that grew with total DB size. Fixed in 1.1.
- **Extension list N+1:** `list_installations` issued 1 + 2N round trips (separate queries per installation for membership and credential-binding). Fixed in 1.1 with batch reads.

### WebUI Dependency
- Significant functionality is WebUI-only. Not suitable for headless/CLI/IRC agent deployments.
- LunarWing's multi-channel, agent-heavy, IRC-native operation model is fundamentally different.

## Summary Comparison

| Area | Ironclaw 1.0/1.1 | LunarWing 2.0.5+/2.0.6.0 |
|------|-------------------|--------------------------|
| CLI quality | Regressed (WebUI-only features) | REPL server/client built from scratch |
| Migration | No path (clean break) | Careful multi-version migrations, 30+ schema changes |
| MCP approach | Hosted marketplace, WebUI registration | Operator-pinned provenance, sandboxed, WASM transport |
| Memory | Extension with declared capabilities | Native knowledge layer + MCP tools (FTS-backed) |
| Channels | Slack + Telegram only | IRC, XMPP, DarkIRC, Weechat, custom WASM |
| Storage | libSQL default, Postgres opt-in | Dual PostgreSQL + libSQL from day one |
| Extension model | IronHub marketplace, hosted-first | Self-hosted GitLab, WASM tools, skills system |
| Failure handling | Next-steps recovery (good idea) | Self-heal pipeline (different angle, complementary) |
