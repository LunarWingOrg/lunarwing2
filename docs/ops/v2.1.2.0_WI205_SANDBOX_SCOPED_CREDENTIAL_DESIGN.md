# Sandbox-scoped gateway credential — design

**Status:** Proposed (not implemented)
**Origin:** WI#205 candidate 3 — "Move gateway auth to a per-sandbox scoped credential that is not present in the tenant env file"
**Companion:** `v2.1.2.0_WI205_CREDENTIAL_EXPOSURE_FIX.md` (the fix that landed)
**Date:** 2026-09-20

## Problem statement

The fix that landed removes the sandbox's *path* to the tenant env file and
stops handing the full gateway bearer to worker lanes. It does not change the
underlying shape: **the gateway has exactly one credential class**, and it is
all-powerful within a tenant. `UserIdentity` is only:

```rust
pub struct UserIdentity {
    user_id: String,
    workspace_read_scopes: Vec<String>,
}
```

There is no route scope, no capability list, no audience and no expiry. Any
process holding the token — desktop client, CLI, worker, agent tool — can hit
every `/api/*` route: memory read/write, log-level mutation, mission webhooks,
voice, SSE streams and file access.

This was acceptable while the only holders were operator-facing clients. It is
not acceptable once an *agent* is a legitimate holder, because the agent is the
untrusted party the sandbox exists to contain. The goal is that a contained
lane holds a **single-purpose badge**, not keys to the kingdom.

## What already exists (and should be reused, not reinvented)

Two patterns in-tree solve adjacent halves of this:

### 1. `ScopedBearerCredential` — host-held, origin-and-path-scoped, never given to the guest

`ic/src/tools/wasm/wrapper.rs`:

```rust
struct ScopedBearerCredential {
    target: ScopedServiceTarget,   // origin + endpoint_prefix
    token: SecretString,
}
```

Construction validates that the service URL is a **bare origin** (no
credentials, query or fragment; path exactly `/`; `https`, or `http` only for
loopback-ish hosts). Each request is then checked:

```rust
fn url_matches_scoped_prefix(request_url: &str, allowed_prefix: &str) -> bool {
    // same origin AND request path starts with the allowed prefix
}
```

The host attaches the header at the HTTP boundary *after* the guest's
leak-scan; the guest never sees the token. LunarVoice uses exactly this, with
the service URL host-injected into the tool context so the guest doesn't even
choose the destination. Nothing about this is WASM-specific — it is a general
"host brokers a narrow credential" mechanism.

### 2. Orchestrator `TokenStore` — minted, per-identity, revocable, in-memory

`ic/src/orchestrator/auth.rs`:

- `create_token(job_id)` mints a fresh random 32-byte hex token per job.
- Validation is constant-time (`subtle::ConstantTimeEq`) and keyed by id.
- `revoke(job_id)` drops token + grants together.
- Tokens are in-memory only, never persisted.
- `worker_auth_middleware` extracts the id from the path (`/worker/{job_id}/…`)
  and validates against **that job only**.
- `CredentialGrant { secret_name, env_var }` hangs off the same id, so grants
  are exactly as scoped as the token.
- `GET /worker/{id}/credentials` brokers secrets *over* the token rather than
  handing them to the container.

That is the shape needed: identity-scoped, time-bounded, revocable, and
optionally a broker rather than a bearer.

## Gap analysis

| Need | Have | Missing |
| --- | --- | --- |
| Origin/path scoping | `url_matches_scoped_prefix` | Applied to gateway tokens |
| Per-identity minting | Orchestrator `TokenStore` | A gateway-side equivalent |
| Expiry | `PendingGate.expires_at` pattern; secret `expires_at` | On gateway tokens |
| Revocation | `TokenStore::revoke` | Gateway token revocation |
| Route-level authorization | `auth_middleware` inserts `UserIdentity` | Any notion of *which* routes an identity may use |
| Multi-token auth | `GATEWAY_USER_TOKENS` parsed (`config/channels.rs`) | Wired to production (`MultiAuthState::multi` is test-only) |

The last row is the cheapest foothold: `GATEWAY_USER_TOKENS` already parses a
token→identity map and already has a multi-token authenticator; it is simply
not constructed in production (`GatewayChannel::new` always builds
`MultiAuthState::single`).

## Proposed design

Three layers, each independently useful. **Layer 1 is the priority**; layers 2
and 3 are only worth building if we want the agent to *have* API access rather
than merely not having the master key.

### Layer 0 — Scoped env file at the mount (Option A)

The concrete shape recommended for the 2.1.3.0 step, and the cheapest thing
that actually removes the file class rather than filtering it:

- The host generates a **per-tenant scoped env file** at provisioning (and on
  capability change) and the sandbox mounts **only that file**.
- Credentials are classified into tiers so the file's contents are decidable
  rather than a judgement call:

  | Tier | Contents | Mount policy |
  | --- | --- | --- |
  | **T0 — never sandbox-visible** | `GATEWAY_AUTH_TOKEN`, LLM provider API keys (unless per-tenant), DB credentials, admin tokens | Host-only. Never exists in any file the sandbox mounts. |
  | **T1 — scoped credential** | Mission webhook tokens (if the tenant's missions need them), LunarVoice scoped token (if voice-enabled), per-tenant LLM key (if the tenant owns one) | Injected per capability, only when that capability is enabled. Generated per-tenant, narrowly scoped, independently revocable. |
  | **T2 — benign config** | Model names, timeouts, feature flags, paths, log level (read-only copy) | May ride the scoped env file freely. Nothing here is a pivot vector. |

- **The critical insight:** the T0/T1/T2 split is a *classification decision*,
  not a filtering mechanism. The reason the WI#205 leak existed is that the
  sandbox could read T0 secrets; no amount of masking changes the fact that T0
  material was stored in a file the sandbox could reach. Separating the tiers
  at rest is what makes the fix durable — a new env var added later cannot leak
  into the sandbox unless someone explicitly classifies it as T1/T2.
- **Pros:** declarative; auditable per-tenant (`cat` the scoped file and see
  exactly what the sandbox holds); trivial rollback.
- **Cons:** still a file on disk, so it needs mode-600 and host-only ownership
  discipline, and every future env var must be classified at PR time.
- **Relationship to what landed:** the mount guard is the enforcement half of
  this design (it is what stops T0 from being reachable), and
  `SANDBOX_PROTECTED_PATHS` is the seam where the tier classification plugs in.
  Option A adds the *generation* half: a curated file instead of an empty
  mask. The two compose — masks for directories that must never be exposed,
  a scoped file for the values the sandbox legitimately needs.

### Layer 1 — Route-scoped gateway tokens

Extend `UserIdentity` with an explicit capability set and enforce it in the
middleware:

```rust
pub struct UserIdentity {
    user_id: String,
    workspace_read_scopes: Vec<String>,
    /// Empty = full access (operator clients, unchanged behavior).
    /// Non-empty = allowlist of route prefixes this token may call.
    allowed_route_prefixes: Vec<String>,
    /// Optional hard expiry for time-bounded credentials.
    expires_at: Option<DateTime<Utc>>,
}
```

- Parsing comes from the existing `GATEWAY_USER_TOKENS` JSON; add
  `allowed_route_prefixes` / `expires_at` keys with `Empty = full` semantics so
  every existing token keeps working byte-for-byte.
- Enforcement sits beside the existing bearer check in `auth.rs`, comparing the
  request path against the allowlist — the same `starts_with` logic
  `url_matches_scoped_prefix` already uses, applied to routes rather than URLs.
- **This is the load-bearing change.** Everything below is about minting and
  delivery.

A sandbox badge would then read:

```json
{
  "allowed_route_prefixes": ["/api/missions/webhook/"],
  "expires_at": "2026-09-20T23:59:00Z"
}
```

— enough for a mission sentinel to fire its own webhook, and nothing else. No
memory, no logs, no voice, no SSE.

### Layer 2 — Minted, per-lane credentials

A `GatewayTokenStore` modelled directly on the orchestrator's:

- `mint(scope, ttl) -> SecretString`, random 32 bytes, held in memory only.
- Bound to the lane identity (sandbox id / worker id), so validation is
  per-identity rather than global.
- Optional grants attached to the same id, mirroring `SandboxJobGrants`.
- `revoke(lane_id)` on lane teardown — a sandbox that exits takes its badge
  with it.

This removes the "static secret staged on disk" property entirely: there is no
file to read, because the credential only exists for the lane's lifetime.

### Layer 3 — Delivery without disclosure

Two options, in order of preference:

1. **Broker (preferred).** The sandbox never holds a gateway bearer at all. A
   narrow host-side proxy accepts lane requests and attaches the credential
   itself — this is exactly `ScopedBearerCredential` semantics, and the sandbox
   proxy already does credential injection for allowlisted egress
   (`sandbox/proxy/http.rs` resolves credentials host-side via
   `EnvCredentialResolver`). Extending that mapping to the gateway origin is
   the smallest version of this.
2. **Injected at spawn.** Where a bearer is unavoidable, inject it as a
   process-spawn env var from the minting store rather than reading it from a
   file. The sandbox runner already supports caller-supplied `-e` entries and
   the shell tool currently passes none — this is the intended extension point.

Broker first: option 2 still puts a live credential in the container's
environment, which `podman inspect` exposes to the tenant user.

## Consequences and non-goals

- **Non-goal:** removing the operator's full-access token. Desktop clients and
  the CLI keep the existing single-token behavior; `Empty = full` preserves it
  exactly.
- **Non-goal:** making the sandbox resistant to a tenant user who already has
  shell access on the host. A tenant user can read their own files; this design
  limits what an *agent inside a lane* can reach, and shrinks the blast radius
  of a leaked worker secret.
- **Compatibility:** `UserIdentity` is constructed in several places; adding
  fields with `Default`-ish semantics (empty vectors, `None`) keeps existing
  call sites compiling and behaving identically.
- **Risk:** route-prefix matching is string-prefix based. `/api/memory` must
  not accidentally permit `/api/memory-admin` if such a route ever exists —
  match on segment boundaries, the way the host-pattern matcher in
  `secrets/types.rs` does, rather than raw `starts_with`.
- **Test surface:** middleware unit tests per scope (allowed / denied / expired
  / full-access default), plus an integration test asserting a scoped token
  gets 403 (not 401 — authenticated but unauthorized) on an out-of-scope route.

## Recommendation

Layer 0 (the scoped env file) plus Layer 1 (route-scoped tokens) is the
recommended long-term fence: the sandbox is given a curated capability set
instead of a path to the tenant's secrets, and any credential it does hold is
narrowly scoped. Sequencing follows the tier work:

- **2.1.3.0** — Option A: per-tenant scoped env mount, T0 separated from
  sandbox-visible env. Builds directly on the `SANDBOX_PROTECTED_PATHS` seam
  introduced with this change.
- **2.1.4.0** — the organizing pass: full T0/T1/T2 classification with a
  PR-time gate ("does this change add env vars? which tier?"), plus the
  capability gating rule below.

The capability-gating rule that makes this scale: **each T1 credential is
generated per-tenant, only if the capability is on, narrowly scoped, and
independently revocable.** Voice enabled → a voice scoped token exists. A
mission with a webhook → a token scoped to *that mission's* endpoint only, not
a generic "missions can call home" token. No voice and no webhooks → the scoped
file is T2-only and the sandbox literally cannot authenticate to anything. Each
badge opens one door, and rotating one never requires rotating a sibling.

Failure modes to fence in review:

1. **Drift** — a tenant gains a capability, the scoped env regenerates, but a
   stale file lingers in an old mount. Fix: rewrite atomically (tmp + rename)
   and remove prior copies on capability change; the sandbox restart is the
   signal to recreate the mount.
2. **`podman inspect` exposure** — if a future step injects at spawn rather
   than mounting, `podman inspect` exposes env to anyone with host podman
   access. Decide explicitly whether that is in-model (host root already owns
   everything) or needs the broker approach instead.
3. **Back-compat migration** — existing tenants have the fat env file.
   Per-tenant migration: generate the scoped env minus T0, flip the mount,
   verify agent boot, then remove T0 from the mounted path. Do it with a health
   gate, not a fleet-wide flag.
4. **New-var trap** — every future env var must be classified at PR time. One
   line in the PR template is cheaper than an annual re-audit.

If Layer 1 alone is ever deemed enough, note what it does *not* solve: a
route-scoped token still lives in a file the sandbox can read. Layer 0 is what
removes the file class; Layer 1 limits the damage when something else goes
wrong. Neither is a substitute for the other.
