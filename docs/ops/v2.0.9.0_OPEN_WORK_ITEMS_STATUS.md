## #80 (OPEN in GitLab; code addressed 2026-08-27) — Sec: role-token neutralization gap in `format_output` (CodeAct step sink)

<https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/80> · reporter: kageho ·
filed 2026-08-26 · severity LOW–MEDIUM

**Addressed 2026-08-27** (goal item #21, branch `rarity/kimi-21-20260827-1801`,
commits `d66b2b4b` + `2c62b4b0`) — exactly the report's recommended fix, applied to
`ic/crates/lunarwing_engine/orchestrator/default.py`:

- `format_output` now runs the shared `neutralize_role_token_openers` over the complete
  rendered step blob (nested-VM `stdout`, `[name]`/`[name ERROR]` action previews,
  `[return]` values) **before** front-truncation, mirroring `format_action_output` —
  idempotent, so already-neutralized history passes through unchanged.
- History repair extended: `sanitize_action_results` additionally neutralizes `User`-role
  message content (no re-truncation — User blobs are bounded at creation), so CodeAct
  blobs persisted by older orchestrator versions are repaired on the next
  `ensure_working_messages` pass; `ActionResult` bounding is unchanged. The recovery
  context shrinker (`shrink_context_for_model_recovery`) renders `working_messages`
  after that repair, so it is covered too.
- Regression tests added in `executor/orchestrator.rs`: stdout/action-preview/
  action-error/return sinks, idempotence, benign passthrough, front-truncation keeping
  the invariant (including a cut landing mid-marker), and persisted User-blob repair.
- Implementing it exposed a real Monty constraint now documented in the file:
  module-level names bind in definition order, so `neutralize_role_token_openers` was
  moved above `format_output` — without the reorder the call silently resolves to `None`
  in the live engine and the turn fails with a `len(None)` TypeError.

Verified: 516/516 `lunarwing_engine` lib tests, `cargo fmt --all -- --check` clean,
zero-warning `cargo clippy -p lunarwing_engine --lib --tests -- -D warnings`
(taskset, 18 threads). Remaining: GitLab work-item close after review.

Finding-time record (verified still present at `cbb0c4c9`, 2026-08-26):

- `format_output` (`ic/crates/lunarwing_engine/orchestrator/default.py:257-287`) performs
  length bounding only; it never calls `neutralize_role_token_openers`. Its output is
  appended verbatim as a User-role message (`default.py:1189`), embedding nested-VM
  `stdout`, `[name]`/`[name ERROR]` action previews, and `[return]` values.
- The Rust side feeds it raw: `handle_execute_code_step` puts unneutralized
  `result.stdout` into the result dict (`executor/orchestrator.rs:915`).
- Persisted-history repair did not cover the sink: `sanitize_action_results`
  (`default.py:311-316`) rewrote only `ActionResult`-role entries, never these User-role
  CodeAct blobs, so a poisoned blob predating a fix would survive repair.
- Mitigating factor (why LOW–MEDIUM): since `35689058` the bridge neutralizes
  `action_results` upstream, so no live attacker-controlled path to this sink is currently
  known; it is a defense-in-depth gap against future unneutralized-stdout paths.
