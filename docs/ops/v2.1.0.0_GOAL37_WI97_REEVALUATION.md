## Verdict

**The repository defect described by WI#97 is fixed.** The current code accepts
both supported XMPP MUC publisher forms, preserves the full occupant identity
through the transport path, and still requires an explicit room join/receive
allowlist. The focused tests pass at the revision above, and the earlier item 27
live run exercised the same behavior end to end through two fresh tenants and a
real isolated Prosody MUC.

This verdict does **not** prove that the original `sunburst` and `ruffles`
deployments have since received the required configuration and restarted. They
are not registered on this host, so their current operational state cannot be
checked here. That is a deployment acceptance question, not an outstanding
repository-code defect.

The public tracker remained open when queried on 2026-09-07. Its last public
non-system note, from 2026-09-04, says that further validation is required. The
issue body also still recommends user bare JIDs, which contradicts both current
source and the completed live matrix.

## WI#97 failure-by-failure assessment

### 1. Coordination room was not joined

This was an operator configuration failure. Joining remains deliberately
explicit and deny-by-default. Item 27 proved the corrected configuration with
both test bridges reporting the room in `configured_rooms` and
`rooms_with_presence` before sending any records.

**Status:** corrected contract is documented and live-proved; original tenant
configuration is not observable from this host.

### 2. Inbound groupchat was discarded

This is the same missing-room condition at the receive boundary. Refusing an
unlisted room is the intended security behavior and must not be weakened. Item
27 proved that configured room traffic reaches the hook, including negative
publisher cases whose exact occupant IDs appeared in receiver logs.

**Status:** working as designed after the room is configured.

### 3. Room-bare publisher entry did not match a full occupant sender

The code fallback is present and covered by both unit and database-backed tests.
Item 27 proved it through the full transport. Exact full-occupant matching also
continues to reject a different nickname in the same room.

**Status:** fixed in code and live-proved.

### Stale user-bare recommendation

The issue body's `user@server` recommendation is not valid for MUC traffic. A
MUC message arrives as `room@server/nick`; the daemon does not infer a real user
JID from the nickname. Item 27 sent a delivered live record with a user-bare
allowlist and proved that it wrote zero rows. The safe supported choices are an
exact full occupant JID or an explicit room-bare, room-wide entry.

## Suggested improvements

These are follow-ups, not blockers to the fixed verdict.

### P0 — reconcile and close the tracker

Update WI#97's stale body so it no longer recommends user bare JIDs. Link the
item 27 live record and this current-revision review. If closure requires proof
on the original two tenants, run the acceptance check below there and record
that deployment evidence; otherwise close the repository bug now and track the
production rollout separately.

### P1 — add a read-only coordination doctor

Extend `lunarwing-mt-admin.sh` with one init-agnostic validation path rather than
adding systemd/OpenRC probes to wrappers. For each tenant it should compare,
without printing secrets:

- `COORD_ENABLED`, `COORD_CHANNELS`, and the knowledge share/publish switches;
- publisher entries classified as exact occupant or room-wide entries;
- installable XMPP `rooms` configuration;
- bridge `configured_rooms` and `rooms_with_presence` from authenticated
  loopback status;
- daemon hook registration/health when a structured status is available.

It should report mismatches and recommended edits but not silently rewrite room
or trust policy. This would catch WI#97 Failures 1 and 2 before a message is
sent, while preserving both OpenRC and systemd-user-manager support.

### P1 — expose bounded ingest diagnostics

The current non-allowlisted path is a debug log
(`ic/src/hooks/coordination_knowledge.rs:535-540`), which is safe against noisy
warning logs but hard to diagnose. Add bounded counters or a small authenticated
status summary for accepted, invalid-sender, non-allowlisted, sender-rate-limit,
global-rate-limit, and storage-failure outcomes. Do not expose message bodies or
raw credentials, and do not emit one warning per hostile room message.

Also emit one startup warning when `COORD_KNOWLEDGE_SHARE=true` but the publisher
list is empty. Empty must continue to deny all; the warning only makes the
operator's opt-in/deny-all combination visible.

### P1 — automate the live matrix

Convert the item 27 Prosody scenario into an opt-in or scheduled integration
harness. Keep the four positive/negative cases and require observed room
presence before assertions so a delivery failure cannot make a refusal case
pass accidentally. It need not burden every unit-test pipeline, but it should
run before releases that modify XMPP, installable channels, hook routing, or
coordination knowledge.

### P2 — strengthen publisher identity when the MUC supports it

Exact occupant entries authenticate only a room nickname, while room-bare
entries deliberately trust every occupant. For non-anonymous, members-only MUCs,
a future protocol could carry the server-reported real bare JID as separate
trusted transport metadata and support an explicit real-JID allowlist mode.
Never infer a bare user JID from a nickname, and never silently broaden an exact
occupant entry to room-wide trust.

## Deployment acceptance check

For each real tenant, after applying configuration and restarting through
`lunarwing-mt-admin.sh`:

1. Confirm the coordination room appears in bridge `configured_rooms` and
   `rooms_with_presence`.
2. Confirm the daemon reports coordination hooks registered with knowledge
   sharing enabled and the expected room scope.
3. Send a unique `KNOW:` topic from tenant A and verify exactly one
   `needs-verification`, `coordination`-tagged row on tenant B with the full
   occupant in `submitted_by` and no self-row on A.
4. Repeat B to A.
5. Temporarily test one wrong occupant or user-bare entry and prove the message
   reaches the receiver but writes zero rows; restore the intended exact or
   room-wide policy afterward.
