## Root-cause analysis of the OOM class (the still-open issue)

Every trace shows the same shape: no compiler diagnostic, only

```
sccache: Compile terminated by signal 9
error: could not compile `lunarwing` (lib test) ... (exit status: 2)
```

Kernel signal 9 on a rustc process is the OOM killer. `rustc` compiling the
`lunarwing` lib alone approaches the 16 GB runner ceiling (`-j2`, libSQL
`-j1`, line-tables-only are the existing in-job mitigations). Two of those
compiles on one host exceed it.

Evidence that this is cross-pipeline contention on one runner host:

- #3742 `rust-test-lib` (job 67187): started 09:13, killed 09:43:58 with
  `sccache: Compile terminated by signal 9` on `lunarwing (lib test)`;
  `rust-test-libsql` (started 09:30, same pipeline, same runner host) was
  mid-compile of the same giant lib at that moment — 3–5 build slots ran
  concurrently on one system ID despite the documented `limit = 1`.
- #3707 `rust-check-libsql` (job 66577): started 01:17, killed 01:36.
- #3708 `rust-check-libsql` (job 66603): started 01:21, finished 01:44 — the
  overlapping window covers 66577's death exactly.
- Both ran on the same runner: `lunarwing-rust-docker`, system ID
  `r_dLo2MDLTpMm2` (runner id 8), build slots `concurrent-1` and
  `concurrent-3`.
- The `.gitlab/README.md` §6 contract says `limit = 1` in the runner
  `config.toml`; live traces show `concurrent-0..3` slots, i.e. the host-side
  contract had drifted. (Fixing the runner host itself is outside this repo;
  the repo-side guard below makes CI independent of that setting.)

## Fixes applied (this branch)

1. **`.gitlab/ci/rust.yml`** — every job that compiles the `lunarwing` lib
   (`rust-check-default`, `rust-cache-refresh`, `rust-check-postgres`,
   `rust-check-libsql`, `rust-check-all-features`, `rust-msrv-check`,
   `rust-clippy-all`, `rust-test-lib`, `rust-test-libsql`,
   `rust-test-postgres-integration`) now carries
   `resource_group: rust-compile-16gb`. GitLab serializes same-group jobs
   **project-wide**, so overlapping pipelines can never run two
   giant-crates compiles at once regardless of runner concurrency. Cheap
   jobs (rustfmt, cargo-metadata, cargo-deny, wasm artifacts) stay outside
   the group. Two commits: initial nine jobs + MSRV follow-up.
2. **`.gitlab/ci/integration.yml`** — `cavepony-wasm` joins the same
   resource group (MR !997 review P2): its `wit_compat` test step compiles
   the `lunarwing` lib test binary, so its `needs` edge to
   `rust-check-default` does not prevent cross-pipeline overlap.
3. **`.gitlab/ci/containers.yml`** — `worker-*-scan` scripts now check for
   `worker-image.env` before sourcing it and fail with the real cause
   ("the candidate job for this worker failed or did not publish an image")
   instead of the cryptic `can't open './worker-image.env'`.
3. **`.gitlab/README.md`** — two new runbook sections:
   - *Rust runner memory budget*: recognize the signal-9 OOM, why both the
     resource group (repo-side) and `limit = 1` (host-side) are required,
     evidence of the `limit = 1` drift, recovery steps. Updated for the
     re-attempt: MSRV check and `cavepony-wasm` are in the group; pipeline
     #3742 added to the evidence list.
   - *container-build runner disk*: the ENOSPC candidate failure shape and
     the scan guard's meaning, recovery steps.

## Five CI/CD improvement suggestions (beyond the fixes)

Investigation surfaced these; all are deliberately **not** implemented here
(scope), recorded for future goals:

1. **Runner-host budget enforcement/alerting.** The `limit = 1` contract is
   documented but nothing watches it. A tiny scheduled job (or runner-host
   cron) that queries `/api/v4/projects/35/jobs?scope[]=running` and alerts
   when more than one giant-crates job reports the same runner system ID
   would catch concurrency drift the same day it happens.
2. **`needs`-based cross-job compile reuse.** The four `rust-check-*` jobs
   and the three test jobs each rebuild dependency rmeta independently in
   their own workspace. Moving check jobs to `artifacts: ic/target` (pull
   into the matching test job) would cut total runner-minutes roughly in
   half; the 40 GiB disk contract has room for one shared target dir per
   feature combo if artifacts expire quickly.
3. **Fail-fast artifact contract for worker lanes.** `worker-*-scan` still
   *runs* (and burns a trivy pull + ~30 s) after a failed candidate because
   the candidate is `allow_failure: true` on the default branch. A `rules:
   when: on_success` + `needs: optional` shape could skip scans entirely
   when no candidate artifact exists, saving runner cycles and making the
   pipeline graph honest.
4. **Docker Hub rate-limit mirror (documented option 2) actually applied.**
   The README documents mirroring the three pinned images into the project
   registry but it has not been done; the `toomanyrequests` failure class
   remains live. One-time `podman pull/tag/push` + three CI variables.
5. **JUnit for Rust jobs.** `python-unit` and `shell-harnesses` emit JUnit;
   the Rust test jobs do not (`--format` json → junit conversion is one
   small script). That would give test-level failure visibility in MR
   widgets instead of raw-log spelunking.
