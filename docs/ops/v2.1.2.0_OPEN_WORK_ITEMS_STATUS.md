### #225 (OPEN) — external workers never materialize + podman store corruption

**The most consequential open item.** Filed 09-23 by ajhermes with a
seven-addendum live investigation in the comments; the consolidated root
cause (Addendum 5–7): the host-global `lunarwing-mt-health.timer` (15-min
cadence) runs `lunarwing-self-heal.sh`, which judges an `ActiveState=inactive`
tenant unit unhealthy and remediation-restarts it (`_systemd_user_restart`,
repo copy at `ic-infrastructure-health-check/lunarwing-self-heal.sh:322-333`).
The restart cascade (`Requires=` chains) stops tenant containers; conmon
exit-cleanup races leave phantom `ContainerState` rows (row without runtime
dir / missing `conmon.pid`) that poison the tenant's rootless podman store —
after which every `podman create` fails (`unable to create a new pause
process … conmon.pid: no such file`) and all worker lanes fail with
connection refused (os error 111). Inttest tenants are the perfect victim
because their units sit inactive between phases. Corroborated on a Gentoo
host (init-agnostic mechanism).

Repo verification this pass: the judgment chain is exactly as described —
`health-systemd.sh` classifies enabled-but-inactive units as `critical`
(down while tenant running, or enabled + not-active), the self-heal main loop
turns every non-healthy/non-skipped report entry into a remediation target,
and there is no intentional-stop suppression (the only suppression is
escalation page cooldown). Review notes in the thread correctly push back on
the two riskier remediation ideas (auto-sqlite-DELETE is too risky; quiescence
does not cover transient healthcheck units) and endorse the minimal fix:
**inactive ≠ failed — remediation should key on failed/degraded substates**,
plus a suppression flag for intentional stops. None implemented at HEAD.
