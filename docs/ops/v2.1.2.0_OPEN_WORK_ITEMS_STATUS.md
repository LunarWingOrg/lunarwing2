<https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/109>

since 2026-09-03.

- Scope A (landed, 2.1.1.0 item 9): generic best-effort `engine/thread_start`
  event dispatch via `MissionCadence::OnSystemEvent` exact-match.
- Scope B (landed, 2.1.2.0 item 11): the WI's stated purpose — purge stale
  cached tool output **before** a mission thread executes — is now a
  synchronous pre-execution sanitizer in `ExecutionLoop::run`
  (`ic/crates/lunarwing_engine/src/executor/loop_engine.rs`). Tier 1
  (`time`/`date`/`datetime`) always purged; Tier 2
  (`web_search`/`http`/`shell`) purged when older than 30 minutes via a
  `_cached_at` timestamp; sanitized state persisted back to the checkpoint
  with a `sanitized_at` observability marker. Runs before the first model
  call of every thread, including Mission threads.
- `_cached_at` stamping (landed, 2.1.2.0 item 11 follow-up): the Python
  orchestrator stamps `_cached_at` (RFC 3339 UTC) onto Tier 2 dict outputs
  at the persisted-state write site (`stamp_cached_at`,
  `ic/crates/lunarwing_engine/orchestrator/default.py`), so Tier 2 aging is
  fully effective — scalar outputs stay un-stamped and un-purged (fail-open,
  per the sanitizer contract).

The in-tree mission definition the WI cites no longer exists
(`projects/sanitize-memory/` is absent from this revision and from all
inspected tenant workspaces), and a mission trigger cannot satisfy the
before-execution ordering requirement — the sanitizer is the correct form.

Record: `docs/ops/v2.1.2.0_WI109_WI126_SANITIZE_MEMORY.md` (scope decision
history: `docs/ops/v2.1.1.0_GOAL4_WI126_THREAD_START_MISSION_SCOPE.md`).

## #135 (OPEN) — cross-thread mission-context leakage (NEW since v2.1.1.0 audit)

<https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/135>

**Verdict: fixed in source at this revision; live canary acceptance recorded.**
Filed 2026-09-12 after live-fire canary testing on tenant `brightdawn`: a
mission's full `mission.json` (goal text + in-band nonce tokens) was retrievable
by sibling missions via `memory_search` — the mission-goal index was
tenant/project-scoped, not mission-scoped. This is the input side of the
WI#110 (#132) contamination loop family.

Landed on `master` (present at `14ccfdd23`):

- `is_mission_path()` in `ic/src/workspace/document.rs:82` excludes the whole
  `engine/projects/{p}/missions/**` subtree (any depth, any suffix) plus the
  tenant-wide `missions.json` listing and its suffixed variants from the search
  index, folded into `is_search_indexable_path()` (`:104`). Mission JSONs stay
  stored and served; they just stop entering the index.
- `Workspace::purge_mission_index_chunks` (`ic/src/workspace/mod.rs:2207`) runs
  the idempotent legacy-chunk DELETE at boot before the embed backfill pass;
  pinned by `purge_mission_index_chunks_removes_legacy_chunks_and_is_idempotent`
  (`:2822`).
- `build_memory_search_output` labels engine-internal docs with
  `"provenance": "engine_internal"` (`ic/src/tools/builtin/memory.rs:207`),
  pinned by `memory_search_output_labels_engine_internal_docs` (`:1164`).

Tracker acceptance: the 2026-09-13 canary refire (round 2) recorded exact-path
isolation PASS, and the follow-up adjacent-path bypass
(`mission.json.bak` / `other.json` / `missions.json` staying indexable) is
closed by the subtree exclusion above (2.1.1.0 items 27/29). Remaining action
is tracker closure citing the canary record.

## #137 (OPEN) — OpenRC respawn/exit race with supervise daemon (NEW since v2.1.1.0 audit)

<https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/137>

**Verdict: fixed in source at this revision; live OpenRC verification not yet
recorded.** Filed 2026-09-13 after tenant `starforce` still reported active
writers after stop on the OpenRC host. Two mechanisms identified: (1) a
respawn/exit race — supervise-daemon child teardown is asynchronous, so the
immediate post-stop quiescence check can see a container still `Running=true`
(or a respawned orphan); (2) an `rc-service` status-classification gap where
unrecognized states fell through to "could not verify".

Landed on `master` (present at `14ccfdd23`, 2.1.1.0 items 31/33):

- `await_writer_quiescence` in `ic/scripts/mt-admin-lib/04-tenant-lifecycle.sh`
  adds a bounded quiesce-wait: poll `tenant_writers_active` every 1s for up to
  ~30s before failing closed, so mid-teardown containers settle instead of
  misclassifying (`:316,361-372,395-416`).
- The OpenRC status classification no longer treats a stopped service whose
  status text says "session is not running" as running (commit `168277615`),
  and runtime-absent tenants classify as quiesced (commit `259b998ad`).

The 2.1.1.0 item-31 mandate — create a fresh OpenRC test tenant and verify
`restart-tenant`, `stop`/`start`, and a kawarimi export all pass — has not been
recorded anywhere this review could find. That live rehearsal is the remaining
action before tracker closure.
