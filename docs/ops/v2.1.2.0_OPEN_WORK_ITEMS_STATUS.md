## #158 (OPEN) — pebble worker: cancels-map entries leak on task completion

<https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/158>

**Verdict: repo-partial (leak confirmed open at source).**

The spawned task closure (`pebble4lunarwing/src/bridge.rs:373-393`) calls
`registry.unregister(&workspace, &task_id)` but does **not** call
`cancels.remove(&task_id)`. The dead `oneshot::Sender` stays in the `cancels`
HashMap for the connection's lifetime. The comment at `:366-367` claims "the
handler owns the workspace claim and the cancel-map entry for the task's
lifetime and clears both on exit" — but only the registry claim is cleared.
SweetieBot independently verified this at master HEAD `2b6c7fffb`.

The leak is bounded (entries live for the connection's lifetime, not
unbounded across connections) and does not cause functional issues (cancel
for a finished task is a no-op that hits the `None` branch), but the comment
is misleading and the map grows without cleanup during a long-lived
connection with many tasks.

Fix shape: add `cancels.remove(&task_id)` to the spawned task's exit path.
This requires either passing a reference to the `cancels` map into the
spawned closure (currently `&mut cancels` is held by the read loop) or
restructuring to use a shared `Mutex<HashMap>` like kimi's `activeTasks`.

Comments reviewed: sweetiebot (2026-09-16) independent verification. 4 total
notes. Remaining: fix the cleanup path.
