Exposure is **opt-in only**: the entire chain compiles only in builds that
explicitly pass `--features libsql-remote-replica` AND configure `LIBSQL_URL`
for Turso remote-replica sync. Default and postgres-only builds exclude it,
pinned by `.gitlab/scripts/check-default-graph-advisories.sh` (CI job
`default-graph-advisory-guard`), which fails if any of the three legacy pins
re-enters either production root or goes stale in `ic/Cargo.lock`. The
`ic/deny.toml` ignores stay required regardless, because CI's cargo-deny gate
queries `--workspace --all-features`, which enables the opt-in feature.

## Clearing options — re-checked 2026-10-16

### 1. Upstream libsql bump — still clears nothing

crates.io re-verification 2026-10-16 (crate record `updated_at`
2026-10-13T18:16:27Z):

- **libsql 0.10.0 went stable on 2026-10-13** (`max_stable_version` 0.10.0;
  the prerelease line ended at 0.10.0-pre.4). This is new since the
  2026-10-10 WI#331 re-check, which saw 0.9.30 as latest stable.
- Its published dependency manifest still requests exactly the pins that
  carry the chain: `hyper-rustls ^0.25` (optional, `webpki-roots`),
  `hyper ^0.14` (optional), `tonic ^0.11` (optional). hyper-rustls 0.25
  resolves rustls 0.22 / rustls-webpki 0.102; tonic 0.11 → hyper 0.14
  resolves h2 0.3.
- RustSec advisory-db `479c888ce4401313bca61ba4aba2d0f6244c4a09` (2026-10-16):
  no 0.102-line webpki patch exists (0049 patched `>=0.103.10`, 0098/0099
  `>=0.103.12`, 0104 `>=0.103.13`), no h2 0.3 patch exists (0258 patched
  `>=0.4.16` only), and no rustls 0.22 patch exists for 0346/0349 (patched
  `>=0.23.46` only). RUSTSEC-2026-0285 does not add exposure: it marks
  `<0.23.13` unaffected, covering 0.22.4.

Clearing trigger unchanged: an upstream libsql release that adopts
rustls 0.23 / hyper-rustls 0.27+ (and a tonic/hyper line that carries
h2 0.4). Re-check this at every release (protocol below).

### 2. Driver migration off libsql 0.6.0 — rejected (unchanged)

PostgreSQL is the primary backend; the remote-replica path is the only
consumer of the vulnerable chain, and no shipped build enables it. Replacing
the driver is a dedicated project, not an advisory-hygiene decision.

### 3. Standing feature-gate mitigation — ADOPTED (this document)

## Decision (WI#418, 2026-10-16)

The WI#331 `libsql-remote-replica` feature gate is accepted as the
**standing long-term mitigation**, not an interim state awaiting a bump:

- The seven acceptances are re-homed from the closed WI#331/WI#409 decision
  records to this document; the **open work item WI#418** is their clearing
  owner until the entries are removed.
- Accepted residual exposure (opt-in builds only): TLS between LunarWing and
  a third-party libSQL/Turso host is validated by webpki 0.102.8 with known
  name-constraint bypasses (0098/0099) plus the CRL issues (0049/0104);
  rustls 0.22.4 session handling carries 0346/0349 (no custom
  `ClientSessionStore` exists in LunarWing sources; 0346's Debug leak has no
  call site, 0349 is not a certificate-authentication bypass); h2 0.3.27
  empty-DATA framing (low severity) applies to the replication HTTP/2
  connection.
- Conditions the acceptance depends on — all must hold, and each is
  regression-pinned:
  1. No shipped build path enables `libsql-remote-replica` by default
     (mt-admin `05-tenant-build.sh`, `scripts/build-lunarwing.sh`,
     `ic/Dockerfile`, `Dockerfile.worker` all use default features; the
     daemon, wizard, `status`, and `doctor` fail closed when `LIBSQL_URL` is
     set without the feature).
  2. The default/postgres-only production graphs stay free of
     rustls-webpki 0.102.8, h2 0.3.27, and rustls 0.22.4 — enforced by the
     default-graph advisory guard, which also fails stale.
  3. The modern line stays patched (rustls >=0.23.46 manifest floor and
     `ic/deny.toml` ban ranges; h2 0.4.20 / webpki 0.103.15 locks) so the
     legacy ignores can never mask a modern-line downgrade.

**Escalation triggers** — any one reopens this decision and re-files the
exposure assessment: a shipped build path enabling the feature by default; a
new advisory against the pinned copies whose impact exceeds the accepted
name-constraint/session/framing class; a default-graph or floor regression;
or the upstream clearing trigger above firing (then clear by bumping).

## Entry-removal protocol (inherited from WI#331 ask 3, unchanged)

Remove an `ic/deny.toml` ignore entry only when its clearing upgrade has
landed in `Cargo.lock` **and** the corresponding lockfile root has been
re-checked with `--config` overrides so the advisory resurfaces as a hard
error if it ever comes back.

## Per-release re-verification (standing, owned by this document)

At every release, for each of the seven entries:

1. Re-check upstream state: crates.io latest libsql stable and prerelease
   dependency manifests (hyper-rustls / hyper / tonic requirements), and the
   advisory `patched`/`unaffected` ranges in the current RustSec DB.
2. Refresh the `(re-verified YYYY-MM-DD)` markers and version numbers in the
   entry's `ic/deny.toml` comment block and `reason` string.
3. Confirm the default-graph advisory guard and the full cargo-deny gate are
   green for the release tree.
4. Record the result on the WI#418 work item (or its successor if re-filed).
