## Advisory findings by lockfile (lockfile-text pass)

The own-implemented lockfile scan reads every registry pin from all 27 locks
and matches it against the 1375 advisory files, honouring `patched` and
`unaffected` ranges. It is independent of feature resolution, so it sees
lockfile-only pins that `cargo-deny`'s graph walk does not.

| Lock | Registry pins | Vulnerabilities | Informational |
|---|---|---|---|
| `ic/Cargo.lock` | 956 | **11** | 17 |
| `ic/bridges/xmpp-bridge/Cargo.lock` | 878 | **3** | 10 |
| every other of the 25 locks | — | **0** | 8 total |

All 14 vulnerability findings in the two `ic` family locks are **accepted
advisories** (`RUSTSEC-2023-0071`, `RUSTSEC-2026-0176/0177`,
`RUSTSEC-2026-0049/0098/0099/0104/0382`, `RUSTSEC-2026-0258`,
`RUSTSEC-2026-0346/0349`). The `cargo-deny` workspace gate above proves the
same set is exactly what `ic/deny.toml` accounts for: it passes with zero
warnings, so there is no un-accepted vulnerability in the resolved graph.

`RUSTSEC-2026-0176/0177` are the **lockfile-only** pyo3 0.28.3 pins: they are
present in `ic/Cargo.lock` and `ic/bridges/xmpp-bridge/Cargo.lock` text but
never resolve into a build graph. `.gitlab/scripts/check-lockfile-only-advisories.sh`
pins that they stay **absent** from the no-default-features non-dev graph, with
a stale-pin check that fails if the pin leaves the lockfile — its ok verdict
above is that guarantee. The exposure is jiter's optional `python` feature,
which monty does not enable; the pin is inert for every LunarWing build.

  `*-channel`, `xmpp-bridge`, `pebble`, `api`/`commands`/`platform`/…);
  they have no registry entry by construction.
- **1 git pin** — `monty 0.0.17` at
  `git+https://github.com/pydantic/monty.git?rev=5c7cf2b6…`, which is
  git-sourced, not registry-sourced (and is on the `[sources].allow-git`
  list).

**0 yanked registry pins.** The frame this closes: the v2.1.7.0 audit had to
fix `clipboard-win 5.4.1` in the pebble override; that crate is now 5.4.3
there and no yanked member exists in any lock.
