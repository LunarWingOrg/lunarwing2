   `lunarwing_health_early_warning` series + deduplicated Gotify path.

   `install-health-metrics-listener.sh`, verify loopback-only bind, bearer
   auth, and the v16 `health_metrics` registry slot.
7. Tear down both tenants (`remove-tenant --purge`) and verify cleanup.
8. Record every result below.

### Step 5 — threshold / early-warning / Gotify dedup (DONE, 09:11–09:13 UTC)

- Installed the shipped example as the live config:
  `cp .../health-metrics-thresholds.conf.example
  /etc/lunarwing/health-metrics-thresholds.conf` (0644).
- Exporter re-run with thresholds active emitted exactly the two rules that
  cross on current live data, both `severity="warn"`:
  - `lunarwing_health_lunarvision_cache_hit_rate` (0.0 < 0.5)

    darktest/chparlive state entries)

  `THRESHOLD_lunarwing_health_lunarvision_target_count="warn:>2 crit:>3"`
  (live value 4) → both `{...,severity="warn"} 1` and
  `{...,severity="crit"} 1` series emitted for the same metric. Conf removed
  afterwards (diff vs shipped example = clean).
- **Deduplicated Gotify path** (verified against a local mock sink on
  127.0.0.1:18099, real `send-notification.sh`, `HEALTH_METRICS_EARLY_WARNING_
  NOTIFY=true`; the host's real Gotify was not touched):
  - Run 1 → exactly 2 POSTs to `/message` with `X-Gotify-Key` header,
    priority 6, escalation-shaped body naming metric + value + rule
    (e.g. `threshold crossed: ..._consecutive_unhealthy=162 (rule: >1)`).
  - Run 2 immediately after → **0** new POSTs; per-metric+severity cooldown
    stamps written under `reports/health/.metrics-notify/<metric>-<sev>.last`.
  - Run 3 with `HEALTH_METRICS_NOTIFY_COOLDOWN=0` → 4 POSTs (the two prior
    warnings re-sent + target_count warn **and** crit), proving the cooldown
    stamp — not the threshold state — gates resends.
- Mock sink torn down; no leftover processes or temp files.
