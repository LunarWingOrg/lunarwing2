## Executive summary

The current GitLab pipeline is a useful Phase 1 merge-request gate. It has a
clear include structure, suppresses duplicate branch pipelines after an MR is
open, pins job images by digest, bounds Cargo CPU use, runs the four core Rust
feature checks, and has blocking shell, Python, version, dependency, and
current-tree secret checks. Those controls should be preserved.

It is not yet a release-grade CI/CD system. The highest-value next work is not
more deployment automation. It is to make existing publication safe, close a
real PostgreSQL-only test blind spot, make protected release tags run the full
quality matrix, and stop runner cache/disk failures. In particular:

1. Manual worker-image jobs can publish mutable tags from any pipeline context,
   before tests, and inherit `interruptible: true`.
2. Published worker images are not reproducible: Kaniko is archived, base
   images are mutable tags, Pebble clones an unpinned upstream branch, OpenCode
   can fall back from its lockfile, and Kimi does not use its committed npm
   lockfile in the image build.
3. Release-tag pipelines skip the PostgreSQL-only, libSQL-only, all-feature,
   libSQL-test, Cavepony, and cargo-deny jobs.
4. A fresh PostgreSQL-only test-target check fails today even though the normal
   PostgreSQL CI check passes, because CI does not compile test targets in that
   feature shape.
5. The documented Rust runner has 25 GB free-disk minimum while sccache is
   allowed to grow to 80 GB. Pipeline #2604 has already failed with `No space
   left on device`.

Production CD should remain disabled until `lunarwing-mt-admin.sh` can install,
verify, atomically activate, health-check, and roll back one immutable package
built once by CI. The current `upgrade-tenant` path still checks out source and
rebuilds per tenant.

## Priority 0 — publication and release correctness

### P0.1 Restrict worker-image publication and separate build from promotion

**Evidence**

- Every worker image has only `- when: manual` in
  `.gitlab/ci/containers.yml:46-101`; there is no protected-ref or default-branch
  condition in repository YAML.
- `.container-job` has `needs: []` at
  `.gitlab/ci/containers.yml:29-33`, so publication can begin before any quality
  gate completes.
- The job writes the version tag, `latest`, and a short-SHA tag in one build
  (`.gitlab/ci/containers.yml:51-57`, `70-77`, and `90-98`).
- It uses automatic registry write credentials
  (`.gitlab/ci/containers.yml:40-44`) and inherits the global
  `interruptible: true` setting.
- No `resource_group` serializes two jobs updating the same moving tags.

Project permissions may limit who can press a manual job, but that is an
external setting. The YAML itself exposes a registry-writing job in every
pipeline context. A permitted user can publish an untested commit, concurrent
jobs can race on moving tags, and redundant-pipeline cancellation can interrupt
publication after only part of the intended state is written.

**Recommendation**

1. Permit candidate builds only from the protected default branch or a strict
   protected release tag. Explicitly reject MR, fork, ordinary branch, trigger,
   and unprotected-tag contexts.
2. Build and push only an immutable full-commit candidate tag first. Record the
   resulting registry digest; do not call a short SHA immutable because tags
   can be overwritten and short hashes can collide.
3. Make smoke tests, vulnerability scan, SBOM generation, and provenance consume
   that exact digest.
4. Add a separate protected, non-interruptible promotion job that retags the
   already-tested digest. It must not rebuild.
5. Serialize promotion per image with a `resource_group`. Avoid `latest` for
   tenant configuration; pin a release manifest to digests.
6. Make moving-tag promotion fail, not `allow_failure`, once it is part of a
   release contract.

**Acceptance criteria**

- No unprotected pipeline can obtain a registry-publishing job.
- No moving tag is written before all required checks and image smoke tests pass.
- Re-running a build cannot silently replace the release candidate consumed by
  staging.
- Every promoted image has full Git SHA, source-lock hashes, image digest, SBOM,
  and scan result in its evidence record.

### P0.2 Replace archived Kaniko and make worker builds reproducible

**Evidence**

- `.gitlab/ci/containers.yml:23-26` uses Kaniko 1.23.2. The upstream
  [GoogleContainerTools/kaniko repository](https://github.com/GoogleContainerTools/kaniko)
  was archived on 2025-06-03 and explicitly says it is no longer developed or
  maintained.
- GitLab now documents
  [rootless BuildKit](https://docs.gitlab.com/ci/docker/using_buildkit/) as the
  unprivileged replacement for Kaniko, including registry caching and migration
  guidance.
- Worker base images use mutable tags rather than digests:
  `pebble4lunarwing/Dockerfile:1,27`,
  `opencode4lunarwing/Dockerfile:11,68`, and
  `kimicode4lunarwing/Dockerfile:11,44`.
- Pebble is cloned from the current upstream default branch with no ref at
  `pebble4lunarwing/Dockerfile:23`.
- OpenCode pins a release tag but explicitly falls back from
  `bun install --frozen-lockfile` to unlocked `bun install` at
  `opencode4lunarwing/Dockerfile:30-34`.
- Kimi has a committed `scripts/package-lock.json`, but the Dockerfile copies
  only `package.json` and runs `npm install` at
  `kimicode4lunarwing/Dockerfile:27-38`.
- Runtime package indexes, GitHub CLI packages, rustup scripts, Go archives, and
  npm/global package transitive resolution are not tied to one build manifest.

The current short-SHA image tag therefore identifies source revision, not
reproducible bytes. Rebuilding the same commit later can produce a different
image.

**Recommendation**

- Migrate to a digest-pinned rootless BuildKit image after proving the
  self-hosted runner's user-namespace/seccomp support. If that support is not
  available, evaluate rootless Buildah rather than weakening seccomp or adding
  a Docker socket.
- Pin every base image by digest and mirror it into the GitLab registry.
- Pin Pebble to a reviewed full commit and verify the checkout.
- Remove the OpenCode unlocked fallback; a lock mismatch must fail the build.
- Copy Kimi's lockfile and use `npm ci`; integrity-pin any separately installed
  build tooling.
- Checksum downloaded toolchain archives/scripts or source them from a reviewed,
  digest-pinned builder image.
- Generate an input manifest before the build and an output provenance record
  afterward. A second clean rebuild should be compared before claiming
  reproducibility.

### P0.3 Make release tags run the complete release gate

**Evidence**

The full Rust jobs use rules that match the default branch, the release
integration branch namespace, or an MR targeting the default branch:

- `.gitlab/ci/rust.yml:14-21`, `30-36`, `45-51`, and `124-130`.
- `.gitlab/ci/integration.yml:27-33`.
- `.gitlab/ci/security.yml:6-12`.

A tag pipeline has no `CI_COMMIT_BRANCH` and is not an MR. Consequently a
protected `v*` tag does not run `rust-check-postgres`, `rust-check-libsql`,
`rust-check-all-features`, `rust-test-libsql`, `cavepony-wasm`, or `cargo-deny`.
The tag-only `release-version` job validates naming/protection/version metadata,
but it does not restore those missing gates.

**Recommendation**

- Define one reusable "full validation context" predicate that covers the
  default branch, MRs into it, release-integration branches, schedules, and
  protected release/RC tags.
- Apply it consistently to every required compile, test, security, WASM, and
  future package prerequisite.
- Add policy tests that evaluate representative MR, branch, schedule,
  unprotected-tag, protected-RC, and final-tag contexts. Validate merged YAML
  using the instance's CI Lint/API before activation.
- Package and publication jobs should `need` the exact complete gate, not merely
  coexist in the same pipeline.

**Acceptance criteria**

A protected RC/final tag cannot reach any artifact-producing job unless all
feature checks, required tests, cargo-deny, secret detection, version policy,
and required WASM compatibility checks ran and passed for that exact SHA.

### P0.4 Close the PostgreSQL-only test-target blind spot

**Evidence**

- `rust-check-postgres` runs `cargo check ... --features postgres` without
  `--tests` (`.gitlab/ci/rust.yml:9-23`).
- The default-feature test job uses `--workspace --lib`, so it deliberately does
  not compile the main package's 64 integration-test targets
  (`.gitlab/ci/rust.yml:100-113`).
- `rust-test-libsql` compiles/runs tests with libSQL, not the PostgreSQL-only
  shape (`.gitlab/ci/rust.yml:115-137`).
- All-feature Clippy can mask one-backend-only cfg defects because both backend
  feature sets are enabled, and it remains nonblocking.
- The PostgreSQL-only `--tests` command run for this audit fails today with
  cfg-shape errors. This is the same defect class recorded in older release
  notes, not a hypothetical gap.

**Recommendation**

1. Repair the current PostgreSQL-only test compilation errors as a dedicated
   change; do not weaken tests or enable libSQL merely to make PostgreSQL pass.
2. Add `cargo check --tests` (or an equivalent all-target check) for each single
   backend shape. Keep default/PostgreSQL/libSQL/all-feature shapes distinct.
3. Add a dedicated disposable `pgvector/pgvector:pg16` service job for
   `postgres+integration`. Missing database, migrations, or `vector` extension
   must fail that job rather than return early.
4. Move `workspace_integration.rs` from `cfg(feature = "postgres")` to the
   intended `postgres+integration` contract and remove graceful connection
   skips in the dedicated DB job.
5. Keep test processes serialized until environment-mutating tests are isolated;
   compilation can remain bounded separately.

**Acceptance criteria**

- PostgreSQL-only and libSQL-only test targets both compile with zero warnings.
- A deliberately unavailable PostgreSQL service makes the DB job fail clearly.
- The DB job reports a nonzero test count and no unexpected skips.
- The same commands are release-tag prerequisites.

### P0.5 Fix the runner disk/cache contract before adding jobs

**Evidence**

- `SCCACHE_CACHE_SIZE` is `80G` at `.gitlab/ci/defaults.yml:37-43`.
- The required Rust runner is documented with only 25 GB free disk at
  `.gitlab/README.md:180-191`.
- Both primary and MSRV caches use static, writable, `pull-push` GitLab cache
  keys (`.gitlab/ci/defaults.yml:78-124`). GitLab archives the sccache directory
  after jobs.
- The release checklist records pipeline #2604 Rust failures caused by
  `No space left on device` (`docs/ops/AGENT_GOALS_2.1.0.0.md:98-101`).
- The checkout itself includes roughly 1.2 GiB of committed vendor source before
  target files, cache archives, container layers, or job logs.

An 80 GB eviction limit cannot protect a runner whose available filesystem is
25 GB. It allows the filesystem to fail first.

**Recommendation**

- Establish an explicit per-runner disk budget. As an initial bound, keep
  sccache below 30–40% of usable runner disk after checkout/target headroom;
  choose the final number from measured high-water marks.
- Prefer a runner-local or object-store sccache backend over repeatedly zipping a
  large compiler cache into GitLab job caches.
- Make MR caches read-only where practical; let one trusted default-branch job
  publish refreshed cache state. Never use untrusted caches for release builds.
- Add before/after disk and `sccache --show-stats` telemetry, with artifacts or
  structured logs. Alert before the filesystem reaches the failure threshold.
- Configure runner-host cleanup for stale Docker layers, worktrees, and cache
  archives. Keep cleanup outside untrusted job scripts.
- Do not add a shared writable `target/` cache; preserve the current isolation.

## Priority 1 — turn existing checks into reliable gates

### P1.1 Promote clean Clippy and architecture ratchets

`rust-clippy-all` still extends `.observational-job`
(`.gitlab/ci/rust.yml:88-98`) even though its stated removal condition is one
clean baseline. The checklist records all-feature zero-warning Clippy passing in
pipeline #2613 and locally (`docs/ops/AGENT_GOALS_2.1.0.0.md:98-105`). The project
policy is zero warnings, so the evidence needed to make it blocking exists.

`architecture-boundaries` is also observational and runs only on schedules,
default-branch pipelines, and the special integration branch
(`.gitlab/ci/integration.yml:39-47` plus
`.gitlab/ci/defaults.yml:133-139`). Regular MR pipelines therefore do not gate
new hard violations. The saved incident log proves the script has caught a real
new hard violation (`docs/ops/CICDARCHISSUE.txt:553-565`), but `allow_failure`
allowed the pipeline to continue until a later task repaired it.

Recommended shape:

- Make all-feature Clippy blocking on MRs into the default branch, the default
  branch, and release tags.
- Split architecture handling into a blocking changed-line/hard-violation
  ratchet for MRs and a scheduled full-tree debt report. Existing warnings need
  not block if the script's exit code remains reserved for regressions.
- Version the debt baseline or emit machine-readable counts so warning totals
  cannot increase silently.
- Revisit the MSRV job: primary and MSRV templates intentionally use the exact
  same Rust 1.96.1 image. Today `rust-msrv-check` duplicates
  `rust-check-default`. Either treat the normal exact-toolchain check as the
  blocking MSRV proof and replace the duplicate with a scheduled current-stable
  compatibility check, or make primary and MSRV genuinely distinct.

### P1.2 Replace per-job bootstrap drift with reviewed CI images

Every shell/Python job runs mutable Debian package installation through
`.gitlab/scripts/bootstrap-shell.sh:4-21`; every Rust job repeats a larger apt
bootstrap through `.gitlab/scripts/bootstrap-rust.sh:4-21`. Python dependencies
are version-pinned but not hash-locked. `ci-config` separately downloads PyYAML
on every run.

This has already caused source-independent CI churn: pipelines #2607, #2608,
#2609, #2612, and #2613 failed because Bookworm ShellCheck 0.9.0 disagreed with
the local 0.11.0 baseline (`docs/ops/AGENT_GOALS_2.1.0.0.md:98-105`). The saved
job log spent about 12 seconds installing the shell environment before a
six-second boundary check and confirms runner 19.2.2 plus ShellCheck 0.9.0
(`docs/ops/CICDARCHISSUE.txt:1,32-44,80-114,233,558`). The CI runbook also
records Docker Hub anonymous pull-rate failures.

Recommendations:

- Build small lint and Rust CI images containing exact ShellCheck, PyYAML,
  compiler components, protobuf, sccache, and required native packages.
- Build those images on a protected maintenance pipeline, scan them, emit SBOMs,
  mirror them to the project registry, and pin consumers by digest.
- Hash-lock Python wheels (`--require-hashes` or an equivalent generated lock)
  and audit the lock. Keep application requirements and CI constraints linked by
  a generated consistency check.
- If dynamic apt remains temporarily, pin a dated snapshot and log exact package
  versions. Do not use insecure repository fallbacks.
- Mirror Docker Hub/GitHub release dependencies to remove documented rate-limit
  and availability failures.

### P1.3 Add reports and pipeline telemetry before optimizing coverage away

No current job declares `artifacts:reports`, JUnit, coverage, or performance
telemetry. Failures are visible only in raw logs, and the plan's warm-cache p95
of 30 minutes cannot be evaluated from committed evidence.

Add:

- JUnit output for Rust, Python, shell harnesses, browser tests, and standalone
  crate tests, with explicit test/skip counts.
- A measured coverage baseline for core Rust plus maintained Python, excluding
  generated/vendor code. Publish first; set ratcheting thresholds only after the
  baseline is trusted.
- `sccache` hit/miss, cache size, checkout/bootstrap/compile/test durations,
  queue time, disk high-water mark, retry reason, and artifact sizes.
- A nightly summary with p50/p95 and source-failure versus runner-failure
  classification. Pipeline #2604 demonstrates why `ENOSPC` must not be reported
  as a code regression.
- Retention limits for reports and artifacts.

Do not tune job coverage or cache complexity until these measurements identify
the actual critical path.

### P1.4 Classify and test every standalone deliverable

There are 26 tracked non-vendor `Cargo.lock` files at the audited revision. Not
all are current deliverables, but CI has no canonical inventory that says which
are production, experimental, fixture, mirror, or retired. Core metadata checks
only `ic/Cargo.lock`; direct CI execution covers a small subset such as XMPP,
WeeChat, and Cavepony. Newer deliverables such as `projects/voice-sidecar` are
not named anywhere under `.gitlab/`.

Create one reviewed manifest of buildable units with owner, status, manifest,
lockfile, targets, required features, security policy, and trigger paths. CI
validation should fail when a new tracked lockfile is unclassified. Then:

- Run locked metadata for every active unit.
- Run format/check/test through a conservative path-triggered matrix for active
  sidecars, bridges, tools, channels, and worker bridge crates.
- Include shared WIT, registry JSON, vendor configuration, CI helpers, and common
  path dependencies in each unit's trigger set.
- Run advisory/license/source policy against every deployable lockfile, not only
  the core workspace.
- Build the strict registry-driven WASM set once and pass exact artifacts to
  compatibility, browser, package, and staging jobs.
- Keep fuzz workspaces and historical duplicate repositories scheduled or
  explicitly exempt with a reason rather than accidentally treating them as
  shipped artifacts.

### P1.5 Add hermetic browser/frontend coverage using one binary artifact

The maintained browser suite is absent from CI. The legacy E2E fixture still
runs a full debug `cargo build` when its binary is stale
(`ic/tests/e2e/conftest.py:198-207`), while the Engine V2 fixture correctly
requires `LUNARWING_E2E_BINARY` (`ic/tests/e2e/conftest.py:212-228`). This both
violates the repository's no-full-debug-build discipline and can rebuild the
same daemon per browser job.

Recommended flow:

1. Build one bounded libSQL test/release-profile daemon artifact.
2. Build strict WASM artifacts once.
3. Pass both to hermetic Playwright jobs using mock LLM/MCP services, temporary
   HOME/state, random ports, and no live providers.
4. Run gateway and onboarding-web browser suites separately for attribution.
5. Add a cheap syntax gate for maintained JavaScript before the browser tier.
6. Keep genuinely network-dependent ClawHub/clipboard scenarios scheduled and
   separate.

The browser job must fail on zero collected tests, unexpected skips, subprocess
leaks, or an attempt to build its own daemon.

### P1.6 Expand CI policy validation beyond syntax and pin parity

`validate_config.py` is valuable but currently cannot catch the highest-risk
findings in this review. It passes while:

- worker publication has no protected-ref gate,
- release tags skip the full matrix,
- `WORKER_IMAGE_TAG` is stale,
- no `resource_group` protects moving tags, and
- build/test/report contracts are incomplete.

Add unit-tested policy assertions for required job names, full-validation
contexts, protected publication rules, non-interruptible promotion,
`resource_group`, artifact/report expiry, cache trust, and centralized worker
versions. Keep GitLab CI Lint as a separate merged-config check; generic YAML
parsing cannot model GitLab rule evaluation.

Pipeline-supplied variables can also override image and runner-tag variables.
Before protected release work exists, restrict who may provide pipeline
variables and ensure release jobs cannot be redirected to arbitrary images or
runner tags. Hard-code trust-sensitive release runner selection or source it
only from protected maintainer-controlled configuration.

## Priority 2 — efficiency, drift control, and developer feedback

### P2.1 Use shallow history by default

`.gitlab/ci/defaults.yml:12-15` globally sets `GIT_DEPTH: "0"`. Full history is
necessary for the scheduled history-secret scan, but not for format, metadata,
compilation, most tests, or current-tree Gitleaks. Version policy already fetches
an exact missing base SHA. Panic and boundary helpers can adopt the same bounded
fetch behavior.

Use a modest shallow default and override to full history only for
`secret-history`. Test long-lived MRs and force-pushes before rollout. The saved
warm-runner log fetched in roughly one second, so this is lower priority than
disk safety and should be justified with clean-runner data.

### P2.2 Reduce repeated checkout/bootstrap overhead safely

A full MR currently fans out into many small validation jobs, each checking out
a repository that contains 1.2 GiB of vendor source and often repeating apt or
pip setup. Separate jobs improve attribution, but sub-minute scripts do not
always justify independent checkout, image pull, and cache upload costs.

After telemetry exists:

- Consolidate the fastest static checks into one sectioned `validate-lightweight`
  job while retaining clear per-check log headings and failure codes.
- Keep security tools requiring a different image separate.
- Make caches pull-only in jobs that should not publish cache state.
- Add a conservative docs-only path that still runs CI policy, Markdown links,
  secret detection, spelling/format checks, and release-note validation, while
  skipping Rust compilation only when no code/config/build inputs changed.
- Use `rules:changes` only from a centrally tested ownership map. A missed shared
  path is worse than a slower pipeline.
- Review timeout retries: retry infrastructure failures, but do not automatically
  spend another hour on deterministic test or job-timeout failures.

### P2.3 Centralize version metadata and automate drift detection

Current drift is already visible:

- `.gitlab/ci/containers.yml:38` defaults worker image tags to `v2.0.9.0` while
  the core manifest is 2.1.0 and this checklist is v2.1.0.0.
- `docs/ops/GITLAB_CONTAINER_REGISTRY.md:152-183` mixes v2.0.8.0 and v2.0.9.0
  examples.
- The validator does not check `WORKER_IMAGE_TAG`, OpenCode's source ref, or
  Kimi's CI build argument against their canonical declarations.

Use one machine-readable release/worker version source and generate or validate
all consumers. Add a scheduled dependency report for Rust lockfiles, CI images,
cargo-deny, sccache, BuildKit, Python locks, npm/Bun locks, and worker upstream
revisions. Automation should open reviewable MRs and run vendor refresh; it
should not auto-merge dependency or image changes.

### P2.4 Add ownership and change-control guardrails

No project `CODEOWNERS` file exists at the audited revision. Add real maintainers
for `.gitlab/**`, release/package scripts, worker Dockerfiles, registry metadata,
security policy, and `ic/scripts/lunarwing-mt-admin.sh`. If the GitLab CE version
cannot enforce approval rules, retain protected `master`/`v*` refs and document a
Maintainer review requirement.

Record the exact GitLab server and Runner versions, runner executor/protection,
cache separation, network policy, disk/RAM limits, and pipeline-variable
restriction in activation evidence. The saved log establishes Runner 19.2.2,
but the server API was not available anonymously during this audit.

## Release and CD sequence — deliberately later

The current mt-admin source confirms that `upgrade-tenant` still:

1. backs up PostgreSQL unless explicitly bypassed,
2. fetches and resolves a requested branch/tag/commit,
3. stops the tenant,
4. checks out that commit,
5. rebuilds the daemon, workers, bridge, and WASM in the tenant checkout,
6. renders/patches configuration, and
7. starts the tenant and tells the operator to verify status
   (`ic/scripts/mt-admin-lib/04-tenant-lifecycle.sh:1171-1272`).

That path is init-aware and resolves the fetched ref to an exact commit before
checkout, which is good, but it does not deploy the artifact tested by CI. Do
not connect it directly to a production runner.

The safe sequence is:

1. **Artifact capability in mt-admin:** install to a versioned directory; verify
   signature, digest, package manifest, WIT/registry compatibility, ownership,
   and runtime dependencies before stopping a tenant.
2. **Atomic activation:** switch a stable symlink/pointer only after extraction
   and preflight. Preserve the previous complete daemon+WASM+unit release.
3. **Health transaction:** start, enforce deep readiness through mt-admin, and
   automatically restore the prior release on failure. Bind database backup and
   migration state to the release record.
4. **Package CI:** build once on native x86_64/aarch64, emit checksums, SBOM,
   provenance, and signatures, then test the extracted package without a source
   checkout or compiler.
5. **Real staging:** install the same digest on both systemd user-manager and
   OpenRC hosts; rehearse rollback and database restore.
6. **Promotion:** promote RC bytes without rebuilding; attach immutable package
   links and evidence to the GitLab release.
7. **Protected CD:** manual canary, observation window, serialized tenant
   batches, stop-on-first-failure, and explicit rollback. Every lifecycle action
   must go through mt-admin.

No production secret, host mount, Docker socket, tenant route, or privileged
runner should ever be reachable from an MR pipeline.

```text
MR / branch (untrusted, no secrets)
  validate-lightweight + secret-current
          |
          +-- Rust feature/test-target checks
          +-- Python + shell suites
          +-- changed standalone/WASM matrix
          +-- Clippy + architecture ratchet
          +-- hermetic browser tests
          `-- dependency policy

protected default branch
  complete MR gate
          +-- measured coverage / scheduled compatibility
          `-- immutable worker-image candidates -> smoke -> scan -> SBOM

protected RC tag
  complete release gate for exact SHA
          `-- native packages -> verify extracted packages -> sign/SBOM
```

## Recommended implementation order

1. Correct runner disk budgeting and add cache/disk telemetry.
2. Restrict worker publication; introduce immutable candidate then protected
   promotion.
3. Replace Kaniko and make all worker image inputs reproducible.
4. Make protected tags run the complete gate.
5. Repair PostgreSQL-only test-target compilation, then gate every feature shape
   and add disposable pgvector integration.
6. Pin/mirror CI tool environments; eliminate ShellCheck/apt/pull-rate drift.
7. Make Clippy and the MR architecture ratchet blocking.
8. Add JUnit, coverage baseline, cache statistics, and p95 reporting.
9. Add the classified standalone/WASM matrix and hermetic browser jobs.
10. Apply shallow/history and job-consolidation optimizations based on measured
    data.
11. Implement package installation/rollback in mt-admin before release
    automation, then prove both-init staging before any production CD.

Steps 1–10 improve CI without granting production access. Step 11 is a separate,
high-risk program and should remain independently reviewable and revertible.

## Success metrics

Track these for at least several default-branch and scheduled runs before
calling the next phase complete:

- Required MR warm-cache duration p50/p95 and queue time; p95 target remains
  at most 30 minutes.
- Checkout, bootstrap, compile, test, cache download/upload, and artifact time
  separately.
- sccache hit rate and size by job; runner disk high-water mark with no ENOSPC.
- Test count, unexpected skip count, flaky retry count, and time-to-diagnosis.
- Full release gate present on 100% of protected RC/final tag pipelines.
- Zero registry writes from unprotected refs and zero mutable-tag races.
- Zero unclassified active lockfiles/deliverables.
- Dependency, image, and scanner pin age with an assigned owner.
- Candidate package/image digest equals staged and promoted digest.
- Successful install and rollback of the same package on systemd user-manager
  and OpenRC staging.

## Bottom line

The next CI/CD investment should harden what LunarWing already publishes and
make current gates trustworthy. The most urgent concrete defects are unsafe
publication topology, unreproducible worker images, incomplete release-tag
rules, PostgreSQL-only test-target compile failures, and an impossible
80-GB-cache/25-GB-runner disk contract. Once those are fixed and measured,
coverage, standalone matrices, browser tests, and package promotion can be added
without increasing operational risk. Production CD remains correctly deferred
until mt-admin can activate and roll back immutable CI artifacts on both
supported init systems.
