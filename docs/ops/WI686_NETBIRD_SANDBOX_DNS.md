# WI#686 — NetBird DNS and access from a fresh tenant sandbox

- Date: 2026-11-15
- Branch: `rarity/kimi-wi686-20261115-1000`
- Work item: https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/686

## Scope

Create a fresh multi-tenant LunarWing tenant named `netbirddnstester` and test
outbound network access from its real generic shell sandbox to hosts on the
existing NetBird overlay. Verify both NetBird MagicDNS name resolution and
connections to the resolved service. If the first configuration fails, test
supported configuration alternatives and record each result here.

The primary target is `cotterhomelab3.netbird.selfhosted`, whose TensorZero
HTTP listener is on port 3000. A second connected overlay peer will be used as
a resolution/control target where useful. No tenant credentials, NetBird setup
keys, gateway tokens, or environment-file contents belong in this report.

## Environment and initial state

- Gentoo/OpenRC development host with rootless Podman and 18 available CPUs.
- Host NetBird client/daemon: 0.74.2; management, signal, and relay connected.
- Host NetBird DNS: `/etc/resolv.conf` is generated by NetBird and uses the
  host's overlay resolver; `netbird.selfhosted` is the search domain.
- Host baseline before tenant creation: both
  `cotterhomelab3.netbird.selfhosted:3000/openai/v1/models` and its numeric
  NetBird IPv4 endpoint answered HTTP 404, proving name resolution and overlay
  reachability independently of LunarWing.
- `netbirddnstester` was absent from the tenant registry before this run.
- Fresh Linux tenants default to `SANDBOX_NETWORK=proxy-enforced`. That mode
  uses `--network none` and a public-only allowlist proxy, so it is not
  expected to provide direct NetBird DNS or private-overlay access.

## Test matrix and results

### 1. Fresh tenant provisioning

`mt-admin add-tenant netbirddnstester --no-health --no-ssh
--no-weechat-bootstrap --llm-base-url http://100.88.232.146:3000/openai/v1
--llm-model tensorzero::function_name::lunarwing` completed successfully. The
tenant received ports 10020–10029 and the managed `lunarwing-sandbox:latest`
image. WeeChat was disabled; no external workers were selected. The required
release daemon build is running through `mt-admin build-tenant` with 18 jobs.

### 2. Rootless-runtime diagnostic (not yet the daemon sandbox)

Before the daemon build completed, this direct one-shot container established
the tenant runtime's baseline without any LunarWing proxy or sandbox policy:

```bash
sudo -u netbirddnstester XDG_RUNTIME_DIR=/run/user/1005 \
  podman run --rm --entrypoint sh lunarwing-sandbox:latest -c \
  'cat /etc/resolv.conf; getent ahostsv4 cotterhomelab3.netbird.selfhosted;
   getent hosts cotterhomelab3.netbird.selfhosted sweetiebot.netbird.selfhosted;
   curl --max-time 10 http://cotterhomelab3.netbird.selfhosted:3000/openai/v1/models;
   curl --max-time 10 http://100.88.232.146:3000/openai/v1/models'
```

Observed:

- `/etc/resolv.conf` contained `search netbird.selfhosted`, runtime resolver
  `169.254.1.1`, and NetBird resolver `100.88.145.188`.
- `getent ahostsv4 cotterhomelab3.netbird.selfhosted` returned
  `100.88.232.146` (exit 0).
- `getent hosts` returned NetBird IPv6 addresses for both `cotterhomelab3` and
  `sweetiebot` (exit 0).
- HTTP by MagicDNS name returned **404** from the target's NetBird IPv6
  address; HTTP by numeric NetBird IPv4 also returned **404**. As on the host,
  the expected unauthenticated `/openai/v1/models` response is evidence of a
  completed HTTP exchange, not an application-level models API success.
- A follow-up probe of `/health` on the same name and port returned **HTTP 200**
  both from the host and from the tenant's one-shot container. The container
  connected to the target's NetBird IPv6 address. Subsequent sandbox tests use
  this positive health response instead of relying on the 404 alone.

This proves the fresh tenant's ordinary rootless-container DNS and overlay
path work. A second mechanism probe with `podman run --network none` returned
`getent` exit 2 and curl exit 6 (`Could not resolve host`, HTTP 000). This
isolates the effect of removing the network namespace, but it is still not a
substitute for the real daemon shell-tool test: `proxy-enforced` also inserts
its Unix-relay HTTP proxy and applies a public-only destination policy. That
end-to-end test follows after the build.

### 3. Untouched real sandbox: `proxy-enforced`, empty extra-domain list

The release daemon and companion bridge builds completed in 9m14s and 8m20s.
`mt-admin start-tenant netbirddnstester` succeeded; gateway health returned
HTTP 200. Before this probe, `lunarwing config get
sandbox.extra_allowed_domains` returned `[]`, and the tenant's
`SANDBOX_NETWORK` was `proxy-enforced`.

A fresh gateway thread asked the agent to run one fixed command through the
`shell` tool. The shell approval was accepted once. Its result had
`"sandboxed":true`, `"success":true`, and `"truncated":false`. The command was:

```sh
printf 'RESOLV_CONF\n'; cat /etc/resolv.conf
printf 'DNS_A\n'; getent ahostsv4 cotterhomelab3.netbird.selfhosted 2>&1
printf 'DNS_A_RC=%s\n' "$?"
printf 'DNS_BOTH\n'; getent hosts cotterhomelab3.netbird.selfhosted sweetiebot.netbird.selfhosted 2>&1
printf 'DNS_BOTH_RC=%s\n' "$?"
printf 'PROXY_HEALTH\n'
curl -sS --max-time 8 -w '\nPROXY_HTTP=%{http_code} REMOTE=%{remote_ip}\n' \
  http://cotterhomelab3.netbird.selfhosted:3000/health 2>&1
printf 'PROXY_RC=%s\n' "$?"
printf 'DIRECT_HEALTH\n'
curl --noproxy '*' -sS --max-time 8 -w '\nDIRECT_HTTP=%{http_code} REMOTE=%{remote_ip}\n' \
  http://cotterhomelab3.netbird.selfhosted:3000/health 2>&1
printf 'DIRECT_RC=%s\n' "$?"
```

Observed in the real sandbox:

- `/etc/resolv.conf` contained only public resolvers `1.1.1.1` and `1.0.0.1`.
- Both `getent` calls returned exit 2 with no addresses.
- The proxied health request returned **HTTP 403** with `sandbox-proxy denied:
  host 'cotterhomelab3.netbird.selfhosted' not in allowlist`.
- Direct curl returned exit 6, **HTTP 000**, `Could not resolve host`.
- No files were modified by the probe. The managed image's `/etc/hosts` was
  also checked separately and contained no NetBird name mappings, so the
  positive runtime lookups above were DNS, not static-host overrides.

**Result:** the untouched secure default does not resolve or reach the fleet
MagicDNS target. This is the expected network-none and allowlist boundary, not
a failure of NetBird or of the tenant's underlying container runtime. Raw
non-secret gateway event evidence is in `/tmp/lw686-default.json` on the test
host.

### 4. `proxy-enforced` plus one allowlisted MagicDNS host

The first configuration attempt used:

```bash
lunarwing config set sandbox.extra_allowed_domains \
  '["cotterhomelab3.netbird.selfhosted"]'
```

After a tenant restart, the identical probe still returned the original
allowlist denial. This was a **settings-scope mistake**, not a network result:
`lunarwing config set` writes the hard-coded `default` user scope
(`ic/src/cli/config.rs`), while this tenant resolves
`LUNARWING_OWNER_ID=netbirddnstester`. `config get` showed the value in the
wrong scope, and the daemon correctly ignored it.

The misplaced `default`-scope row was reset. The authenticated gateway API was
then used to set the same value in the daemon's actual owner scope:

```http
PUT /api/settings/sandbox.extra_allowed_domains
Content-Type: application/json

{"value":["cotterhomelab3.netbird.selfhosted"]}
```

The API returned 204, GET returned the expected value, and the tenant was
restarted again. The repeated real-sandbox probe showed:

- Resolver contents and both `getent` failures were unchanged.
- The proxy denial changed to **HTTP 403** with `sandbox-proxy denied:
  proxy-enforced forbids non-public destination addresses`.
- Direct curl still returned exit 6 and **HTTP 000**.
- The shell result again had `"sandboxed":true` and `"truncated":false`.

**Result:** the hostname allowlist and public-address policy are independent.
Allowlisting the MagicDNS name is not enough: enforced mode intentionally
rejects NetBird's CGNAT/ULA destinations and network-none prevents direct DNS.
Event captures are `/tmp/lw686-enforced-allowlisted.json` (wrong-scope attempt)
and `/tmp/lw686-enforced-owner-allowlist.json` (corrected scope).
