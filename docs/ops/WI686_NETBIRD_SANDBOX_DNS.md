# WI#686 — NetBird DNS and access from a fresh tenant sandbox

Date: 2026-11-15  
Branch: `rarity/kimi-wi686-20261115-1000`  
Work item: https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/686

## Scope

Create a fresh multi-tenant LunarWing tenant named `netbirddnstester` and test
outbound network access from its real generic shell sandbox to hosts on the
existing NetBird overlay. Verify both NetBird MagicDNS name resolution and
connections to the resolved service. If the first configuration fails, test
supported configuration alternatives and record each result here.

The primary target is `cotterhomelab3.netbird.selfhosted`, whose TensorZero
HTTP listener is on port 3000. A second connected overlay peer will be used as
a resolution/control target where useful. No tenant credentials, NetBird setup
keys, gateway tokens, or environment-file contents belong in this report.

## Environment and initial state

- Gentoo/OpenRC development host with rootless Podman and 18 available CPUs.
- Host NetBird client/daemon: 0.74.2; management, signal, and relay connected.
- Host NetBird DNS: `/etc/resolv.conf` is generated by NetBird and uses the
  host's overlay resolver; `netbird.selfhosted` is the search domain.
- Host baseline before tenant creation: both
  `cotterhomelab3.netbird.selfhosted:3000/openai/v1/models` and its numeric
  NetBird IPv4 endpoint answered HTTP 404, proving name resolution and overlay
  reachability independently of LunarWing.
- `netbirddnstester` was absent from the tenant registry before this run.
- Fresh Linux tenants default to `SANDBOX_NETWORK=proxy-enforced`. That mode
  uses `--network none` and a public-only allowlist proxy, so it is not
  expected to provide direct NetBird DNS or private-overlay access.

## Test matrix and results

### 1. Fresh tenant provisioning

`mt-admin add-tenant netbirddnstester --no-health --no-ssh
--no-weechat-bootstrap --llm-base-url http://100.88.232.146:3000/openai/v1
--llm-model tensorzero::function_name::lunarwing` completed successfully. The
tenant received ports 10020–10029 and the managed `lunarwing-sandbox:latest`
image. WeeChat was disabled; no external workers were selected. The required
release daemon build is running through `mt-admin build-tenant` with 18 jobs.

### 2. Rootless-runtime diagnostic (not yet the daemon sandbox)

Before the daemon build completed, this direct one-shot container established
the tenant runtime's baseline without any LunarWing proxy or sandbox policy:

```bash
sudo -u netbirddnstester XDG_RUNTIME_DIR=/run/user/1005 \
  podman run --rm --entrypoint sh lunarwing-sandbox:latest -c \
  'cat /etc/resolv.conf; getent ahostsv4 cotterhomelab3.netbird.selfhosted;
   getent hosts cotterhomelab3.netbird.selfhosted sweetiebot.netbird.selfhosted;
   curl --max-time 10 http://cotterhomelab3.netbird.selfhosted:3000/openai/v1/models;
   curl --max-time 10 http://100.88.232.146:3000/openai/v1/models'
```

Observed:

- `/etc/resolv.conf` contained `search netbird.selfhosted`, runtime resolver
  `169.254.1.1`, and NetBird resolver `100.88.145.188`.
- `getent ahostsv4 cotterhomelab3.netbird.selfhosted` returned
  `100.88.232.146` (exit 0).
- `getent hosts` returned NetBird IPv6 addresses for both `cotterhomelab3` and
  `sweetiebot` (exit 0).
- HTTP by MagicDNS name returned **404** from the target's NetBird IPv6
  address; HTTP by numeric NetBird IPv4 also returned **404**. As on the host,
  the expected unauthenticated `/openai/v1/models` response is evidence of a
  completed HTTP exchange, not an application-level models API success.
- A follow-up probe of `/health` on the same name and port returned **HTTP 200**
  both from the host and from the tenant's one-shot container. The container
  connected to the target's NetBird IPv6 address. Subsequent sandbox tests use
  this positive health response instead of relying on the 404 alone.

This proves the fresh tenant's ordinary rootless-container DNS and overlay
path work. It does not by itself prove the real shell sandbox works: the
`proxy-enforced` sandbox deliberately removes container networking and applies
a public-only destination policy. That end-to-end test follows after the build.
