# WI#686 — NetBird DNS and access from a fresh tenant sandbox

Date: 2026-11-15  
Branch: `rarity/kimi-wi686-20261115-1000`  
Work item: https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/686

## Scope

Create a fresh multi-tenant LunarWing tenant named `netbirddnstester` and test
outbound network access from its real generic shell sandbox to hosts on the
existing NetBird overlay. Verify both NetBird MagicDNS name resolution and
connections to the resolved service. If the first configuration fails, test
supported configuration alternatives and record each result here.

The primary target is `cotterhomelab3.netbird.selfhosted`, whose TensorZero
HTTP listener is on port 3000. A second connected overlay peer will be used as
a resolution/control target where useful. No tenant credentials, NetBird setup
keys, gateway tokens, or environment-file contents belong in this report.

## Environment and initial state

- Gentoo/OpenRC development host with rootless Podman and 18 available CPUs.
- Host NetBird client/daemon: 0.74.2; management, signal, and relay connected.
- Host NetBird DNS: `/etc/resolv.conf` is generated by NetBird and uses the
  host's overlay resolver; `netbird.selfhosted` is the search domain.
- Host baseline before tenant creation: both
  `cotterhomelab3.netbird.selfhosted:3000/openai/v1/models` and its numeric
  NetBird IPv4 endpoint answered HTTP 404, proving name resolution and overlay
  reachability independently of LunarWing.
- `netbirddnstester` was absent from the tenant registry before this run.
- Fresh Linux tenants default to `SANDBOX_NETWORK=proxy-enforced`. That mode
  uses `--network none` and a public-only allowlist proxy, so it is not
  expected to provide direct NetBird DNS or private-overlay access.
