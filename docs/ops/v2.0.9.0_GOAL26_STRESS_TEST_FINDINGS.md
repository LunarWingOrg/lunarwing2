## Findings

### Finding 1 — concurrent same-document appends return 500 after committing (medium)

`Workspace::append` (`ic/src/workspace/mod.rs:948`) commits the content
append atomically (`append_document`, `ic/src/workspace/repository.rs:158`,
single `UPDATE ... content || sep || new`), then re-chunks in a **separate**
transaction (`reindex_document` → `replace_chunks`,
`ic/src/workspace/repository.rs:534`: `DELETE FROM memory_chunks ...` then
re-INSERT). Under 8-way concurrent appends to one document, ~58% of requests
failed with HTTP 500 `Document chunking failed: Insert failed: db error`
**even though the content append had already committed** (all 50 concurrent
appends were present in the final document; chunks converged to the last
successful reindex). Hazards: clients cannot distinguish committed from
failed appends, so retries silently duplicate content; the underlying
PostgreSQL error is swallowed and only the literal text `db error` reaches
the client, hampering diagnosis. Fix direction: route `append` through the
existing atomic `update_document_and_replace_chunks` (already used by
`write()`), or serialize reindexing per document; propagate the real DB
error text.

### Finding 2 — memory HTTP API accepts `..` path segments (low)

`normalize_path` (`ic/src/workspace/mod.rs:2219`) only trims leading/trailing
slashes and collapses duplicates. `POST /api/memory/write` with
`path = "../escape.md"` stored a document literally named `../escape.md`
plus a `..` directory entry in the tree; `path = "/etc/passwd"` normalized to
`etc/passwd`. There is no filesystem escape (workspace paths are virtual,
DB-backed), but traversal-shaped entries pollute the virtual hierarchy and
break consumers that assume normalized relative paths. Fix direction: reject
or resolve `..` segments at the workspace boundary.

### Finding 3 — ws_adapter WebSocket heartbeat is incompatible with WeeChat 4.10.0's api relay (medium)

The adapter connects with aiohttp `heartbeat=25`
(`lunarwing_weechat_wss/weechat_relay/ws_adapter.py:210`). WeeChat 4.10.0
(relay api v0.6.0) never answers protocol-level WS PINGs — verified by direct
probe (no PONG within 15 s) — so aiohttp tears down the socket every
~25-37 s: the tenant's adapter logged **110 reconnects in ~85 minutes** with
`/api/health` reporting `last_disconnect: {type: "error", reason: "No PONG
received after 12.5 seconds"}`. The work-item-#78 resilience machinery
(reconnect reason surfacing, `recover_after_connect` backfill, outbox)
masked all message loss — S6 delivered 40/40 replies during the churn — but
the constant reconnect loop wastes cycles and spams logs. Fix direction:
disable the WS heartbeat (or make it opt-in) and rely on the existing
sync/event flow, or use an application-level keepalive the relay answers.

### Finding 4 — gateway chat send without `thread_id` silently drops the reply (low)

`POST /api/chat/send` without `thread_id` is accepted and the turn is
processed, but response delivery fails with ERROR `Channel gateway is
missing a routing target: respond() requires a thread_id on the incoming
message` — 15 occurrences in the daemon journal during the first S5 attempt.
The client never sees the reply. Fix direction: reject such sends with 400
(or route them to an implicit default thread) so the contract is explicit.

### Finding 5 — startup broadcast always errors on the weechat channel (cosmetic)

On every boot the daemon fans a 113-char broadcast (`user_id=default`) out to
all channels; the WeeChat WASM channel rejects it (`WeeChat proactive target
must use irc.<network>.<nick-or-channel>`) and the DarkIRC channel errors
when its daemon is absent. Harmless but noisy; consider suppressing
proactive broadcast on channels with no qualified target.

## Environment notes (not product bugs)

- The first S5 run failed 30/30 because the initial mock LLM replied with
  plain JSON while the Engine V2 path always requests SSE (`"stream": true`,
  rig-core streaming client); after adding SSE to the mock, 30/30 passed.
- Unprovisioned-but-active channels (darkirc, xmpp, multica) produced ~217
  background ERROR log lines over the run (connection retries to absent
  daemons); expected on a tenant without those daemons, but it inflates logs.
- `/relay del api` removes the WeeChat listener but keeps existing WS
  connections alive, so the S7 outbox flush needed a new `/api/input` to
  trigger; queued bodies addressing a buffer that did not survive the WeeChat
  restart were 400-dropped per design (non-retryable 4xx).
