## Findings

### Finding 1 (low) — memory HTTP API accepts `..` path segments (still present)

`POST /api/memory/write` with `path = "../escape.md"` returned 200 and
stored a document literally named `../escape.md`; `/etc/passwd`
normalized to `etc/passwd`. No filesystem escape exists (workspace paths
are virtual, DB-backed), but traversal-shaped entries pollute the virtual
tree. Same as first-attempt Finding 2.
Fix direction: reject or resolve `..` segments in
`Workspace::normalize_path` (`ic/src/workspace/mod.rs`).

### Finding 2 (medium) — ws_adapter heartbeat incompatible with WeeChat 4.10.0 relay (still present)

The adapter connects with aiohttp `heartbeat=25`
(`lunarwing_weechat_wss/weechat_relay/ws_adapter.py:446`). WeeChat
4.10.0's api relay never answers protocol-level WS PINGs, so aiohttp
tears the socket down every ~44-90 s: **19 "No PONG received after 12.5
seconds" reconnects in ~20 min** (daemon journal), visible in
`/api/health` as `last_disconnect: {type: error, reason: "No PONG
received after 12.5 seconds"}`. Identical to goal-25 F2 / first-attempt
Finding 3. **No message loss** — H3 delivered 40/40 during the churn —
because the item-1/item-29 machinery (reconnect backfill from persisted
watermarks + journal) masks it. Still: wasted cycles, log spam, and
flapping `ws_connected` for health consumers.
Fix direction: disable the WS heartbeat (or make it opt-in) and rely on
the sync/event flow, or use an application-level keepalive the relay
answers.

### Finding 3 (low) — gateway chat send without `thread_id` silently drops the reply (still present)

`POST /api/chat/send` without `thread_id` returns 202 and the turn is
processed (the mock LLM was called, tools ran), but delivery fails with
ERROR `Channel gateway is missing a routing target: respond() requires a
thread_id on the incoming message` (exactly 1 occurrence, matching the
probe). The client never sees the reply. Same as first-attempt Finding 4.
Fix direction: reject such sends with 400 (or route to an implicit
default thread) so the contract is explicit.

### Finding 4 (cosmetic) — startup broadcast always errors on unqualified channels (still present)

Every boot fans a broadcast to all channels; the WeeChat WASM channel
rejects it (`WeeChat proactive target must use
irc.<network>.<nick-or-channel>`) and multica errors
(`channel does not support broadcast`). Harmless but noisy. Same as
first-attempt Finding 5.
Fix direction: suppress proactive broadcast on channels with no
qualified target.

### Finding 5 (low) — `/api/memory/search` returns document UUIDs in `path` (NEW on this branch)

`memory_search_handler` (`ic/src/channels/web/handlers/memory.rs:222`)
maps `SearchHit.path = r.document_id.to_string()` instead of
`r.document_path` — verified live: a search for "ledger" returned hits
whose `path` was a bare UUID (e.g. `dc9ae088-…` for `AGENTS.md`,
`0be3b286-…` for the ledger doc), and those UUIDs are not readable via
`/api/memory/read?path=`. Search content/score are correct; only the
path field is wrong, but it breaks any consumer that follows a search
hit to its document. `SearchResult.document_path` already exists and
holds the right value (`ic/src/workspace/search.rs:137`) — one-field fix.

## Notes (observed behavior, not bugs)

1. **`memory_write` tool is rate-limited at 20/min, 200/hour**
   (`ic/src/tools/builtin/memory.rs:644`). C1's 30 fast sequential turns
   (≈30 writes/min) had 12 writes rejected with
   `Tool 'memory_write' is rate limited. Try again in Ns.` — the tool
   result carries the error, so the agent *knows* the write failed.
   Dispatch→DB fidelity for accepted writes was 100% (verified against
   Postgres: 33/33 `memory_write` ActionResults, 12 rate-limit errors,
   21 landed = exactly the 21 markers found in the daily doc). This is
   the intentional write-tool limiter doing its job, but it means a
   chatty agent doing >20 memory writes/min will lose writes unless it
   retries.
2. Engine V2 writes per-thread state into the workspace
   (`engine/.runtime/threads/active/*.json`, ~80-93 KB each); these
   documents are searchable via the memory API and inflate search hit
   space for marker-like strings.
3. Unprovisioned-but-active channels (darkirc, xmpp, multica) produced
   most of the 62 background ERROR lines (connection retries to absent
   daemons); expected on a tenant without those daemons.
4. `/relay del api` removes the WeeChat listener but keeps existing WS
   connections alive; H5's outbox flush needed a fresh `/api/input` to
   trigger (known design; non-retryable 4xx bodies are dropped by
   design).
5. The tenant's WeeChat needed a manual `/connect stress` after tenant
   restart because the test server was added without `autoconnect` —
   harness choice, not a product defect. Pairing survived the restart
   (sender allowlist persisted).
