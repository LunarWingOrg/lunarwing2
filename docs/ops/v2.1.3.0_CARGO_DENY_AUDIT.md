## Conclusion

`ic/deny.toml` currently ignores **eight** advisories. All eight were
re-verified against the live RustSec advisory database and against crates.io
on 2026-09-26. **None of them can be removed for v2.1.3.0** — every ignore
is pinned by an upstream constraint that is outside LunarWing's control
today:

- the `libsql 0.6.0` legacy TLS chain pins `rustls-webpki 0.102.8` and
  `h2 0.3.27` (five of the eight);
- `russh 0.62.6` pins `rsa 0.10.0-rc.18`, and even the newest `russh 0.63.3`
  still requests the same unpatched `rsa` (one of the eight);
- the vendored `libsignal-protocol` path dep pins `failure 0.1.8` (two of
  the eight).

What was changed in this audit: the `deny.toml` ignore entries were
rewritten so each one is self-contained — no bare string entries, no
"same as X" boilerplate — and each records the upstream version pin that
keeps it blocked plus the re-verification date. No advisory was added or
removed; the ignore count is unchanged at eight.

Non-`ignore` settings (unchanged, verified correct):

| Section | Setting | Value |
|---|---|---|
| `advisories` | `unmaintained` | `"workspace"` |
| `advisories` | `yanked` | `"deny"` |
| `licenses`  | `version` | `2` |
| `licenses`  | `allow` | 17 OSI/FSF-approved licenses (AGPL-3.0-or-later, MIT, Apache-2.0, Apache-2.0 WITH LLVM-exception, BSD-2/3-Clause, ISC, Unicode-3.0, Unicode-DFS-2016, OpenSSL, Zlib, MPL-2.0, 0BSD, BSL-1.0, CC0-1.0, Unlicense, CDLA-Permissive-2.0) |
| `bans`      | `multiple-versions` | `"allow"` (required: libsql legacy chain forces duplicate `rustls`, `rustls-webpki`, `h2`, `hyper`, `tonic`) |
| `bans`      | `wildcards` | `"allow"` |
| `sources`   | `unknown-git` | `"deny"` |
| `sources`   | `unknown-registry` | `"deny"` |
| `sources`   | `allow-git` | `pydantic/monty`, `astral-sh/ruff` only |
| `sources`   | `allow-registry` | rust-lang crates.io index only |

`bans.multiple-versions = "allow"` cannot be tightened to `"warn"`/`"deny"`
while the libsql legacy chain ships — it inherently pulls two copies of
`rustls` (0.22 + 0.23), `rustls-webpki` (0.102 + 0.103), `h2` (0.3 + 0.4),
`hyper` (0.14 + 1.x), and `tonic` (0.11 via libsql + the modern one). That
is a known consequence of the libSQL chain, not a hidden loosening.

## The eight accepted advisories

| # | Advisory | Locked path | Why it is still ignored |
|---|---|---|---|
| 1 | `RUSTSEC-2026-0049` | `libsql 0.6.0 → hyper-rustls 0.25.0 → rustls 0.22.4 → rustls-webpki 0.102.8` | CRL distributionPoint matching. Patched in `rustls-webpki 0.103.x`, but `rustls 0.22` requires 0.102. **libsql 0.9.30 (latest stable) and 0.10.0-pre.4 (latest prerelease) still request `hyper-rustls ^0.25` and `hyper ^0.14`** — re-verified 2026-09-26 against crates.io. Even a libsql bump today keeps the vulnerable chain. |
| 2 | `RUSTSEC-2026-0098` | same libsql chain | URI name constraints accepted after signature verification. Same upstream block as #1. |
| 3 | `RUSTSEC-2026-0099` | same libsql chain | Wildcard certificates can bypass a permitted-subtree name constraint. Same upstream block as #1. |
| 4 | `RUSTSEC-2026-0104` | same libsql chain | Reachable panic parsing a CRL. Same upstream block as #1. |
| 5 | `RUSTSEC-2026-0258` | `libsql 0.6.0 → tonic 0.11 → hyper 0.14.32 → h2 0.3.27` | h2 unbounded empty DATA frames. The 0.4 line in the lock is already at 0.4.16 (patched); the residual 0.3.27 copy is the final release of the 0.3 line and has no upstream patch. Same libsql legacy chain as #1–#4. |
| 6 | `RUSTSEC-2023-0071` | `russh 0.62.6 → rsa 0.10.0-rc.18` | Marvin RSA timing side channel. **Re-verified 2026-09-26: `rsa 0.10.0-rc.18` is still the newest published release (max stable `0.9.10` predates the rc), and `russh 0.63.3` (latest, 2026-09-09) still requests `rsa =0.10.0-rc.18` as an optional dep.** Bumping russh does not clear the advisory. Clearing needs either an upstream constant-time `rsa` release or a LunarWing policy change (reject RSA keys at ingestion, drop the `russh/rsa` feature). Operators should use Ed25519/ECDSA keys. |
| 7 | `RUSTSEC-2019-0036` | vendored `ic/vendor/libsignal-protocol 0.1.0 → failure 0.1.8` | `failure` type confusion. `failure 0.1.8` is the final release; clearing requires porting the vendored wrapper off `failure`/`failure_derive`. |
| 8 | `RUSTSEC-2020-0036` | same vendored libsignal chain | `failure` is officially unmaintained. Same upstream block as #7. |

## What can be taken out, and when

| Advisory | Remove the ignore when … |
|---|---|
| #1–#5 (libsql TLS + h2 chain) | An upstream `libsql` release adopts `rustls 0.23` / `hyper-rustls 0.27+` / `hyper 1.x` / `tonic 0.12+` (or LunarWing migrates off libsql). After the lock no longer contains `rustls-webpki 0.102.x` or `h2 0.3.x`, drop the five entries and re-run `cargo deny check advisories` — they should stay cleared. |
| #6 (rsa Marvin) | Either `rsa` ships a constant-time release that `russh` adopts (then bump `russh` and drop the entry), or LunarWing rejects RSA keys at ingestion and disables the `russh/rsa` feature (then `rsa` leaves the lock and the entry goes with it). |
| #7–#8 (failure) | The vendored `ic/vendor/libsignal-protocol` wrapper is ported off `failure`/`failure_derive` onto a maintained error library (e.g. `thiserror`). |

## What is not in `deny.toml` (and does not need to be)

- **No yanked crates.** `yanked = "deny"` is active and the check is clean.
- **No unmaintained crates outside the accepted set.** `unmaintained = "workspace"` flags workspace members only; the two `failure` advisories cover the one unmaintained third-party crate in the graph.
- **No license loosening.** The allow-list is unchanged from v2.0.8.0; nothing new was added.
- **No new git/registry sources.** `unknown-git` and `unknown-registry` remain `"deny"`; only the two pre-approved git deps (monty, ruff) and the rust-lang crates.io index are allowed.

## Out of scope for this item

Applying compatible maintenance updates (`cargo update`), bumping `h2`
0.4.16 → 0.4.19, or attempting the libsql/russh/libsignal migrations —
those are separate work items (dependency refresh, libSQL migration, SSH
policy hardening, Signal wrapper modernization). This audit only confirms
the deny.toml ignore list is accurate, justified, and self-describing for
v2.1.3.0.
