**Date:** 2026-09-19

**Status:** investigation complete. The nine findings below describe the inspected
revision; implementation progress is tracked in the
[Goal 8 hardening record](v2.1.2.0_GOAL8_INSIGHTS_HARDENING.md) and
[WI #183](https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/183).
The September 16 incident has not been causally attributed.

## Conclusion

Conversation insights has several concrete ways to turn weak or model-generated
input into durable, repeatedly recalled claims. The strongest findings are:

1. A stored prompt overlay still becomes system instructions with
   `ORCHESTRATOR_SELF_MODIFY=0`; the write-side exception also trusts a
   model-supplied `source: compiled_in` field.
2. Insight inputs are project/user batches, can include research/child goals,
   and are described to the model as actual user requests without source IDs.
3. Insight missions retain maintenance-document retrieval, including fix
   patterns and orchestrator source, despite the stricter conversational policy.
4. The insight writer requires neither supporting user evidence nor a stable
   insight identity; identical saves create separately retrievable lessons.
5. Generated mission focus and outcome history feed the next run even when no
   insight document was saved.

These are reproducible mechanisms or source-verified gaps, **not proof that any
one caused the reported September 16 response**. Existing provenance labels,
role-token neutralization, and stream-integrity checks do not validate the
truth of a generated preference or domain claim.

## How conversation insights actually runs

```text
ThreadManager terminal event
  -> MissionManager::start_event_listener
  -> count successful non-Mission events per (project_id, user_id)
  -> every fifth event: conversation_insights_due payload
  -> fire_on_system_event -> fire_mission_inner
  -> retrieve mission-context docs + build_meta_prompt
  -> spawn a new Mission thread with trigger_payload in initial state
  -> normal engine / Monty orchestrator / LLM loop
  -> __save_memory_doc__ -> MemoryDoc -> HybridStore -> workspace
  -> later retrieval, plus mission focus/history on subsequent runs
```

- **Separate inference? Yes.** A new Mission thread runs its own normal LLM
  loop; it can make several calls and use tools. It is not a deterministic
  summary attached to the foreground reply. See
  `ic/crates/lunarwing_engine/src/runtime/mission.rs:880-941` and
  `ic/crates/lunarwing_engine/orchestrator/default.py:1142-1176`.
- **When?** Every five successful non-Mission terminal events, with an
  in-process counter keyed by project and user. The default insight mission
  permits two runs per UTC day. This is not five messages in one conversation.
  See `ic/crates/lunarwing_engine/src/runtime/mission.rs:1256-1262`,
  `:1292-1295`, `:1447-1450`, `:1514-1566`, and `:1688-1702`.
- **What input?** Latest five non-Mission goals by creation time, plus up to ten
  User-role messages from the triggering thread, each cut to 200 characters.
  The rendered trigger preview is cut to 4,000 characters; the full payload
  remains accessible in `state["trigger_payload"]`. Retrieved excerpts appear
  both in the mission meta-prompt (up to ten docs) and the first-step system
  append (up to five).
- **What output?** The compiled prompt asks for `lesson` docs tagged `insight`,
  created by `__save_memory_doc__`, then a FINAL report and next focus. The
  default owner is the initiating user; the source thread is the writer's
  Mission thread. See
  `ic/crates/lunarwing_engine/prompts/mission_conversation_insights.md` and
  `ic/crates/lunarwing_engine/src/executor/scripting.rs:1954-2060`.
- **Which boundary?** Retrieval content is role-token-neutralized and labeled
  `untrusted_memory_retrieval`; meta-prompts are neutralized as a whole. The
  same LLM bridge/provider stack handles these mission calls. Those controls
  protect representation and execution boundaries, not factual accuracy.

## Findings

### G8-F1 — prompt-overlay authority is not fully behind self-modification

**Priority: high. Verified by runtime probe for consumption; source-verified
for the write-side exception.**

`ExecutionLoop::run` fetches shared docs and builds the CodeAct system prompt
before checking `ORCHESTRATOR_SELF_MODIFY` for orchestrator selection.
`extract_prompt_overlay` accepts the reserved title/tag, without checking the
gate or origin. The result appears under **Learned Rules (from
self-improvement)**. Disabling the gate therefore leaves an already-stored
overlay active in new threads. The conversational-recall exclusion does not
affect this separate instruction-loading path.

The write-side check has a related authenticity gap: `HybridStore` permits a
protected document when `metadata.source == "compiled_in"`. The mission host
writer accepts that metadata unchanged for non-Skill docs and allows
`shared=True`. A mission can supply the field used to distinguish a host seed
from a model-authored write. This is a source-verified route through the
production guard, not a live-tenant write performed by this audit.

Evidence:

- `ic/crates/lunarwing_engine/src/executor/loop_engine.rs:350-385,443-453`.
- `ic/crates/lunarwing_engine/src/executor/prompt.rs:122-147,181-195`.
- `ic/crates/lunarwing_engine/src/executor/scripting.rs:2015-2052`.
- `ic/src/bridge/store_adapter.rs:1762-1802`; persisted overlays reload via
  `:436-465`.

The probe pre-seeded a shared overlay, ran a foreground greeting with the gate
explicitly `0`, and observed its canary in the system message while
`orchestrator_version` remained `0`. This corrects the broader “both paths
fail-closed” characterization in the earlier Goal 25 report: runtime Python
selection and the structured self-improvement update path are gated; overlay
consumption is not.

**Follow-up:** enforce the intended gate at overlay consumption; make
system-internal writes depend on host-owned authority rather than writable
metadata. Cover pre-existing overlays, genuine compiled seeds, and forged
`compiled_in` metadata. Insight persistence should not be able to write
engine-control documents.

### G8-F2 — extraction inputs overstate user origin and conversation scope

**Priority: high. Verified by source and runtime probes.**

`recent_conversation_thread_goals` excludes only `ThreadType::Mission`. It
does not require successful completion, a top-level foreground origin, or
membership in the triggering conversation. The counter also excludes only
Mission threads; successful managed research/child threads count toward the
five-event threshold. The stronger foreground/parent filter nearby applies
only to `thread_start`, not insight completion handling.

The compiled prompt describes `thread_goals` as “what the user asked for” and
`sample_user_messages` as “actual user messages.” However, the manager's
string-goal spawn API creates a User-role message even for a generated research
goal. Filtering on role alone cannot establish human origin.

The sample comes only from `thread.messages` of the triggering thread, not
from each selected source thread. That thread can inherit conversation history;
`.take(10)` takes the **first** ten user messages, potentially missing the
latest correction. The 200-character prefix can omit a negation or conclusion,
and there is no per-excerpt truncation marker. The payload carries no source
thread list, message identity/timestamp, or conversation ID with which to
verify an inference.

Evidence:

- `ic/crates/lunarwing_engine/src/runtime/mission.rs:66-81,1292-1308,1514-1557`.
- `ic/crates/lunarwing_engine/src/runtime/manager.rs:246-269` and
  `ic/crates/lunarwing_engine/src/types/message.rs:84-97`.
- `ic/crates/lunarwing_engine/src/runtime/conversation.rs:404-423,605-632`.
- `ic/crates/lunarwing_engine/prompts/mission_conversation_insights.md:5-16`.

Probes demonstrated that a failed research child is eligible for goal
sampling, and five successfully completed managed research children trigger
insights with only the fifth child's synthetic goal in `sample_user_messages`.
The latter ran with skill self-improvement disabled.

Scope qualification: the `rlm_query` helper currently runs an inline child loop
without attaching the manager's store/event bus
(`ic/crates/lunarwing_engine/src/executor/scripting.rs:1640-1714`). The probe
establishes eligibility of **managed/stored** children, not that every inline
recursive query currently contributes an event. Also, insight sampling reads
visible `messages`, not all `internal_messages`; ordinary tool-result/nudge
history is not automatically sampled wholesale.

**Follow-up:** define the intended learning scope explicitly and select
identified, successful, eligible user turns. Preserve source references,
origin, timestamps, and truncation information through extraction. Mark
generated goals as generated, rather than promoting their role label to proof
of human authorship.

### G8-F3 — insights inherits maintenance recall and its fallback

**Priority: high. Verified through the shipped mission and Monty paths.**

The stricter conversational policy excludes maintenance docs and requires
positive whole-token relevance. Insight missions use `retrieve_mission_context`
at both prompt construction and first-step retrieval. That policy deliberately
permits maintenance docs and type/recency fallback. Its first query is the
generic insight-extraction program, not just the user's evidence batch.

A freshly seeded project with skill learning enabled produced an insight
thread whose goal **and system context** included `fix_pattern_database` and
whose goal also included `orchestrator:main`. The labels survived, so this is
not a repeat of the old discarded-provenance bug. It is an avoidable semantic
input: engine maintenance vocabulary participates in a user-preference task.

Evidence:

- `ic/crates/lunarwing_engine/src/runtime/mission.rs:880-886,2246-2265`.
- `ic/crates/lunarwing_engine/src/memory/retrieval.rs:60-139`.
- `ic/crates/lunarwing_engine/src/executor/orchestrator.rs:2085-2117`.
- `ic/crates/lunarwing_engine/orchestrator/default.py:1142-1147`.

**Follow-up:** select retrieval policy by mission purpose. Give insight
extraction only relevant user evidence and relevant prior insights; retain
maintenance access for actual maintenance work. Test both retrieval stages,
including an empty evidence batch and a freshly seeded project.

### G8-F4 — unsupported or duplicate insights become ordinary lessons

**Priority: high. Verified at the host writer and retrieval boundary.**

The writer validates mission authorization, non-empty title/content, and doc
type. It does not require evidence, a source user quote, confidence, or a
distinction between explicit preference and inference. The example prompt uses
empty metadata. `source_thread_id` records the generating mission, not the
user turns supporting the claim.

Every call creates a new DocId. Saving the same title/content twice creates two
lessons, despite the prompt saying “merge with existing insight docs.” The
“max 5” and “do not record personal information” instructions are also prompt
rules, not writer-enforced constraints. Existing insights can be recalled
during future extraction and ordinary conversations without an evidence check.

The probe saved an unsupported synthetic claim twice from a Mission with no
source messages. Both calls returned IDs; both docs were selected by ordinary
recall on a matching token. Fixed untrusted-reference labels still apply at
render time; the finding concerns eligibility and truth, not metadata-based
promotion by that renderer.

Evidence: `ic/crates/lunarwing_engine/src/executor/scripting.rs:1954-2060`,
`ic/crates/lunarwing_engine/src/memory/retrieval.rs:93-139`, and
`ic/crates/lunarwing_engine/prompts/mission_conversation_insights.md:13-38`.

**Follow-up:** persist a typed insight with host-validated evidence references,
explicit/inferred status, and stable identity/upsert behavior. Prior generated
insights must not count as independent user corroboration. Verify contradiction
handling and repeated saves as well as the zero-evidence rejection case.

### G8-F5 — mission outcome history is an independent feedback channel

**Priority: high. Verified by source and a deterministic outcome probe.**

Every successful mission FINAL is recorded as an approach. Text after
`next focus:` becomes `current_focus`. The next meta-prompt embeds it under
**Current Focus**, plus recent **Previous Approaches**. These fields have no
equivalent of the retrieved-doc source/trust labels or evidence requirement.
Whole-prompt role-token neutralization and bounded approach excerpts remain
present, but ordinary false statements survive both.

The probe processed a synthetic generated focus, saved **zero user MemoryDocs**,
and found the focus in the next meta-prompt. Thus “no saved insight” does not by
itself rule out all persistent feedback channels. This does not contradict the
incident's reported absence of subsequent bleed; it identifies a separate path
to inspect in a trace.

Evidence: `ic/crates/lunarwing_engine/src/runtime/mission.rs:2211-2244,2305-2311,2347-2371`.

**Follow-up:** for batch extraction, derive work from the next evidence batch
rather than a model-invented next agenda. Where history is useful, label it as
generated run history and verify any claim before promoting it to an insight.

### G8-F6 — a same-user system event dispatches across projects

**Priority: medium. Verified by runtime probe.**

`fire_on_system_event` filters ownership and cadence, but not project. An
insight event from project A can fire matching active missions in project B
owned by the same user. Those threads use B's project and retrieve B's docs
while receiving A's payload; any doc they write inherits B's project.

The probe created Alice's insight missions in A and B and Bob's in B. One
Alice/A event spawned two Alice mission threads containing A's canary; Bob's
mission did not fire. This is demonstrated **same-user cross-project mixing**,
not evidence of cross-tenant leakage.

Evidence: `ic/crates/lunarwing_engine/src/runtime/mission.rs:1065-1110,883,919-930`.

**Follow-up:** make event project scope a host-validated dispatch argument and
require a match for project-local insight missions. Keep genuinely global
subscriptions explicit. Test same-user/different-project and different-user
cases separately.

### G8-F7 — the batch “content hash” is a restart-sensitive counter

**Priority: medium. Verified by source and manager-recreation probe.**

The payload's `content_hash` is `insights:<project UUID>:<count>`, not a hash of
the evidence. The counter starts from zero in every event listener, while
processed trigger keys persist on the mission. After restart, a genuinely new
batch numbered five collides with the previously processed batch numbered
five and is silently skipped. The same applies to later retained keys; the
key list is FIFO-bounded to 512 entries.

The probe fired an old batch, recreated the manager on the same store, and
submitted different content with the reset counter's key. No new thread was
created. It models the reset key explicitly; it is not a process-crash test.
Counter loss on restart and broadcast lag also make “every five” best-effort.

This primarily loses learning and confounds an on/off experiment: an Active
mission or elapsed conversations do not prove that extraction ran.

Evidence: `ic/crates/lunarwing_engine/src/runtime/mission.rs:1260-1262,1514-1554,831-840,1572-1575`
and `ic/crates/lunarwing_engine/src/types/mission.rs:197,323-338`.

**Follow-up:** derive idempotency from stable source identities/content and
scope, or persist a source watermark. Test redelivery of the same batch versus
new messages after restart, with observable skip reasons.

### G8-F8 — disabling skill learning or deleting missions is not an insight opt-out

**Priority: medium / operational. Verified by source and existing lifecycle tests.**

Conversation insights and expected behavior are baseline, ungated missions.
`SKILL_SELF_IMPROVEMENT=false` disables diagnosis/extraction/skill maintenance,
not conversation insights. The research-trigger probe confirms insights still
runs with that gate off. There is no separate insights-enable setting in the
inspected config.

Startup reconciliation recreates missing built-ins and reactivates old
Completed/Failed built-ins, while preserving an operator pause. For an on/off
experiment, pause the insight mission via the existing mission API and check
that an already-running mission has finished or been stopped before measuring.
Pausing changes future firing; it does not undo previous insight writes.

For custom purged missions, the resurrection gap from WI #132 note 3109 remains:
deletion removes the record and active entry without a tombstone; creation
deduplicates only live same-name missions. A surviving conversation can request
the mission again. Built-in reconciliation and model-requested recreation are
distinct mechanisms.

Evidence: `ic/crates/lunarwing_engine/src/runtime/mission.rs:50-64,467-537,739-767,1650-1702,1823-1909`;
`ic/src/bridge/effect_adapter.rs:419-441,489-514`.

**Follow-up:** document and expose a persistent insight opt-out if that is the
intended product control; preserve operator pauses across reconciliation.
Treat purge tombstones and surviving-history cleanup as their own lifecycle
work, not as something the search-index exclusion already solves.

### G8-F9 — a returned doc ID does not guarantee durable workspace persistence

**Priority: medium. Source-verified; no database fault injection in this audit.**

The host writer raises when `Store::save_memory_doc` returns an error. However,
production `HybridStore::save_memory_doc` inserts into the in-memory map, calls
`persist_doc`, and returns success. `persist_text` logs a workspace write error
at debug level and returns unit; `persist_doc` still records the path.

Consequences of a write failure: the model can truthfully report a returned doc
ID, engine recall can see that doc in-process, and a restart can lose it. A
workspace search and engine recall may disagree. This is distinct from the
fixed content-committed/chunks-stale outbox case. It is not evidence that this
failure occurred during September 16.

Evidence: `ic/src/bridge/store_adapter.rs:664-670,1114-1144,1762-1802` and
`ic/crates/lunarwing_engine/src/executor/scripting.rs:2054-2060`.

**Follow-up:** propagate durable content-write failures before reporting
success and keep the cache/path map consistent. Fault-inject the workspace
write and reload a fresh store; separately preserve the existing distinction
between committed content and a repairable search-index failure.

## What corruption handling does, and what it cannot establish

The current native provider path has two relevant behaviors:

| Signal | Current handling | Limit |
|---|---|---|
| Repeated prose phrase or role delimiter | `StreamIntegrityProvider` detects it at Done, appends a warning, and emits a Corrupted observation. The bridge strips provider/kind strings; the engine retains text and discards executable calls/code classification. | Text deltas have already streamed. This is not a guarantee that the user never sees the text, nor a detector for arbitrary invented vocabulary. |
| Malformed/contaminated REPL arguments or fences | Typed `repl_argument_corruption` rejection before execution; bounded one-repair path. | Valid code that saves a false string is still valid code. Ordinary Python errors retain the separate Monty correction path. |

Evidence:

- `ic/src/llm/mod.rs:487-507`: integrity wrapper around the configured native
  provider stack.
- `ic/src/llm/stream_integrity.rs:324-378,458-566`: text forwarding, marker,
  detection signatures, and exclusion of code/quoted prose from that detector.
- `ic/src/bridge/llm_adapter.rs:146-175` and
  `ic/crates/lunarwing_engine/src/executor/llm_stream.rs:96-138`: observation
  relay and non-executable-text result.
- `ic/crates/lunarwing_engine/src/executor/orchestrator.rs:754-784,844-872`:
  live ResponseDelta emission and typed repair result.
- `ic/crates/lunarwing_engine/orchestrator/default.py:1184-1218,1227-1338`:
  recovery, text retention/completion, roleplay and fabricated-tool-success
  nudges. These are bounded heuristics, not a factuality check.
- [Goal 34 / WI #161](GOAL34_REPL_ARGUMENT_INTEGRITY.md): the newer REPL
  boundary and verification record.

The old relay note's “Text can be displayed. Text cannot execute” accurately
describes demotion. It does **not** substantiate the September 16 claim that a
particular nonsensical response was suppressed. That observation could involve
a rejected REPL draft, a nudge, reasoning-only output, or another response
path; the affected trace is required to identify which. The native provider
wrapper also does not establish how an external worker handled its own model
stream.

## Follow-up order and the missing incident experiment

1. **Close G8-F1's instruction-authority gap.** Gate overlay consumption and
   separate host seeding authority from model metadata. This is independently
   actionable even if insights is not the September 16 trigger.
2. **Make extraction evidence-driven (G8-F2–F5).** Establish eligible source
   turns, a purpose-specific retrieval policy, evidence-bearing/idempotent
   insight writes, and generated-history labeling. Regression acceptance must
   include a clean greeting, unrelated maintenance docs, quoted/corrected
   claims, long messages with late negation, generated children, duplicate
   writes, and a no-new-insights batch.
3. **Repair scope and operational contracts (G8-F6–F9).** Project-scoped
   dispatch, source-based batch identity, persistent opt-out/recreation policy,
   and honest durable-write outcomes. Check both in-process and reloaded state.
4. **Attribute the live incident with evidence.** Obtain the affected tenant,
   approximate UTC time, conversation/thread ID, exact build and provider/model,
   worker job ID if applicable, and original trace. Correlate foreground thread,
   insight mission/thread, trigger payload, retrieved doc IDs, provider
   observations, attempted saves, mission history, and final delivery outcome.

For the proposed “does it happen without insights?” experiment, start paired
disposable tenants from the same clean snapshot/config/model, with insights
active in one and **operator-paused** in the other. Hold skill learning,
self-modification, worker configuration, and input corpus constant. Confirm
actual mission fires rather than assuming the counter or Active status proves
execution. Account for G8-F7 across restarts and drain in-flight runs before
starting the paused arm. Record separately: malformed model output, rejected
execution, visible delivery, saved knowledge, mission focus/history, and
cross-thread recall. Reproduce any captured bad stream deterministically before
comparing repeated live-model runs; one quiet run cannot prove causality or a
fix.

Use `ic/scripts/lunarwing-mt-admin.sh` for tenant lifecycle/status on both
systemd-user and OpenRC hosts. Inspect stored document content as well as search
results; an absent search hit is not proof of absent persistence. Preserve the
incident evidence before any cleanup, and quiesce the daemon before a purge so
in-process caches cannot recreate removed content.
