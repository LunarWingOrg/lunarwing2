# Goal 33 / WI#162 — explicit shell-output truncation

## Root cause and result contract

Verified against `a/goal33/v2.1.2.0` on 2026-09-17. Both the work item and its
voice cross-reference comment were read.

`SandboxManager` and the container runners already tracked truncation. The
manager divides its 65,536-byte capture budget between stdout and stderr, which
explains the reported **32,768-byte** stdout boundary. `ShellTool` discarded
`ExecOutput.truncated`; its own 65,536-byte display limiter could not detect
data already discarded by the manager. Separately, the direct developer shell
captured 65,536 bytes per stream and discarded the rest while draining, without
retaining a truncation flag.

The fix carries capture completeness through both paths and the combined display
limiter. Every successful tool invocation now returns:

```json
{
  "output": "[output truncated] Captured output is incomplete. ...",
  "exit_code": 0,
  "success": true,
  "sandboxed": true,
  "truncated": true,
  "warning": "[output truncated] Captured output is incomplete. ..."
}
```

`exit_code` remains the real process exit code; `success` remains its zero-exit
test. `truncated` is independent of success. A complete capture returns
`truncated: false`, `warning: null`, and the original unmarked output. The warning
is **prefixed** after display clipping so shorter gateway/history previews also
retain it. Direct pipe read errors now fail rather than silently returning a
partial success. No output-limit configuration key is introduced: the limits
above are internal byte limits, not the reported `sandbox_max_output_bytes`
setting (which does not exist in this source tree).

### Voice cross-reference

This fixes the silent-loss signal; it does not recover bytes already discarded.
Never strip the warning and forward the remaining fragment as audio or file
contents. `voice_transcribe_tool` currently accepts an `audio` base64 string,
not a local file path. For that tool, reconstruct the complete payload from
verified bounded chunks inside the REPL, or use the gateway's supported audio
upload path. A 32,768-character base64 fragment can still be syntactically valid
base64 while containing incomplete audio. The older 4,332-character failure in
the comment is below this cap and cannot be attributed to it on this evidence.

Open the fresh tenant's gateway using its allocated port and token (obtain the

following via the REPL and report **only the small summary**, not the full output.
Use actual `shell` calls and approve them. `truncated` must come from the returned

```python
checks = [
    (30000, "", 0),
    (32768, "", 0),
    (32769, "", 0),
    (40000, "", 0),
    (40000, ">&2", 7),
]
summaries = []
for size, redirect, code in checks:
    command = "head -c " + str(size) + " /dev/zero | tr '\\000' A " + redirect
    result = shell(command=command + "; exit " + str(code))
    summaries.append({
        "requested_bytes": size,
        "stderr": redirect != "",
        "exit_code": result.get("exit_code"),
        "success": result.get("success"),
        "truncated": result.get("truncated"),
        "warning": result.get("warning"),
        "captured_chars": len(result.get("output", "")),
        "prefix": result.get("output", "")[:200],
    })
print(summaries)
```
