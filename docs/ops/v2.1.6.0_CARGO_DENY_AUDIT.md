## 2026-10-17 follow-up — `unsound` advisory scope widened to "all" (WI#360)

The October 10/11 audit below ran with `unsound` unset in `ic/deny.toml`,
which in cargo-deny 0.20.2 defaults to `Scope::Workspace`: an unsound
advisory fires only when the affected crate is a **direct** dependency of
a workspace member, so transitive unsound advisories never reached any
gate — a detection blind spot, not a known live vulnerability. The
reproduction in the !1518 review (note #7368, DC-1; advisory-db
`7eebec69c`, 2026-10-10) had already shown the widened scope adds exactly
one unaccepted finding, and that is unchanged on today's tree.

- **Policy change:** `ic/deny.toml` `[advisories]` now sets
  `unsound = "all"` explicitly. `unmaintained` stays `"workspace"` —
  moving it is a separate decision this item deliberately does not make
  (the informational `unmaintained = "all"` sweep further down remains a
  one-off).
- **New acceptance:** RUSTSEC-2021-0145 (`atty` 0.2.14, Windows-only
  unaligned read, no patched release). `atty` reaches `ic/Cargo.lock`
  only as a dev-graph transitive via the vendored libsignal-protocol
  workspace member's dev-dep `env_logger 0.6.2` — never a production
  edge, which `check-lockfile-only-advisories.sh` (`no-dev` mode) pins.
  Clearing owner: **WI#367** — extended by the !1703 run-142 review
  (JH-2) to own the `atty` acceptance too: its summary now lists the
  `atty` chain and its acceptance criteria require that `atty` leave
  `ic/Cargo.lock` together with the RUSTSEC-2021-0145 ignore, the guard
  entry, and the JH-1 `[bans]` entries. Clearing means dropping the
  `env_logger` dev-dep edge (or otherwise removing `atty` from the
  lock), not just porting `failure`/`rental` — the port alone would
  leave the dev-dep in place.
- **Acceptance scope restriction (!1703 run-142 review, JH-1):** the
  RUSTSEC-2021-0145 ignore is keyed by ID, which would also suppress
  findings for `atty` in any other root or graph position — exactly
  the transitive case the scope widening was meant to catch, left
  invisible in 24 of the 26 swept roots. `[bans]` now restricts the

  under `env_logger`, and `env_logger <0.10.0` is banned except under

## 2026-10-16 follow-up — yanked `zip 2.4.2` (WI#417)

Between the run-130 review pipeline 5793 (`cargo-deny` green at about
03:05Z) and pipeline 5794 (red at about 05:00Z), crates.io yanked every
`zip` release below 9.0.3 (2.3.0 through 7.4.0 included; only 9.0.3 and
9.0.4 remain). With `yanked = "deny"` in `ic/deny.toml`, every pipeline on
`aragents/kimil00p/v2.1.6.0` from 5794 onward failed `cargo-deny` and
`satellite-advisory-sweep` with `error[yanked]` on `ic/Cargo.lock` and the
XMPP bridge lock. The yank followed three GitHub advisories against
`zip` up to 9.0.0 (GHSA-4v9h-p7m9-rh26, GHSA-vv5m-jxxh-4627,
GHSA-4684-h2q9-2vcp; fixed in 9.0.0/9.0.1). RustSec had not imported them
at advisory-db `479c888ce4401313bca61ba4aba2d0f6244c4a09`; the red came from
the yank, not from an advisory ID. Tracking item:
[WI#417](https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/417).

- **Exposure: none found.** All three advisories concern `extract()`
  (symlink targets outside the destination, preserved SUID/SGID bits,
  permissions applied through symlinks). LunarWing never extracts to disk:
  `ic/src/document_extraction/extractors.rs` reads Office XML entries in
  memory through size-capped readers, and
  `ic/crates/lunarwing_skills/src/catalog.rs` reads `SKILL.md` and `*.py`
  entries in memory behind `MAX_ARCHIVE_FILES`, `enclosed_name()` and
  `take(max + 1)` caps. The bump is dependency hygiene; a fully yanked
  major line receives no further fixes.
- **Upgrade:** `zip` **2.4.2 → 9.0.4** in `ic/Cargo.toml` and
  `ic/crates/lunarwing_skills/Cargo.toml` (both keep
  `default-features = false, features = ["deflate"]`), updated in
  `ic/Cargo.lock` and `ic/bridges/xmpp-bridge/Cargo.lock` with
  `cargo update -p zip` from the unvendored repo root. Each lock gains
  `typed-path 0.12.3` and drops `derive_arbitrary 1.5.0` (zip 2's optional
  `arbitrary` support); nothing else moves. zip 9.0.4 declares
  `rust-version = 1.88`, below the repo's 1.96.1.
- **Vendor:** `ic/scripts/refresh-vendor.sh` regenerated `ic/vendor/zip`
  (package checksum
  `a954114b47a54df49f83d2722814e86b23d4bb1b54a1b90fb7d92b41619ddc22`, matching
  the lock), added `ic/vendor/typed-path`, and the orphaned
  `ic/vendor/derive_arbitrary` was removed (no synced lockfile references
  it; same shape as the `d34f45d3c` wnaf yank bump). The set check reports
  1148 crate dirs / 833 unique names matching the synced lockfiles, and the
  rig-core WI#292 patch was restored.
- **Backend change to note:** zip 2's `deflate` selected `flate2/rust_backend`
  (miniz_oxide); zip 9's `deflate` selects `flate2/zlib-rs`. flate2 prefers
  `zlib-rs` over `miniz_oxide` when both are enabled, so the whole `ic`
  workspace now inflates and deflates through the already-vendored
  `zlib-rs 0.6.8` (pure Rust). No C zlib is introduced.
- **API changes absorbed:** `ZipFile` gained a reader type parameter and
  `ZipFile::name()` now returns `ZipResult<Cow<str>>`. The extractor helpers
  are generic over the reader; an entry whose stored name does not decode is
  skipped by the slide/sheet scans and reported as `<undecodable entry name>`
  in size-limit diagnostics. `enclosed_name()`, `is_dir()`, `size()`,
  `by_index`, `by_name` and the writer API are unchanged.
- **Behaviour change found while pinning:** zip 2's `enclosed_name()`
  refused an absolute entry name; zip 9 strips the root and keeps the rest
  inside the destination (`/etc/SKILL.md` → `etc/SKILL.md`). `..`
  traversal is still refused. Neither caller extracts, and the catalog reads
  entries by file name only, so no LunarWing behaviour changes.
- **Regression protection:** `lunarwing_skills` gains three catalog tests
  that build real deflated archives in memory: a SKILL.md plus `*.py`
  happy path, a `../evil/SKILL.md` entry that must be refused as "unsafe
  file path", and an absolute `/etc/SKILL.md` entry that is read as a
  relative one, so the next zip bump cannot change what `enclosed_name()`
  accepts or rejects unnoticed.

## 2026-10-14 follow-up — pipeline 5710 Wasmtime failures

After the rustls fix, advisory-db
`edb58f5974b83eb8302332821cb6d389777aa351` added findings against Wasmtime
36.0.17. Master pipeline **5710**, commit
`39cea55fbaff4a98c87a68fb3cdbf93c4cbbe38b`, failed
[`cargo-deny` job 110686](https://git.lunarwing.org/lunarwing/lunarwing2/-/jobs/110686)
and [`satellite-advisory-sweep` job 110687](https://git.lunarwing.org/lunarwing/lunarwing2/-/jobs/110687).
The sweep failed for `ic` and `ic/bridges/xmpp-bridge`.

- **RUSTSEC-2026-0363 (`wasmtime`):** component-model handle tables had only
  per-instance caps, allowing guest-controlled instances to exhaust host
  memory. The patch adds a store-wide live-handle limit, defaulting to
  **100,000**; exhausting it traps. LunarWing uses the component model for
  untrusted WASM tools and channels.
- **RUSTSEC-2026-0352 (`wasmtime-wasi`):** renaming symlinks with trailing
  slashes can escape the filesystem sandbox on macOS/FreeBSD. The patched
  rename path avoids following those symlinks outside the preopened root.
- **Fix:** raise both manifest minimums to **36.0.18** and update both
  affected lockfiles, including the matching Wasmtime/Pulley/Wiggle/Winch
  **36.0.18** and Cranelift **0.123.18** crates. Exactly **37** package
  records change in each lockfile, limited to versions and checksums.
  Regenerate the corresponding **37** vendor directories with
  `ic/scripts/refresh-vendor.sh`; the committed rig-core patch is preserved.
  Both advisories are fixed by the upgrade; the existing **11** advisory
  acceptances remain the policy total.

**Local verification:** the vendor refresh and full unvendored cargo-deny
gate pass against the database above (advisories, bans, licenses, sources,
and registry/yanked checks). All **1,447** files in the updated vendor
crates match their generated checksums, and package checksums match the
lockfiles. The satellite advisory sweep passes all **26** manifest roots
(one manifest-less Pebble override skipped as designed), and the real
default-graph guard passes. Rustfmt and diff checks pass. Compilation and
targeted runtime tests are pending at this checkpoint. Remote CI must run
on the patched commit; retrying pipeline 5710 still tests the old locks.

Deployment requires rebuilding and restarting the daemon and XMPP bridge
through the existing tenant lifecycle tooling. The new per-store handle
cap can trap components that previously accumulated more than 100,000 live
handles; rolling back below 36.0.18 reintroduces these vulnerabilities.

## Conclusion

**Six vulnerability advisories, one unsound advisory, and two unmaintained
advisories are accepted and shipped; none of them is unaccounted for, and
no committed lockfile contains any *other* crate with an active applicable
security advisory.** This is a risk-acceptance statement, not a clean
bill. The goals item is therefore checked off as "audit complete,
acceptances accounted and owned" — **not** as "zero vulnerabilities". The
clearing decisions are owned by work item
[WI#331](https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/331)
(goals item 11); its libsql mitigation landed with item 11, and the
residual clearing work is split into
[WI#367](https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/367)
(libsignal-protocol off `failure`/`rental`) and
[WI#368](https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/368)
(rsa policy / upstream tracking). Until those land, "cargo-deny green"
means *accepted*, not *fixed*.

- **1 of the 6 vulnerability advisories compiles into default builds**;
  the other 5 moved behind the opt-in `libsql-remote-replica` cargo
  feature (WI#331, item 11) and are regression-pinned there by
  `.gitlab/scripts/check-default-graph-advisories.sh`.
  - `rustls-webpki 0.102.8` (RUSTSEC-2026-0049/0098/0099/0104, two of them
    certificate name-constraint bypasses) and `h2 0.3.27`
    (RUSTSEC-2026-0258) via the libsql 0.6.0 legacy chain: **opt-in
    `libsql-remote-replica` builds only** — absent from default and
    postgres-only builds.
  - `rsa 0.10.0-rc.18` (RUSTSEC-2023-0071) via russh's LunarWing-enabled
    `"rsa"` feature: **every feature set, including postgres-only**.
- **The unsound advisory is `failure 0.1.8`** (RUSTSEC-2019-0036 type
  confusion) via the vendored libsignal-protocol wrapper (XMPP OMEMO):
  every feature set.
- **The two unmaintained advisories are informational** (no
  vulnerability): `failure 0.1.8` (RUSTSEC-2020-0036, same path) and
  `rental 0.5.6` (RUSTSEC-2021-0134, visible only in the widened
  `--workspace --all-features` graph).
- Every accepted entry names WI#331 as its clearing owner (the v2.1.5.0
  items #304/#305/#306 are **closed** — see the ownership section), and
  the patched copies of advisory-pinned crates are protected against
  silent downgrade by `[bans]` version floors.

All 26 checkable manifest roots pass `cargo deny check advisories`
(cargo-deny 0.20.2, `--workspace --all-features`, shared `ic/deny.toml`
policy) against the advisory DB above; the one manifest-less reviewed lock
(`pebble4lunarwing/upstream/Cargo.lock`) remains gated by
`pebble4lunarwing/scripts/verify_upstream_lock.py`. Of the 27 non-vendor

with an empty `ignore` list (scope note, WI#360: these 2026-10-10/11 runs
predate the 2026-10-17 `unsound = "all"` widening and were measured at

### Corrected RUSTSEC-2023-0071 (rsa Marvin) exposure — MR !1505 review CP-3

Previous audits named "the ssh tool authenticating with RSA keys" as the
only exposure. That is wrong twice over, verified on this tree:

1. **The named path is dead by label, and the label check is bypassable.**
   The built-in ssh tool refuses RSA (`ic/src/tools/builtin/ssh.rs`: the
   `SSHKeyType::Rsa` arm errors out before connecting, pinned by
   `test_rsa_key_rejected`) — but only on the *declared* key-type label.
   `ic/src/bridge/ssh_client.rs` `parse_key` /
   `russh::keys::decode_secret_key` parses whatever key material it is
   given, so RSA material uploaded under an `ed25519` label still reaches
   the vulnerable signer.
2. **The live path is the tenant SSH agent that signs for untrusted
   worker containers.** `ic/src/bridge/ssh.rs` loads *every* configured
   host key from the secrets store into `SshAgentServer` with no algorithm
   filter; `ic/src/bridge/ssh_agent.rs` `confirm_request` returns `true`
   (no per-request confirmation) and the socket is mode `0o666`;
   `ic/scripts/lunarwing-mt-admin.sh` (`ssh-agent-dir-ro` in the
   `OPENCODE_ROOTLESS_LAUNCH_CONTRACT`, `OPENCODE2_ROOTLESS_LAUNCH_CONTRACT`
   and `PEBBLE_ROOTLESS_LAUNCH_CONTRACT`; `mt-admin-lib/07-units-systemd.sh`
   bind-mounts the socket read-only and exports `SSH_AUTH_SOCK`) mounts
   that agent into the opencode, opencode2 and pebble worker containers,
   which AGENTS.md treats as untrusted. The signing chain is unblinded:
   vendored russh `keys/agent/server.rs` SIGN_REQUEST → ssh-key
   `SigningKey::try_sign` → rsa `pkcs1v15` `sign::<DummyRng>(None, …)`,
   and `rsa` blinds only when an RNG is supplied. A tenant that configures
   an RSA host key therefore exposes unlimited chosen-message RSA
   signatures with fine-grained local timing to any prompt-injected or
   compromised worker — exactly what the advisory's workaround says to
   avoid.

Reachability: confirmed by code trace above (also confirmed in the MR
!1505 lead review). Whether rc.18's crypto-bigint signing leaks
exploitably in this configuration is unverified; a timing harness against
`SigningKey::try_sign` would settle it and is **not** part of this audit.

**Clearing path (owned by WI#331, not this item):** reject RSA key
material by *parsed algorithm* (not label) at key upload and at agent
load, then drop the russh `"rsa"` feature — `cargo tree -i rsa` shows only
russh and ssh-key pull it in. Until then the advisory stands accepted.

Upstream re-verification (crates.io sparse index, 2026-10-10): libsql
0.9.30 (max stable) and 0.10.0-pre.4 (newest) still request
`hyper-rustls ^0.25` / `hyper ^0.14` / `tonic ^0.11`, so a libsql bump
today keeps the chain (#1–#5). The advisory text still declares
`patched = []` and names rsa 0.10.0-rc.18; rsa 0.10.0-rc.19 has since been
published but the advisory is unchanged (rc.19 is published, not marked
patched) and russh 0.64.1 (latest) still requests `rsa =0.10.0-rc.18` as
an optional dep (#6). failure 0.1.8 is the final release (#7–#8).

**Downgrade protection:** the advisory ignores are keyed by ID, which
cannot fire if a future lockfile regresses the *patched* copy. `[bans]`
denies `h2 >=0.4.0, <0.4.19` and `rustls-webpki >=0.103.0, <0.103.15`,
flooring the patched lines while leaving the accepted legacy copies
(0.3.27 / 0.102.8) outside the denied ranges. Every committed lock
currently sits at h2 0.4.20 / rustls-webpki 0.103.15 on the patched
lines (h2 moved 0.4.19 → 0.4.20 in the item-1 sweep, MR !1507).
