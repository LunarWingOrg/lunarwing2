- **RUSTSEC-2026-0379 (`wasmtime`, GHSA-mghf-wjfp-p5xm, dated 2026-10-19,

  an incorrect target on a large Wasm `br_table` instruction. Patched
  ranges: `>=36.0.19, <37.0.0`, `>=48.0.7, <49.0.0`, `>=49.0.4`.
- **RUSTSEC-2026-0380 (`wasmtime`, GHSA-897f-g5gm-fmxm, dated 2026-10-19,

  `>=43.0.0`.

Wasm-level safety guarantees LunarWing relies on when executing untrusted
WASM tools and channels, so they are fixed by upgrade, not accepted.

  affected lockfiles. Exactly **37** package records change in each

  **0.123.19**), limited to versions and checksums. Regenerate the
  corresponding vendor directories with `ic/scripts/refresh-vendor.sh`;
  the committed rig-core patch is preserved. Both advisories are fixed by
  the upgrade; the existing **12** advisory acceptances remain the policy
  total (no new ignore entries).

**Local verification (branch `rarity/kimi-28-20261020-1643`):** the vendor
refresh and the full unvendored cargo-deny gate pass against advisory-db
`b19b2c83c` — the exact revision that failed pipeline 6121 (advisories,
bans, licenses, sources ok). The satellite advisory sweep passes all **26**

gate — a detection blind spot, not a known live vulnerability. The
reproduction in the !1518 review (note #7368, DC-1; advisory-db
`7eebec69c`, 2026-10-10) had already shown the widened scope adds exactly
one unaccepted finding, and that is unchanged on today's tree.

## 2026-10-16 follow-up — yanked `zip 2.4.2` (WI#417)

Between the run-130 review pipeline 5793 (`cargo-deny` green at about
03:05Z) and pipeline 5794 (red at about 05:00Z), crates.io yanked every
`zip` release below 9.0.3 (2.3.0 through 7.4.0 included; only 9.0.3 and
9.0.4 remain). With `yanked = "deny"` in `ic/deny.toml`, every pipeline on
`aragents/kimil00p/v2.1.6.0` from 5794 onward failed `cargo-deny` and
`satellite-advisory-sweep` with `error[yanked]` on `ic/Cargo.lock` and the
XMPP bridge lock. The yank followed three GitHub advisories against
`zip` up to 9.0.0 (GHSA-4v9h-p7m9-rh26, GHSA-vv5m-jxxh-4627,
GHSA-4684-h2q9-2vcp; fixed in 9.0.0/9.0.1). RustSec had not imported them
at advisory-db `479c888ce4401313bca61ba4aba2d0f6244c4a09`; the red came from
the yank, not from an advisory ID. Tracking item:
[WI#417](https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/417).

- **Exposure: none found.** All three advisories concern `extract()`
  (symlink targets outside the destination, preserved SUID/SGID bits,
  permissions applied through symlinks). LunarWing never extracts to disk:
  `ic/src/document_extraction/extractors.rs` reads Office XML entries in
  memory through size-capped readers, and
  `ic/crates/lunarwing_skills/src/catalog.rs` reads `SKILL.md` and `*.py`
  entries in memory behind `MAX_ARCHIVE_FILES`, `enclosed_name()` and
  `take(max + 1)` caps. The bump is dependency hygiene; a fully yanked
  major line receives no further fixes.
- **Upgrade:** `zip` **2.4.2 → 9.0.4** in `ic/Cargo.toml` and
  `ic/crates/lunarwing_skills/Cargo.toml` (both keep
  `default-features = false, features = ["deflate"]`), updated in
  `ic/Cargo.lock` and `ic/bridges/xmpp-bridge/Cargo.lock` with
  `cargo update -p zip` from the unvendored repo root. Each lock gains
  `typed-path 0.12.3` and drops `derive_arbitrary 1.5.0` (zip 2's optional
  `arbitrary` support); nothing else moves. zip 9.0.4 declares
  `rust-version = 1.88`, below the repo's 1.96.1.
- **Vendor:** `ic/scripts/refresh-vendor.sh` regenerated `ic/vendor/zip`
  (package checksum
  `a954114b47a54df49f83d2722814e86b23d4bb1b54a1b90fb7d92b41619ddc22`, matching
  the lock), added `ic/vendor/typed-path`, and the orphaned
  `ic/vendor/derive_arbitrary` was removed (no synced lockfile references
  it; same shape as the `d34f45d3c` wnaf yank bump). The set check reports
  1148 crate dirs / 833 unique names matching the synced lockfiles, and the
  rig-core WI#292 patch was restored.
- **Backend change to note:** zip 2's `deflate` selected `flate2/rust_backend`
  (miniz_oxide); zip 9's `deflate` selects `flate2/zlib-rs`. flate2 prefers
  `zlib-rs` over `miniz_oxide` when both are enabled, so the whole `ic`
  workspace now inflates and deflates through the already-vendored
  `zlib-rs 0.6.8` (pure Rust). No C zlib is introduced.
- **API changes absorbed:** `ZipFile` gained a reader type parameter and
  `ZipFile::name()` now returns `ZipResult<Cow<str>>`. The extractor helpers
  are generic over the reader; an entry whose stored name does not decode is
  skipped by the slide/sheet scans and reported as `<undecodable entry name>`
  in size-limit diagnostics. `enclosed_name()`, `is_dir()`, `size()`,
  `by_index`, `by_name` and the writer API are unchanged.
- **Behaviour change found while pinning:** zip 2's `enclosed_name()`
  refused an absolute entry name; zip 9 strips the root and keeps the rest
  inside the destination (`/etc/SKILL.md` → `etc/SKILL.md`). `..`
  traversal is still refused. Neither caller extracts, and the catalog reads
  entries by file name only, so no LunarWing behaviour changes.
- **Regression protection:** `lunarwing_skills` gains three catalog tests
  that build real deflated archives in memory: a SKILL.md plus `*.py`

### Corrected RUSTSEC-2023-0071 (rsa Marvin) exposure — MR !1505 review CP-3

Previous audits named "the ssh tool authenticating with RSA keys" as the
only exposure. That is wrong twice over, verified on this tree:

1. **The named path is dead by label, and the label check is bypassable.**
   The built-in ssh tool refuses RSA (`ic/src/tools/builtin/ssh.rs:100`: the
   `SSHKeyType::Rsa` arm errors out before connecting, pinned by
   `test_rsa_key_rejected` at `ic/src/tools/builtin/ssh.rs:278`) — but only
   on the *declared* key-type label. `parse_key` and
   `russh::keys::decode_secret_key` live in
   `ic/src/bridge/ssh_agent.rs:59-64` and parse whatever key material they
   are given (`ic/src/bridge/ssh_client.rs:146` is the caller on the
   outbound-connection path), so RSA material uploaded under an `ed25519`
   label still reaches the vulnerable signer.
2. **The live path is the tenant SSH agent that signs for untrusted
   worker containers.** `ic/src/bridge/ssh.rs:472-535`
   (`start_agent_server`) loads *every* configured host key from the
   secrets store into `SshAgentServer` with no algorithm filter
   (`SshAgentServer::start` at `ic/src/bridge/ssh.rs:535`);
   `ic/src/bridge/ssh_agent.rs:76` `confirm_request` returns `true` (no
   per-request confirmation) and the socket is mode `0o666`
   (`ic/src/bridge/ssh_agent.rs:153`). The socket is mounted into the
   opencode, opencode2 and pebble worker containers, which AGENTS.md treats
   as untrusted, on **both** init paths:
   - systemd Quadlet: `ic/scripts/mt-admin-lib/07-units-systemd.sh:608-609`
     (`Volume=…:/tmp/ssh-agent:ro,z` plus `SSH_AUTH_SOCK`);
   - the imperative `podman run` paths in
     `ic/scripts/mt-admin-lib/09-worker-config.sh` — `:1655-1657`
     (`start_tenant_opencode`), `:1855-1857` (`start_tenant_opencode2`) and
     `:2512-2514` (`start_tenant_pebble`) — which serve OpenRC and the
     older-Podman fallback.

   `ssh-agent-dir-ro` is the recorded contract label in
   `ic/scripts/lunarwing-mt-admin.sh` (`OPENCODE_ROOTLESS_LAUNCH_CONTRACT`,
   `OPENCODE2_ROOTLESS_LAUNCH_CONTRACT`,
   `PEBBLE_ROOTLESS_LAUNCH_CONTRACT`). The signing chain is unblinded:
   vendored russh `keys/agent/server.rs` SIGN_REQUEST
   (`ic/vendor/russh/src/keys/agent/server.rs:355`) → ssh-key
   `SigningKey::try_sign` → rsa `pkcs1v15` `sign::<DummyRng>(None, …)`, and
   `rsa` blinds only when an RNG is supplied. A tenant that configures an
   RSA host key therefore exposes unlimited chosen-message RSA signatures
   with fine-grained local timing to any prompt-injected or compromised
   worker — exactly what the advisory's workaround says to avoid.

   Context, not a severity claim: the agent never decodes the
   sign-request flags word, so an `rsa-sha2-*` request is answered with a
   legacy `ssh-rsa`/SHA-1 signature (ssh-key's `None` hash arm at
   `ic/vendor/ssh-key/src/signature.rs:715`), which OpenSSH >= 8.8 rejects
   by default. The maintainer has stated that RSA keys are not used in
   LunarWing deployments (note #7376), so this path is currently unreachable
   in practice; it stays documented because the acceptance is what keeps
   RUSTSEC-2023-0071 in the policy set.

Reachability: confirmed by code trace above (also confirmed in the MR
!1505 lead review). Whether rc.18's crypto-bigint signing leaks
exploitably in this configuration is unverified; a timing harness against
`SigningKey::try_sign` would settle it and is **not** part of this audit.

**Clearing path (owned by WI#331, not this item):** reject RSA key
material by *parsed algorithm* (not label) at key upload and at agent
load, then drop the russh `"rsa"` feature — `cargo tree -i rsa` shows only
russh and ssh-key pull it in. Until then the advisory stands accepted.

Upstream re-verification (crates.io sparse index, 2026-10-10): libsql
0.9.30 (max stable) and 0.10.0-pre.4 (newest) still request
`hyper-rustls ^0.25` / `hyper ^0.14` / `tonic ^0.11`, so a libsql bump
today keeps the chain (#1–#5). The advisory text still declares
`patched = []` and names rsa 0.10.0-rc.18; rsa 0.10.0-rc.19 has since been
published but the advisory is unchanged (rc.19 is published, not marked
patched) and russh 0.64.1 (latest) still requests `rsa =0.10.0-rc.18` as
an optional dep (#6). failure 0.1.8 is the final release (#7–#8).

**Downgrade protection:** the advisory ignores are keyed by ID, which
cannot fire if a future lockfile regresses the *patched* copy. `[bans]`
