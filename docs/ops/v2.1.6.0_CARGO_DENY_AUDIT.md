### Corrected RUSTSEC-2023-0071 (rsa Marvin) exposure — MR !1505 review CP-3

Previous audits named "the ssh tool authenticating with RSA keys" as the
only exposure. That is wrong twice over, verified on this tree:

1. **The named path is dead by label, and the label check is bypassable.**
   The built-in ssh tool refuses RSA (`ic/src/tools/builtin/ssh.rs`: the
   `SSHKeyType::Rsa` arm errors out before connecting, pinned by
   `test_rsa_key_rejected`) — but only on the *declared* key-type label.
   `ic/src/bridge/ssh_client.rs` `parse_key` /
   `russh::keys::decode_secret_key` parses whatever key material it is
   given, so RSA material uploaded under an `ed25519` label still reaches
   the vulnerable signer.
2. **The live path is the tenant SSH agent that signs for untrusted
   worker containers.** `ic/src/bridge/ssh.rs` loads *every* configured
   host key from the secrets store into `SshAgentServer` with no algorithm
   filter; `ic/src/bridge/ssh_agent.rs` `confirm_request` returns `true`
   (no per-request confirmation) and the socket is mode `0o666`;
   `ic/scripts/lunarwing-mt-admin.sh` (`ssh-agent-dir-ro` in the
   `OPENCODE_ROOTLESS_LAUNCH_CONTRACT`, `OPENCODE2_ROOTLESS_LAUNCH_CONTRACT`
   and `PEBBLE_ROOTLESS_LAUNCH_CONTRACT`; `mt-admin-lib/07-units-systemd.sh`
   bind-mounts the socket read-only and exports `SSH_AUTH_SOCK`) mounts
   that agent into the opencode, opencode2 and pebble worker containers,
   which AGENTS.md treats as untrusted. The signing chain is unblinded:
   vendored russh `keys/agent/server.rs` SIGN_REQUEST → ssh-key
   `SigningKey::try_sign` → rsa `pkcs1v15` `sign::<DummyRng>(None, …)`,
   and `rsa` blinds only when an RNG is supplied. A tenant that configures
   an RSA host key therefore exposes unlimited chosen-message RSA
   signatures with fine-grained local timing to any prompt-injected or
   compromised worker — exactly what the advisory's workaround says to
   avoid.

Reachability: confirmed by code trace above (also confirmed in the MR
!1505 lead review). Whether rc.18's crypto-bigint signing leaks
exploitably in this configuration is unverified; a timing harness against
`SigningKey::try_sign` would settle it and is **not** part of this audit.

**Clearing path (owned by WI#331, not this item):** reject RSA key
material by *parsed algorithm* (not label) at key upload and at agent
load, then drop the russh `"rsa"` feature — `cargo tree -i rsa` shows only
russh and ssh-key pull it in. Until then the advisory stands accepted.

Upstream re-verification (crates.io sparse index, 2026-10-10): libsql
0.9.30 (max stable) and 0.10.0-pre.4 (newest) still request
`hyper-rustls ^0.25` / `hyper ^0.14` / `tonic ^0.11`, so a libsql bump
today keeps the chain (#1–#5). The advisory text still declares
`patched = []` and names rsa 0.10.0-rc.18; rsa 0.10.0-rc.19 has since been
published but the advisory is unchanged (rc.19 is published, not marked
patched) and russh 0.64.1 (latest) still requests `rsa =0.10.0-rc.18` as
an optional dep (#6). failure 0.1.8 is the final release (#7–#8).

**Downgrade protection:** the advisory ignores are keyed by ID, which
cannot fire if a future lockfile regresses the *patched* copy. `[bans]`
denies `h2 >=0.4.0, <0.4.19` and `rustls-webpki >=0.103.0, <0.103.15`,
flooring the patched lines while leaving the accepted legacy copies
(0.3.27 / 0.102.8) outside the denied ranges. Every committed lock
currently sits at h2 0.4.20 / rustls-webpki 0.103.15 on the patched
lines (h2 moved 0.4.19 → 0.4.20 in the item-1 sweep, MR !1507).
