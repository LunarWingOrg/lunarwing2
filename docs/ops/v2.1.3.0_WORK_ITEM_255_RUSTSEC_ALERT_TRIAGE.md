# Work Item 255 — RUSTSEC-2026-0101 Alert Triage

**Date:** 2026-09-28

**Source branch:** `rarity/kimi-45-20260928-1647`

**Work item:** https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/255

**Goal:** determine whether the alerts-daemon alert about `RUSTSEC-2026-0101`
labelled "PyPI Critical Vulnerability" / "CVSS 9.1" / "bump PyO3" is a
hallucination, and whether any action is needed in this repo.

## TL;DR

The alert is **misattributed**, and its "action" (bump PyO3 in
`Cargo.toml`) is **not applicable as stated** — but the underlying concern
is not entirely baseless. Findings:

1. **RUSTSEC-2026-0101 is not a PyO3 advisory.** The real
   [RUSTSEC-2026-0101](https://rustsec.org/advisories/RUSTSEC-2026-0101) is
   about the crate `safe-agent-rs`, removed from crates.io on 2026-04-13 for
   affiliation with malicious code (same owner as `pretty-changelog-logger`
   and `microsoftsystem64`). It has no CVSS, no patched versions, and nothing
   to do with PyO3 or PyPI. The alerts-daemon fused the ID with the wrong
   advisory text.

2. **`safe-agent-rs` is not in any LunarWing dependency graph.** Grep across
   every `Cargo.toml`/`Cargo.lock` in the repo (including
   `ic/bridges/xmpp-bridge/Cargo.lock`) finds zero references.
   `cargo deny check advisories` against the advisory DB fetched fresh today
   (HEAD `ef03605` "Assigned RUSTSEC-2026-0312 to x509-validator",
   2026-09-28) reports `advisories ok: 0 errors, 0 warnings`.

3. **PyO3 *is* pinned in the lockfile, but is not compiled.** Both
   `ic/Cargo.lock` and `ic/bridges/xmpp-bridge/Cargo.lock` pin `pyo3
   0.28.3` — but only as the *optional* `python` feature of `jiter 0.13.0`,
   which `monty 0.0.17` (git dep of `lunarwing_engine`) enables **without**
   `python`. Verified with `cargo tree -i pyo3 --target all` → "nothing to
   print" on both lock roots; `jiter` resolves only `num-bigint`.

4. **The related advisory the item hints at (RUSTSEC-2026-0176) is real but
   does not currently flag.** [RUSTSEC-2026-0176](https://rustsec.org/advisories/RUSTSEC-2026-0176)
   is the PyO3 out-of-bounds read in `BoundListIterator::nth` /
   `BoundTupleIterator::nth` (affected `>=0.24.0, <0.29.0`, patched
   `>=0.29.0`). Our lock pins `pyo3 0.28.3`, which is inside the affected
   range **if it were compiled**. `cargo-deny 0.20.2` filters it out because
   the crate is not in the resolved (built) dependency graph — only in the
   lockfile. This means the advisory is invisible to `cargo deny` today
   while the lockfile entry remains.

## Risk assessment

- **Current risk: none.** No LunarWing binary compiles pyo3; the vulnerable
  `Bound*Iterator::nth` code paths only exist when jiter's `python` feature
  is on, and nothing in the workspace enables it (`monty` does not forward a
  `python` feature; its own features are `memory-model-checks`,
  `ref-count-return`, `test-hooks` only).
- **Latent risk: low but real.** The pinned `pyo3 0.28.3` sits in the
  affected range. If a future `monty`/`jiter` update starts enabling
  jiter's `python` feature (or LunarWing adds a Python host bridge), the
  advisory becomes live and `cargo deny` will start failing with no prior
  warning. Today that failure mode is masked by the lockfile-only pin.

## Recommended actions

1. **No code change required for #255 itself.** The alert was a
   misattribution; `safe-agent-rs` is absent; `cargo deny check advisories`
   is green.
2. **The alerts-daemon labeling/freshness review requested in the work item
   stands on its own merits** (out of scope for this repo — the daemon is an
   external service). Its ID→text fusion produced "PyPI Critical
   Vulnerability" for a crates.io malware-removal entry and quoted a CVSS
   9.1 that no RustSec record carries.
3. **Optional hardening (not done here):** bump `jiter`/`pyo3` off 0.28.x,
   or add a `cargo tree`/`cargo deny` gate asserting pyo3 stays out of the
   built graph, so a future feature flip surfaces as a loud error rather
   than a silent lockfile entry. Blocked on upstream: `monty 0.0.17` at rev
   `5c7cf2b6` requests `jiter 0.13.0` and does not forward a `python`
   feature, and `jiter 0.13.0`'s `python` feature pulls `pyo3 0.28`.
