# Goal 30 — Mission Output "Not Saving Into Memory": Root Cause and Fixes

> **Goal item:** `docs/ops/AGENT_GOALS_2.1.0.0.md` item 30
> **Date:** 2026-09-03
> **Branch:** `cmc/item-44-20260903-1831` (fix commit `e146a43ce`)
> **Scope:** investigation + source fixes + live reproduction and verification.

## The report

"Look into issue of missions not saving output properly into memory and fix
if possible."

The concrete instance is Kageho's security-audit mission (Engine V2,
rev 5 spec): each mission thread is supposed to persist an audit note that
later threads and the operator can find again. From the operator's chair the
failure presented as both "the mission didn't save its output" and "the agent
can't find output it saved" — indistinguishable symptoms with very different
causes.

## What is actually broken (TL;DR)

**Persistence is not broken. Recall is.** Mission threads persist output
correctly through CodeAct `__save_memory_doc__` → engine store → workspace
file (`engine/knowledge/{type}/{slug}--{id8}.md`) → chunked into the search
index. Kageho verified this with tools on her own host: three audit threads
(#4–#6) produced on-disk files and knowledge notes that existed *before* the
question "did you save it" was asked. Her earlier "confabulation confession"
was itself the second-order failure: a real retrieval miss produced a false
"it was never saved" narrative, which was then written to memory and
re-verified against after restart.

Three recall-layer defects each **fail closed to an empty result**, and an
empty search result reads to a model as "the data does not exist":

1. **Embedding-provider failure aborted the whole search.**
   `Workspace::search_with_config` (`ic/src/workspace/mod.rs`) propagated any
   `provider.embed(query)` error as `WorkspaceError::EmbeddingFailed`,
   failing the entire query — keyword search never ran. One embedding-backend
   hiccup therefore presented to the agent as "memory search failed/empty".

2. **FTS AND-semantics: one stray word kills the query.**
   `plainto_tsquery('english', $3)` requires *every* query lexeme to match a
   chunk. Agent-formed natural-language queries routinely contain words that
   do not appear in the target document, so the strict pass returns zero rows
   even when strong matches exist. Verified live on tenant `derpy` (pre-fix
   binary):
   - `fix_pattern_database` → 5 hits (the data exists and is indexed)
   - `fix_pattern_database zebra unicorn` → **0 hits**
   - `what did the fix pattern database learn about trace patterns this week`
     → **0 hits**

3. **Engine `RetrievalEngine` zero-overlap filter was a no-op.**
   `retrieve_context` (`ic/crates/lunarwing_engine/src/memory/retrieval.rs`)
   filtered candidates with `combined_score > 0`, but the doc-type priority
   bonus (0.05–0.5) keeps every score positive, so *no document was ever
   filtered* — zero-relevance docs ranked as matches purely on type weight,
   and genuinely matching docs could rank below unrelated higher-type docs.

## Persistence path (traced, for future readers)

- Mission outcome (`process_mission_outcome_and_notify`,
  `runtime/mission.rs`) records the final response in
  `Mission.approach_history` (unbounded, never truncated) and broadcasts a
  `MissionNotification` to `notify_channels`. It does **not** write memory by
  itself — persistence is the thread's job via tools.
- Mission threads write via CodeAct `__save_memory_doc__`
  (`executor/scripting.rs`, mission-only, raises on failure) → engine `Store`.
- On LunarWing, the engine store is the **hybrid workspace adapter**
  (`ic/src/bridge/store_adapter.rs`): memory docs become workspace files under
  `engine/knowledge/{type}/{slug}--{id8}.md`; `engine/.runtime/**` holds
  runtime state and is excluded from search indexing
  (`is_search_indexable_path`).
- Workspace documents are chunked (`memory_chunks`) into the hybrid search
  index (Postgres FTS `content_tsv` + optional pgvector embeddings).
- `memory_search` (the tool agents and the gateway `POST /api/memory/search`
  actually call) searches this index. Both surfaces therefore see mission
  output — **when the query succeeds**.

Live cross-check on `derpy` (2.1.0.0 dev, ENGINE_V2=true): 3,887 `engine/`
workspace documents under a single user scope; `engine/knowledge` 911 docs /
1,003 search chunks; `engine/.runtime` 2,966 docs / 0 chunks (correctly
excluded); gateway `memory_search` returns engine-knowledge hits.

## Fixes (two commits)

First commit `e146a43ce` — recall reliability:

1. **Degrade on embedding failure** (`ic/src/workspace/mod.rs`): a failed
   `embed()` logs a warning and the search continues keyword-only, instead of
   erroring the whole query.
2. **FTS OR-relaxation second pass** (`ic/src/workspace/repository.rs`,
   single- and multi-scope): when the strict `plainto_tsquery` pass returns
   zero rows, one relaxed pass runs with `to_tsquery('english', ...)` over
   the query's alphanumeric terms OR-joined. The term builder
   (`fts_or_query`) splits on every non-alphanumeric character, so no
   tsquery operator syntax can be injected through user text; terms are
   deduplicated and capped at 24.
3. **Honest relevance filtering + never-empty fallback**
   (`lunarwing_engine/src/memory/retrieval.rs`): candidates are filtered on
   `keyword_score > 0` (the original intent; filtering the combined score was
   a no-op). When *no* document matches any keyword, retrieval degrades to
   doc-type-priority + recency ordering instead of returning empty — weak
   context beats a false "not found".

Second commit `5696c184d` — mission doc-writer availability (found live, see
below):

4. **`__save_memory_doc__` resolvable in mission rlm children.** The live
   probe thread could not call `__save_memory_doc__` at all — every attempt
   raised NameError and the model honestly pivoted to `memory_write` with a
   custom path, losing doc_type/tags/metadata. Root cause:
   `handle_rlm_query` hardcodes child threads as `ThreadType::Research`,
   while the mission-only host function registers on `ThreadType::Mission`
   alone — code executed inside a mission's rlm child could never resolve
   the name. Fix: `ThreadConfig.mission_child` (serde default) is set by
   `handle_rlm_query` when the parent is a Mission; both the NameLookup
   registration and the `handle_save_memory_doc` guard accept it. Research
   semantics (inherited leases, anti-recursion) are unchanged.
5. **Mission system prompts advertise the function.** `__save_memory_doc__`
   is a host function, not a leased action, so it never appears in the
   action list the model sees; mission threads' system prompt now names it,
   its doc_type set, and its raise-on-failure contract. Without this every
   user-created mission had to guess at the mechanism (the compiled-in
   learning missions carry their own prompts and were never affected).

## Side observations (not fixed here)

- **Turn-level upstream flakiness**: the tenant LLM upstream (TensorZero,
  LAN) intermittently failed streaming turns tonight ("error decoding
  response body" on derpy; several gateway turns ended `Failed` with empty
  responses on probe30 until a retry succeeded). Environmental, not source;
  noted because empty assistant turns superficially resemble the recall
  failures investigated here.
- **mission_create during a turn that later fails leaves orphaned missions**:
  two failed creation attempts still persisted Active mission records with
  the same webhook path, so one webhook fire matched two missions
  (`missions_fired: 2`). The rev-5 mission spec's verification-gate
  discipline (never re-run mission_create after partial failure) covers the
  operator side; an engine-side dedupe on (name, webhook path) is a tracker
  candidate.
- **Goal-phrase auto-complete trap is real**: probe-1's charter did not
  include the spec's banned-phrase clause, the model ended its honest report
  with "GOAL ACHIEVED: YES", and the mission auto-Completed after one run
  (`mission.rs` response parsing; pitfall 5 of the rev-5 spec). User-created
  missions remain exposed to this unless their goal text carries the
  contract.
- `fix_pattern_database` docs are re-seeded as *new* documents instead of
  updating one canonical doc (three duplicates with distinct ids observed on
  `derpy`, created 08-21, 09-02, 09-03). Harmless for recall, wasteful for
  corpus growth; tracker candidate.
- `Mission.approach_history` stores full responses unboundedly — the opposite
  failure direction of this report (data can never be lost), but corpus
  growth is unbounded. Tracker candidate.
- derpy's pre-existing mission `29rc1-hourly-live-test` had exhausted its
  daily thread budget (10/10) during testing — budget behavior working as
  designed, noted to avoid confusing it with a defect.
