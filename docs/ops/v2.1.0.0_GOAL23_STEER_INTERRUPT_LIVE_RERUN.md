## Issues found along the way (documented and/or fixed)

1. **mt-admin OpenRC LLM_BASE_URL broken without `--enable-proxy` — FRESH
   FINDING, operator-fixed on the tenant; root cause open.** A fresh
   `add-tenant falcon --tensorzero-url http://192.168.1.157:3000` on OpenRC
   (proxy disabled by default; `tenant_proxy_enabled` false) wrote
   `LLM_BASE_URL=http://192.168.1.157:3000` — the bare TensorZero root. The
   daemon's OpenAI-compatible client POSTs `<LLM_BASE_URL>/chat/completions`;
   a bare TensorZero gateway answers `404 {"error":"Route not found: POST
   /chat/completions"}`, so **every LLM turn failed** with the gateway-visible
   "The model provider kept failing after retries and one recovery attempt."
   while `/api/health` stayed `healthy` and all channel plumbing looked fine.
   Fix applied in-tenant: `LLM_BASE_URL=http://192.168.1.157:3000/openai/v1`
   + `restart-tenant` (LLM_BASE_URL is a documented operator knob; the
   `--enable-proxy` default-`v1` path is the in-tree alternative).
   Recommendation: when the proxy is disabled, env-generation should derive a
   path-aware `LLM_BASE_URL` (append `/openai/v1` to a bare upstream root), or
   enable the local proxy by default on OpenRC too — follow-up work item. Not
   to be confused with the known AGENTS.md note about the upstream
   `/openai/v1/models` probe; this one breaks **all** tenant LLM traffic
   while every health check stays green.
2. **Steer cannot influence an in-flight single-batch tool plan — BEHAVIOR
   BOUNDARY (intentional), now documented.** With FrontierTEED composing all
   10 `memory_write` calls in ONE assistant round (one LLM round → 10
   parallel tool calls, observed in the first G2 attempt), a mid-turn steer
   queued and acked correctly but could not change anything: the batch was
   already fully composed; the note is injected only at the NEXT LLM round,
   and there was none before the summary. The second, sequential-mandated G2
   run (one write per LLM round) reproduced item 9's signature exactly
   (note 01 ponies pre-steer, notes 02–10 dragons post-steer). Boundary:
   steer influences **future LLM rounds**, never an in-flight batch. Not a
   defect — the queuing/injection path is what item 3 specified; documented
   here so evaluators don't mistake batch shape for a steer regression.
3. **Interrupted turns still render `Failed` in gateway v1 turns-history —
   reconfirmed (item-9 finding #5).** The G1 interrupted thread shows
   `state=Failed, tools: 0`. Harmless but operator-misleading; keep the
   item-9 recommendation (explicit Interrupted state) in the follow-up queue.
4. **Priority-control vs queued-prompt race — expected semantics reconfirmed.**
   A fast-completing 10-note turn (~100 s warm engine) finishes before a
   harness-delayed control lands; the control then correctly answers
   `Nothing to interrupt.` Controls govern RUNNING turns by design (same
   class as item-9 finding #4).
5. **Transient upstream flake — NOT a bug.** One W2 attempt hard-failed with
   `model provider kept failing … failure_kind=transient` at 20:08 UTC during
   a LAN-TensorZero hiccup; the immediate retry passed. Noted for completeness.
6. **Harness-only artifacts (not product issues), recorded so the false
   negative can't mislead a future run:** an early `wc_driver` run reported
   "no reply" because its IRC reader raced an asyncio pump task
   (`readuntil() called while another coroutine is already waiting` — pump
   silently dead); a tmux-less `nohup miniircd` died between tool calls; and
   WeeChat's default finite `autoreconnect_count` ran out during mock
   downtime until pinned infinite via fifo `/connect miniircd`. All three
   were fixed in the harness; the product was innocent (relay `/api/input`
   loop-verified by direct manual test: relay input → outbound `PRIVMSG`
   reached miniircd intact).
7. **Pre-existing exclusions reconfirmed:** `tools-src/gitlab` stale lockfile
   still fails the wasm build loop (`build-tenant --with-wasm` → `FAILED:
   gitlab`; `install-wasm` reports "11 installed, 2 skipped (not built)" —
   same exclusion as items 9/11). Darkirc channel correctly **skipped** on
   this `enable_darkirc=false` tenant (item-9 fix #3 still working).
