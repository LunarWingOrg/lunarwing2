### F1 — Concurrent appends to the same document fail with 500 (product bug, MEDIUM)

- Symptom: 24/40 concurrent `append:true` writes to one path returned
  `500 Document chunking failed: Insert failed: db error`.
- Postgres evidence: `duplicate key value violates unique constraint
  "unique_chunk_per_doc"` (`ic/src/workspace/repository.rs` chunk insert).
- Cause: concurrent append transactions both replace chunk rows for the
  same `document_id` with overlapping `chunk_index` values; the unique
  index rejects the loser. No retry/serialization.
- Impact: **loud** failure (good: no silent corruption — all 16 successful
  appends landed intact, zero mangled lines); but any integration that
  appends to a shared doc (daily logs!) from concurrent contexts will see
  intermittent 500s. The `append()` doc comment claims "concurrent
  appenders cannot lose writes" — true for content SQL-concat, false for
  the chunk-replace step that follows.
- Recommendation: serialize per-document chunk replacement (advisory lock
  on document_id) or retry on 23505.

### F4 — LLM intermittently skips the tool call and claims success (behavioral, worth documenting)

- In same-thread sequential multi-tool turns, the model (FrontierTEED)
  skipped the `memory_write` call on ~20–40% of turns, then replied as if
  it had written ("The text `payload-trace-08-72226` has been saved to
  `memory/stress/trace/0…").
- Verified via `engine/.runtime/events/<thread>.json`: no `ActionExecuted`
  for those turns; DB row never changed (even +30s). Not a LunarWing
  data-plane bug — everything dispatched was executed faithfully.
- Product-level takeaway: agent self-reports of memory writes are not
  trustworthy; verification workflows must read back. Also observed one
  cosmetic `FINAL` pseudo-action error `No lease for action 'FINAL'`
  (turn completed normally).

### F2 — ws_adapter ↔ WeeChat relay WebSocket: perpetual reconnect churn (MEDIUM)

- `ws_adapter.py` v0.3.0 connects with aiohttp `heartbeat=25` (ping every
  25s, pong required within 12.5s). WeeChat 4.7.2's relay WS never answers
  protocol pings → **every connection dies ~44s in** with `No PONG received
  after 12.5 seconds`, reconnects 5s later, forever. 177 such events in
  ~80 min of logs; `/api/health` flaps `degraded` in each window.
- Impact: cosmetic-but-constant churn; item #1's in-process backfill makes
  it lossless, but health sampling is flaky (H1 caught it) and every cycle
  re-syncs. Fix: drop `heartbeat` (rely on relay traffic) or use
  application-level `ping` requests the relay understands.

### F3 — ws_adapter PROCESS restart loses messages accepted while down (HIGH for channel users)

- `restart-weechat-adapter` mid-burst: all 12 messages that WeeChat had
  accepted into the buffer around the restart were **never delivered** to
  the agent (0/12; adapter healthy after; new messages flow fine — H5).
- Cause: adapter state (`last_line_id` watermarks, event log) is
  in-memory. On process start, the first connect *seeds* watermarks from
  current buffer contents without replaying (the item-#1 behavior intended
  for first-ever connect), so lines accepted while the adapter was down
  are classified as history and skipped. The backfill path only covers WS
  reconnects within the same process.
- Fix direction: persist per-buffer watermarks (tenant state dir) and
  distinguish first-ever connect (no state file → seed) from restart
  (state file → backfill from persisted watermark).

## Harness errata (for the record)

- First P2 runs reported false failures: the completion check matched the
  marker in the *user's own message* in thread history. Fixed by requiring
  ≥2 occurrences (user + assistant). Also: history `tool_calls` are
  cumulative across the thread and truncated (~6 previews) — not suitable
  for per-turn attribution; engine events are the reliable source.
- First P3 run used self-messages (`/api/input` into the buffer), which
  the channel correctly skips via `self_msg`; real IRC delivery requires
  an actual server — hence miniircd. A harness-side IRC parsing bug
  (trailing-parameter split) initially delivered only the first word,
  which *looked* like a channel truncation bug (`content_len=5`); it was
  the harness, and the product was innocent.
- H2's one "miss" was answered at 96s vs a 90s timeout (cold engine for a
  fresh channel thread); delivery was 10/10.
