# v2.1.0.0 — HTTP MCP Header Secret References (`--secret-header` / `header_secrets`)

**Status:** implemented on `cmc/mcpoauth210/v2.1.0.0`, verification below.
**Origin:** live deployment gap — hosted HTTP MCP servers that authenticate with
a static `Authorization: Bearer` header could not be installed conversationally:
`tool_install` exposes no header parameters for HTTP transport, and the only
native credential path is OAuth, which non-OAuth servers fail during activation
(auth discovery 404s, server lands inactive despite `authenticated: true`).
Header values were previously CLI-only literals persisted into
`mcp-servers.json`.

## What was added

- `McpServerConfig.header_secrets: HashMap<header name, secret name>`
  (`ic/src/tools/mcp/config.rs`) — owner-scoped secret references for HTTP
  headers, mirroring `env_secrets` for stdio. Serde-defaulted, omitted when
  empty, so existing `mcp-servers.json` files are untouched.
- `--secret-header KEY=SECRET_NAME` on `lunarwing mcp add` (http transport
  only; mutually exclusive with `--client-id`). `mcp update` preserves the
  mapping like plain headers.
- `tool_install` / web install accept `headers` (literal) and `header_secrets`
  (secret references) for http transport; transport defaults to `http` when a
  url plus header fields are provided. Secret-bearing installs force the
  Always approval requirement, same as `env_secrets`.
- Factory: `resolve_http_header_secrets()` resolves every reference through
  the activating owner's secrets store at activation and injects the resolved
  values into the server's header map before client construction. Fails closed
  (missing store, missing secret, wrong owner). When `header_secrets` is
  configured the OAuth path is skipped entirely — stored tokens, including
  stale ones from earlier auth attempts, cannot override the resolved header
  (client.rs already skips OAuth Bearer injection when a custom
  Authorization header exists; the adapter now also refuses the
  authenticated-client path so no refresh/discovery is ever attempted).

## Semantics

- The secret value **replaces the header value entirely**: for
  `Authorization: Bearer lwst_…`, store the full `Bearer lwst_…` string as the
  secret.
- Validation (`McpServerConfig::validate`): http transport only; RFC 9110
  header-name checks, case-insensitive duplicate detection against plain
  headers, managed-header rejection (`mcp-session-id`, `content-type`,
  `accept`, gateway routing headers), and plain-vs-secret conflict rejection.
- Resolution is per-activation and owner-scoped; decrypted values never enter
  persisted configuration.

## Operator usage

```bash
lunarwing mcp add study-notes https://mcp.lunarwing.org/mcp \
  --secret-header "Authorization=lw2study_hosted_token" \
  --description "LunarWing2 study notes (hosted)"
lunarwing mcp test study-notes
```

Conversational equivalent for agents (no secret value ever appears in the
conversation): install with
`{"name": "study-notes", "url": "https://mcp.lunarwing.org/mcp",
"transport": "http", "header_secrets": {"Authorization": "lw2study_hosted_token"}}`.

## Addendum (same day): requires_auth suppression + live verification

Live tenant verification (derpy) exposed one more gate: `requires_auth()`
returned `true` for any remote HTTPS server, so `mcp test`, `tool_activate`
and list labels demanded OAuth for `header_secrets`-authenticated servers and
`test` refused before ever dialing. `requires_auth()` now returns `false`
when `header_secrets` is configured (static credentials satisfy auth).
Config tests cover the suppression, the stdio rejection, plain/secret
conflicts, and managed-header reservation.

Live result: `lunarwing mcp add --secret-header` on the derpy tenant
persisted the reference, `mcp toggle --enable` activated the server with the
resolved Bearer header ("Connected … and loaded tools"), and the hosted
study-notes server (~1,336 documents) answered authenticated requests.
