## Verdict

**PASS — the WI#97 repository fix works end to end.** Two temporary LunarWing
tenants joined the same real XMPP MUC through separate bridge processes and
exchanged `KNOW:` records in both directions. The merged publisher matcher
accepted both documented forms:

- a full occupant JID (`room@server/nick`) as an exact, nick-pinned publisher;
- a room bare JID (`room@server`) as an explicit room-wide opt-in.

It rejected both forms that must remain unauthorized:

- a user bare JID (`user@server`) did not match a MUC occupant sender;
- another occupant nick in the same room did not match an exact full-occupant
  entry.

The receiver databases held the expected durable records with the full MUC
occupant in `submitted_by`, `needs-verification` status, the `coordination` tag,
and the coordination-wire sentinel. No repository defect was found and no code
change was needed.

The original `sunburst` and `ruffles` production tenants were not changed. This
run instead exercised the same contract on isolated throwaway tenants, as item
27 permits. The public tracker was still `opened` when queried on 2026-09-03.

## Tracker analysis reconciled

The discussion on WI#97 contains contradictory recommendations. Ruffles' source
analysis is the correct one for MUC traffic:

- XMPP groupchat `sender_id` is the full occupant JID;
- before commit `d3ea2ebe6`, publisher matching was exact
  case-insensitive equality, so a user bare JID could not match that sender;
- the merged hardening now additionally strips the occupant nick and compares
  the resulting room bare JID.

Consequently, the issue body's and final Sunburst comment's claim that
`user@server` is the correct `COORD_KNOWLEDGE_PUBLISHERS` value is stale and was
live-disproved below. Current valid MUC entries are the exact full occupant JID
or the room bare JID. The repository documentation already states this
correctly.

## Findings

1. **WI#97 is fixed in the repository.** The room-bare fallback works on the
   full live transport, and exact full-occupant matching still preserves its
   narrower trust boundary.
2. **The room-receive configuration remains mandatory.** Both
   `XMPP_ALLOW_ROOMS_JSON` (bridge) and the daemon/installable-channel room
   configuration were populated. Empty means no MUC join and inbound groupchat
   denial by design; the example file warns about this.
3. **User bare JIDs are not a MUC publisher identity.** This was proved both by
   source and by a delivered live message that the hook ignored. Operators must
   not follow the stale user-bare recommendation still present in the tracker.
4. **Room-bare allowlisting is intentionally broad.** It survives nick changes
   but trusts every occupant identity the room forwards. Exact full-occupant
   allowlisting is safer when only one stable nick should publish.
5. **Harness-only setup note:** Prosody's default new-room locking let the first
   occupant create the room but held the second occupant out until the mock MUC
   was configured with `muc_room_locking=false`. After correcting the isolated
   server configuration, both bridges immediately reported room presence. This
   was not a LunarWing failure.
