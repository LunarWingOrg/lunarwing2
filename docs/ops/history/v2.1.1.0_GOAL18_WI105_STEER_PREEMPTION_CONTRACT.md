## The question goal #41 left open

WI#105's original report conflated two controls: `/interrupt` during a
120-second shell tool, and `/steer` during the same. Goal #41 verified the
interrupt half fixed (in-flight tool futures are cancellable through the run
token) and stated that steer intentionally waits for the current step — but
flagged that whether WI#105 *expects* steer to preempt a tool "needs reporter
clarification or an explicit scope decision".

## Scope decision (resolved)

**Steer is an inject-after-current-step control, not a tool-preemption
control. No preemptive-steer feature will be built for 2.1.1.0.** Grounds:

1. **The tracker question is moot.** WI#105 was closed on 2026-09-05, before
   this item started, with the interrupt half demonstrably fixed and live-
   verified (item 43 / G1c: `/interrupt` during a 120s in-flight shell tool
   aborted the turn ≤5s after the control). No reporter follow-up remains.
2. **The current contract is the safer one.** A steer note is advisory input
   to the model, not a control-plane signal. Making it cancel an in-flight
   tool would give a plain text-adjacent command side-effect semantics that
   `/interrupt` already owns, and would blur the interrupt/steer division the
   2.1.0.0 release notes document.
3. **The composition already covers the demand.** "Stop this long tool and
   redirect" is `/interrupt` + `/steer`: the interrupt cancels the tool, and
   the steer note (queued during the interrupt race, per
   `steer_after_xmpp_interrupt_reaches_next_turn`) lands on the next turn.

## The contract, source-verified

Mechanics on the current tree (anchors at the inspected revision):

- The bridge wraps the note (`wrap_steer_note`,
  `ic/src/agent/dispatcher.rs:406`) and routes it through
  `inject_message` (`ic/src/bridge/router.rs:2864-2926`), which sends
  `ThreadSignal::InjectMessage` on the thread's signal mailbox
  (`ic/crates/lunarwing_engine/src/runtime/manager.rs:976-1022`). Send is
  refused for cancelled threads; failure falls back to durable next-turn
  queueing.
- The signal is consumed only by `__check_signals__`
  (`ic/crates/lunarwing_engine/src/executor/orchestrator.rs:1865-1884`),
  which the Python loop polls once per iteration
  (`ic/crates/lunarwing_engine/orchestrator/default.py:1061`), i.e. at the
  next model-call boundary — after the current tool's result.
- The cancellation token — not the inject signal — wraps `__execute_action__`,
  `__execute_actions_parallel__`, and `__execute_code_step__`
  (`orchestrator.rs:481-556`), so only `/interrupt` can abort an in-flight
  tool.
- The legacy classic loop has the same boundary semantics
  (`ChatDelegate::check_signals`, `ic/src/agent/dispatcher.rs:415-430`).

**New regression pin** (this item):
`injected_steer_note_waits_for_in_flight_tool_and_lands_at_next_boundary`
(`ic/crates/lunarwing_engine/src/executor/orchestrator.rs`) drives the exact
loop host-call order around one barrier-synchronized tool call and proves the
note queued mid-tool: does not abort the tool (its `ActionExecuted` event
exists), does not stop the thread (`Completed`), and is appended to the
durable transcript as a user message before the turn's final assistant
message. It complements the existing cancellation pin
(`cancelled_code_step_aborts_in_flight_tool`): together they pin both halves
of the WI#105 mid-turn control contract.

**Contract statement added** to `docs/architecture/ENGINE-V2.md` (Channel
Routing And Delivery section) so the architecture doc states the exclusion
explicitly, not just the injection behavior.

## If preemptive steer is ever wanted

That would be a new feature, not a bug fix — a semantic change to the
control plane. Minimum scope if ever approved: a distinct signal variant
(e.g. `ThreadSignal::InjectAndPreempt`) or an explicit steer flag, routed
through the same cancellation token the interrupt uses, with a decision on
whether the preempted tool's lease use is refunded, plus boundary tests for
the parallel-batch and CodeAct child cases. Nothing in 2.1.1.0 requires it.
