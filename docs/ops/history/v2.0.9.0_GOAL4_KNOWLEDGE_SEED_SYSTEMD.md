## Verification contract

Item 3 introduced two provisioning invariants that required a live systemd-host
check:

1. A newly created tenant using `add-tenant --with-study-mcp` is armed exactly
   once, imports the current shared lw2studymcp checkout on first daemon startup,
   preserves knowledge metadata, and does not rerun after restart.
2. A tenant created from a pre-seed commit remains unarmed and empty after the
   real `upgrade-tenant` path moves it to the seed-capable branch.

All tenant lifecycle and status operations used
`ic/scripts/lunarwing-mt-admin.sh`; tenant unit status came from each tenant's
systemd user manager, not the system bus.

## New tenant: `aj4new`

`aj4new` was provisioned directly from the tested branch with
`--with-study-mcp --no-health --no-ssh --no-weechat-bootstrap`, then release
built and started through mt-admin.

Before first start:

- tenant checkout was exactly `d52dc11e9fbbc395a7c5413c6996e471995a5340`;
- `KNOWLEDGE_SEED_FROM_STUDY_MCP=1` occurred exactly once in
  `lunarwing.env`;
- mt-admin had rendered systemd user units and the PostgreSQL Quadlet was active.

The first daemon startup completed the background import. Journal evidence was:

```text
Seeded tenant knowledge store from lw2studymcp checkout seeded=1249 skipped_existing=4
knowledge seed: 2 note(s) failed ... seed is complete and will not rerun
```

The two failures were the same upstream empty-body notes recorded by item 3.
The marker at `~/lunarwing/state/knowledge_seed_state.json` recorded:

```text
notes_seeded=1249
notes_skipped_existing=4
notes_failed=2
source_home=/var/cache/lunarwing/lw2studymcp
```

Direct PostgreSQL verification found 1,249 `study-notes/%` documents. All 1,249
had `provenance=study-note`, and all had the required `agent`, `topic`, and
`status` metadata. A metadata spot check returned a correctly paired path,
agent, topic, status, and provenance.

After `restart-tenant aj4new`:

- the marker SHA-256 was unchanged;
- the provenance-qualified row count remained 1,249;
- no new `Seeded tenant knowledge store` journal entry appeared;
- `lunarwing-aj4new.service` and the expected selected systemd services were
  active according to `mt-admin status`.

This verifies the one-shot and no-repopulation behavior under a systemd user
manager.

## Existing tenant upgrade: `aj4old`

`aj4old` was created with `--with-study-mcp` from pre-seed commit
`1ac605cf6f4efcd6fac39df3b0f0ff9146284eb4`. That snapshot contains the Study
Notes MCP provisioning path but has neither the knowledge-seed module nor any
`KNOWLEDGE_SEED_FROM_STUDY_MCP` reference.

Before upgrade, with the old daemon running under systemd:

- the seed env flag occurred zero times;
- no `knowledge_seed_state.json` marker existed;
- PostgreSQL contained zero `study-notes/%` documents;
- mt-admin reported the tenant daemon and expected systemd user services active.

The actual upgrade path then ran:

```text
upgrade-tenant aj4old --target aj/kimi-4-20260824-1202 \
  --source-repo <temporary-accessible-bare-source> --no-backup
```

The source was mirrored under `/tmp` and mt-admin was launched from `/` so the
unprivileged tenant Git process had a traversable working directory. The first
attempt from the operator's non-traversable home failed safely during `git
fetch`, before checkout or service stop; no tenant state changed. The corrected
run checked out the tested commit, release-built LunarWing and the XMPP bridge,
built and installed all 13 WASM extensions, re-rendered systemd units, patched
the env, and started the tenant successfully.

After upgrade and again after a separate `restart-tenant aj4old`:

- the checkout was exactly `d52dc11e9fbbc395a7c5413c6996e471995a5340`;
- the seed env flag still occurred zero times;
- no seed marker existed;
- PostgreSQL still contained zero `study-notes/%` documents;
- no knowledge-seed journal entry appeared;
- `lunarwing-aj4old.service` and the expected selected systemd services were
  active according to `mt-admin status`.

This verifies that `upgrade-tenant` does not arm, populate, or repopulate an
existing tenant on systemd.
