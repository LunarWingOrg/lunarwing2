## Fixed this cycle

### 1. RUSTSEC-2026-0285 reachability (carried from !1264 via !1262, re-verified)

**rustls accepted TLS 1.3 handshake messages sent at the wrong encryption
level** when they followed a key-changing message in the same record, violating
RFC 8446 §5.1; a peer could send messages that should be encrypted in
plaintext without rustls rejecting the connection. Functionally the same bug
as Go's GO-2026-4340 (CVE-2025-61730). Patched in `rustls >= 0.23.45`.

- Advisory: <https://rustsec.org/advisories/RUSTSEC-2026-0285>
  (GHSA-2mjx-qc3c-rqvc).
- Reached via `reqwest → hyper-rustls → rustls` in the pebble worker image
  (upstream pinned at a commit with rustls 0.23.41), the pebble mirror tree,
  and ocr-sidecar. The `ic` main workspace was already on 0.23.45.
- The remediation (reviewed patched-lock build input with digest gate,
  canonical `PEBBLE_LOCK_SHA256` default, complete-record allowlist,
  `build_inputs` classification, worker-image CI coverage) landed through
  !1262 and is the baseline this audit re-verified — not re-applied here.

### 2. Restored no-op override rejection (`04dd93103`)

!1262's checker consolidation had dropped !1264's no-op rejection: once the
pinned upstream lock ships its own rustls fix, a stale override would
silently keep building from the reviewed input instead of surfacing the
change. `check_package_delta` now requires at least one allowlisted record to
actually change and prints every override it accepted; the regression suite
gained `test_noop_override_rejected` and
`test_earlier_version_record_edit_rejected`.

### 3. Retired the yanked `chacha20 0.10.1` pin (`3998522ab`)

The reviewed override inherited upstream's yanked chacha20 0.10.1. The patched
lock now pins 0.10.2 (semver-identical, no advisory either way), the guard
allowlist admits `chacha20` with rationale, `PEBBLE_LOCK_SHA256` is refreshed
to `e58df660…`, and the regression fixtures cover it.
