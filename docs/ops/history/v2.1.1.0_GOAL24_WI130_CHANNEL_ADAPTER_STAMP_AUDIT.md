## 1. Executive verdict

**The WI's central hypothesis is refuted on the current tree — a wrong stamp cannot merge two rooms' LLM contexts.**

- `IncomingMessage::is_shared_conversation()` (`ic/src/channels/channel.rs:162-178`) does **not** gate Engine-V2 context collapse. Context merging is decided solely by the engine conversation key `engine_conversation_key(message)` = `(channel:scope, user)` (`ic/src/bridge/router.rs:90-95`), and every shipping Engine-V2 adapter attaches a real per-room / per-peer / per-principal scope.
- The stamp-derived `shared_conversation` flag drives **approval gating only**, and every consumption point fails closed (blocks approvals in shared rooms; never widens anything).
- Vector 4 (conversation create-on-miss) was a real defect whose hardening was **lost** (it existed only as uncommitted working-tree state on Sep 8 and never reached any commit). It has been **re-landed on this branch** (§7) with tests.
- One claim from comment 2554 is materially wrong and is corrected in §6: weechat *does* have a group-auth-status suppression — it is keyed on `is_dm`, not on the shared flag, and weechat's delivery of approval prompts to groups is a deliberate, bounded policy (analysis and test evidence in §6).

**One trust note for the record:** comment 2555 (cmc) asserted the V4 hardening was "applied, cargo check clean, 18/18 tests" — true at the time, but the work was uncommitted and did not survive the worktree move. This is the second recorded incident of uncommitted WI-130-adjacent work evaporating; the re-landing in this branch closes it.

## 2. The guard, exactly as it stands (`channel.rs:162-178`)

```rust
pub fn is_shared_conversation(&self) -> bool {
    self.metadata.get("chat_type")    == Some("group")
    || self.metadata.get("xmpp_type") == Some("groupchat")
    || (self.channel.ends_with("-relay")
        && self.metadata.get("event_type") != Some("direct_message"))
}
```

Three OR branches: `chat_type == "group"`, `xmpp_type == "groupchat"`, or a `-relay`-suffixed channel whose `event_type` is anything but `direct_message`. Its own unit test (`channel.rs:721-739`, `shared_conversation_detects_groups_but_not_direct_messages`) pins exactly the WI's contract: xmpp groupchat → shared, signal group → shared, `darkirc-relay` + `channel_message` → shared, `darkirc-relay` + `direct_message` → **not** shared (the relay DM guard), xmpp DM → not shared. Verified verbatim.

## 4. What actually decides context collapse (the mechanism the WI feared)

1. Engine-V2 routing: `gateway` always; only `xmpp`, `darkirc`, `weechat` may opt in via `ENGINE_V2_CHANNELS` (`router.rs:40` `ENGINE_V2_OPT_IN_CHANNELS`, `router.rs:50-74`). Signal, multica, http, repl are legacy-loop only.
2. Conversation key: `engine_conversation_key` = `channel:scope` when the message carries `conversation_scope()` (= `conversation_scope_id` falling back to `thread_id`, `channel.rs:204-209`), else bare channel (`router.rs:90-95`).
3. Conversation lookup: `get_or_create_conversation(&channel_key, &message.user_id)` (`router.rs:3421-3428`) — per `(scope, user)` surfaces; a foreground thread per conversation.
4. The stamp is consulted **after** all of that, only to fill `ThreadConfig.shared_conversation` (P1), which flows to D2.

Conclusion: **the delimiter between two rooms is the scope key, not the stamp.** For a stamp to cause cross-room context merging, an adapter would have to (a) omit the scope *and* (b) the two rooms would need to collapse into one `(channel:scope, user)` key. Verified: no shipping adapter omits scope (§5). The WI's "the stamp is the only thing standing between two rooms and one merged LLM context" was inaccurate for the current tree — the scope key is the delimiter; the stamp's blast radius is approvals.

## 6. Weechat approval routing — answering comment 2554's open questions

**Q1: "does an approval prompt on a weechat GROUP go to the whole room?"** Yes — deliberately, and it is safe.

- Weechat's status suppression is **keyed on `is_dm`**, not on the shared flag: `should_suppress_auth_status` (`channels-src/weechat/src/lib.rs:1477-1482`) suppresses `AuthRequired`/`AuthCompleted` (OAuth URLs, setup secrets) in non-DM buffers, and `should_suppress_external_waiting` (`:1498-1500`) suppresses `ExternalWaiting`. **Approval prompts and job-started notices are documented as intentionally deliverable to groups** (`:1470-1474` doc comment, enforced at the send path `:859/:866`).
- So comment 2554's "verify whether an equivalent suppression exists for weechat groups" resolves to: **an equivalent for the dangerous statuses exists** (auth secrets — the actual leak vector it worried about); the approval-prompt difference vs XMPP is a *policy* difference, not a missing guard. XMPP suppresses **all** status delivery in groupchats (`channels/xmpp/mod.rs:1181-1186`, "surfacing approval prompts in shared rooms would let anyone in the room answer").

**Why the weechat policy is still safe — gate authorization is per-principal:**

- The engine gate is keyed `PendingGateKey { user_id, thread_id }` (`gate/pending.rs:14-17`) and created with `user_id = message.user_id` (`router.rs:409`) — for weechat that is the **sender's principal** (`lib.rs:1690`), not the room.
- Resolution filters `list_for_user(message.user_id)` **and** requires the same scoped conversation **and** the same source channel (`scoped_pending_gates`, `router.rs:2042-2056`; `gate_channel_matches` `:2018-2021`; atomic `take_verified` at `:2440-2442`).
- Therefore participant B's `yes` in the group carries B's principal, misses A's gate in `list_for_user`, and cannot resolve it. Only the participant whose message triggered the gate can approve it — and they can do so from the group or a DM.
- Test evidence pins scoped resolution for exactly these shapes: weechat DM-scope `yes` resolves only the DM gate and never the group gate (`router.rs:8894-8933`), gateway `yes` is thread-scoped (`:7896-7962`), darkirc scope isolation (`:8810-8819`).
- Exposure that remains: other participants *see* the prompt (parameters are redacted before display, `router.rs:400-404` / `PendingGate.display_parameters`, `gate/pending.rs:48-49`). That is a deliberate information-sharing choice by the weechat adapter, bounded to redacted content.

**Q2: "is `is_dm` fully consistent with the host's `is_shared_conversation()`?"** They measure different things and the divergence is now well-characterized: `is_dm` (weechat's own transport-level truth) gates *status delivery*; the host stamp gates *approval availability*. For weechat the stamp is always false, so the host treats weechat groups like DMs for approval availability — acceptable because per-principal gate auth holds (above). A host-side equivalence is **not required for safety**; it would only be cosmetic unification. (Sweetiebot's medium-confidence worry "approval prompts / auth-status lines could be delivered into weechat GROUP buffers where any participant can read (**or answer**) them" — the "answer" half is refuted; the "read" half is deliberate and redacted.)

## 7. Vector 4 — `get_or_create_conversation` create-on-miss: defect confirmed, hardening lost, re-landed

**Defect (confirmed against current `crates/lunarwing_engine/src/runtime/conversation.rs:72-114`):**

1. **TOCTOU duplicate creation.** Lookup order is (a) read-lock index probe, (b) `store.list_conversations(user)` scan, (c) create + write-lock insert **without re-checking the index**. Two concurrent first messages on the same key both pass (a) and (b), each create a surface and persist it; the index keeps whichever write lands last and the other surface is orphaned — its history becomes unreachable while reads keep succeeding. History **loss**, never cross-injection (keys remain proper IDs).
2. **Silent scoped-miss creation.** A scoped key `channel:scope` should already have a surface (bootstrap or prior turn). Creating fresh on a scoped miss silently severs the scope from its prior turns — the "amnesia masquerade" the WI described. Persisted-conversation re-linking (`conversation.rs:87-100`) covers the common restart case, but a scoped miss with no persisted surface still created silently at `debug!` level.

**History of the fix:** comment 2555 / KB topic `engine-conversation-create-hardening` recorded a hardening applied 2026-09-08 @`7ee88ac14` — "(1) re-check the index under the write lock before inserting; (2) `warn!` when creating a conversation for a *scoped* key" — explicitly **uncommitted**. Verified against this tree on 2026-09-10: **the change was absent** (file had no `warn!` import, no re-check, no `contains(':')`). The full hardened file had been pasted into WI comment 2581 ("code in comments"), which is what made reconstruction possible.

**Re-landed on this branch** (this goal's code change), matching the pasted version's logic exactly:

- write-lock re-check of `channel_user_index` before insert (first-writer-wins; closes the race);
- `warn!` on scoped-key (`channel.contains(':')`) creation, so a scope suddenly missing its surface is operator-visible instead of silent history restart;
- lookup order, tenant-ownership checks, and the unscoped fast path unchanged. Log-not-fail is retained deliberately (failing would brick scopes across restart/topology gaps — same rationale as the original).

**Verification:** `cargo test -p lunarwing_engine --lib conversation::` green (§10); the write-lock re-check path is unreachable single-threaded, so no new deterministic unit test (same conclusion as the original note; existing get_or_create/bootstrap tests pin behavior).

## 8. Residual vectors (post-audit, ranked)

- **B′ — unscoped third-party WASM channels (the only live isolation-adjacent gap).** WASM host ingestion maps `thread_id → with_thread` and, when scope is still absent, derives a scope from `routing_target_from_metadata` (`channels/wasm/wrapper.rs:937-947`, keys `signal_target|chat_id|target|xmpp_target|xmpp_room` at `channels/channel.rs:224-258`; ingestion at `wrapper.rs:2817-2877`). A registry-installed channel emitting neither **collapses all its messages per `(channel, user)` into one conversation**. The four bundled adapters are all safe (§5); the *adapter contract* ("multi-context channels must emit a scope") is undocumented. Recommendation: document it in the channels spec and consider a host-side warn on unscoped emissions from non-bundled channels.
- **D — XMPP room JID == peer bare JID (exotic, operator misconfig).** `target_jid = room_jid ?? sender_bare` (`xmpp/mod.rs:1586`) + `user_id = target_jid` (`:1615`): a MUC whose JID equals a user's bare JID makes DM and room share uuid5 scope *and* user id → one conversation. Recommend an xmpp-config sanity check/warn.
- **E — stamp-contract drift (cosmetic today).** Legacy `is_group_chat` (`dispatcher.rs:70-74`) accepts `chat_type ∈ {group, channel, supergroup}` (Telegram-isms) for MEMORY.md exclusion, while `is_shared_conversation()` accepts only `group`. No adapter stamps `channel`/`supergroup` (verified), so today this is unreachable; if one ever did, that stamp would get MEMORY.md exclusion *without* approval gating. Recommendation: widen the guard or narrow the legacy check in one small commit.
- **Non-finding:** for XMPP groupchat the inbound `user_id` is the **room JID** shared by all participants (`:1615`) — i.e., inbound identity is room-scoped by design ("the room is the user"). Combined with per-principal keys elsewhere this *looks* like an approval-risk (any participant's `yes` shares the gate's user id), but D1/D2/D3 all fire for shared conversations and block the gate path entirely — fail-closed on top of the identity quirk.

## 12. Recommendations

1. **Land the V4 hardening** (done on this branch; see §7). Keep it in any eventual merge.
2. **Document the WASM adapter scope contract** (B′): multi-context channels must emit `thread_id` (or recognizable routing metadata) or their messages collapse per `(channel, user)`. Add a host warn for unscoped emissions from non-bundled channels.
3. **Close drift E** in a small follow-up: make `is_shared_conversation()` and the legacy `is_group_chat` accept the same `chat_type` set (widen one, narrow the other — widening the guard is the safer direction: fail-closed).
4. **XMPP config sanity (D):** warn at connect time if a configured MUC JID equals any allowed peer's bare JID.
5. **Relay adapter contract (V2):** any future `-relay` channel must stamp `event_type=direct_message` on DMs; failure mode today is fail-closed (approvals blocked), which is acceptable, but the contract should be written down next to `is_shared_conversation`.
6. Optional policy harmonization: weechat delivers (redacted) approval prompts to groups while XMPP suppresses all group status — both safe; pick one policy if adapter parity ever matters for UX.
