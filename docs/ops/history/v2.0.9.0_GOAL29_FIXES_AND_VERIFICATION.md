## Fix 1 — F1: concurrent appends to the same document (commit `00dd6552`)

- Root cause: `append()` updates content atomically in SQL, then calls
  `reindex_document()` → `replace_chunks()`, a DELETE+INSERT transaction on
  `memory_chunks`. Two concurrent appenders to the same document interleave
  their chunk replacement and the loser violates `unique_chunk_per_doc`
  → 500 "Document chunking failed: Insert failed".
- Fix: `lock_document_chunks()` takes a transaction-scoped
  `pg_advisory_xact_lock(hashtextextended(<document_id>, 0))` inside BOTH
  chunk-replacement transactions (`replace_chunks`,
  `update_document_and_replace_chunks`) in
  `ic/src/workspace/repository.rs`. Only same-document writers serialize;
  unrelated documents proceed in parallel; locks auto-release at commit.
  libSQL relies on its existing single-writer serialization (unchanged).
- Regression coverage: `ic/tests/workspace_concurrent_append_postgres.rs`
  (`DATABASE_URL`-gated) replays the 40-way scenario at the `Workspace`
  level: zero failures, all markers present exactly once, document still
  searchable.

## Fix 2 — F3: adapter process restart message loss (commits `8ba70dda`, `50300ccb`)

- Root cause: per-buffer `last_line_id` watermarks lived only in adapter
  memory. On process start the first connect *seeded* watermarks from
  current buffer contents (correct only for a first-ever start), so lines
  the relay accepted while the adapter process was down were classified as
  history and never delivered. Live verification additionally exposed a
  SECOND window with the same loss shape: lines accepted by the dying
  process but not yet drained by the WASM poller's 30s `/api/wait` cadence
  (see V2 below) — fixed by journaling inbound events.
- Fix (ws_adapter v0.3.0 → v0.4.1,
  `lunarwing_weechat_wss/weechat_relay/ws_adapter.py`):
  - Watermarks persist to a state file, default
    `$LUNARWING_BASE_DIR/weechat-adapter-state.json` (every mt-admin tenant
    unit already exports `LUNARWING_BASE_DIR` to the tenant state dir; no
    unit/env changes required). Override: `WS_ADAPTER_STATE_FILE`;
    `none` disables.
  - Atomic tmp+rename write on every watermark advance (and on
    buffer-close cleanup). Best-effort: failures log, never drop a line.
  - Startup with an existing state file ⇒ treated as a RESTART: first
    connect backfills from the persisted watermark exactly like an
    in-process reconnect. No state file ⇒ first-connect seeding (no history
    replay), preserving the intended item-#1 behavior.
  - Watermarks older than 7 days are discarded (WeeChat line ids are not
    stable across a WeeChat restart); corrupt files fall back to fresh.
  - Inbound events journal to an append-only `<state-stem>-journal.jsonl`
    (compacted to the newest 2000 entries past ~4 MB) and restore on
    startup with ORIGINAL seq numbers — closing the unpicked-events window.
  - `/api/health` exposes `state_file`, `persisted_watermarks`, and
    `journal_file`.
- Regression coverage: 13 new pytest cases in
  `lunarwing_weechat_wss/weechat_relay/ws_adapter_tests.py` (suite 27/27
  green), including direct replays of both H4 windows at the
  `recover_after_connect`/journal level.

tenant (file copy + adapter restart — the adapter is a Python script run
