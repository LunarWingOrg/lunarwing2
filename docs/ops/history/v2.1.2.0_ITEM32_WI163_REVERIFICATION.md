`ensure_learning_missions` / `ensure_self_improvement_mission`
(`ic/crates/lunarwing_engine/src/runtime/mission.rs:1589-1760`) manages the
same five missions, all `OnSystemEvent` on terminal/lifecycle events other

| Mission | source | event_type |

Nothing consumes `thread_start`. This matches the WI#126 decision ("keep the
existing default fleet; add no default thread-start mission") recorded in

### 2. thread_start producer exists — the 09-07 "one-line swap" landed

- `ExecutionLoop::run` transitions the initial Created → Running via
  `transition_to_broadcast` (`loop_engine.rs:341-348`), broadcasting the
  `StateChanged` event to subscribers (mission listener, gateway SSE).
- `start_event_listener` (`mission.rs:1247`) matches
  `StateChanged { from: Created, to: Running }` and fires `engine/thread_start`
  via `fire_on_system_event` (`mission.rs:1065`) — restricted to top-level
  Foreground threads; Mission threads skipped at `:1285` (no recursive
  spawning) and parented children at `:1300` (no research-child fan-out).
  Dedup rides the `source_thread_id` payload key.
- `transition_to_broadcast` second call site: `loop_engine.rs:543` (Failed
  transition on orchestrator error). Same-file call sites only.
- Regression suite: `thread_start_fires_once_for_fresh_foreground_thread`,
  `thread_start_does_not_fire_for_mission_or_research_threads`,
  `thread_start_child_foreground_thread_does_not_dispatch`,
  `thread_start_resumes_do_not_dispatch`, `thread_start_isolated_per_user`,
  `thread_start_duplicate_delivery_deduplicates`
  (`mission.rs:6005-6260`).

### 3. The cadence grammar can now spell the trigger

`parse_cadence` (`ic/src/bridge/effect_adapter.rs:1076`) accepts
`system:<source>/<event_type>` (`:1096-1110`) → `MissionCadence::OnSystemEvent`,
the only variant `fire_on_system_event` matches (`mission.rs:1092`). The
`mission_create` capability schema documents it (`router.rs:1549`). Lint:
`create_mission`/`update_mission` reject an `OnEvent` cadence whose pattern is
a known system event type (`mission.rs:2026` area,
`KNOWN_SYSTEM_EVENT_TYPES` at `types/mission.rs:188-193`), so a
`event:thread_start` mis-registration is refused at the door instead of being
born dead. Registry honesty: `mission_list` surfaces
`last_fired_at`/`never_fired` (`effect_adapter.rs:411-431`).
Tests: `effect_adapter.rs:1288-1358` (system grammar, normalization,
rejections) and `mission.rs:3900-4010` (create/update lint).

### 5. dwarfstar's secondary finding (09-16 note on #109)

"`mission_list`/`mission_fire` are unwired from the tenant session" does not
hold at the capability level: both are registered as `missions` capability
actions in `ic/src/bridge/router.rs:1537-1578` (list/fire/pause/resume/
create/update), which is the tenant-session tool path. If a tenant still
cannot probe missions, the cause would be deployment-specific (stale tenant,
capability attenuation, or old binary), not a repo gap. Repo-side, the
failure mode *is* visible to tenants: `mission_list` now reports
`last_fired_at`/`never_fired` per mission.
