## Batch 1 — implemented contracts

### G8-F1 — instruction authority

- Both prompt builders require the self-modification policy explicitly. The
  execution loop supplies the same host-selected policy to prompt-overlay and
  runtime-orchestrator loading. A persisted overlay does not become new system
  instructions when `ORCHESTRATOR_SELF_MODIFY` is off.
- Generic memory writes no longer treat `metadata.source == "compiled_in"` or
  the `orchestrator:failures` title as proof of internal origin. Native compiled
  seeding and failure bookkeeping call `Store::save_internal_memory_doc`;
  `__save_memory_doc__` cannot select that entry point.
- The host writer and production store reject control-doc writes while the gate
  is off. Reserved `prompt:` / `orchestrator:` title prefixes and control tags
  are protected independently, including renamed tagged docs.
- The mission manager assigns insight workers a typed `MissionContext`, inherited
  by their children. Their host writer refuses shared and maintenance outputs
  even when self-modification is enabled. An opted-in maintenance mission can
  still save a runtime patch.

### G8-F3 — purpose-specific automatic recall

- Insight meta-prompts and first-step host retrieval use the conversational
  maintenance exclusion and positive whole-token relevance policy.
- The recall query comes from the current trigger's goal/message samples, never
  the generic extraction program or generated next focus. An absent/empty batch
  has no fallback recall. `__retrieve_docs__` arguments and mutable REPL state
  cannot replace the host-owned query or enable maintenance recall.
- Relevant prior knowledge retains source IDs and fixed untrusted labels.
  Explicit tools such as `memory_search` remain separate from automatic recall.

### G8-F5 — generated-history feedback

- Insight prompts exclude both `current_focus` and `approach_history`, including
  legacy values. Their output instructions request supporting evidence instead
  of a next agenda, and outcome processing does not adopt a new generated focus.
- Run reports remain in mission history for operational inspection. A no-save
  run therefore leaves an audit record without feeding its claims into the next
  extraction prompt.
- The extraction prompt now describes the batch contract accurately; the batch-1
  description of goal/message sampling was superseded by batch 2's
  host-verified `sources` (see G8-F2 below).

### G8-F9 — honest durable saves

- `HybridStore` propagates serialization/workspace content-write errors before
  publishing a MemoryDoc or its path in the in-process cache.
- A failed rename write preserves the existing durable document, cache value,
  and source path. The old file is deleted only after the new write succeeds.
- A store-local write lock serializes document persistence/cache publication.
  Workspace-less stores retain their intentional in-memory semantics.
- This path uses the existing `Workspace::write` content/chunk contract. It does
  not alter the distinct append-committed/index-repair contract.

## Batch 2 — implemented contracts

### G8-F2 — identified, eligible user evidence

- Top-level Foreground threads capture each ingested `User`-role message as an
  `InsightSource` (fresh, untruncated, with message/thread/conversation
  identity and timestamp) at `Thread::add_message` time. Inherited history and
  programmatic goals do not enter this collection: spawned goals, steer notes,
  and system injections are minted as `ThreadMessage::generated_goal`
  (`Provenance::LlmGenerated`), and `inject_message_system` forces
  `Provenance::System`.
- A batch admits only `Done` top-level Foreground threads in the firing
  project/user that carry only complete, bounded user inputs. Research children,
  mission threads, failed threads, other users' or other projects' threads,
  legacy pre-upgrade threads (no captured inputs), and truncated inputs are
  ineligible. Missing evidence therefore fails closed instead of sampling by
  role label.
- Eligibility bounds are whole-thread: a conversation whose captured inputs
  exceed the per-statement (8,000-character) or per-thread (16,000-character)
  limit is entirely ineligible — a single oversized paste (e.g. a pasted log)
  disqualifies that conversation's other statements too. This is deliberate
  fail-closed behavior: partial or truncated evidence is never extracted, and
  the cost is losing that one conversation's learning, not corrupting it.
- Batch selection (`runtime/insights::select_batch`) is deterministic: ordered
  by durable `(completed_at, thread_id)`, five threads minimum, and a
  content-derived identity (`insights:v2:<project>:<sorted message ids>`)
  rather than a counter.
- Insight triggers ignore caller-supplied payload content entirely;
  `fire_mission_inner` reconstructs the batch from persisted threads under the
  mission fire lock and re-seeds `state["trigger_payload"]` with it. The recall
  query derives only from the batch.
- The extraction prompt describes the new `sources` contract, including the
  generated-goal/legacy exclusions and the distinction between "what the user
  said" and "a true claim".

### G8-F4 — host-validated evidence and stable insight identity

- A new Store entry point, `save_conversation_insight`, is the only write path
  for insight threads. `__save_memory_doc__` routes insight-context calls to
  it; unsupported adapters deny the write (fail closed).
- The writer re-validates every citation against the persisted source thread
  in the same project/user scope: the quote must equal the entire captured user
  statement, the source must still be an eligible top-level Foreground thread,
  and the run must be one this mission actually reserved (`thread_history`
  membership) with a current status and generation.
- `metadata.insight` is a typed request (`InsightRequest`, deny-unknown-fields):
  `kind` (`explicit` or `inferred`) plus complete citations. Explicit content
  must equal the cited user statement verbatim; an inferred record is a
  hypothesis over one evidence set.
- The host mints the durable identity itself: titles (`insight:<kind>:<DocId>`),
  the `insight` tag, and metadata are overwritten, so model-supplied titles,
  tags, and trust metadata cannot become a second assertion channel. Explicit
  statements upsert by exact content; inferred records upsert by evidence set,
  so paraphrases cannot mint duplicates.
- Run budget: at most five distinct accepted insights per run id, enforced by
  the writer, not the prompt. The first save returns a stable DocId that the
  upsert path reuses.
- Automatic recall excludes insight-shaped docs unless they carry a
  host-minted, current-version `InsightRecord` of `Explicit` kind whose sources
  are complete and equal to the doc content. Inferred records stay inspectable
  via explicit tools but never ride automatic recall, so prior generated
  insights cannot become independent user corroboration. A statement that
  conflicts with an earlier explicit insight is simply a new explicit
  statement — both are kept.
- The insight record round-trips through knowledge-doc frontmatter
  (`insight:` JSON line) so a fresh store reload preserves classification and
  citations.

### G8-F6 — project-scoped event dispatch

- `fire_on_system_event` now takes the dispatching project as a host-supplied
  argument; a mission only fires when its project matches the event's project.
  All internal dispatch sites (thread start, diagnosis, skill extraction,
  skill maintenance, conversation insights, expected behavior) pass the source
  thread's project. The bridge's `user_feedback/expected_behavior` dispatch
  passes the reporting thread's project.
- Same-user cross-project mixing from the report (one event firing project B's
  mission with project A's payload) is no longer reachable through this path.

### G8-F7 — restart-safe batch identity

- The per-conversation in-memory completion counter is gone. The mission
  persists an `InsightCursor` (`completed_at`, `thread_id`) with the durable
  reservation, so the consumed batch boundary survives restarts.
- Redelivery of the consumed batch cannot re-fire (cursor is not advanced past
  nothing new), and a genuinely newer batch cannot collide with an old
  processed key because identity is content-derived from message ids, not
  `insights:<project>:<count>`.
- Durable source scanning in `tick` also catches completions that raced their
  event's persistence, broadcast lag, and work accumulated at restart —
  "every five" is no longer best-effort-only.

### G8-F8 — explicit opt-out, purge, and recreation semantics

- Deleting a conversation-insights mission is now an explicit, persistent
  opt-out: the mission record persists as a `Paused` tombstone with
  `deleted_at`, and its `insight_generation` is bumped so any in-flight or
  suspended writer from the old run fails the write gate. In-flight runs are
  stopped.
- Startup reconciliation and same-name `create_mission` dedupe onto the
  tombstone instead of resurrecting it. An explicit `resume_mission` clears the
  tombstone and re-enables extraction from the **resume point** forward
  (skip-until-resume): conversations completed while the mission was paused or
  tombstoned are deliberately never learned, so no disabled-window backlog
  fires on re-enable. The same semantic applies to an operator pause/resume —
  statements made while the mission was disabled are not extracted later. This
  is the chosen behavior; it trades a learning gap during the disabled window
  for not replaying opted-out or experiment-paused content.
- `mission_delete` accepts `purge_insights` (conversation-insights only): the
  host purges only **host-minted insight records** (docs carrying a validated
  insight record) in that exact project/user scope; user- or model-authored
  docs that merely carry an `insight:` title or `insight` tag are never
  destroyed by it, because the flag is model-invocable. Source conversations
  and run audit history are retained. The tool description documents the
  tombstone semantics.
- Operator pauses continue to survive gate reconciliation as before.

## Verification (batch 2)

- Batch selection admits only eligible user sources — excludes mission/research
  goals, other users/projects, legacy threads without captured inputs, and

  advances strictly past the cursor with a distinct content-derived identity.

## MR !1043 review fixes (batch 2a)

Four findings from the !1043 review of `eecf9a4fb` were addressed:

1. **Purge scope (medium):** `purge_conversation_insights` now filters on the
   host-minted insight record (`doc.insight.is_some()`) instead of the broad
   `is_insight` title/tag predicate — a model-invocable purge can no longer
   destroy a user-authored doc titled `insight:` or tagged `insight`. The
   store regression now proves such a doc survives alongside ordinary lessons.
   The trait doc states the narrowed contract.
2. **Resume semantics (medium):** skip-until-resume stands (code unchanged);
   the documentation no longer claims a "deletion-time cursor". Resume
   re-enables from the resume point, and the disabled window — for an opt-out
   *or* a brief operator pause — is explicitly documented as never replayed,
   including the learning-gap trade-off.
3. **Oversized inputs (minor):** the whole-thread eligibility bounds
   (one >8k-char statement disqualifies its conversation's other statements)
   are now documented as deliberate fail-closed behavior.
4. **Trait comment (minor):** `Store::save_conversation_insight` now documents
   the actual serialization contract — validation+publication serialize with
   mission lifecycle persistence (status/generation bumps through
   `save_mission`) and with purge; insight missions are tombstoned rather
   than hard-deleted, so `delete_mission` never interacts with insight
   documents, and validation fail-closes on missing/inactive/unreserved runs.

## Compatibility and remaining work

- No database migration or dependency update is required. New mission/thread
  fields (`insight_cursor`, `deleted_at`, `insight_generation`,
  `conversation_id`, `insight_inputs`, `generation`) have serde defaults for
  old records. The new Store entry points (`save_conversation_insight`,
  `purge_conversation_insights`) deny by default; the production adapter
  implements them under its document write lock. Other Store adapters must
  opt in explicitly to support insight runs.
- Legacy thread records have no captured `insight_inputs` and fail closed for
  extraction: they are never selected as sources. Pre-upgrade accepted
  insight-shaped lessons (title/tag without a host record) no longer ride
  automatic recall; they remain loadable through explicit tools. `purge_insights`
  does not remove them — purge is restricted to host-minted records because it
  is model-invocable and cannot distinguish those lessons from user-authored
  notes; remove legacy insight lessons explicitly if needed.
- These controls govern newly assembled prompts and newly configured insight
  runs. Existing transcripts/checkpoints can already contain old system text or
  retrieved material; upgrading does not scrub them. Use fresh runs for the
  controlled incident experiment. Old suspended insight threads predate the new
  purpose/batch fields and fail the write gate; drain them before comparing
  behaviors.
- Restoring an older binary restores the metadata-based write exception,
  ungated overlay loader, counter-based batch identity, cross-project event
  dispatch, and hard mission deletion. Preserve the hardening when backporting;
  keep operator pauses and incident evidence intact during any rollback.
- **All nine G8 findings are now implemented** (F1, F3, F5, F9 in batch 1;
  F2, F4, F6, F7, F8 in batch 2). Stale-file cleanup after a successful rename
  remains best-effort, as before; the G8-F9 regression targets failed content
  writes. Inferred insights are kept for inspection but never auto-recalled;
  promoting one would require a new, explicit decision.
- The September 16 response still requires its original tenant/build/provider,
  thread/time, trace, and persistence evidence for causal attribution.
