# Standing Advisory Ownership Record — the doc-only clearing owner for `ic/deny.toml`

**Date:** 2026-11-21

**Work item:** [#779](https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/779)
— "Re-home the 12 advisory acceptances whose clearing owners WI#367 and
WI#418 closed without clearing"

**Policy file:** `ic/deny.toml`, `[advisories].ignore`

**Standing decision record.** This document is the clearing owner for the 14
advisories accepted in `ic/deny.toml` (nine heapless entries cleared by
WI#934 on 2026-11-28). Every `reason` string ends with
`clearing owner docs/ops/v2.2.2.0_STANDING_ADVISORY_OWNERS.md`, and this
document lists each accepted advisory ID as the first cell of a row in its
"Accepted advisories" tables. It replaces the four closed work
items that previously held those owner tokens: WI#367 (closed
2026-10-18T06:22:49Z), WI#418 (closed 2026-10-18T06:22:33Z), WI#749 (closed
2026-11-17T15:48:52Z) and WI#781 (closed 2026-11-20T07:37:51Z). Each of them
closed while its pinned crates were still locked, so each left standing
acceptances without an owner that can be re-verified.

## Why the owner is a document and not a work item

WI#418 established the rule this record now applies to itself: **a closed work
item cannot own a standing acceptance**
(`docs/ops/v2.1.6.0_WI418_LIBSQL_LEGACY_CHAIN.md`, "Standing decision
record"). It was filed for exactly the failure it later repeated — the item
was re-opened on 2026-10-17 for this reason and closed again about seven hours
later with the chain still locked. WI#749 and WI#781 repeated it in the same
window: #781 accepted nine heapless advisories and was closed hours later,
becoming the ninth-owner of nine acceptances on the day it closed.

A tracked document has no closure event. It is the only owner shape that stays
valid for as long as the pins stay locked, and it is checkable offline:

- `.gitlab/scripts/validate_config.py` (`validate_deny_toml_advisories`)
  requires every `[advisories].ignore` reason to name
  `clearing owner <repo-relative>.md`, requires that path to be a tracked
  path, and requires the document to list the entry's advisory ID as the
  first cell of a table row; a mention elsewhere, such as the superseded
  table below, does not count. An acceptance whose owner record is deleted,
  untracked, renamed, or loses that row fails the `ci-config` lane.
- Owner liveness stays out of scope, per the unchanged WI#363 scope decision
  of 2026-10-20: whether a *work item* is open cannot be checked offline and
  an online gate could only run failed-allowed against a tree whose owners
  were already closed. The doc-only model removes the question instead of
  trying to poll it.

`.gitlab/tests/test_deny_toml_guards.py` carries the fixture and negative
cases for that check, and the suite runs in the `python-unit` job.

## What this record does not change

The accepted set is byte-for-byte the same set of advisory IDs before and
after the re-home: 23 entries at that change, no ID added, removed or
re-worded in a way that widens exposure, and no `[bans]` restriction touched. Only the owner token and
the prose that named a closed work item as owner changed. The re-home
carried over the exposure analysis from the v2.2.1.0 crate security audit
(`docs/ops/v2.2.1.0_CARGO_DENY_AUDIT.md`, WI#768), which re-verified every
entry against advisory-db `472a4c9a` on 2026-11-19 and found none removable.

### heapless via postcard and monty — 9 entries, cleared 2026-11-28

**Cleared by WI#934.** All nine rows and their `ic/deny.toml` ignores were
removed together under the entry-removal protocol below. `ic/patches/monty`
is a path patch of Monty at the pinned revision
`5c7cf2b62be8e4421a4828072d41ebe69328bbf2` whose only change is
`default-features = false` on the `postcard` dependency (it keeps
`features = ["alloc"]`); both `ic/Cargo.lock` and
`ic/bridges/xmpp-bridge/Cargo.lock` lost `heapless 0.7.17`,
`atomic-polyfill 1.0.3`, `hash32 0.2.1` and `spin 0.9.9` and gained nothing.
That also drops `atomic-polyfill`'s RUSTSEC-2023-0089 maintenance notice from
the graph. Provenance and refresh notes:
`ic/patches/monty/LUNARWING-PATCH.md`.

The historical analysis, kept for the reasoning it records: at release tree
`c58fcfb26133879aca00b7239d98fd76a3aab60d` and RustSec
`c5279d0b0c9e8b70df666eb6d1edbabcfd1176bd`, all nine advisories matched
`heapless 0.7.17` in both locks. Monty 0.0.17, a git dependency of
`lunarwing_engine`, requested `alloc` and left postcard 1.2.0's defaults on;
the default `heapless-cas` feature pulled in 0.7.17. The other parents
(`wasmtime`, `wasmtime-environ`, `wasmtime-internal-cache`) already disabled
defaults and requested `alloc`; Wasmtime's `std` feature also enables
postcard's `use-std`. Neither `alloc` nor `use-std` pulls in heapless.

Neither heapless API was needed for Monty's snapshot path. In
`ic/patches/monty/src/{run,run_progress,repl}.rs`, `dump` uses
`postcard::to_allocvec` (an `alloc::vec::Vec<u8>`), and `load` uses
`postcard::from_bytes` to deserialize Monty types from a slice.
[RUSTSEC-2026-0577](https://rustsec.org/advisories/RUSTSEC-2026-0577.html)
covered panic safety in `Deque::clear`, `HistoryBuf::{clear,write}`,
`IndexMap::{clear,retain,truncate}`, and `heapless::vec::IntoIter::drop`; the
snapshot path creates no heapless Vec iterator and calls none of the other
affected methods. That was a source-based assessment of these callers, not an
exemption for all uses of `heapless::Vec`.

The `[bans]` rules are unchanged: the direct parent of heapless `<0.9.4`
remains restricted to `postcard`, and postcard `<2.0.0` to `monty`,
`wasmtime`, `wasmtime-environ` and `wasmtime-internal-cache` (WI#788). They
check parent names, not which features an already-allowed parent enables, so
they stay as the tripwire if the old edge returns; cargo-deny reported no
finding and no `advisory-not-detected` on the clearing change.

## Per-release re-verification (standing, owned by this document)

At every release, for each of the 14 entries:

1. Re-read the RustSec record in the current advisory-db revision: does the
   pinned copy still match, is the entry still necessary, and has a patched
   range appeared? An entry that no longer matches must be removed (cargo-deny
   reports it as `advisory-not-detected`).
2. For the eight libsql-chain entries, re-check upstream: latest stable libsql
   and its `hyper-rustls` / `hyper` / `tonic` requirements, and confirm no
   shipped build path enables `libsql-remote-replica` by default.
3. Refresh the `(re-verified YYYY-MM-DD)` markers and version numbers in the
   entry's `ic/deny.toml` comment block and `reason` string.
4. Confirm all four advisory gates are green: `cargo-deny-check.sh`,
   `check-satellite-advisories.sh`, `check-default-graph-advisories.sh`,
   `check-lockfile-only-advisories.sh`; and that
   `python3 .gitlab/tests/test_deny_toml_guards.py` passes.
5. Record the result on the release's crate-security audit item (the v2.2.2.0
   train's audit is WI#768's successor; this document does not close).

## Entry-removal protocol (inherited unchanged)

Remove an `ic/deny.toml` ignore entry only when its clearing upgrade has
landed in `Cargo.lock` **and** the corresponding lockfile root has been
re-checked with `--config` overrides so the advisory resurfaces as a hard
error if it ever comes back. Remove the corresponding row here in the same
change; the guard fails if a `clearing owner` token names a document that
does not exist or has no table row whose first cell is that entry's advisory.
