# v2.1.0.0 — Knowledge Store Resynchronization Options

**Status:** design investigation complete; no synchronization behavior is changed by this document  
**Work item:** [#121 — tenant study layer has no refresh path](https://git.lunarwing.org/lunarwing/lunarwing2/-/work_items/121)  
**Source reviewed:** `aj/kimi-44-20260907-0001` at `74a82a6d27db27b4807795aee52c92d6f39275b6`

## Recommendation

Keep the existing one-shot seed as a cold-start bootstrap. Add a separate,
opt-in `knowledge_sync` subsystem that pulls a revisioned, paginated change feed
from the hosted Study Notes service and reconciles only records that it can prove
it manages. The first delivery should be **additive only** (new upstream notes),
then enable updates and tombstones after per-note source digests, conflict
handling, and crash recovery are proven on both database backends.

Do not automate deletion of `knowledge_seed_state.json` plus tenant restarts.
That reuses a startup bootstrap as a scheduler, causes avoidable service churn,
and still cannot update or remove an existing note.

If the hosted service cannot add an export/change-feed contract in the 2.1
window, a periodic scan of an operator-synchronized checkout is a useful
interim additive refresh. It must be described as checkout freshness, not hosted
store parity: hosted writes may exist before they are committed to that Git
checkout.

Direct hosted-MCP reads are already technically possible and should remain an
operator-selectable live path. They are not by themselves a transparent repair
for the native store because the bundled skill currently calls native
`knowledge_*` tools, while external MCP tools are name-prefixed, and an
always-online dependency changes the native store's offline and migration
properties.

## What exists now

There are two independently useful stores:

1. The central hosted Study Notes MCP, which work item #121 identifies as the
   live source of truth. Its corpus changes continuously.
2. Each tenant's native workspace-backed knowledge store, queried by the
   built-in `knowledge_*` tools and migrated with the tenant database.

The native copy is intentionally a snapshot:

- `sync_study_notes_checkout()` clones or fast-forwards a clean host checkout,
  under a host-side `flock` (`ic/scripts/mt-admin-lib/06-env-generation.sh:114`).
  It runs during provisioning or an explicit `configure-study-mcp --sync`; it is
  not a periodic updater.
- New-tenant `provision_tenant_study_mcp()` syncs that checkout, configures the
  legacy read-only stdio MCP, and calls `arm_tenant_knowledge_seed()`
  (`ic/scripts/mt-admin-lib/09-worker-config.sh:853-883`).
- `KnowledgeSeedConfig` is only enabled by
  `KNOWLEDGE_SEED_FROM_STUDY_MCP=1` and `LW2STUDYMCP_HOME`
  (`ic/src/config/knowledge.rs:59-100`).
- Startup spawns `run_knowledge_seed_once()` in the background
  (`ic/src/app.rs:1200-1219`).
- The importer returns immediately whenever
  `knowledge_seed_state.json` exists (`ic/src/workspace/knowledge_seed.rs:129-157`).
- Even after an operator removes that marker, `seed_note()` skips every existing
  workspace path (`ic/src/workspace/knowledge_seed.rs:183-237`). Therefore a
  forced re-seed imports newly added paths but does not propagate changed
  content, changed lifecycle metadata, supersedure, or deletion.
- The state marker records aggregate counts and the source path, not an upstream
  revision, cursor, per-note digest, or ownership proof
  (`ic/src/workspace/knowledge_seed.rs:97-106`, `493-513`).

The current safety behavior is valuable and must not be weakened: operator
content is never overwritten, malformed notes do not crash the daemon, the
`coord-*` namespace is excluded, and a missing checkout can retry later. See
[`TENANT_KNOWLEDGE_SEED.md`](../guides/TENANT_KNOWLEDGE_SEED.md) and the
[native knowledge proposal](../proposals/study-notes-native-lunarwing-proposal-2.0.6.0.md).

Remote authenticated reads are also available today. HTTP MCP configuration can
resolve an `Authorization` header from an owner-scoped secret without persisting
its value (`McpServerConfig.header_secrets`,
`ic/src/tools/mcp/config.rs:142-152`). The hosted Study Notes endpoint was
live-verified through that path; see
[`v2.1.0.0_MCP_HTTP_HEADER_SECRETS.md`](v2.1.0.0_MCP_HTTP_HEADER_SECRETS.md).
MCP results are marked for sanitization (`ic/src/tools/mcp/client.rs:813-868`).

## The actual synchronization problem

A correct design has to solve four separate problems. Re-running the present
seeder solves only part of the first one.

1. **Discover changes:** new notes, content/metadata updates, and removals or
   tombstones from a stable source generation.
2. **Identify managed records:** distinguish an unmodified imported note from a
   tenant or operator note at the same `study-notes/<agent>/<topic>.md` path.
   Current metadata does not carry a sync origin or source digest;
   `submitted_by=None` is not a safe ownership test.
3. **Apply changes safely:** never overwrite local divergence, never expose a
   half-updated body/metadata pair, and never advance the source cursor past a
   failed write.
4. **Report freshness:** a tenant must not silently claim parity when its source
   is unavailable, its checkout is stale, a cursor expired, or conflicts were
   preserved.

The current seven-tool knowledge API is optimized for agent research, not
replication. `knowledge_list_topics` plus one `knowledge_get_topic` call per
topic could reconstruct much of a corpus, but it is an expensive N+1 crawl with
no generation pin, change cursor, or deletion tombstone. It cannot guarantee a
consistent mirror while writers continue changing the hosted store.

## Required invariants

Any implementation should preserve these contracts:

- **Opt-in and backward compatible.** Existing tenants and the default single
  instance must retain today's behavior until an operator enables sync.
  `KNOWLEDGE_SEED_FROM_STUDY_MCP` remains a one-shot seed flag.
- **Tenant isolation.** Source credentials are owner-scoped secrets. Tokens,
  note bodies, and authorization headers are never written to env-generation
  logs or synchronization state.
- **Preserve local work.** An existing record can be changed automatically only
  when its current digest equals the last digest written by the synchronizer.
  Otherwise preserve it and report a conflict.
- **Consistent generations.** Every page belongs to one immutable snapshot or
  ordered change-log generation. Concurrent upstream writes are consumed on the
  next pass, not mixed into the current one.
- **Cursor correctness.** Advance a cursor only after all records in the page
  are durably applied. Replaying a page must be idempotent.
- **Safe failure.** Serve the last good local corpus during source outages,
  retry with bounded exponential backoff and jitter, and expose stale status.
- **Bounded work.** Cap records, bytes, pages, response sizes, and run duration.
  A synchronization pass must not monopolize embeddings or database writes.
- **Backend parity.** PostgreSQL is primary, but sync-state and workspace
  operations need PostgreSQL and libSQL implementations or an explicitly
  documented PostgreSQL-only boundary.
- **Init agnosticism.** Host checkout scheduling and tenant lifecycle actions go
  through `lunarwing-mt-admin.sh`; systemd user units and OpenRC are both
  first-class. No wrapper may call bare system-bus `systemctl` for a tenant.
- **No implicit trust upgrade.** Synced notes remain research data. Preserve
  provenance and the existing source-verification guidance; do not turn hosted
  content into system instructions.

## Option 1 — Formalize the manual refresh

Add an mt-admin command such as:

```text
lunarwing-mt-admin.sh refresh-knowledge <tenant> [--sync-source]
```

The command would validate the tenant and source, optionally run the existing
flock-protected checkout sync, request one additive import, wait for a report,
and show counts. A daemon control/API call is preferable to deleting a state
file and restarting the tenant. If a control call is not initially available,
mt-admin must own the restart through its existing init abstraction.

**Benefits**

- Smallest operational improvement and a safe recovery primitive for later
  automation.
- Keeps current never-overwrite behavior.
- Gives operators a supported command with an auditable result.

**Limits**

- Not automatic.
- Still additive only unless the importer gains ownership/digest tracking.
- A Git checkout is not necessarily at the same revision as the live hosted
  database.

**Use:** immediate fallback and debugging surface, regardless of the long-term
choice.

## Option 2 — Periodic additive scan of the shared checkout

Split `knowledge_seed` into reusable parsing/import logic plus two callers:

- the existing one-shot startup bootstrap; and
- a new cadence-guarded `knowledge_sync` pass that imports only missing paths.

A host-global systemd timer or OpenRC-compatible scheduler, installed and
managed by mt-admin, would update the shared checkout with the existing
`sync_study_notes_checkout()` lock. Tenant daemons would scan after an atomic
host-published generation marker changes. The daemon should not run `git pull`
or gain write access to the root-managed shared checkout.

Do not attach this solely to the conversational heartbeat. A tenant may disable
heartbeat; source freshness should use its own Tokio interval/cadence state.
Use the stale sweep's `AtomicBool` and persisted-cadence pattern as a reference,
not as a requirement to share its trigger (`ic/src/workspace/knowledge_sweep.rs`).

To avoid reading a checkout while `git pull` changes it, the host updater must
either publish immutable generation directories or atomically write a manifest
only after the checkout validates. A weaker but acceptable prototype can read a
source revision before and after collection and discard the pass if it changed.

**Benefits**

- Reuses the proven parser, validation limits, path rules, and workspace write
  pipeline.
- Preserves local/offline native search.
- Additive mode directly fixes the observed ever-growing document-count gap.

**Limits**

- Does not propagate updates, lifecycle changes, or deletion.
- Requires two schedulers: one host source updater and one per-tenant importer.
- Freshness is bounded by Git publication plus two cadences; it cannot promise
  parity with uncommitted hosted state.

**Use:** acceptable 2.1 interim if server-side export work cannot land.

## Option 3 — Make hosted MCP the primary read path

Configure the hosted endpoint with the existing owner-scoped HTTP header secret
support and teach the bundled study-notes workflow to query its prefixed tools
for central research. Keep native `knowledge_*` tools for private tenant notes,
coordination shares, and offline fallback. Responses must label which source was
queried and whether fallback data may be stale.

A stronger variation adds a federating layer beneath the stable native tool
names, merging hosted canonical results with private/shared native results. That
is more transparent to skills but puts network latency and availability into
every native knowledge query.

**Benefits**

- No replicated central corpus can drift; reads observe the hosted service.
- Authentication and output sanitization already exist.
- No per-tenant bulk import, embedding work, or deletion reconciliation.

**Limits**

- Changes the native feature from self-contained/offline to network-dependent.
- The current bundled skill explicitly uses native tools, while external MCP
  tools are prefixed; merely installing the endpoint does not redirect it.
- Local and hosted ranking cannot be merged exactly without a federation layer.
- Hosted service outage, rate limits, or credential expiry affect research.
- It does not refresh the native copy, so local benchmarks or consumers that
  explicitly inspect native `knowledge_stats` still see a snapshot.

**Use:** good for operators who value immediate freshness over offline parity;
also useful as a live fallback while a mirror protocol is built.

## Option 4 — Revisioned hosted delta feed and managed local mirror

This is the recommended complete solution. Add a machine-oriented export
contract to lw2studymcp rather than crawling agent-oriented search tools. It may
be an authenticated MCP tool or a dedicated HTTPS endpoint, but it needs the
following semantics:

```text
request:  schema_version, cursor|null, snapshot_id|null, limit
response: snapshot_id, source_revision, records[], next_cursor, has_more
record:   sequence, operation(upsert|delete), agent, topic,
          title, content, metadata, canonical_digest
```

Contract details:

- Starting without a cursor opens an immutable full snapshot. Later requests
  consume an ordered append-only change log.
- Upserts include complete canonical content and metadata, not patches.
- Deletes emit durable tombstones. A cursor that falls behind retention returns
  an explicit `cursor_expired` result and a new full-snapshot path.
- Pagination is bounded by both record count and encoded bytes.
- `canonical_digest` is computed over a versioned canonical representation so
  server and client agree.
- A snapshot remains readable until its final page is acknowledged or a
  documented expiry is reached.
- Authentication uses the existing owner-scoped secret-header mechanism over
  HTTPS. The client applies normal outbound URL, timeout, redirect, and body
  limits and never logs credential values.

The tenant maintains a versioned sync manifest, preferably in the tenant
database so cursor and managed-record state can participate in durable update
logic:

```text
source_id, source_revision, cursor, last_attempt_at, last_success_at,
last_error_class, path -> {last_source_digest, last_local_digest}
```

Reconciliation rules:

1. **New source path, no local document:** import and record both digests.
2. **Existing managed path, local digest still equals `last_local_digest`:**
   apply the upstream body and metadata, then record new digests.
3. **Existing path with no ownership proof, or locally changed managed path:**
   preserve it, record/report a conflict, and do not claim ownership.
4. **Tombstone for an unchanged managed path:** initially mark it stale with a
   source-deletion reason; permit hard deletion only under an explicit policy.
5. **Tombstone for a divergent/unmanaged path:** preserve it and report a
   conflict.
6. **Malformed or failed record:** do not silently skip and advance the page.
   Retain the previous cursor, quarantine the failure summary, back off, and
   surface degraded freshness.

For tenants created before manifest tracking, the first sync can safely adopt a
record only when the current local body and canonical metadata exactly match the
current source version. Everything else remains unmanaged. This means some old
snapshots may require an operator conflict decision, but it avoids guessing that
`submitted_by=None` means "seeded."

The existing body-then-metadata workspace write is a two-step operation. Before
full updates are enabled, add either a transactional database operation or a
durable per-record pending journal that can recognize and finish the target
body/metadata pair after a crash. The source cursor must remain at the previous
page until that repair completes.

**Benefits**

- Near-current local native search with offline operation and normal tenant
  migration.
- Efficient incremental traffic after one snapshot.
- Complete semantics for content, metadata, supersedure, and deletion.
- Explicit, measurable freshness rather than count comparison.

**Limits**

- Requires coordinated changes in lw2studymcp and LunarWing.
- Needs durable cursor/manifest schema, conflict UX, source retention, and more
  extensive crash/replay testing.
- Mirroring 1,000+ notes into every tenant duplicates storage and embedding
  work; deployments should be able to choose live-only mode instead.

**Use:** preferred when local native parity and offline availability are product
requirements.

## Option 5 — Share the hosted database or one writable filesystem

Pointing tenant tools directly at one shared SQLite database/filesystem, or
letting tenants write a host-global checkout, appears simple but should be
rejected. It collapses tenant isolation, gives every participant influence over
other tenants' prompt input, complicates locking and backup consistency, and
leaves tenant migration dependent on external state. Existing mt-admin code
intentionally snapshots mutable Study Notes state per tenant and mounts shared
code read-only (`ic/scripts/mt-admin-lib/09-worker-config.sh:718-818`).

## Comparison

| Option | Fresh central reads | Offline native copy | Updates/deletes | Main risk |
| --- | --- | --- | --- | --- |
| Manual refresh command | On demand | Yes | No, initially | Operator forgets |
| Periodic checkout scan | Cadence/Git bounded | Yes | No, initially | Mistaken parity claim |
| Hosted MCP primary reads | Yes | Fallback only | Source-owned | Network dependency |
| Revisioned delta mirror | Cadence bounded | Yes | Yes, conflict-safe | Cross-repo complexity |
| Shared DB/filesystem | Yes | No | Shared mutation | Isolation failure |

## Proposed rollout

### Stage A — Safe operator surface and additive refresh

1. Extract the canonical note parser/import candidate from
   `knowledge_seed.rs`; keep all existing seed tests unchanged.
2. Add `KnowledgeSyncConfig`, default disabled, with source, cadence, limits,
   and preserve-on-conflict defaults. Do not reinterpret the seed flag.
3. Add a dedicated cadence runner and versioned state/report. In this stage it
   imports missing paths only.
4. Add `mt-admin refresh-knowledge <tenant>` as the same code path's manual
   trigger. Add systemd-user and OpenRC harness coverage; do not place init
   commands in onboarding wrappers.
5. Extend `knowledge_stats` or status output with source revision, last success,
   last attempted run, additions, failures, conflicts, and observed lag.
6. If the source is a checkout, add the host-global updater and an atomic
   validated generation marker.

This stage is independently useful but must report `mode=additive`; it must not
claim an exact mirror.

### Stage B — Hosted source protocol

1. Add the revisioned export/change-feed contract to lw2studymcp.
2. Consume it through an owner-scoped authenticated source adapter with strict
   page/byte/time limits.
3. Store source cursor and per-path digests durably.
4. Exercise full snapshot, replay, source mutation during paging, cursor expiry,
   malformed pages, authentication failure, timeout, and last-good fallback.

### Stage C — Managed updates and tombstones

1. Add atomic update or pending-journal recovery for body plus metadata.
2. Enable updates only for records whose local digest proves they are unchanged
   synchronizer output.
3. Start with tombstone-to-stale behavior. Make hard deletion a separate
   operator policy after live validation.
4. Add conflict listing and an explicit operator resolution command; never
   choose upstream silently.
5. Consider optional live hosted reads when sync lag exceeds policy, with clear
   source/freshness labels.

## Configuration sketch

Names are illustrative and should be finalized during implementation:

```text
KNOWLEDGE_SYNC_ENABLED=false
KNOWLEDGE_SYNC_SOURCE=hosted-mcp       # hosted-mcp | checkout
KNOWLEDGE_SYNC_CADENCE_HOURS=6
KNOWLEDGE_SYNC_MCP_SERVER=study-notes-hosted
KNOWLEDGE_SYNC_MAX_RECORDS_PER_RUN=500
KNOWLEDGE_SYNC_MAX_BYTES_PER_RUN=10485760
KNOWLEDGE_SYNC_DELETE_POLICY=mark-stale # ignore | mark-stale | delete-managed
```

The hosted endpoint credential belongs in the tenant's encrypted secret store
and is referenced through `header_secrets`; it must not be another plaintext env
variable. Cadence should use jitter to avoid all tenants polling at once.

## Verification plan for an implementation

### Unit and database tests

- Existing one-shot seed behavior and explicit opt-out remain unchanged.
- Full snapshot and multi-page delta replay are idempotent.
- New note import preserves every canonical metadata field.
- Upstream body and metadata updates apply only to unchanged managed records.
- Local body change, local metadata change, and pre-existing unowned path each
  produce a conflict without mutation.
- Tombstones follow `ignore`, `mark-stale`, and `delete-managed` policy; a local
  divergence is never deleted.
- Crash/failure before content, between content and metadata, before manifest
  update, and before cursor advance all converge on retry.
- A failed page cannot advance the cursor; cursor expiry starts a bounded full
  snapshot without discarding the last good corpus.
- Concurrent calls collapse to one run; cadence state survives restart.
- PostgreSQL and libSQL produce equivalent reports.

### mt-admin and security tests

- New settings survive env regeneration and upgrade without being invented for
  existing tenants.
- Manual refresh and scheduler rendering work through both systemd user-manager
  and OpenRC abstractions.
- Shared checkout updates remain host-owned and flock-serialized; tenant users
  cannot modify source code or notes.
- Missing/wrong-owner secrets fail closed; logs and reports contain no token or
  note body.
- Redirect, private-address policy, body limits, malformed JSON, excessive
  pages, and timeout behavior are covered for hosted sources.

### Live acceptance

1. Create a temporary tenant through mt-admin and seed a known source
   generation.
2. Add one upstream note, update another's body and status metadata, and
   tombstone a third.
3. Locally edit one managed tenant note before the next pass.
4. Run automatic and manual sync without restarting the tenant.
5. Confirm the add/update/tombstone policy, preserved local conflict, native
   search results, embeddings, source revision, and lag report.
6. Stop the hosted service and verify last-good native reads plus degraded
   freshness; restore it and verify recovery/backoff.
7. Repeat the critical path on PostgreSQL and libSQL, and validate systemd and
   OpenRC lifecycle paths.
8. Remove the temporary tenant through mt-admin.

## Decision points for the implementer

Before coding beyond additive mode, the operator/product owner should choose:

1. Whether the target is a live-only hosted research path, an offline local
   mirror, or both.
2. Whether lw2studymcp can provide a stable revisioned export/change feed and
   deletion tombstones.
3. Whether deletion means retain, mark stale, or delete unchanged managed data.
4. The acceptable freshness objective and per-host polling budget.
5. Whether existing seed-only tenants should opt in manually or be migrated by
   a fleet operation.

Absent another choice, use the recommendation in this document: opt-in additive
sync first, revisioned hosted delta mirror next, preserve-on-conflict always,
and tombstones marked stale before any hard-delete policy is enabled.
