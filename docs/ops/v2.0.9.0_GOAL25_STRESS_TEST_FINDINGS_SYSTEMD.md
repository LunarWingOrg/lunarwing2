### F1 — Initial chat-phase failure was a mock-LLM calibration bug (harness, not product; resolved mid-run)

- Symptom: 0/44 stress-path documents present after all turns completed.
  Thread inspection (`chat-inspection.json`) showed every turn's
  `memory_write` tool call targeting the **fixed default path**
  `daily/2026-08-28.md` instead of the per-turn `PATH=` argument — the
  mock's scripted tool-call arguments did not substitute the per-turn
  path. Because the mock wrote with `append:false` to the same path,
  each write overwrote the previous, and `memory_search` for the
  payloads correctly returned 0 results (only the last payload ever
  existed).
- The agent itself behaved correctly: every tool call succeeded, every
  turn reached `Completed`, no 5xx, no message loss.
- Fix: corrected mock with per-turn path interpolation + restart
  (`corrected_mock=healthy`), then the corrected harness passed 44/44
  byte-exact.
- Behavioral note for future harnesses (real constraint, not a defect):
  tool rate limits (`rate_limit_config` for memory tools) require
  bursty concurrent turns to schedule their tool calls within the rate
  window — the corrected run inserted 62.0s of rate-window waits across
  44 turns. Harnesses and integrators should poll/back off on 429
  rather than free-firing concurrent tool-heavy turns on one thread.

### F3 — One soak chat turn timed out (1/30, LOW/MEDIUM — RESOLVED by item #2)

Original observation: `SOAKCHAT-G26-029-44e740`, the final turn submitted in
the soak window, did not complete before the harness deadline. Its state stayed
consistent and there was no message loss or corruption.

Follow-up source investigation found a product-side latency mechanism matching
that tail signature. `Agent::run()` admitted channel input while a turn was
active but allowed only one ordinary `handle_message` task globally. Every
other ordinary message entered one FIFO, so an independent gateway thread could
remain behind an unrelated slow LLM/tool turn until the fixed soak deadline.
This was deterministic head-of-line blocking, even though the archived harness
evidence cannot prove how much of this one observation was queue delay versus a
tight window-close deadline.

Item #2 replaces that global active slot with a bounded scheduler:

- scoped Engine V2 gateway `UserInput` is keyed by `(channel, authenticated
  user, conversation scope)`;
- up to four distinct keys for one user may run concurrently;
- the same thread, every non-gateway path, and control/auth/approval messages
  remain serialized;
- different users and exclusive messages are fairness barriers, and the
  waiting queue remains bounded at 256 with the existing explicit busy reply;
- supervisor and Engine V2 outcome cancellation guards prevent shutdown from
  leaving detached inner handlers or engine threads.

The regression uses a first gateway thread whose LLM never returns, then submits
an independent second thread. It times out against the pre-fix dispatcher and
completes immediately after the fix; a companion test proves a same-thread
follow-up remains queued. The eight-test ingress suite also covers interrupts,
overflow, soft timeout, and abrupt shutdown cancellation. Focused scheduler
coverage verifies lane caps and fairness. Default `cargo check`, formatting, and
zero-warning clippy pass. No tenant was created for this follow-up because the
queue mechanism and completion contract are reproduced deterministically in the
full agent/channel test rig.

Correction to the original finding: this was not a documented second
cross-host occurrence. The original OpenRC report records 29/29 chat turns
answered, and the later OpenRC rerun records 30/30. The systemd 29/30 result is
the only checked-in tail timeout; item #2 nevertheless fixes the real global
head-of-line mechanism exposed by the investigation.
