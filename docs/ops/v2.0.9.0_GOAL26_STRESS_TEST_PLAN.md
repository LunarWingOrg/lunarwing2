## Objective

Prove that a freshly provisioned multi-tenant LunarWing instance survives
realistic and abusive load across every user-visible surface — web gateway
chat, tool loop, memory subsystem, and the WeeChat relay channel — without
message loss, data corruption, hangs, or resource exhaustion. All findings
are recorded in the findings doc; the tenant is destroyed at the end.

## Environment

- Host: this Arch Linux dev machine (systemd user managers with linger,
  12 threads usable, podman for tenant containers).
- Tenant: `aj26stress`, created via `ic/scripts/lunarwing-mt-admin.sh
  add-tenant aj26stress --llm-base-url http://127.0.0.1:39260/v1
  --llm-api-key stress-mock` from this working branch
  (`aj/kimi-26-20260827-1834`, mt-admin clones the source repo's current
  branch), release build with all WASM extensions
  (`build-tenant aj26stress --with-wasm`), started with `start-tenant`.
- Ports (auto-allocated block 10010-10019): gateway 10010, postgres 10013,
  weechat relay 10015, orchestrator 10016, ws_adapter 10019.
- LLM: loopback mock OpenAI-compatible server on `127.0.0.1:39260`
  answering every user turn with three real tool calls
  (`memory_read SOUL.md`, `memory_write` daily append, `memory_search`)
  and a `STRESS-OK` final reply. The mock must speak SSE streaming
  (`stream: true` is always sent by the Engine V2 rig-core client).
  Rationale: deterministic, fast, no external dependency; the LLM itself
  is not the surface under test.
- `ENGINE_V2=true`, `ENGINE_V2_CHANNELS=xmpp,weechat,darkirc`
  (mt-admin defaults for this branch).
- Init: systemd user units rendered by mt-admin (`lunarwing-aj26stress`,
  weechat relay + ws-adapter units, postgresql container via Quadlet).
- Existing tenants (`alpha`, `hermes`) keep running — the test must not
  disturb them; they serve as isolation witnesses (status checked before
  and after).

## Seed data ("real data" requirement)

Seeded through the authenticated web gateway memory API
(`/api/memory/write`, bearer token from `mt-admin tokens aj26stress`):

- `SOUL.md` — non-trivial persona definition (~2 KB prose).
- `IDENTITY.md` — identity card.
- `AGENTS.md` — house rules doc the agent must follow.
- `context/profile.json` — valid `PsychographicProfile`-shaped JSON
  written with `append: false` (per the item-14 guidance).
- `memory/facts.md`, `memory/preferences.md` — topical notes.
- `daily/<today>.md` — a daily log with several entries.
- `memory/stress/ledger.md` — integrity ledger for the append phases.
- Nested path `projects/stress/harness.md` — tree-depth coverage.

Every seed is read back and byte-compared before stress begins.

## Phases

Each phase records: request count, success/failure counts, latency
(min/avg/max where useful), observed errors, and pass/fail against the
criteria. Phase IDs match the goal-25 plan for cross-host comparability.

### P0 — Provision, seed, baseline

1. `add-tenant` (LLM overrides above), `build-tenant --with-wasm`,
   `start-tenant aj26stress`.
2. Wait for `/api/health` 200 and `mt-admin status aj26stress` all-green
   (systemd `….service: active` shape).
3. Seed all data above; read back every document and byte-compare.
4. PASS: tenant healthy, all seeds verified.

### P1 — Memory API stress (no LLM)

Direct gateway API, bearer auth, concurrency via parallel workers:

- W1: 200 sequential `memory_write` to distinct paths → 200 reads,
  byte-compare each. PASS: 0 mismatches.
- W2: 200 writes / 20 paths / 8-way concurrency, then read-all compare.
  PASS: 0 mismatches, no 5xx; every doc matches exactly one written
  round (no torn writes).
- W3a: 100 sequential appends to the shared ledger. PASS: all 100
  markers present, order preserved.
- W3b: 50 concurrent appends (8-way) to the shared ledger
  (`append: true`). PASS: all 50 markers present, line-intact, and —
  post item-29 — **zero HTTP 500s** (goal-25 F1 and the first attempt's
  Finding 1 both produced ~50% 500s here; the `pg_advisory_xact_lock`
  fix must eliminate them while preserving content).
- W4: 300 reads + 100 searches + 50 tree + 50 list mixed under
  concurrent write load. PASS: no 5xx, sane latency, writes intact.
- W5: large-document write (500 KB) → read-back compare; then 1.5 MB
  write → clean documented rejection (413/4xx), not 500/truncation.
- W6: adversarial payloads: `..` path segments, absolute paths, role
  tokens (`<|im_start|>` etc.) in content, invalid profile JSON
  overwrite attempt. PASS: documented behavior; profile JSON stays
  valid on overwrite; no daemon errors beyond the request level.
  (First-attempt Finding 2: `..` segments accepted — confirm current
  behavior and record.)

### P2 — Chat + tool-loop stress (mock LLM)

Via `POST /api/chat/send` (fresh thread per worker unless noted):

- C1: 30 sequential multi-tool turns; the mock drives 3 real tool calls
  per turn. PASS: 30/30 turns complete, 90 tool executions, distinct
  threads, `STRESS-OK` received.
- C2: chat send without `thread_id`. PASS: documented behavior (first
  attempt Finding 4: reply silently dropped with a routing-target
  ERROR — confirm and record).
- C3: memory consistency after chat: read the daily path the mock told
  the agent to append and verify marker content landed via the real
  `memory_write` tool. PASS: markers present (also verifies the
  Engine V2 tool dispatch → DB path end to end).

### P3 — WeeChat channel stress

Truly end to end through a loopback **fake IRCd**: the tenant's real
WeeChat 4.10.0 connects to it as an IRC client; a fake peer injects
PRIVMSGs (auto-creating the `irc.stress.<nick>` query buffer) and
captures outbound replies. Chain: fake-ircd → WeeChat → relay api →
ws_adapter → WASM channel → agent → relay → WeeChat → fake-ircd.

- H1: relay/adapter healthy: adapter `/api/health` 200, relay port
  listening, WeeChat connected to fake IRCd.
- H2: pairing flow: first DM triggers pairing; approve the code via the
  gateway API. PASS: pairing completes, subsequent DMs flow.
- H3: 40 DM burst from the fake peer. PASS: 40/40 injected, 40/40 agent
  replies captured IRC-side (mock LLM makes replies fast).
- H4: adapter process restart mid-traffic
  (`restart-weechat-adapter aj26stress`): send messages while the
  adapter is down, then restart. PASS — post item-29 — messages
  accepted by WeeChat while the adapter was down are recovered from the
  persisted watermark + journal (goal-25 F3 lost 12/12; the first
  attempt did not cover this case).
- H5: relay outage: stop the relay api (or WeeChat), send via adapter
  `/api/input`. PASS: sends 202-queued into the bounded outbox, drained
  after relay return, none silently dropped.
- H6: channel ↔ memory: over WeeChat, ask the agent to write a marker
  to memory; verify via gateway API. PASS: marker present and correct.
- H7: observe ws_adapter heartbeat behavior against WeeChat 4.10.0
  (goal-25 F2 / first-attempt Finding 3: relay never answers protocol
  PINGs → reconnect churn). Record reconnect count from `/api/health`;
  PASS criterion is no message loss, with churn recorded as a finding.

### P4 — Gateway abuse

- A1: no auth → 401; bad token → 401.
- A2: malformed JSON → 400; unknown route → 404.
- A3: body limits: 8 MiB accepted, >10 MiB → 413.
- A4: 200-request flood on health + memory read. PASS: no wedge, no 5xx.

### P5 — Restart resilience

`restart-tenant aj26stress` after the load phases, then:
PASS: seeded + stress-written documents byte-identical, chat history
persisted, weechat stack reconnects, `/api/health` 200 within 2 minutes,
all expected systemd user units active.

### P6 — Resource observation

Sampled across phases from `/proc` (tenant uid): daemon RSS baseline /
peak / post-restart, thread count, open FD count, postgres container
RSS. PASS: no monotonic FD/thread leak, RSS returns near baseline after
restart, no OOM.

## Isolation & safety

- Tenant gets its own auto-allocated port block (10010-10019); no
  hand-picked ports.
- Mock LLM, fake IRCd, and all drivers bind loopback only; raw
  artifacts live in `/tmp/aj26stress/` (removed at teardown).
- All traffic targets the tenant's own ports only; `alpha` and `hermes`
  are untouched witnesses (checked before/after via `mt-admin status`).
- No daemon code changes; black-box plus API-level testing.
- Tokens/passwords are written to mode-600 files and never printed into
  the findings doc.

## Cleanup (mandatory)

1. `stop-tenant aj26stress` → `remove-tenant aj26stress --purge`
   (stops services, deallocates ports, deletes OS user + home + PG
   container/volume).
2. Stop mock LLM + fake IRCd; remove `/tmp/aj26stress/`.
3. Verify: tenant absent from `list-tenants`, no `aj26stress` user, no
   leftover ports in `/etc/lunarwing/ports.json`, other tenants still
   healthy.
4. Findings doc committed; item #26 checked off in the goals file.
