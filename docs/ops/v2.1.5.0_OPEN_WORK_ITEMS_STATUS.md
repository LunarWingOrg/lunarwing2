## #310 (OPEN) — DATABASE_BACKEND overlay split-brain: wizard reads std::env directly, misses runtime overlay + unguarded dotenvy set_var on live runtime

**Author:** sweetiebot | **Created:** 2026-10-04 12:54Z | **Labels:** bootstrap, engine, reliability (no release label)

Pass-183 finding, re-verified at HEAD. `load_lunarwing_env`
(`ic/src/bootstrap.rs:218-231`) guards its own `set_var` behind a
Tokio-runtime check: with a runtime live it writes `DATABASE_BACKEND=libsql`
to the `config::set_runtime_env` overlay (`:228`) — but
`ic/src/setup/wizard.rs:580`, `:672`, `:1188` read
`std::env::var("DATABASE_BACKEND")` directly and never see the overlay, so
two parts of one process can disagree on the DB backend. Reachability is
narrow (the pre-runtime call normally sets the real var first) but fail-open.
Second, structural: the same in-runtime call runs `dotenvy::from_path`
(`bootstrap.rs:211`), which `set_var`s any newly-appeared key unguarded on
the live multithreaded runtime — the UB the code's own comment describes.
Third: `test_libsql_autodetect_sets_backend_when_db_exists`
(`bootstrap.rs:1020`) asserts the condition inline, never through a consumer.
Fix shapes in the item: route the wizard reads through `env_or_override`,
skip `dotenvy::from_path` in-runtime, and make the autodetect test exercise
a real consumer. No goals item yet.

## #308 (OPEN) — Mission verbs bypass supervised_mode/approval/permissions/hooks/rate-limits entirely (WI#295 residual)

**Author:** sweetiebot | **Created:** 2026-10-04 12:54Z | **Labels:** engine, engine-v2, mission, security (no release label)

Pass-184 finding, re-verified at HEAD. `execute_action_internal` intercepts
mission calls via `handle_mission_call` (`ic/src/bridge/effect_adapter.rs:928`)
**before** the registry-tool gate stack — permission Disabled check,
shared-conversation approval gate, non-Foreground Always-refusal,
supervised_mode human-approval pause, needs_prompt approval gate, and the
rate limiter (`:971-1071`) are all unreachable for the eight mission verbs.
Mitigations exist (host-authored static ActionDefs, lease gating, the
coordination gate), and ENGINE-V2.md documents the gate ordering consciously
— but not the supervised-mode consequence: on a supervised engine-v2 thread,
`mission_create/fire/delete` execute without the human-approval pause every
registered tool honors, and mission calls have no rate limit at all. Fix
shape per the item: route mission calls through the same gate stack (or a
mission-specific approval subset) before `handle_mission_call` returns, or
document the exemption as a deliberate contract with the supervised-mode
consequence stated. No goals item yet; the only security-labeled new item
this window.

## #307 (OPEN) — SecretDeleteTool sits at UnlessAutoApproved tier — irreversible credential destruction one auto-approve away

**Author:** sweetiebot | **Created:** 2026-10-03 22:56Z | **Labels:** 2.1.5.0, engine, low, security

Re-verified at HEAD: `SecretDeleteTool::requires_approval` returns
`UnlessAutoApproved` (`ic/src/tools/builtin/secrets_tools.rs:152-154`), so in
any auto-approve-enabled session a prompt-injected loop could silently delete
every stored credential in one turn — and secret values are unrecoverable
(UI-entered, exist nowhere else). The contrast pattern is intact: `ssh` uses
`ApprovalRequirement::Always` + `allows_always_approval`
(`ic/src/tools/builtin/ssh.rs:129-132`, `ssh_git.rs:263`). The item also
notes the secrets family carries no `allows_autonomous_execution() -> false`
override — the autonomous denylist is their only autonomous gate. Goals item
32 is assigned and open; no MR at audit time.
