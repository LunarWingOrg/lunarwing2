## #267 (OPEN) — heartbeat finding in reference to MR !1227

**Labels:** 2.1.3.0 | **Author:** cmc | **Created:** 2026-09-29

Review finding at head `04cfda7c`: a heartbeat-only timeout is presented as
recovered investigation evidence. `external_worker.rs` correctly excludes
`[worker] ` progress from `note_activity`, but still appends every such delta
to `accumulated_output`. A silent Kimi CLI still produces the executor's
synthetic "Still waiting…" messages (default every 120s,
`kimicode4lunarwing/scripts/kimi_task_executor.ts:203-209`); when the
15-minute silence watchdog returns `timed_out`, the evidence fallback stores
those heartbeats as `partial_output` — an idle worker can falsely appear to
have produced an investigation.

**Verified at HEAD (`ef4ccb215`): the finding stands.**
`external_worker.rs:1247` (`accumulated_output.push_str(&progress.delta)`)
is unconditional; `is_genuine_progress` at `:1654` gates only the
`note_activity` call at `:1241`; on `TimedOut` with empty `task_result.output`
the fallback at `:1407-1411` uses `accumulated_output`, and
`preserve_timeout_evidence`'s nonempty-only guard at `:1702` persists it.

**Fix-attempt history (all closed unmerged):** !1235
(`aj/kimi-48-20260929-2101`), !1237 (`aj/kimi-48-20260929-2200`), !1239
(`aj/kimi-48-20260929-2301`, head `bde879dfb`, closed 23:50). !1239's review
(ajpoc2oc2, 23:48) accepted the !1237 findings as addressed but found a new
regression: the heartbeat-only gate at `:1743-1747` of that branch treated
whitespace-only frames (`" "`, `"\n"`) as heartbeat-only, dropping genuine
separators that opencode2 forwards untrimmed
(`opencode2.4lunarwing/scripts/opencode_task_executor.ts:323-328`), so
`["alpha", " ", "beta"]` recovered as `"alphabeta"`. The same review also
flagged a goals-file URL typo introduced by that branch. Goal item 48 (open)

## #243 (OPEN) — mission threads_today_date rollover never lands

**Labels:** 2.1.4.0 | **Author:** dwarfstar | **Created:** 2026-09-27

Mission day-counter `threads_today_date` never rolls to the current date
(dwarfstar tenants; `expected-behavior` pinned at `2026-07-29`,
`canary-delta-m4t` at `2026-09-12`), so `max_threads_per_day` gating runs
against a stale date.

**Mechanism verified at HEAD:** the rollover exists —
`fire_mission_inner` resets `threads_today` and updates the date when the
stored date differs from today
(`ic/crates/lunarwing_engine/src/runtime/mission.rs:1001-1011`) — but every
early return **before** that block exits without persisting a rolled-over
date: paused mission (`:951`), suppressed skill-learning mission (`:955`),
insights batch below the five-thread threshold (`:973`), and
already-processed dedup key (`:991`). A mission whose fires keep hitting
those paths (e.g. an insights mission that repeatedly has fewer than five
new eligible threads) never crosses the rollover, leaving the date pinned
and the daily budget unreset — matching the weeks-stale evidence. Also
tracked as goal item 53.
