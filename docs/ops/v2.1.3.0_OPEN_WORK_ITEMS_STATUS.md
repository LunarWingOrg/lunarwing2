## #245 (OPEN) — tool_list output truncates at ~19 entries

**Labels:** 2.1.3.0 | **Author:** dwarfstar | **Created:** 2026-09-27

Reproduced on dwarfstar (2.1.3.0 build 6): with 31 MCP servers installed,
`tool_list` exposes only ~19, with no `truncated` flag or offset. Source
verification at `bce13b778` finds **no entry cap in the tool path**:
`ToolListTool::execute` serializes whatever `ExtensionManager::list`
returns with an explicit `count` (`ic/src/tools/builtin/extension_tools.rs:984-1058`),
and `list` iterates every configured server, WASM tool, and channel
(`ic/src/extensions/manager.rs:1413+`). The truncation the reporter sees
must come from a downstream rendering layer; the candidate layers are:

- the safety sanitizer (`max_output_length`, default 100 000 B) — but this
  appends a loud `[... truncated: showing X/Y bytes. Use the json tool with
  source_tool_call_id ...]` notice, which the reporter says is absent;
- thread-history rebuild, which truncates each stored tool result to 1000
  chars with only a trailing `...` (`ic/src/agent/session.rs:533-547`) —
  indicator-less, and would present exactly as a prefix cut;
- UI/event rendering of the result.

Recovery already exists: full outputs are stashed per call id and can be
re-read with the `json` tool's `source_tool_call_id`
(`ic/src/agent/dispatcher.rs:1012-1020`, `ic/src/tools/builtin/json.rs`).
Next step is reproducing against the raw JSON result to identify which layer
drops the tail, then adding pagination/`truncated` metadata if a real cap is

## #243 (OPEN) — mission threads_today_date rollover never lands

**Labels:** 2.1.3.0 | **Author:** dwarfstar | **Created:** 2026-09-27

Missions on dwarfstar carry `threads_today_date` pinned weeks in the past
(`2026-07-29`, `2026-09-12`), so `max_threads_per_day` gating runs against a
stale day. Source verification shows the rollover logic **exists and is
unit-tested**: `fire_mission` compares `threads_today_date` to today,
resets `threads_today` and advances the date on mismatch
(`ic/crates/lunarwing_engine/src/runtime/mission.rs:1001-1008`), and tests
exercise both the new-day budget restore and legacy first-fire preservation
(`:6840-6905`). Dates that never advance therefore indicate the fire path is
not being reached for those missions at all (cadence/`next_fire_at` gating,
a paused/deactivated mission, or the scheduler never selecting them) rather
than broken rollover arithmetic. Investigation should start at why
`fire_mission` is not invoked after a day boundary. Not addressed.
