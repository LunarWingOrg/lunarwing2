## #259 (OPEN) — lunarvoice 502 error on replies that are too long

**Labels:** 2.1.3.0 | **Author:** cmc | **Created:** 2026-09-28

The item body (enriched 2026-09-28) carries a source-verified root cause:
the 502 is the gateway mislabeling the sidecar's over-length rejection —
the sidecar returns HTTP 422 when synthesis would exceed `max_tts_audio_secs`
(300 s, `projects/voice-sidecar/src/api.rs:295-299`), but the gateway's
`map_proxy_error` only special-cases 429/400
(`ic/src/channels/web/voice.rs:493-510`), so 422 collapses into BAD_GATEWAY
502 while the gateway's own 10 000-char text budget (`MAX_SYNTH_TEXT_CHARS`)
permits ~2x the audio cap. The body also documents a zombie-synthesis
amplifier (the sidecar's 120 s timeout abandons but cannot cancel the Kokoro
inference, holding the global TTS mutex and an inference permit) and the
equal-timeout race between gateway and sidecar.

**Fix lineage and status.** First branch `aj/kimi-44-20260928-1000` (!1212)
was closed unmerged; its findings (mirroring the configured sidecar cap, and
the equal-timeout race producing 504-vs-502 for the same stall) were
addressed on the re-land. The current reference fix is
`aj/kimi-44-20260928-2201` (head `55c4bd413`, !1219, closed unmerged): the
gateway keeps sidecar 422/503/504 semantics, rejects over-long synthesis
text up front, and the synthesis-duration bound follows
`VOICE_MAX_TTS_AUDIO_SECS`; docs updated.

**Open finding on the re-land (from !1219 review):** `voice.rs:703-708`
clamps every speed above 1.0 to 1.0 when estimating duration for the hard
`text_too_long` (422) rejection, but the sidecar passes the requested speed
(up to 2.0) through to Kokoro (`projects/voice-sidecar/src/engine.rs:311`).
A reply estimated at e.g. 320 s at 1× — roughly 160 s at 2×, inside the
300 s cap — is rejected outright and labeled permanently too long without
consulting the sidecar. Remaining work: account for the requested speed in
the eligibility check (or make the heuristic advisory rather than a hard
rejection) and add a test showing a reply rejected at 1× can pass at 2×.

## #254 (OPEN) — investigate podman build DNS resolution (deb.debian.org)

**Labels:** 2.1.3.0, infrastructure, investigation | **Author:** applejack | **Created:** 2026-09-27

another resolves cleanly. The item's own analysis (verified against the
tree) is that every mt-admin build lane passes `--network=host`

container DNS rather than build DNS). A per-host `lw-dns-net` network with
explicit `--dns` and `default_network` in `containers.conf` is the
documented workaround. Open investigation; no repo change since.

## #245 (OPEN) — tool_list output truncates at ~19 entries

**Labels:** 2.1.3.0 | **Author:** dwarfstar | **Created:** 2026-09-27

Reproduced on dwarfstar (2.1.3.0 build 6): with 31 MCP servers installed,
`tool_list` exposes only ~19, with no `truncated` flag or offset. Source
verification at HEAD confirms **no entry cap in the tool path itself**
(`ToolListTool::execute` serializes whatever `ExtensionManager::list`
returns, `ic/src/tools/builtin/extension_tools.rs:986-1059`), so the
indicator-less prefix the reporter saw comes from the downstream safety
layer, which clips oversized tool output at `max_output_length` = 100 000
bytes (`ic/src/settings.rs:977-979`, enforced at
`ic/crates/lunarwing_safety/src/lib.rs:62-86`), compounded by the
thread-history rebuild truncating stored tool results to 1000 chars
(`ic/src/agent/session.rs:533-547`).

**Fix lineage and status.** First branch `aj/kimi-46-20260928-1200`
(head `6666f28c5`, !1213) was closed unmerged with two findings: pagination
advanced only between extensions (a 40-tool server could never expose names
26–40), and the nominal output bound was not actually enforced. The re-land
`aj/kimi-46-20260929-0000` (head `7dba142a5`, !1221, closed unmerged) added
`tools_offset`/`tools_limit` windows, a 60 KiB serialized page budget with
`fit_page_to_budget`, `bound_field` per-field elision, a deterministic
`extension_sort_key`, and a 31-server regression test.

**Open findings on the re-land (from !1221 review):**

1. **Single-entry page fit.** `fit_page_to_budget` stops at one entry
   without checking whether that entry fits. The 200-char field limit does
   not bound serialized bytes: 100 tool names of 200 JSON-escaped control
   characters (accepted by the MCP tool-name deserializer,
   `ic/src/tools/mcp/protocol.rs:92-96`) serialize to > 120 KiB, over the
   100 KiB safety cap, producing a clipped page that still says
   `truncated=false`. Bound serialized size at the single-entry level and
   add an escaped/multibyte worst-case test.
2. **Identifier elision.** `bound_field` elides the actual identifiers
   (extension `name` and every `tools[]` value) past 200 chars. Real tool
   names longer than that are returned identically elided at every offset,
   `extension_info` exposes no full names, and two tools sharing a
   198-char prefix become indistinguishable. Keep identifiers lossless or
   provide a full-name retrieval path; elide descriptive fields instead.
3. **Sort-key instability.** `extension_sort_key` is
   `(kind, name.to_lowercase())` with no original-name tie-breaker; case-fold-
   equal names (Alpha vs alpha) compare equal, and WASM discovery comes from
   a freshly allocated HashMap (`ic/src/tools/wasm/loader.rs:719-751`), so
   separate pagination calls can repeat or skip an entry across offsets.
   Add the original name as tie-breaker and test a case-fold collision.

## #243 (OPEN) — mission threads_today_date rollover never lands

**Labels:** 2.1.3.0 | **Author:** dwarfstar | **Created:** 2026-09-27

Missions on dwarfstar carry `threads_today_date` pinned weeks in the past
(`2026-07-29`, `2026-09-12`), so `max_threads_per_day` gating runs against a
stale day. The rollover logic exists and is unit-tested: `fire_mission_inner`
compares `threads_today_date` to today, resets `threads_today` and advances
the date on mismatch (`ic/crates/lunarwing_engine/src/runtime/mission.rs:1001-1012`),
and tests exercise both the new-day budget restore and legacy first-fire
preservation (`:6840-6905`).

**Correction to the prior cut's inference.** The !1218 version of this
section concluded that stale dates "therefore" mean `fire_mission` is not
invoked at all. That does not follow. `fire_mission_inner` has several
`Ok(None)` returns **before** the rollover block executes:

- terminal / paused / (skill-learning missions while self-improvement is
  disabled) — `mission.rs:947-960`;
- **insights missions with fewer than five new eligible source threads** —
  `:962-984`: `select_batch` (`ic/crates/lunarwing_engine/src/runtime/insights.rs:32-65`)
  returns `None` unless at least `INSIGHT_BATCH_THREADS` = 5 eligible threads
  are newer than the mission's durable cursor (`types/insight.rs:92`), and
  the fire path returns early **without touching the date**;
- trigger-dedup replay of an already-processed payload — `:990-996`.

The cron ticker *does* deliberately re-enter `fire_mission_inner` for
conversation-insights missions on every tick regardless of `next_fire_at`
(`mission.rs:2086-2088`), so an insights mission is invoked frequently —
and if its cursor has fewer than five new eligible threads every day, its
date stays stale forever while the scheduler works correctly. Note the
reported example (`expected-behavior`, `threads_today=0`, never fired) may
be exactly this shape, or may be `max_threads_per_day` exhaustion (which
also returns before spawning but *after* the rollover), or genuine
non-invocation.

**Corrected triage:** instrument or trace which early return the affected
missions actually hit — the sub-batch insights gate, terminal/paused
filters in `tick` (`:2062-2080`), cadence/`next_fire_at` gating, or true
non-invocation — before proposing a fix. The !1218 instruction to
"investigate why `fire_mission` is not invoked" presumed the last case and
is withdrawn.
