**Date:** 2026-10-03

**Scope:** every committed `Cargo.lock` in the repo — the `ic/` workspace, all

## Conclusion

**No committed lockfile contains a crate with an active, applicable security
advisory.** All 26 checkable manifest roots pass `cargo deny check advisories`
against a fresh RustSec advisory database (fetched 2026-10-03, HEAD `f8dee89`
dated 2026-10-02), and the one manifest-less reviewed lock
(`pebble4lunarwing/upstream/Cargo.lock`) scans clean under an offline
raw-lockfile evaluation of the same database.

- The **eight** accepted advisories in `ic/deny.toml` were all re-verified
  against upstream on 2026-10-03. Every one is still pinned by an upstream
  constraint outside LunarWing's control; none could be removed, and none
  needed to be added. The `deny.toml` comments now carry the new
  re-verification date.
- The eight fresh Wasmtime advisories published 2026-10-02
  (RUSTSEC-2026-0320 through -0327) are **already cleared**: the lock pins
  wasmtime/wasmtime-wasi **36.0.17**, which is the patched release for the
  three that apply to the 36.x line (0321/0322/0323) and below the
  `unaffected` floor for the other five.
- Two lockfile-only pins with live advisories that `cargo deny` cannot see
  (never resolved into the built graph) are now covered by
  `.gitlab/scripts/check-lockfile-only-advisories.sh`: **pyo3 0.28.3**
  gained a second guard entry for RUSTSEC-2026-0177 (thread-safety, same
  uncompiled `jiter/python` feature pin as the already-guarded 2026-0176),
  and **atty 0.2.14** (RUSTSEC-2021-0145, Windows-only unaligned read, no
  patched release) is newly guarded — it sits in the ic lockfiles only via
  the vendored `libsignal-protocol` dev-dependency on `env_logger 0.6.2`.
  The guard now also accepts cargo tree's "did not match any packages" as an
  absent marker, since crates held out of the resolve graph entirely are as
  safe as present-but-unbuilt ones.

## Method

1. **CI gate locally:** `.gitlab/scripts/cargo-deny-check.sh` (cargo-deny
   0.20.2 from `.ci-bin/`, repo-root context so the vendored source
   replacement cannot hide the crates.io index) →
   `advisories ok, bans ok, licenses ok, sources ok`.
2. **Every satellite manifest root:** the same cargo-deny binary and
   `ic/deny.toml` config, `check advisories --hide-inclusion-graph`, run from
   the repo root against all 25 satellite `Cargo.toml`s (ic bridges,
   channels-src, tools-src, openclaw-ports, test fixture, unix-socket-client,
   plus the root-level darkirc / weechat / gotify / unix-socket / pebble /
   pebble4lunarwing / ocr-sidecar / voice-sidecar / replv2git roots). All OK.
3. **Raw-lockfile offline scan:** a small evaluator parsed every committed
   `Cargo.lock` (27 files, including the manifest-less
   `pebble4lunarwing/upstream/Cargo.lock`) and matched each pin against the
   local advisory-db checkout with full semver `patched`/`unaffected` range
   evaluation. This catches lockfile-only pins that cargo-deny filters out
   (the WI#255 pyo3 class). Findings beyond the eight accepted advisories:
   exactly the two lockfile-only pins now guarded (pyo3 0177, atty 0145) —
   see "Lockfile-only pins" below.
4. **Lockfile-only guard:** `.gitlab/scripts/check-lockfile-only-advisories.sh`
   → `ok` (pyo3/atty confirmed absent from both the ic and xmpp-bridge build
   graphs).
5. **Upstream re-verification:** crates.io sparse index checked 2026-10-03
   for `libsql`, `russh`, `rsa`, `rustls-webpki`, `h2`, `failure` (details in
   the table below).

dropping `russh/rsa`), #7–#8 need the vendored libsignal wrapper ported to a
maintained error library.

## Lockfile-only pins (cargo-deny-invisible, now guarded)

cargo-deny filters crates that are pinned in a lockfile but never resolved
into the built graph, so advisories against such pins stay invisible to the
main gate. `.gitlab/scripts/check-lockfile-only-advisories.sh` makes a
feature flip that starts compiling one a loud CI failure. The guarded set is
now:

| Crate | Advisories | Path that would activate it |
|---|---|---|
| `pyo3 0.28.3` | RUSTSEC-2026-0176 (OOB read), RUSTSEC-2026-0177 (`PyCFunction::new_closure` missing `Sync`) | monty/jiter enabling the optional `python` feature |
| `atty 0.2.14` | RUSTSEC-2021-0145 (Windows-only unaligned read; no patched release) | the vendored `libsignal-protocol` dev-dep `env_logger 0.6.2` leaking into a shipped build |

`atty` is held out of the resolve graph entirely (cargo tree reports "did not
match any packages"); the guard now treats that marker as absent too, since a
crate outside the resolve graph cannot be compiled.

not a release blocker. The `workspace`-scope policy and the

this sweep exists so the full-graph state is on record, not to change policy.
