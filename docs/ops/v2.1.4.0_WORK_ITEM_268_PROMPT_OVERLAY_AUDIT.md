   writes are all gated on `ORCHESTRATOR_SELF_MODIFY` accepting only `true` or
   `1` (`ic/crates/lunarwing_engine/src/executor/orchestrator.rs:149-154`).
2. **No live tenant runs with the gate on.** Both registered tenants
   (`antelope`, `hermes`) have the flag **unset** in their rendered env and in

3. **No overlay document exists in either tenant database.** Zero rows match
   the overlay identity (reserved title/tag or the bridge storage path
   `engine/orchestrator/codeact-preamble-overlay.md`) in `antelope` (36 docs)
   and `hermes` (9 docs). Stored overlay state is **absent**, not merely
   inactive.
4. **No existing thread snapshot carries an injected overlay.** The two active
   engine threads in `antelope` contain no `Learned Rules (from
   self-improvement)` section.
5. **`SKILL_SELF_IMPROVEMENT=true` (the new-tenant provisioning default) is a
   separate subsystem flag and does not authorize prompt alteration.** Tenant
   `antelope` runs with `SKILL_SELF_IMPROVEMENT=true` **and**
   `ORCHESTRATOR_SELF_MODIFY` unset — its effective system prompt is the
   compiled one.
6. **One narrow test gap found and closed:** the `prompt_additions` overlay
   *writer* had no gate-off regression test. Added
   `self_improvement_outcome_skips_prompt_additions_when_gate_off`
   (`ic/crates/lunarwing_engine/src/runtime/mission.rs`). All other requested
   regressions (gate-off consumption, gate-on injection, 4,000-char cap,
   protected writes) already existed and pass.

No defect was found. The existence of this opt-in mechanism is **not** a bug;
nothing here alleges a gate bypass.

## How the overlay mechanism works (source-verified)

### Storage

- The overlay is a **shared, project-scoped MemoryDoc** with title
  `prompt:codeact_preamble` and tag `prompt_overlay`
  (`ic/crates/lunarwing_engine/src/executor/prompt.rs:82-85`).
- On the host bridge it persists at workspace path
  `engine/orchestrator/codeact-preamble-overlay.md`
  (`ic/src/bridge/store_adapter.rs:1213-1216`) and is shared-owner scoped
  (`__shared__` or legacy `system`).
- Shared-doc lookup iterates both shared owner candidates
  (`ic/crates/lunarwing_engine/src/traits/store.rs:161-172`), so a legacy
  `system`-owned overlay is equally visible to prompt assembly.

### Writers (three, all gated)

1. **Mission structured output** — `process_self_improvement_output` appends
   `prompt_additions` rules to the overlay doc
   (`ic/crates/lunarwing_engine/src/runtime/mission.rs:3172-3222`). Skips
   silently when the gate is off.
2. **Mission host function `__save_memory_doc__`** — rejects any
   engine-control document while the gate is off
   (`ic/crates/lunarwing_engine/src/executor/scripting.rs:2147-2161`).
   Engine-control identity is structural — `orchestrator:`/`prompt:` title
   prefixes or the `orchestrator_code`/`orchestrator_meta`/`prompt_overlay`
   tags (`ic/crates/lunarwing_engine/src/types/memory.rs:72-84`) — so
   model-supplied metadata (renames, tag edits, `source: compiled_in`) cannot
   grant write authority.
3. **Host-only seeding** uses `Store::save_internal_memory_doc` and is not a
   model-writable path.

### Consumption

- Prompt assembly fetches shared docs once and extracts the overlay
  (`ic/crates/lunarwing_engine/src/executor/loop_engine.rs:350-388`);
  extraction returns `None` unless the gate is on
  (`prompt.rs:182-202`).
- When present and enabled, up to **4,000 characters** are appended under
  `## Learned Rules (from self-improvement)` between the platform section and
  the tool list. The compiled template is never replaced — the overlay only
  supplements it.
- **Thread lifetime caveat:** assembly happens only when the thread has no
  existing System message (`loop_engine.rs:366-372`). A reused/persisted
  thread retains its previously assembled prompt; disabling the gate or
  deleting an overlay does not retroactively rewrite existing threads.

### Relationship to other flags

- `ORCHESTRATOR_SELF_MODIFY` — the single host policy for runtime orchestrator
  code, prompt overlays, and protected writes. Not an overlay-only setting.
- `SKILL_SELF_IMPROVEMENT` — gates the skill feedback/patch/prune subsystem
  and its missions only (`ic/crates/lunarwing_engine/src/lib.rs:26-35`). The
  new-tenant provisioning default `SKILL_SELF_IMPROVEMENT=true`
  (`ic/scripts/mt-admin-lib/06-env-generation.sh:1083`) does **not** enable
  overlays.

## Operator runbook: "is this agent using a runtime overlay, and why?"

All steps are read-only and init-agnostic (tenant status via
`ic/scripts/lunarwing-mt-admin.sh`, never bare system-bus `systemctl`).

1. **Effective gate state** — check the tenant's rendered env and, when the
   unit is running, the live process environment:
   ```bash
   ic/scripts/lunarwing-mt-admin.sh status <tenant>
   sudo grep -E '^ORCHESTRATOR_SELF_MODIFY=' /home/<tenant>/lunarwing/env/lunarwing.env
   pid=$(sudo systemctl --user -M <tenant>@ show lunarwing-<tenant>.service -p MainPID --value)
   sudo cat /proc/$pid/environ | tr '\0' '\n' | grep '^ORCHESTRATOR_SELF_MODIFY='
   ```
   Unset, or any value other than `true`/`1` (e.g. `TRUE`, `yes`) → overlays
   are inert regardless of what is stored. Do not paste env file contents
   into tickets — they are secret-bearing; report presence/absence only.
2. **Stored overlay state** — query the tenant's own DB (fingerprint, don't
   dump content):
   ```bash
   sudo machinectl shell <tenant>@ /bin/bash -c \
     'podman exec lunarwing-pg-<tenant> psql -U lunarwing -d lunarwing -At -F"|" -c \
     "select path, md5(content), length(content), user_id, updated_at from memory_documents \
      where path = '"'"'engine/orchestrator/codeact-preamble-overlay.md'"'"' \
         or content like '"'"'%prompt_overlay%'"'"'"'
   ```
   No rows → **absent**. Rows + gate off → **stored but inactive**. Rows +
   gate on → **eligible for any newly built prompt**.
3. **Existing-thread retention** — a stored overlay that was ever active can
   still live inside a persisted System message even after the gate is turned
   off or the overlay deleted:
   ```bash
   ... -c "select path from memory_documents \
      where path like 'engine/.runtime/threads/%' \
        and content like '%Learned Rules (from self-improvement)%'"
   ```
   Hits → that thread's snapshot **already contains** the overlay; it is not
   evidence of a currently active injection.
4. **Attribution** — overlay docs carry `user_id` (always a shared owner),
   `source_thread_id`, and `updated_at`. These identify the writer *record*,
   not authority: model-supplied metadata is never write authority (see
   `is_engine_control` above), so treat `metadata.source` as descriptive.

### Safe enable/disable semantics

- **Enable** (operator decision, requires service restart to take effect):
  set `ORCHESTRATOR_SELF_MODIFY=true` in the tenant env and restart through
  mt-admin. Note this simultaneously opts into stored runtime orchestrator
  code — it is not an overlay-only switch.
- **Disable**: remove the flag or set `false`; a restart makes new prompt
  builds ignore any stored overlay, but existing thread snapshots keep their
  assembled System message. Audit step 3 tells you which threads are affected.
- **Never** delete overlays, reset conversations, or toggle gates as part of
  an audit without separate operator authorization.
