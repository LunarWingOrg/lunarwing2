## Review findings addressed on this branch

The prior MR (!1261) was closed with two operator-audit correctness findings.
The refreshed !1276 review found two remaining PID-validation gaps and a
fixture-process cleanup defect. All are addressed in the tooling itself:

1. **[P2] Keep an unreadable live environment distinct from an absent flag**
   (runbook step 1b). The old pipeline
   `sudo cat /proc/$pid/environ | tr | grep … || echo "absent"` returned
   `absent`/exit 0 even when the read itself failed — a daemon restart
   between PID resolution and the read, or an unreadable `environ`, could
   certify "gate off" with no live evidence at all.
   **Fix:** the runbook now separates the read from the classification. The
   environment is captured to an owner-only 0600 temp file; a failed capture is
   reported as **`uninspected (live gate)`** with a non-zero exit; only a
   successful read with no enabling line is classified `absent`. No
   intermediate environment ever reaches a group/world-readable log or ticket
   (values are reduced to presence/absence before printing).

2. **[P2] Validate the PID record rather than converting malformed data into a
   PID** (`ic/scripts/mt-admin-lib/04-tenant-lifecycle.sh`). Both branches
   previously ran `tr -cd '0-9'` *before* the numeric check, so a fixture
   record like `<live-pid>-not-a-number` was silently collapsed into that live
   PID — pointing the audit at an unrelated process while claiming rejection.
   **Fix:** `tenant_daemon_pid` validates the record **as written**, including
   raw NUL bytes. The shared stream reader uses Bash `read -d ''` to detect and
   reject a NUL before command substitution could discard it. Only surrounding
   whitespace is stripped; digits+non-digits and multi-value records fail.
   Capture failures also fail closed, even if a failing producer printed digits.

3. **[P2, !1276] Verify the daemon executable, not arbitrary arguments.** The
   original command-line substring checks accepted a same-user Python worker
   whose arguments mentioned the tenant's home, or a spoofed `argv[0]`.
   **Fix:** require a live tenant-owned PID whose `/proc/<pid>/exe` exactly
   matches the canonical `$(tenant_repo)/target/${PROFILE}/lunarwing` launch
   path used by both service renderers. Symlinked launch paths are resolved;
   missing, unreadable, deleted/replaced, or mismatching executables fail as
   **uninspected**, not as gate-off evidence. The profile defaults to `release`;
   use the same `LUNARWING_MT_PROFILE` setting as the rendered launcher.

4. **[P3, !1276] Track and reap fixture processes in the parent shell.** Spawns
   no longer append to a subshell's discarded PID array. Cleanup iterates the
   initialized parent array directly, terminates every child, and waits for
   every child. The harness verifies that none of its fixture PIDs remain in
   `/proc` after cleanup, including on a test-failure exit.

The expanded real-process harness has **39 assertions** across both init
branches. Before the production fix it reproduced 13 incorrect acceptances
(NULs, worker paths/forged arguments, and failed MainPID capture); all 39 now
pass. This follow-up used isolated fixtures only. It did **not** repeat a live
tenant audit, read any real tenant environment/database, or restart services.

## How the overlay mechanism works (source-verified)

### Storage

- The overlay is a **shared, project-scoped MemoryDoc** with title
  `prompt:codeact_preamble` and tag `prompt_overlay`
  (`ic/crates/lunarwing_engine/src/executor/prompt.rs:80-85`).
- On the host bridge it persists at workspace path
  `engine/orchestrator/codeact-preamble-overlay.md`
  (`ic/src/bridge/store_adapter.rs:1213-1216`) and is shared-owner scoped
  (`__shared__` or legacy `system`).
- Shared-doc lookup iterates both shared owner candidates
  (`ic/crates/lunarwing_engine/src/traits/store.rs:161-172`), so a legacy
  `system`-owned overlay is equally visible to prompt assembly.

### Writers (three, all gated)

1. **Mission structured output** — `process_self_improvement_output` appends
   `prompt_additions` rules to the overlay doc
   (`ic/crates/lunarwing_engine/src/runtime/mission.rs:3147-3225`). Skips
   silently when the gate is off (now covered by the new regression test).
2. **Mission host function `__save_memory_doc__`** — rejects any
   engine-control document while the gate is off
   (`ic/crates/lunarwing_engine/src/executor/scripting.rs:2146-2162`).
   Engine-control identity is structural — `orchestrator:`/`prompt:` title
   prefixes or the `orchestrator_code`/`orchestrator_meta`/`prompt_overlay`
   tags (`ic/crates/lunarwing_engine/src/types/memory.rs:72-84`) — so
   model-supplied metadata (renames, tag edits, `source: compiled_in`) cannot
   grant write authority.
3. **Host-only seeding** uses `Store::save_internal_memory_doc` and is not a
   model-writable path.

### Consumption

- Prompt assembly fetches shared docs once and extracts the overlay
  (`ic/crates/lunarwing_engine/src/executor/loop_engine.rs:350-390`);
  extraction returns `None` unless the gate is on
  (`prompt.rs:182-204`).
- When present and enabled, up to **4,000 characters** are appended under
  `## Learned Rules (from self-improvement)` between the platform section and
  the tool list (`prompt.rs:152`). The compiled template is never replaced —
  the overlay only supplements it.
- **Thread lifetime caveat:** assembly happens only when the thread has no
  existing System message (`loop_engine.rs:366-444`). A reused/persisted
  thread retains its previously assembled prompt; disabling the gate or
  deleting an overlay does not retroactively rewrite existing threads.

### Relationship to other flags

- `ORCHESTRATOR_SELF_MODIFY` — the single host policy for runtime orchestrator
  code, prompt overlays, and protected writes. Not an overlay-only setting.
  Since WI#282, multi-tenant provisioning writes it as `true` for new tenants
  and preserves an explicit operator opt-out on re-render; the runtime itself
  remains fail-closed when the variable is absent or invalid.
- `SKILL_SELF_IMPROVEMENT` — gates the skill feedback/patch/prune subsystem
  and its missions only (`ic/crates/lunarwing_engine/src/lib.rs:26-35`). The
  new-tenant provisioning default `SKILL_SELF_IMPROVEMENT=true`
  does not independently authorize overlays.

## Operator runbook: "is this agent using a runtime overlay, and why?"

All steps are read-only. Tenant inventory, unit state, the live daemon PID,
and every database query go through `ic/scripts/lunarwing-mt-admin.sh`
(override with `LUNARWING_MT_ADMIN`) — its `_ctr` helper resolves the correct
container store, its service reporting handles both systemd user units and
OpenRC, and its `daemon-pid` resolves the supervised daemon on both init
systems with record validation and tenant-association checks. Never call bare
system-bus `systemctl` or `rc-service` against tenant units, and never read
the OpenRC supervisor pidfile to answer a question about the daemon's
environment.

1. **Effective gate state**
   a. **Rendered env + unit state (init-agnostic).**
      ```bash
      ic/scripts/lunarwing-mt-admin.sh status <tenant>
      sudo grep -c '^ORCHESTRATOR_SELF_MODIFY=true$\|^ORCHESTRATOR_SELF_MODIFY=1$' \
        /home/<tenant>/lunarwing/env/lunarwing.env
      ```
      `status` prints `Services (systemd)` or `Services (openrc)` with each
      unit's state — both shapes are authoritative, never re-derive them with
      bare `systemctl`/`rc-service`. The grep prints `0` when the flag is
      unset or any non-enabling value; `1` means enabling. A failed grep
      (unreadable file) is **uninspected (rendered env)**, not `0` — check
      `$?` before trusting the count. Do not paste env file contents into
      tickets — they are secret-bearing; report the count or presence/absence
      only.
   b. **Live process environment (init-agnostic through mt-admin).** Do this
      only when the unit reports running. The read and the classification are
      **separate steps** — a failed read is never "flag absent":

      ```bash
      pid="$(sudo ic/scripts/lunarwing-mt-admin.sh daemon-pid <tenant>)" \
        || { echo "uninspected (live gate): daemon PID unresolvable"; exit 1; }

      envf="$(mktemp)"; chmod 600 "$envf"
      if ! sudo cat "/proc/$pid/environ" >"$envf" 2>/dev/null; then
        rm -f "$envf"
        echo "uninspected (live gate): /proc/$pid/environ unreadable"
        exit 1
      fi

      if tr '\0' '\n' <"$envf" | grep -q '^ORCHESTRATOR_SELF_MODIFY='; then
        tr '\0' '\n' <"$envf" | grep '^ORCHESTRATOR_SELF_MODIFY=' \
          | grep -q '^ORCHESTRATOR_SELF_MODIFY=\(true\|1\)$' \
          && echo "enabled (gate ON)" || echo "present, non-enabling (gate OFF)"
      else
        echo "absent (gate OFF)"
      fi
      rm -f "$envf"
      ```

       The temp file is owned by the invoking operator, mode 0600, and removed
       immediately; only the
      classification word is printed, so no environment value reaches a
      shared log or ticket. `daemon-pid` failing (unit down, malformed
       `child_pid`/`MainPID` record, including raw NUL bytes, or a PID that is
       not alive / not owned by the tenant / not executing its launch binary) means
      *uninspected*, never "flag absent".

      On OpenRC `daemon-pid` reads OpenRC's `child_pid` record
      (`$RC_SVCDIR/options/lunarwing-<tenant>/child_pid`, written by
      supervise-daemon itself), **not** the `run/lunarwing.pid` pidfile — that
      file holds the supervise-daemon *supervisor's* PID, and the tenant env
      is loaded later, by `lunarwing-openrc-env-exec.sh` in the child, so the
      supervisor's environment cannot answer gate questions. On systemd it
       reads the unit's `MainPID` from the tenant user manager.

       Both branches verify the actual `/proc/<pid>/exe` against the canonical
       tenant launch binary, not its command-line spelling. `release` is the
       default profile. For a differently rendered profile, pass the same
       `LUNARWING_MT_PROFILE` value to the sudo command; a mismatch, unreadable
       executable, or an executable deleted/replaced since launch is
       **uninspected**. This checks launch identity, not build-version provenance.

      Unset, or any value other than `true`/`1` (e.g. `TRUE`, `yes`) →
      overlays are inert regardless of what is stored.
2. **Stored overlay state** — query the tenant's own DB through mt-admin's
   container abstraction (fingerprint, don't dump content). Anchor the
   absent/present call on the **reserved path**:
   ```bash
   sudo ic/scripts/lunarwing-mt-admin.sh psql <tenant> -At -F'|' -c \
     "select path, md5(content), length(content), user_id, updated_at from memory_documents \
      where path = 'engine/orchestrator/codeact-preamble-overlay.md'"
   ```
   The psql subcommand runs inside `lunarwing-pg-<tenant>` against the
   tenant's own store on both init systems. A failed query (container
   stopped, psql error) is **uninspected (stored state)** — never record
   "absent" from it. No rows at the reserved path → **absent**. Rows at the
   path + gate off → **stored but inactive**. Rows at the path + gate on →
   **eligible for any newly built prompt**.
3. **Existing-thread retention** — a stored overlay that was ever active can
   still live inside a persisted System message even after the gate is turned
   off or the overlay deleted. Match the marker **only inside a System-role
   message**; a plain `content like` over the whole snapshot also hits User /
   Assistant / ActionResult messages that merely quote the heading, which is
   not evidence of an injected overlay:
   ```bash
   sudo ic/scripts/lunarwing-mt-admin.sh psql <tenant> -At -F'|' -c \
     "select d.path from memory_documents d, json_array_elements(d.content::json->'messages') m \
      where d.path like 'engine/.runtime/threads/%' \
        and m->>'role' = 'System' \
        and m->>'content' like '%Learned Rules (from self-improvement)%'"
   ```
   Hits → that thread's snapshot **already contains** the overlay in its
   System message; it is not evidence of a *currently active* injection.
   Threads matched by the naive LIKE but excluded here are candidates only —
   inspect the role before citing them.
4. **Attribution** — overlay docs carry `user_id` (always a shared owner),
   `source_thread_id`, and `updated_at`. These identify the writer *record*,
   not authority: model-supplied metadata is never write authority (see
   `is_engine_control` above), so treat `metadata.source` as descriptive.

**Probe outcomes — a failed probe is never a clean result.** Classify only
from evidence you actually obtained; anything else is *uninspected*:

| Observation | Classification |
|---|---|
| `mt-admin status` fails / tenant not in registry | **uninspected** — no finding may be recorded |
| Rendered-env grep itself fails (file unreadable) | **uninspected (rendered env)** — `0` from a failed read is not "absent" |
| `daemon-pid` exits non-zero (unit down, record missing/malformed — including NULs — failed capture, or PID not alive / not tenant-owned / wrong executable) | **uninspected (live gate)** — fall back to rendered-env evidence only and say so |
| Unit reports running, `daemon-pid` resolves, environ **read fails** | **uninspected (live gate)** — never "absent"; re-run after confirming the daemon did not restart mid-probe |
| environ read succeeds, flag unset / non-enabling | gate **off** (overlays inert) |
| environ read succeeds, flag `true`/`1` | gate **on** — proceed to steps 2-3 |
| psql query returns no rows at the reserved path | overlay **absent** |
| psql query errors / pg container stopped | **uninspected (stored state)** — never record "absent" |
| Rows at the reserved path + gate off | **stored but inactive** |
| Rows at the reserved path + gate on | **eligible for a newly built prompt**; check step 3 for threads that already embed it |
| Role-aware query (step 3) hits | snapshot **already contains** the overlay in its System message |
| Naive LIKE hits with no role-aware hit | user/assistant quote only — **not** an overlay; inspect the role before citing |

### Safe enable/disable semantics

- **Enable** (operator decision, requires service restart to take effect):
  set `ORCHESTRATOR_SELF_MODIFY=true` in the tenant env and restart through
  mt-admin. Note this simultaneously opts into stored runtime orchestrator
  code — it is not an overlay-only switch.
- **Disable**: remove the flag or set `false`; a restart makes new prompt
  builds ignore any stored overlay, but existing thread snapshots keep their
  assembled System message. Audit step 3 tells you which threads are affected.
- **Never** delete overlays, reset conversations, or toggle gates as part of
  an audit without separate operator authorization.
