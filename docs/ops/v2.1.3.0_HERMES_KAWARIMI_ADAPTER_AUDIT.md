# Hermes Kawarimi Adapter — Cursory Breakage Audit (v2.1.3.0)

- Date: 2026-09-26
- Branch: `aj/kimi-14-20260926-2100`
- Scope: `hermes_kawarimi/` (extract → mapper → loader) and every LunarWing-side
  contract it depends on. Cursory audit only, per goal item #14 — no code changes.

## Verdict

**Nothing in the codebase has broken the adapter.** Every external contract it
consumes — mt-admin verbs/flags, the Python sibling-package API surface, the
PostgreSQL schema it populates, and the provisioning env keys — is intact at
HEAD. All 49 of its own unit tests pass. One latent hazard (not new, but worth
recording for the later in-depth pass) is noted at the bottom.

## What the adapter depends on, checked one by one

### 1. mt-admin verb contract (`hermes_kawarimi/loader.py`)

The loader shells out to `lunarwing-mt-admin.sh` for:
`add-tenant --no-health`, `build-tenant --with-wasm`, `install-wasm`,
`start-tenant`, `stop-writers`, `stop-tenant`, `start-pg`, `stop-pg`.

- All verbs still exist in `ic/scripts/lunarwing-mt-admin.sh` (dispatch at
  lines 977/1070/1093/1103) and all flags the loader passes
  (`--no-health`, `--docker-group`, `--tensorzero-url`, `--llm-model`,
  `--with-pebble/--with-opencode/--with-kimi`, `--with-toolchains`) are still
  parsed for add-tenant/build-tenant (lines 576–658, 713–742).
- `stop-writers` still performs verified writer quiescence via
  `tenant_writers_active` (`ic/scripts/mt-admin-lib/04-tenant-lifecycle.sh:327`),
  which the loader relies on for its race-free PG-only populate window
  (WI#133/#134/#137 semantics unchanged — item-31 doc parity commits touched
  docs/tests only).
- `start-pg`'s comment in mt-admin explicitly names the hermes_kawarimi loader
  as its consumer (`lunarwing-mt-admin.sh:1096`), so this coupling is
  intentional and documented on both sides.

### 2. Sibling-package API (`lunarwing_mt_onboard`)

The loader imports `secrets_ops` (`ensure_dependencies`, `list_tenants`,
`parse_tenant_env`, `insert_secret`) and `provisioner` (`PhaseResult`,
`ensure_mt_admin`, `run_command`). All symbols still exist with unchanged
signatures (`lunarwing_mt_onboard/secrets_ops.py:22/43/73/174`,
`lunarwing_mt_onboard/provisioner.py:29/108/125`). `config.py` imports
`TenantConfig.validate_name` — also still present. The Nanocode retirement
commit (`0c796b13a`) is already reflected: `ImportPlan.with_nanocode` validates
to a hard error, which is correct behavior.

### 3. Provisioning env keys

After add-tenant the loader requires `DATABASE_URL`, `SECRETS_MASTER_KEY`,
`LUNARWING_OWNER_ID` from the rendered tenant env. The WI#239 env-generation
rework (goal item #5, `06-env-generation.sh`) added explicit variables and
dropped a header comment but did not remove or rename any of these three keys.

### 4. PostgreSQL schema targets (`loader._populate` / `_insert_secrets`)

- `memory_documents`: columns used (`user_id`, `agent_id`, `path`, `content`,
  `metadata`, `updated_at`) unchanged since V1. V21 (`UNIQUE NULLS NOT
  DISTINCT`) and V27 (added `indexed_at`, nullable) do not remove or retype
  anything the loader writes.
- `conversations` / `conversation_messages`: V1 shape unchanged — all INSERT
  columns still exist with the same types; PK conflict targets (`id`) intact.
- `settings` (V8): `(user_id, key)` PK and JSONB `value` unchanged; the
  loader's `ON CONFLICT (user_id, key)` is still valid.
- `secrets` (V2): `UNIQUE (user_id, name)` constraint and the
  `encrypted_value`/`key_salt` columns that `secrets_ops.insert_secret` upserts
  against are unchanged. No later migration alters `secrets`.
- Sentinel table for the schema-wait poll (`memory_documents`) still created by
  the daemon's refinery run, so the start-then-stop bootstrapping approach
  still works. Latest migration is V27; nothing renames the sentinel.

## Notes / latent hazards for the in-depth pass

1. **V21 changed the `memory_documents` unique constraint** to
   `UNIQUE NULLS NOT DISTINCT (user_id, agent_id, path)`. The loader's comment
   still says "NULL is treated as distinct so ON CONFLICT won't fire" — that
   premise is now stale. The loader deliberately uses manual
   UPDATE-then-INSERT, which is still correct and idempotent for its
   daemon-down populate window, so no fix is required; but if populate were
   ever run concurrently with a live daemon, two writers could now race into a
   unique-violation error instead of silently duplicating. Switching to
   `INSERT ... ON CONFLICT ON CONSTRAINT unique_path_per_user DO UPDATE`
   (the daemon's own pattern, `ic/src/workspace/repository.rs:127`) would make
   it race-safe. Not urgent: the populate window is structurally daemon-down.
2. **V27 added `memory_documents.indexed_at`** with a stale-index sweep keyed
   on `updated_at`. Loader-populated docs get `indexed_at = NULL` (column
   default), which the daemon treats as "needs indexing" — the desired outcome
   — so imported memory is picked up by the indexer on first boot. Verified
   benign, worth re-asserting in any live rehearsal.
3. **New mt-admin surface the adapter doesn't know about:** `--with-opencode2`
   (OpenCode 2 worker) exists on add-tenant/build-tenant but the adapter has no
   flag for it. Not a breakage — an enhancement candidate for the upkeep pass.
4. The repo has a shell regression suite for the *machine-migration* Kawarimi
   (`ic/scripts/tests/test-kawarimi-import-flags.sh`, targets
   `import-tenant.sh`/`export-tenant.sh`); there is no equivalent host-level
   harness for `hermes_kawarimi`'s mt-admin argv wiring beyond its Python fakes.
   Live `--apply` rehearsal remains the acceptance step (as the README states).
