## Immediate release implications

1. **Five 2.1.4.0-labeled items remain open:** #281, #280, #269, #270, #271
   (plus #184 pending design revision). None is a build breaker, but #281,
   #280, and #269 are agent-visible correctness defects discovered on test

   `routine not found` error, whose goals-item-5 fix was a fallback inside
   `routine_history` rather than the item's preferred dedicated tool). The
   goals file's unchecked items mapping onto these are 11 (#184), 18 (#269),
   19 (#270), 22 (#280), and 24 (#271); #281 has no goals item yet.
2. **#281 is the widest-impact open defect.** The engine CodeAct preamble
   (`ic/crates/lunarwing_engine/prompts/codeact_preamble.md:36-39`) instructs
   every Engine V2 agent that `mission_create`/`mission_list`/`mission_fire`/
   `mission_pause`/`mission_resume` are callable functions. Those effects are
   real only inside engine threads via the effect bridge
   (`ic/src/bridge/effect_adapter.rs:425-669`, gated on a mission manager that
   is wired in `ic/src/bridge/router.rs:1745-1762`); the v1 agent runtime and
   job workers expose no such tools, so agents outside engine threads fail on
   the advertised contract. Fix is one of: expose, remove, or re-scope the
   preamble copy — the item offers all three options.
3. **#280 is a self-referential safety false-positive.** `daily/*.md` writes
   are injection-scanned (`ic/src/workspace/mod.rs:129,137-140,152-180`) with
   a substring/regex scanner (`ic/crates/lunarwing_safety/src/sanitizer.rs`)
   that has no notion of quoting or description context — patterns like
   "user:", "ignore previous", "system:" match verbatim inside descriptive
   security notes. Any fix must not weaken the scan for actual injections;
   the item's suggested direction (context relaxation at the memory-write
   boundary only) is the safe scope.
4. **#184 has concrete review feedback to address.** MR !1294 was closed with
   two P2 design-contract findings (legacy `@username` matching cannot be
   preserved by exact-digest lookup; unkeyed SHA-256 names don't deliver the
   claimed authorization-list privacy) plus a non-blocking hot-path
   enumeration finding. The next attempt should revise
   `docs/proposals/PAIRING_SECRETS_STORE_DM_AUTH.md` (branch-only on
   `rarity/kimi-11-20261001-0700`; not on master) rather than re-submit
   unchanged.
5. **Tracker hygiene:** #198/#199 are empty-bodied high/security items whose

## #280 (OPEN) — SafetyLayer prompt-injection detector false-positives on daily_log writes containing security-flavored content

**Author:** dwarfstar | **Created:** 2026-10-01 | **Labels:** 2.1.4.0

Filed from dwarfstar post-deploy smoke testing (medium severity). Writing a
`daily_log` note that *describes or quotes* injection patterns (e.g. logging
prompt-injection test results) is rejected with "prompt injection detected
(Attempt to inject user message / Attempt to override previous instructions)".
Verified in source:

- Daily logs are treated as prompt-write surface and scanned on every write
  (`ic/src/workspace/mod.rs:129` via `is_daily_log_file` `:137-140`, scan in
  `reject_if_injected` `:152-180`, wired into `write()`).
- The scanner (`ic/crates/lunarwing_safety/src/sanitizer.rs`) is
  substring/regex based with no quoting or description-context awareness:
  `"user:"` → High "Attempt to inject user message" (`:109-113`), `"ignore
  previous"` → High "Attempt to override previous instructions" (`:62-66`),
  `"system:"` → Critical (`:98-103`). A verbatim quote inside a describing
  sentence matches the same as a live injection.
- The reporter's ruled-out hypothesis (first-vs-second write) is consistent
  with the code: nothing in the scan path is write-count aware; it is purely
  content-triggered.

Suggested fix direction in the item: relax the detector at the memory-write
boundary for quoted/describing content, or run a sanitization/allow-list pass
for internal memory writes before detection. Any change here is
security-sensitive (`ic/AGENTS.md`: do not weaken injection rejection), so
the regression suite in `workspace/mod.rs:2652+` and the sanitizer's own
tests must keep rejecting genuine injections.

## #184 (OPEN) — pairing: replace file-store DM pairing mechanism with secrets-store-based DM auth (design discussion)

**Author:** sweetiebot | **Created:** 2026-09-19 | **Updated:** 2026-10-01 | **Labels:** 2.1.5.0, architecture, enhancement, medium, security, tech-debt

Re-labeled from 2.1.4.0 to 2.1.5.0 on 2026-10-01. This is goals item 11's
item; its implementation MR !1294 ("Item #11: work on …pairing…") was
**closed** on 2026-10-01 after a refreshed review left two P2 design-contract
findings against `docs/proposals/PAIRING_SECRETS_STORE_DM_AUTH.md` (the
proposal exists only on the rejected !1294 branch
`rarity/kimi-11-20261001-0700`; it is not on master):

1. **Exact-digest lookup contradicts legacy username matching.** The proposal
   promises every lookup derives one digest and requires byte-for-byte
   principal match, while also migrating legacy entry bytes unchanged and
   claiming preservation of today's `is_sender_allowed` behavior — which
   allows exact trimmed id *or* case-insensitive username/`@username`
   matching (`ic/src/pairing/store.rs:450-461`). A migrated `@Alice` record
   would no longer authorize username `alice` under the new contract.
   Requested: a source-tagged legacy compatibility matcher (with regression
   covering the WASM `pairing_is_allowed` path,
   `ic/src/channels/wasm/wrapper.rs:630-638`), or a lossless migration
   representation.
2. **Unkeyed SHA-256 names don't provide the claimed privacy.** Truncated
   unkeyed digests stored outside the encrypted grant allow dictionary
   attacks on likely public IRC/XMPP principals without the master key,
   contradicting the proposal's "keyed digest / master-key-required" claims.
   Requested: domain-separated tenant-scoped keyed derivation with key
   lifecycle, or an explicit membership-leakage threat-model statement.

Non-blocking finding: decrypt-per-grant enumeration is on the DM hot path
(Signal sender gating), so bounded caching or a revised performance claim is
needed. Prior !1284 findings (lossy SSH-style identity key; in-process-only
mutex claim) were addressed in the final revision. The next attempt should
revise the proposal document (carrying the !1294 branch forward or
re-creating it) to resolve both P2s rather than re-submit.

The !1283 stopgap (sbpatch1 pairing-allowlist preservation,
`ic/src/pairing/store.rs`) is merged and shipped in v2.1.3.0/v2.1.4.0;
#200 (the stopgap tracker item) was closed 2026-10-01.
