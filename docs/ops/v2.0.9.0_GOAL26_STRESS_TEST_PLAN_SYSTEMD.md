# v2.0.9.0 — Goal 26: Stress Test Plan (Arch/systemd)

Status: plan executed twice on 2026-08-28. The latest fresh rerun used tenant
`goal26r2` at source `ae9ae4fd`; both runs are recorded in
`v2.0.9.0_GOAL25_STRESS_TEST_FINDINGS_SYSTEMD.md`.

Companion to item #26 of `AGENT_GOALS_2.0.9.0.md` — the systemd-host
edition of the item #25 plan (`v2.0.9.0_GOAL25_STRESS_TEST_PLAN.md`).
Objective: prove a freshly provisioned multi-tenant LunarWing instance
survives realistic and abusive load across every user-visible surface —
web gateway chat, tool loop, memory subsystem, and the WeeChat relay
channel — without message loss, data corruption, hangs, or resource
exhaustion, with the tenant destroyed at the end.

## Environment

- Host: Arch Linux, systemd PID 1, Podman, cgroup v2 delegated. Tenant
  units run in the tenant user's manager (`systemctl --user` under
  `/run/user/<uid>`, linger enabled) — never the system bus.
- Latest tenant: `goal26r2` via `ic/scripts/lunarwing-mt-admin.sh add-tenant`
  from the working branch, `build-tenant --with-wasm --require-wasm` (release
  build, all 13 WASM extensions), `start-tenant`. Ports 10010–10019, PG 16
  Quadlet, LunarVision sidecar (20015/20016). The prior run used `goal26sd`.
- LLM: harness-controlled OpenAI-compatible streaming fixture with
  deterministic text, tool-call, delay, and iteration scripts.
- Neighbors: alpha + hermes stay running as isolation witnesses; status
  verified before and after.
- All lifecycle operations go through mt-admin (HARD RULE).

## Phases

- **P0 Seed**: 25 documents (SOUL.md, AGENTS.md, profile.json, 16
  topical notes, daily log, append ledger) via authenticated
  `/api/memory/write`; byte-compare read-back; manifest SHA-256.
- **P1 Memory API**: W1 200 sequential write+read; W2 50 concurrent
  distinct-path writes; W3 3 × 40 concurrent same-path appends (item-29
  regression check: markers exactly once, no 500s); W4 200 search + 100
  write mixed; W5 500 KB + 1.5 MB documents; W6 tree/list under write
  load; adversarial path/role-token checks.
- **P2 Chat + tool loop**: C1 sequential, C2 concurrent workers, C3
  burst — each turn drives a memory_read → memory_write → memory_search
  triplet; C4 readback byte-exact verification of all stress paths +
  seed-restore check; gateway abuse (bad/no auth, malformed JSON,
  blank/missing thread, oversized body, unknown route, 200-request
  flood).
- **P3 WeeChat E2E**: fake IRC peer → `fake_ircd.py` → WeeChat → relay
  WS → ws_adapter → WASM channel → agent → back. H1 pairing + warmup;
  H2 sequential 20; H3 burst 50; H4 adapter process restart mid-stream
  (item-29 watermark/journal regression check: zero loss); H5 channel
  memory.
- **P4 Soak (15 min)**: continuous chat turns + memory read/write/search
  loop + weechat traffic; resource sampling (RSS, threads, fds) every
  ~15s.
- **P5 Restart resilience**: full stop-tenant/start-tenant; measure
  healthy-elapsed; verify all seeds + large docs SHA-256, threads,
  channel memory.
- **P6 Destruction + isolation**: remove-tenant --purge; verify
  user/home/ports/registry absent, no stray listeners; neighbors
  healthy.

## Pass criteria

- No 5xx on any compliant client behavior; abuse probes return expected
  codes.
- Zero message loss in all chat/weechat phases; zero memory corruption
  or mismatch anywhere.
- No resource leak trend over the soak.
- Tenant fully destroyed; neighbors unaffected.

Execution notes: both systemd runs used a deterministic mock LLM instead of
live TensorZero so tool dispatch and message accounting were objectively
checkable. The original `goal26sd` run used a 45-second calibration pre-run; the
fresh `goal26r2` run used a streaming fixture and discarded/reran two harness
attempts after history-state and expected tool-rate-limit behavior were exposed.
Those corrections and all authoritative results are explicit in the findings.
