# Agent Rules — kimicode4lunarwing

## What This Is

Persistent container worker for upstream Kimi Code CLI (MoonshotAI/kimi-code). The WebSocket bridge is Node.js/TypeScript and spawns `kimi -p <prompt> --output-format stream-json` as a subprocess per task.

## Key Files

- `scripts/lunarwing_bridge.ts` — The WebSocket server/client. Changes here affect protocol behavior.
- `scripts/kimi_task_executor.ts` — Task execution via the Kimi Code CLI subprocess. Controls process spawn, stream-json parsing, timeout/cancel. Since WI#848 it also snapshots `$KIMI_CODE_HOME/mcp.json` at startup (`captureTrustedMcpConfig`, called by the task runner and the legacy in-bridge server) and rewrites the file from that snapshot immediately before every spawn, so a task's registration cannot reach a later session; a failed restore fails the task closed. Since WI#847 it re-asserts the WI#206 `[[hooks]]` entry in `$KIMI_CODE_HOME/config.toml` before every spawn via `scripts/guard_config.ts`, because that effective config is task-owned; a missing or unrepairable config fails a managed task instead of spawning it unguarded.
- `scripts/lunarwing_runtime.ts` — Shared types and envelope helpers. Keep in sync with `agent_comm_protocol.json`.
- `scripts/lunarwing_tool_proxy.ts` — WI#324 worker-side relay: per-task unix socket that turns the in-task MCP shim's requests into `tool_call`/`tool_list` hub frames and routes replies back by call id.
- `scripts/lunarwing_mcp_server.ts` — WI#324 thin stdio MCP server the CLI spawns per task (registered in `$KIMI_CODE_HOME/mcp.json`, materialized at container start from the baked `config/mcp.json` by `entrypoint-task-setup.sh` and restored before every spawn — WI#848). Advertises zero tools without the per-task proxy env; the hub stays deny-by-default without a `tool_allowlist` grant.
- `scripts/task_runner.ts` — WI#454 task-container daemon, uid 10002 (refuses root and hub credential variables). Owns `/run/lunarwing-shared/runner/task-runner.sock`, executes tasks and provides the bounded ping health probe.
- `scripts/task_runner_client.ts` — Bridge-container delegation client, uid 10102 in task group 10002. Cancels on the run's own connection; the task container owns process cleanup across the PID namespace boundary.
- `entrypoint-split.sh` — Managed `split-bridge` / `split-task` launcher. The bridge's token is private to `/home/kimi-bridge`, task setup runs as kimi, and rootful starts verify the pinned workspace inode before setup. IPC uses the role-owned sticky `-ipc-v2` volume; this separates bridge credentials, not jobs sharing the task uid.
- `task_runner_bind.py` — Legacy host/rehearsal helper for a root-bound inherited descriptor; managed split containers do not invoke it.
- `entrypoint.sh` — Dispatches managed roles to the split launcher and retains one-shot/host legacy paths. Split images require an explicit websocket role. The Dockerfile fixes boot scripts at 0555 and config/hooks/scripts at 0555 directories / 0444 files independent of checkout modes. See `docs/ops/WORKER-CONTAINERS.md` for lifecycle, env/mount and upgrade contracts.
- `config/config.toml` — Kimi Code CLI default config (model, provider, thinking, fail-closed permission policy). Baked into the image. Default provider is the TensorZero gateway (function `tensorzero::function_name::FrontierCODEK`), not the managed api.kimi.com service — see README. Since WI#330 the baked `base_url` is an `.invalid` placeholder that `entrypoint.sh` refuses to run; mt-admin renders `KIMI_BASE_URL` per tenant (default: the tenant's own LLM endpoint).
- `hooks/headless_command_guard.mjs` — WI#206 fail-closed PreToolUse guard. The 2.0.2 behavior was live-verified; the real-CLI contract gate was re-run against 2.5.2 on 2026-11-08 (WI#582), 2.5.3 on 2026-11-12 (WI#609), 2.6.3 on 2026-11-19 (WI#775) and 2.7.2 on 2026-11-21 (WI#804), and all four lanes pass in each, so the hook table and the `-p`/`--yolo` flag contract hold at the current pin; the protected worker image build remains the in-image proof. Print mode forces the auto policy and the upstream dangerous-command guard is skipped in auto mode. Since 2.6.0 config `[[permission.rules]]` do load, in print mode too (the baked config's rules and, for a trusted workspace, those of `<project>/.kimi-code/local.toml`), which 2.5.3 did not do; the lane bakes no rule, keeps the workspace untrusted, and this hook runs in the earlier phase, so it is still the only in-CLI enforcement point for the headless lane. A here-document that a shell or a stdin interpreter reads denies when its delimiter is unquoted and its body holds such a substitution or such a variable (`bash <<EOF` / `$(curl …)` / `EOF`), and every here-document body of every line is checked as a command line of its own (`ssh host <<EOF` runs it elsewhere); a decoded substitution or a filled variable at a body's command position counts only where a shell word reads the body (also behind a launcher the guard does not know, `docker exec -i c sh <<'EOF'`), so a document that shows one stays data. Ordinary substitutions stay data: `bash -c "$(cat build.sh)"`, `bash <(cat build.sh)`, `eval "$(ssh-agent -s)"`, `source <(kubectl completion bash)`, `x=$(echo <b64> | base64 -d); echo "$x"`. Since WI#889 a redirection is read out of the command line before any rule sees it: the clause, word, segment, listener, git-verb and raw-shape readers all step over every form of `man bash` REDIRECTION (`[n]<word`, `[n]>word`, `[n]>|word`, `[n]>>word`, `&>word`, `>&word`, `&>>word`, `[n]<<[-]word`, `[n]<<<word`, `[n]<&word`, `[n]>&word`, `[n]<>word`, each also with `{varname}` and with or without blanks), so `rm 2>&1 -rf /home/kimi/x`, `git 2>/dev/null reset --hard`, `kimi 2>/dev/null server`, `python3 -m 2>/dev/null http.server` and `bash 2>/dev/null -c "kimi server"` deny like the plain spellings, while the false refusals the old reading made (`rm -rf /tmp/x 2> /dev/null`, `rm -rf /tmp/x </dev/null`, `rm -rf 2>&1 /tmp/x`) pass. `|&` is bash's `2>&1 |`, so its bar splits a pipeline (`curl … |& sh` denies); a redirection's own `&`/bar are not control operators; a write target stays visible to the device rule (`>&/dev/sda1`, `1>&/dev/sda1`, `&>/dev/sda1`); and a here-string body is read as the command line it spells (`bash <<<"kimi server"` denies). Since WI#890 the interpreter deletion rule reads a one-liner
however the interpreter is named and however its code is attached. The name may
sit behind any number of directory parts, absolute or relative, with `~`, a
variable or a quote in the path (`/usr/bin/python3`, `/usr/local/bin/node`,
`../bin/node`, `~/bin/node`, `"python3"`), and the interpreter is the last part
of the path. The names the base image ships for one interpreter are read as that
interpreter: `nodejs`, and a versioned perl (`perl5.36.0`, any version — the
pattern holds no version number). `interpreterFamily()` maps a spelling to the
family whose option table and deletion reader apply. The code is read in every
form the interpreter's own option syntax accepts: a separate word, attached to
the flag (`-c"…"`, `-e'…'`), attached to a flag cluster (`-Ic"…"`, `-le'…'`),
and `--eval=…`/`--print=…`, so the short-option cluster is walked letter by
letter and a letter that takes a value consumes the rest of its word. Perl's
numeric `-0` and `-l` modifiers remain in that walk, so a later eval flag is
still read. The temp-root test is unchanged, so a deletion inside `/tmp`
still passes, and `/usr/bin/python3 script.py`, `-m pytest`, `node app.js` and
`/usr/bin/perl -pe 's/a/b/' f` stay ordinary work.

## Guard Scope

The command guard is a guard against naive use. Its purpose is to refuse the
plain spelling of a command that a task must not run: the command itself, and
the same command as a body behind `bash -c` or `eval`, in a here-document or
in a here-string. What it reads beyond the plain spelling is described in this
file. That coverage is not extended. The container and tenant egress policy
remain the security boundary.

Other spellings of a refused command are outside the guard's scope. By the
maintainer's decision of 2026-11-26 these are documented limits, not defects:

- WI#907: literal text handed to a shell another way, such as
  `echo 'kimi server' | sh`, a file written and then run, a variable given to
  `eval` or `sh -c`, or a `trap` action.
- WI#904: the further routes, listed in that item, by which decoded or fetched
  content reaches a shell, such as `x=$(curl …); y=$x; $y`.
- WI#909: Git's own listeners (`git daemon`, `git instaweb`), and Git programs
  named by their dashed path, such as
  `/usr/lib/git-core/git-rebase -x '<body>'`.

## Guard Quote Handling

The WI#895 Git body check recognizes both `git submodule foreach` and
`git submodule--helper foreach`, as well as `git rebase` exec options. It reads
shell words before passing a body to the guard, so a quoted description of a
Git command is not treated as a call.

WI#898 uses the Git 2.56 command manuals and option parsers for `filter-branch`
filters, diff and merge tools, grep's pager, pack commands on fetch, pull,
clone, ls-remote, fetch-pack, push and send-pack, and archive's remote command.
It checks command-valued settings in `-c`, `--config-env`, clone configuration,
`git config` writes, and the `GIT_CONFIG_*` environment forms. Covered keys
include editor, pager, SSH, external diff, merge, filter, pack, credential-helper,
`trailer.<name>.cmd` and `trailer.<name>.command`, fsmonitor and man-viewer
settings. The guard refuses explicit enabling of Git's external command transport.

The eight environment names checked across shell clauses are `GIT_EDITOR`,
`GIT_SEQUENCE_EDITOR`, `GIT_PAGER`, `GIT_SSH_COMMAND`, `GIT_EXTERNAL_DIFF`,
`EDITOR`, `VISUAL` and `PAGER`. For these names, WI#906 distinguishes bare and
command-prefix assignments, operands of `export`, `declare`, `typeset`,
`readonly` and `local`, and `env` assignments before its command, from
assignment-shaped arguments to other programs.

A Git command value or an assignment to one of the eight names that the outer
shell can change is refused as unverifiable, even without Git on the line.
For example, use `export PAGER=less` instead of `export PAGER="${PAGER:-less}"`.
An assignment-shaped argument to another program whose value holds an
expansion (such as `echo "EDITOR=$EDITOR"`) no longer triggers that refusal.
Literal values are still checked as shell bodies even in arguments. A
single-quoted literal body can pass if it passes the body rules, as in
`git rebase -x 'cargo test -p $CRATE' main`. Coverage is limited to recognized
Git command words, options and setting names. Direct helper executables,
dynamic command or option words, runtime expansion inside the body, settings
already installed elsewhere, and unlisted settings such as send-email or
IMAP commands remain outside this check. The container and tenant egress
policy remain the security boundary.

Since WI#867 the clause splitter, punctuation view and listener scan share
quote and substitution spans. A backslash escapes the next character outside
quotes, escapes nothing inside single quotes, and inside double quotes only
escapes `"`, `\`, `$`, a backtick or a newline. Parenthesized substitutions
have their own quote context. A backtick body closes at the first unescaped
backtick, regardless of the quotes in its body. Operators inside a
substitution split only its own commands, not the enclosing clause. The
guard scans the body separately without running it.

The guard rejects ANSI-C backslash escapes other than escaped apostrophes
instead of decoding them. Use literal shell words.

The WI#873 raw-shape word view removes empty quoted spans within a word but
preserves a standalone empty argument. It checks the literal spelling of Bash
locale-quoted words (`$"…"`) without looking up translations. The raw-shape
checks can conservatively deny a one-word quoted mention, just as they can
deny an unquoted mention.

Since WI#883 a further view drops each unquoted parameter expansion and
substitution so the verb a word may become is read (`${EMPTY}tee` → `tee`).
A word that is only an expansion becomes empty and stays a word, and an
unquoted `${IFS…}` becomes a separator, matching the reading `checkRm` already
uses. An expansion inside quotes is left alone. Like the other views it can
only add denials; it does not evaluate the shell. A second such view reads an
operator expansion as the word bash may use in its place (`${X:-tee}` →
`tee`, for `:-`, `-`, `:=`, `=`, `:+` and `+`), inside double quotes too; it
is checked beside the first view, never instead of it.

Comments and literal-delimiter heredocs do not carry quote state into later
commands. The listener rule still checks heredoc lines as potential shell
input. For supported literal brace groups it expands the alternatives before
splitting unquoted IFS markers, including slices; quoted IFS stays data.
Since WI#868 a brace group is expanded when its own `{`, `,` and `}` are
unquoted, so a quoted alternative no longer suppresses it: `{kimi,"server"}`,
`{"kimi",server}`, `{kimi,'server'}` and `{kimi,$'server'}` all deny like
`{kimi,server}`, as bash runs them, while a quoted group
(`echo "{kimi,server}"`) or a quoted comma stays literal.

The continuation and Git word readers reuse escape helpers but keep separate
conservative views. Since WI#872 the `env -S`/`--split-string` reader is one
more: it reads the string as `env` arguments rather than Bash, treating
unquoted space, tab, LF, CR, VT and FF as separators. The listener and
decode-pipe checks share the option walk: long options resolve by exact name
or unique abbreviation, and parsing restarts after each split. A `${NAME}`
expansion or more than 16 splits in one `env` invocation is refused as
unverifiable. Since WI#887 the launcher body readers (`flock`, `watch`,
`su`, `parallel`, and `script` beside the shells) are one table keyed by the
launcher's own name; each reads the string that launcher would run, with the
quoting the listener word reader has already removed. This is not a full Bash parser: it does not evaluate runtime
words or implement general brace expansion. The container and tenant
egress policy remain the security boundary.

## Guard Redirection Handling

Since WI#889 a redirection is neither a clause end nor a word, wherever it
stands in a simple command (`man bash`, REDIRECTION). One reader blanks every
redirection out of the command line and keeps its targets and here-string
bodies beside it, and the clause, word, segment, listener, git-verb and
raw-shape readers all read that view, so `rm 2>&1 -rf /x`, `git 2>/dev/null
reset --hard` and `kimi 2>/dev/null server` read as the commands bash runs.
The forms are `[n]<word`, `[n]>word`, `[n]>|word`, `[n]>>word`, `&>word`,
`>&word`, `&>>word`, `[n]<<[-]word`, `[n]<<<word`, `[n]<&word`, `[n]>&word`
and `[n]<>word`, with `{varname}` in place of `n` where a descriptor is
accepted, and with or without blanks before the target. The digits or
`{varname}` count as the descriptor only as a word of their own. The
combined output forms `&>` and `&>>` take no descriptor, so `2&>f`
retains `2` as an argument.

The `&` of `2>&1`, `<&0`, `&>`, `>&` and the bar of `>|` are operator
characters, not control operators; `|&` is bash's `2>&1 |`, so its bar
splits a pipeline and its `&` does not. A target a write rule owns is still
seen: `>&word`, `n>&word`, `&>word` and `&>>word` at a block device deny,
and `truncate`/`of=` keep their own readings. The guard removes shell
quoting from each here-string word and applies the full command rule set to
the resulting body. A here-string word the guard cannot read (an expansion,
a substitution, `~`) is refused when anything on the command line could run
it: a shell or `eval`, `source`/`.` of standard input, an interpreter with
no script operand, a program given `/dev/stdin` or `/dev/fd/N`, or a command
word the guard cannot read, substitutions included; and on any line that
also holds a here-document. Otherwise the line can only read it as data, so
`read -r a <<< "$line"` and `jq . <<< "$json"` stay ordinary.
Temporary-file cleanup can put redirections before or after the operands.
For example, `rm 2> /dev/null -rf /tmp/x` and `rm </dev/null -rf /tmp/x`
both pass.

## Protocol Compatibility

The `lunarwing-agent-v1` WebSocket subprotocol is shared with Pebble and OpenCode workers. The legacy `ironclaw-agent-v1` alias has been removed and is not accepted. Changes to `agent_comm_protocol.json` or envelope format must stay backward-compatible or be coordinated across all workers.

## Build Notes

The Dockerfile installs the official Kimi Code CLI with `npm ci` from `kimi-cli/package-lock.json`; update that lock and the `KIMI_CODE_VERSION` default together. The bridge uses `scripts/package-lock.json`. Base images, Debian package indexes, rustup, and Go archives are pinned, so refresh their recorded digests/checksums deliberately rather than restoring unlocked installers. The CLI install `RUN` ends with `touch -d "@${SOURCE_DATE_EPOCH}" /usr/local`: npm's global install does not deterministically modify that directory, and the resulting candidate-vs-rebuild mtime race flaked the CI reproducibility gate five times in October 2026 — keep the pin when editing the step.

Keep `ARG SOURCE_DATE_EPOCH=0` before the runtime `useradd`, not only before the CLI install. The same-layer assertion checks the account's `/etc/shadow` day against the source epoch so candidate/rebuild pairs spanning UTC midnight stay deterministic (WI#510). All four worker snapshots and `CI_DEBIAN_SNAPSHOT` move together; `20261105T082236Z` includes the Brotli OS-package fixes, not a fix for Node's separately bundled decoder (WI#514). Snapshot sources stay HTTPS and every APT call sets `Acquire::https::Timeout=60` (WI#561). The old client's update and apt-only bootstrap install use `Acquire::Retries=0`; after the `dpkg --compare-versions` `2.6.2` floor passes, the fixed client installs the remaining packages with `Acquire::Retries=3`, including the toolchain layer. Every update uses `--error-on=any`. Keep both direct CA-bundle copies from the digest-pinned Python image before APT and run `update-ca-certificates` after package installation; the slim Node base may have no system trust store.

The in-image test gate runs `npm test` first, then re-runs just the real-CLI contract lane (`scripts/kimi_cli_contract_test.ts`) against the locked CLI — that lane self-skips on a host with no kimi binary, so the Dockerfile is the only place the flag contract (headless `-p` accepted, `--yolo` rejected alongside `-p`, and the baked `[[hooks]]` PreToolUse guard table valid) is asserted for real. Since MR !1549 (WI#324 EF-5) the lane also pins the MCP contract the tool-proxy shim relies on: the CLI loads `$KIMI_CODE_HOME/mcp.json`, spawns the stdio server with parent-env pass-through, and completes `initialize` → `tools/list` over NDJSON.

Both CLI installs apply `scripts/disable_kimi_feedback.ts` after `npm ci`
(WI#916). It disables built-in TUI feedback and, where present, KAP feedback
routes and discovery. The bundled gateway cannot read
`KIMI_CODE_FEEDBACK_BASE_URL`; the task-env scrub alone is not the off control.
Unreviewed bundle hashes fail the build. Review both feedback paths at the next
pin and re-run the offline real-CLI gate, including the loopback KAP probe.

The in-image `npm test` runs as root inside rootless BuildKit, which grants no `CAP_SYS_PTRACE`. The root `worker-kimi-ts` lane passed such reads in master pipeline 6308 while the image build failed on them, so only the protected candidate build catches this. A root test therefore cannot read another uid's `/proc/<pid>/{exe,environ,fd}`. Tests that inspect the dropped runner read those entries through a capability-free probe on the runner's own uid (`runnerProc` in `entrypoint_config_test.ts` and `task_runner_client_test.ts`). The world-readable `/proc/<pid>/stat` and `status` need no probe. To reproduce the gate's shape on a host, run the suite under `podman unshare setpriv --bounding-set=-sys_ptrace --`.

## Do Not

- Break the `lunarwing-agent-v1` envelope format
- Store secrets in config files (use `KIMI_API_KEY` env var; entrypoint writes it to the runtime config)
- Remove the health server — orchestration depends on it
- Run `kimi` in interactive TUI mode inside the container — the worker uses `-p` (print mode) only
- Remove or weaken the fail-closed policy (WI#206): keep the `PreToolUse` Bash guard hook in `config.toml` + `hooks/headless_command_guard.mjs`, keep `dangerous_command_guard = true`, and never export `KIMI_CODE_DANGEROUS_COMMAND_GUARD` or `KIMI_CODE_TRUST_WORKSPACE` (the entrypoint unsets both and the executor scrubs both from per-task env; the latter is kimi-code 2.2.0's workspace-trust switch, which auto-spawns a repo's `.mcp.json` servers before any model turn, outside the hook — WI#411). Since WI#848 the user-level registration is a root-owned image input: `entrypoint-task-setup.sh` materializes `$KIMI_CODE_HOME/mcp.json` from `KIMI_MCP_SOURCE` (default `/app/config/mcp.json`) at every container start, the executor restores the same bytes before every spawn, and the hook denies commands that name the file through the config directory. Keep the per-task re-assert (WI#847): `$KIMI_CODE_HOME/config.toml` is written as the task uid, so it is the task, not the image, that owns the effective guard registry; `ensureGuardHook()` must run before every spawn, must fail the task rather than spawn unguarded, and the presence check must not accept a decoy inside a comment or multi-line string. The permission-mode reminder stays off (`KIMI_CODE_PERMISSION_MODE_REMINDER=0`) — it is prompt noise for a fixed-mode worker, and with the hook enforcing denials there is no approval stall to avoid.
- Pass the kimi-code 2.5.x creation-time environment flags (`--environment`, `--environment-cwd`) or set `[workspace] require_trust = false`; the executor's headless argv is pinned without them, and task-supplied workspace trust stays scrubbed. The lane does not use the server API or the optional global search index.
- Let the worker self-expose (WI#357): this lane runs `kimi -p` per task and has no server mode, pairing, sharing, or tunnel; keep it that way, and keep `telemetry = false` in `config/config.toml`. Workers must never open their own inbound path or publish session content — see `docs/ops/WORKER-CONTAINERS.md` → "Worker exposure policy". Since WI#833 the guard denies `kimi server`/`kimi web` and the closed listener verb list from a task's Bash tool; since WI#852 the service list also names `kimi rc`/`kimi remote` and `kimi vis`, while `kimi acp` and `kimi -p` still pass, including behind a subshell or command substitution (WI#839); since WI#858 the rule reads the listener words at any word position rather than after a fixed launcher list, so `taskset -c 0 kimi server`, `eval kimi server`, `script -qc 'kimi server'`, `cat <(kimi server)` and `{kimi,server}` all deny, and the executor drops every task-supplied `KIMI_CODE_*` value not allowed by `TASK_SETTABLE_KIMI_CODE_ENV` (forcing `KIMI_CODE_NO_AUTO_UPDATE=1` and `KIMI_DISABLE_TELEMETRY=1`). New `KIMI_CODE_*` names are blocked from task input by default. At each bump, review and test new subcommands that open listeners; they are not covered until the hook recognizes them.
